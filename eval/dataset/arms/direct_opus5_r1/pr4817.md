# Review — PR #4817 · `fc423e5a9e86`

## Verdict: **Approve the fix, with one blocking follow-up**

The core change is correct and well-argued. `sm_100`/`sm_101`/`sm_103` (cc 10.x) and `sm_120`/`sm_121` (cc 12.x) really are separate, non-cross-compatible families, and `tcgen05` — which CuteDSL's `BlockScaledMmaOp` requires — exists only on the former. `>= 10` was matching cc 12.x, so narrowing to `== 10` removes the per-GEMM `try quack / except → FlashInfer` fallback on the hot denoising loop. The env escape hatch is checked first in `quack_enabled()` (`quack_fp8.py:38-41`), so both defaults remain overridable. Verified locally at head SHA: `pytest tests/quantization/test_quack_fp8_gate.py` → **18 passed**.

**CI:** the two failing gates (`vllm-omni-amd-ci`, `vllm-omni-npu-ci`) do not overlap this diff — no `.buildkite` lane references `tests/quantization`, and the changed source is CUDA-capability gating that neither lane exercises. Pre-existing lane state; not a reason to block.

## Comments

### 1. `tests/quantization/test_quack_fp8_gate.py:1` — the regression guard never runs in CI (blocking)

This PR creates `tests/quantization/` as a brand-new directory whose only file is this test. **No BuildKite lane collects that path.** Every lane enumerates explicit directories, and the existing quantization unit tests live in a different tree:

```
.buildkite/test-ready.yml:13   pytest -sv tests/diffusion tests/model_executor -m 'core_model and cpu' ...
.buildkite/test-merge.yml:13   pytest -sv tests/diffusion tests/model_executor -m 'core_model and cpu' ...
.buildkite/test-amd-ready.yaml:19  (same)
```
`rg -n "tests/quantization" .buildkite/` returns nothing.

There is a second, independent reason it would still not run: the file declares no pytest markers. Sibling `tests/diffusion/quantization/test_fp8_config.py:8` has `pytestmark = [pytest.mark.core_model, pytest.mark.diffusion, pytest.mark.cpu]`, and there is no `pytest_collection_modifyitems` auto-marker in any conftest — so `-m 'core_model and cpu'` would deselect this file even after a path fix.

**Why it matters:** the whole value of a hardware-free gate test is that it fails when someone loosens the capability check back to `>= 10`. As merged, it passes on a developer laptop and is invisible to CI — the exact regression it guards against can land unnoticed.

**Smallest fix:** move the file to `tests/diffusion/quantization/test_quack_fp8_gate.py` (already-collected, has `__init__.py`) and add at module scope:
```python
pytestmark = [pytest.mark.core_model, pytest.mark.cpu]
```

### 2. `vllm_omni/quantization/quack_fp8.py:131` — `warmup_quack_fp8` bypasses the gate this PR just fixed

`install_quack_fp8_patch` correctly early-returns on `if not quack_enabled():` (line 102). `warmup_quack_fp8` does not — it goes straight to `_load_quack()` (line 136) with no capability check.

**Triggering path:** `docs/user_guide/quantization/fp8.md:73-75` — the file this PR edits — documents `warmup_quack_fp8` as a public pre-warm API and shows users calling it directly at image-build time. On an `sm_120` box with `quack-kernels` installed, after this PR the docs at line 48-53 tell the user quack is off, yet that snippet still:
- succeeds in `_load_quack()` (the `import quack.gemm_interface` works; CuteDSL rejects the arch at *compile/dispatch* time, not import), and logs the now-false `"Quack FP8 fused-bias GEMM enabled (CuteDSL)."` (line 76);
- then calls `quack_scaled_fp8_mm` → `gemm.gemm_tuned` (line 97) with **no** `try/except` — unlike the patched `apply_scaled_mm` at line 118-124. The `OpError: expects arch to be one of [Arch.sm_100a]` propagates out and breaks the build step.

**Smallest fix:** mirror line 102 —
```python
def warmup_quack_fp8(...) -> None:
    if not quack_enabled():
        return
    if _load_quack() is None:
        return
```
This also makes `VLLM_OMNI_USE_QUACK_FP8=0` actually suppress warmup, which today it does not.

### 3. `vllm_omni/quantization/quack_fp8.py:32` — `== 10` is narrower than the PR's own root-cause evidence (nit)

The PR body states `tcgen05.mma` targets `sm_100a / sm_101a / sm_103a / **sm_110a**`, but the implemented gate is `major == 10`, which excludes cc 11.x. That's a defensible conservative default given no `sm_110` silicon is shipping and the docstring at lines 19-27 only claims 10.x — but the code and the cited evidence disagree, and when `sm_110` appears quack will silently stay off with no signal. Either `10 <= major <= 11`, or a one-line comment noting `sm_110` is deliberately excluded pending validation, would close the gap.

Relatedly: forcing `VLLM_OMNI_USE_QUACK_FP8=1` on an incapable arch (now explicitly advertised at `docs/user_guide/quantization/fp8.md:54`) reinstates the >400 s pathology with only a `warning_once` from line 123. A one-time `logger.warning` in `install_quack_fp8_patch` when `not _is_quack_capable()` but the override forced it on would make that self-diagnosing.
