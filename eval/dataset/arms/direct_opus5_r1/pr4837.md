### 1. `vllm_omni/diffusion/models/ming_flash_omni/pipeline_ming_imagegen.py:449-461` — P1: `super().forward(...)` no longer matches `ZImagePipeline.forward`

```python
outputs: DiffusionOutput = super().forward(
    z_req,
    prompt=None,
    height=height,
    ...
    output_type="pt",
    return_dict=True,
)
```

At this head, `ZImagePipeline.forward` is `def forward(self, req: DiffusionRequestBatch) -> DiffusionOutput:` — a single positional parameter, no `**kwargs` (`vllm_omni/diffusion/models/z_image/pipeline_z_image.py:413`). Commit `1b0de21c` ("[Chore]: refactor out unused/redundant params in diffusion pipelines", an ancestor of this PR's merge-base) deleted all 22 keyword parameters from that signature and did not update this subclass.

**Trigger:** the exact `curl` in the Test Plan. `MingImagePipeline.forward` → line 449 → `TypeError: forward() got an unexpected keyword argument 'prompt'` on every request, before any of this PR's changed lines below it execute.

The PR body pins the passing run to **vLLM-Omni commit `5c51782c`**, which predates `1b0de21c` — so the attached image does not validate this head.

Fixing the signature alone is not sufficient, and this is the part worth deciding before merge. The refactored base now derives everything from `req.sampling_params` and hard-sets `prompt_embeds = None` / `negative_prompt_embeds = None` at `pipeline_z_image.py:423-424`, then unconditionally calls `self.encode_prompt(...)` at line 498. That removes the only channel Ming has for injecting its pre-computed `cap_feats` (built at `pipeline_ming_imagegen.py:414-418`), and `MingImagePipeline.__init__` deliberately skips `ZImagePipeline.__init__` so the Z-Image text encoder is never loaded (see the comment at line 110) — `encode_prompt` has nothing to run on.

Two further fields the base now reads are absent from the `_ZPipelineSamplingParams` shim (`pipeline_ming_imagegen.py:62-76`), so they would `AttributeError` even after the call site is corrected:
- `req.sampling_params.latents` (`pipeline_z_image.py:464`)
- `req.sampling_params.cfg_normalize` (`:466`), `.extra_args` (`:467`), `.output_type` (`:471`)

**Smallest fix direction:** stop routing Ming through `super().forward()`. Either (a) add the four missing fields to `_ZPipelineSamplingParams` (`latents`, `cfg_normalize`, `extra_args: dict = field(default_factory=dict)`, `output_type: str = "pt"`), drop all keyword arguments from the line-449 call, and give `ZImagePipeline.forward` a way to accept pre-computed embeds (e.g. honour `req.sampling_params.prompt_embeds` when set instead of forcing `None` at `:423`); or (b) if the refactor intends model pipelines to own their own denoise loop, inline the loop in `MingImagePipeline` rather than inheriting it. Either way, re-run the Test Plan at `78cc4dcbb161` — not at `5c51782c` — before this is considered fixed.

### 2. `vllm_omni/engine/orchestrator.py:1290` — the fix is right; the `len > 1` case is still an uncontrolled failure

```python
if len(diffusion_prompt) == 1:
    diffusion_prompt = diffusion_prompt[0]
```

Dropping `already_submitted and` is correct and minimal. Previously the unwrap only ran on the `submit_update` branch (line 1296), so a bridge returning `[{...}]` on first submit fell through to `submit_initial` (line 1298) and hit the list rejection in `stage_pool.py:951-955`. That is exactly issue #4839, and this one-line change resolves it for the single-element case on both paths.

The gap worth flagging, given the PR title says "request batching": when the bridge returns **more than one** element, `diffusion_prompt` stays a `list` and falls straight through to `submit_initial`/`submit_update`, both of which raise `ValueError("Diffusion list-prompt batch requests are no longer supported...")` (`stage_pool.py:951-955` and `:1022-1026`). That is inconsistent with the two sibling branches in this same block: `diffusion_prompt is None` (lines 1239-1263) and the empty-list case (lines 1264-1289) both build an `OmniRequestOutput.from_error`, push it to `output_async_queue`, and call `_cleanup_request_ids`. The `len > 1` case gets none of that — it raises out of `_forward_to_next_stage` instead of producing a terminal error output for the request.

**Fix direction:** extend the existing `isinstance(diffusion_prompt, list)` block with an `else` for `len(...) > 1` that emits the same terminal `from_error` + `_cleanup_request_ids` + `return` as the empty case, with a message pointing at "submit multiple independent requests" — so a multi-element bridge output surfaces as a clean request-level error rather than an orchestrator-level exception.
