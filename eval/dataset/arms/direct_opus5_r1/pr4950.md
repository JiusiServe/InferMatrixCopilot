- **"Silent audio, not text-only" is right**, and this is the correction that matters most. Without `<|tts_bos|>` in the thinker output, `llm2tts` never populates the span — `vllm_omni/model_executor/stage_input_processors/minicpmo_4_5_omni.py:104-119` only sets `tts_token_ids`/`tts_hidden_states` when `tts_bos_idx` is found. The talker stage still runs and still yields an audio output, so the client does get an `audio` field. The pre-PR "text-only (which is also faster)" wording was actively misleading.
- **Two-`choices` response shape is right.** `serving_chat.py:2125-2185` loops over `final_outputs` and `choices.extend(choices_data)` per `final_output_type`, so text and audio land in separate choice entries.

### `recipes/OpenBMB/MiniCPM-o-4_5.md:124-127` — tell readers to select the audio choice by field, not by position

The new text says "text in one choice's `message.content` and base64 WAV in another choice's `message.audio.data`... you typically get two `choices` entries". The count is correct, but a reader will reach for `choices[0]` and `choices[1]`, and neither index nor order is a contract here:

- The text choice is built with a hardcoded `index=0` (`serving_chat.py:2159`, and again in the diffusion-text branch at `:2160-2166`).
- The audio choice uses `index=output.index` (`serving_chat.py:2569`), which is also `0` for a single-completion request.

So **both entries carry `index=0`**, and their order in the array is just the order the stages' `OmniRequestOutput`s arrive in `final_outputs`. A client that does `resp.choices[1].message.audio.data` will silently read the wrong entry whenever the talker output lands first.

Smallest fix: change "in another choice's" to explicit guidance, e.g. *"pick the entry whose `message.audio` is non-null — both entries report `index: 0`, and the order of the two is not guaranteed."* One sentence, and it turns a shape observation into something a reader can code against.
