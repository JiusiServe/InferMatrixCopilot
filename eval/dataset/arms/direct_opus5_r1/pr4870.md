## Review — PR #4870 `[Bugfix] Fix Qwen3-TTS no-async-chunk payload splitting`

**Snapshot:** head `231b3ddb97c177e6cee50f16be5ab8e9dee9228c`, base `0798b0bf03cb`. State: **MERGED**. Gate: `buildkite/vllm-omni-amd-ci` is red on this head — that's the outstanding CI signal, unchanged by this review.

**Verdict: the worker fix is correct and is the right root-cause fix. The serving-side half is where the risk is** — it changes public streaming behavior and I believe it routes streaming Qwen3-TTS `async_chunk=False` into a consumer that misreads the payload it now receives.

I verified the worker change end-to-end: `codes.audio` is built at `qwen3_tts_talker.py:593` as `torch.cat(audio_codes_list, dim=0)` where each contribution has `shape[0] == span_len` (that request's scheduled tokens). So it is token-aligned, and gating `to_payload_element` (`utils/mm_outputs.py:131`) on `total_num_scheduled_tokens` rather than `hidden_states.shape[0]` matches the `start = query_start_loc_cpu[idx]` / `end = start + num_scheduled_tokens_np[idx]` offsets the slice actually uses. The removed `seq_len` parameter has exactly one call site (`gpu_ar_model_runner.py:2027`) and one consumer (line 1790), both updated — no dangling reference survives.

### 1. `vllm_omni/entrypoints/openai/serving_speech.py:3509` — streaming + `async_chunk=False` now delivers a cumulative-snapshot list to a consumer that treats lists as append-only chunks

```python
qwen3_full_payload = self._tts_model_type == "qwen3_tts" and not bool(async_chunk)
is_streaming_request = request.is_streaming() and not qwen3_full_payload
```

Trigger: `POST /v1/audio/speech` with `stream_format="audio"` (or `stream_format="sse"`), Qwen3-TTS served with `--no-async-chunk`. `create_speech` reaches `serving_speech.py:4069` / `:4089`, both of which feed the generator into `_generate_audio_chunks` (`:2883`, `:4071`).

Two places in this same file disagree about what a list-valued `audio` payload means under `async_chunk=False`:

- `_generate_audio_bytes` at `serving_speech.py:3829-3836` states it explicitly — *"Non-async Qwen3-TTS returns cumulative history snapshots"* — and therefore walks the list in reverse and keeps only the **last non-empty** tensor.
- `_generate_audio_chunks` at `serving_speech.py:2749-2752` takes the opposite reading — *"Cumulative mode: each update grows the list; emit only new tail"* — and emits `audio_val[prev_count:]`, i.e. every element, concatenated onto the wire.

Before this PR the streaming path was coerced to `DELTA`, so `prev_count` advanced per yield and incidentally suppressed all but the first snapshot. With `FINAL_ONLY`, a single output arrives carrying the whole snapshot list, `prev_count` is 0, and `new_chunks` is the entire list — so the client receives snapshot₁, then snapshot₁₊₂, then snapshot₁₊₂₊₃ back to back rather than the waveform once.

Smallest fix direction: give `_generate_audio_chunks` the same `async_chunk` awareness `_generate_audio_bytes` already has — when the flag is false, keep only the newest non-empty snapshot and emit its *unsent suffix* (track emitted sample count, not `len(list)`). The new unit test only asserts the argument passed to `coerce_param_message_types`; it never drives bytes through `_generate_audio_chunks`, so this path is currently unasserted either way.

### 2. `vllm_omni/entrypoints/openai/serving_speech.py:3507` — same flag, two opposite defaults in one file

```python
async_chunk = getattr(self.model_config, "async_chunk", True)     # line 3507  → default True
async_chunk = bool(getattr(self.engine_client.model_config, "async_chunk", False))  # line 3823 → default False
```

`self.model_config` and `self.engine_client.model_config` resolve to the same object here (`OmniOpenAIServingSpeech` is constructed at `api_server.py:1081` with only `engine_client` + `models`, and never assigns `self.model_config` itself), so the *attribute source* is fine. The defaults are not: if `async_chunk` is ever absent from `model_config`, line 3507 concludes "async chunking, keep DELTA" while line 3823 concludes "non-async, take the last cumulative snapshot" — for the same request. Fold both into one accessor with one default rather than adding a second, divergent read.

### 3. `vllm_omni/worker/gpu_ar_model_runner.py:1734` — the fix silently no-ops when a batch member contributes no codes

`mm_seq_len = int(scheduler_output.total_num_scheduled_tokens)` is only effective while `codes.audio` covers *every* scheduled token. It doesn't always: in `make_omni_output` (`qwen3_tts_talker.py:556-558`) a request is added to `audio_codes_list` only `if isinstance(ac, torch.Tensor)`, and `preprocess` returns without any `codes.audio` on the multi-token branch at `qwen3_tts_talker.py:720-726` (only the prompt-embeds branch at `:717` emits the zeros placeholder). A mixed batch — one request taking that prefill branch while others decode — yields `audio_codes.shape[0] < total_num_scheduled_tokens`, the `element.shape[0] == seq_len` guard at `utils/mm_outputs.py:131` fails, no slicing happens, and every request in that step gets the whole concatenated payload. That is the exact corruption in #4851, just narrowed to mixed batches. The `start`/`end` offsets would also be misaligned against a compacted tensor even if the lengths did coincide.

This is a pre-existing silent-fallback in `to_payload_element`, not something the PR introduced — but the PR now depends on the invariant, so it should be made loud rather than assumed. Smallest fix direction: `logger.warning_once` (or an assert in the mm payload builder) when a known per-token mm key's `shape[0]` is neither `seq_len` nor a cached/passthrough shape, so this degrades visibly instead of returning wrong audio.

### 4. Test coverage note — `tests/worker/test_gpu_ar_model_runner.py:441`

The new regression test sets `runner.model.omni_pooler_payload_include_hidden = False`, which skips the hidden branch entirely. That's the branch at `gpu_ar_model_runner.py:1710-1717`, which clamps to `min(total_num_scheduled_tokens, hidden_states.shape[0])` and then slices with token-space `start`/`end` — the combination that ships for models that *do* include hidden with tail-only hidden states. Not a defect in this diff (that code is untouched), but the "tail-only hidden states" regression test doesn't cover the configuration where tail-only hidden states are actually consumed.
