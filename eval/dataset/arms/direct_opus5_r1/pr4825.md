**Snapshot:** head `ac3a2ce5a9b9f89cd74e2e456bb9eac1f48dac20`, merge-base `d526dc93e89a`. PR state MERGED. CI: 2 failing gates — `buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci` (the diff is arch-neutral, so these should be checked against the gates rather than re-argued here).

### Verdict

**Request changes (non-blocking on the core idea).** The change is directionally right and the reported before/after images are real: without `unet` in the scan list, `_replace_layers_with_lora` never enters the SDXL denoiser and the adapter is a no-op. But the diff makes SDXL LoRA *partially* work, and the partial-ness is silent. For attention-only adapters (the common diffusers case, and almost certainly the one in the test plan) it is fully correct; for adapters that also train feed-forward or `proj_in`/`proj_out`, this lands you either in a hard load error or in a silent drop that looks exactly like the bug being fixed. Additionally, the change widens a shared global when the repo already has the narrower opt-in hook it needs.

### 1. `vllm_omni/diffusion/lora/manager.py:375-381` — use the existing per-pipeline opt-in, not the global default

The comment two lines above the change (`manager.py:369-370`) states the invariant: *"opt-in; other pipelines unchanged."* The change does the opposite — it adds `unet` to the shared `default_components`, so every pipeline that exposes a `.unet` attribute is now scanned by default.

The repo already has the right mechanism, consumed on the very next line (`manager.py:382`) and used in production by `vllm_omni/diffusion/models/sensenova_u1/pipeline_sensenova_u1.py:543`:

```python
_lora_components: ClassVar[list[str]] = ["language_model"]
```

And `StableDiffusionXLPipeline` already declares its denoiser at `vllm_omni/diffusion/models/sdxl/pipeline_sdxl.py:46` (`_dit_modules: list[str] = ["unet"]`), so it's the natural home.

**Fix:** revert `default_components` to the original 4-tuple and add one line to `pipeline_sdxl.py`:

```python
_lora_components: ClassVar[list[str]] = ["unet"]
```

Behaviour is identical today (no other top-level pipeline currently exposes `.unet`), it's a net line removal in shared code, and it stops future `unet`-bearing pipelines from silently inheriting LoRA scanning.

---

### 2. `vllm_omni/diffusion/lora/manager.py:375-381` — SDXL's feed-forward layers are renamed in this repo, so FF LoRA weights can't resolve

This is the substantive one. `SDXLUNet2DConditionModel.load_weights` deliberately renames the diffusers checkpoint layout into a different live module tree (`vllm_omni/diffusion/models/sdxl/sdxl_unet.py:836-849`):

- `.ff.net.0.proj.` → `.ff.geglu.proj.` (live module: `SDXLGEGLU.proj`, `sdxl_unet.py:121`)
- `.ff.net.2.` → `.ff.out_proj.` (live module: `SDXLFeedForward.out_proj`, `sdxl_unet.py:133`)

LoRA checkpoints for SDXL are keyed against the *diffusers* names. Nothing in the LoRA path undoes that rename: `LoRAModel.from_local_checkpoint` is called with `weights_mapper=None` (`manager.py:309`), and `_get_lora_weights` (`manager.py:487-509`) only tries full name → component-relative name → bare suffix. None of those bridge `ff.net.0.proj` ↔ `ff.geglu.proj`.

Two concrete failure paths, both newly reachable because `unet` is now scanned:

**(a) Hard load failure.** vLLM validates every checkpoint module's last name component against `expected_lora_modules` and raises otherwise (`vllm/lora/lora_model.py:233-239`: `elif module_name.rsplit(".", 1)[-1] not in expected_lora_modules: unexpected_modules.append(...)`). `_expected_lora_modules` is derived from `get_supported_lora_modules()`, i.e. the suffixes of vLLM `LinearBase` leaves (`manager.py:113-135`). In the SDXL unet the only bare-integer `LinearBase` leaf is `to_out.0` (`sdxl_unet.py:151-155`, `175-179`), which contributes suffix `"0"` — nothing contributes `"2"`. So a checkpoint key `unet.…​.ff.net.2.lora_A.weight` yields `part_name == "2"`, which is not expected → `ValueError` and the **entire adapter fails to load**. Same reasoning applies to `proj_in`/`proj_out`, which are plain `nn.Linear` (`sdxl_unet.py:281`, `296`) and therefore never appear in `get_supported_lora_modules()` at all.

**(b) Silent drop.** `unet.…​.ff.net.0.proj` *passes* the gate (suffix `"proj"` exists via `SDXLGEGLU.proj`), so the adapter loads cleanly — but the live module is named `…​.ff.geglu.proj`, so `_match_target_modules` never matches it during replacement (`manager.py:407-420`) and `_get_lora_weights` never resolves it. The FF delta is dropped with no user-visible signal.

**Fix direction:** supply a `weights_mapper` (or an SDXL-specific alias table) at `manager.py:300-310` and in `_get_lora_weights` that maps `ff.net.0.proj → ff.geglu.proj` and `ff.net.2 → ff.out_proj` — i.e. reuse the same rename table `load_weights` already owns, rather than duplicating it. At minimum, scope the PR honestly: state that attention-only SDXL LoRAs are supported and that FF/`proj_in`/`proj_out` adapters are not yet.

*(Note: I verified this from the module definitions and vLLM's validation code, not by instantiating the SDXL unet against a real FF-targeting adapter — see the validation gap below.)*

### 3. `vllm_omni/diffusion/lora/manager.py:536`, `:552`, `:573` — no signal when an adapter binds zero (or few) layers

The exact bug this PR fixes — adapter loads, activates, and produces base-identical output — is unobservable today: every miss path calls `lora_layer.reset_lora(0)` and the only logging is `logger.debug`. That is why the gap survived until someone diffed two images by eye.

**Fix:** at the end of `_activate_adapter` (`manager.py:631`), log at `info`/`warning` how many of `lora_model.loras` were actually bound versus how many were reset, e.g. `"Adapter %d: bound %d/%d LoRA modules"`, and warn when the bound count is 0. One line, and it converts finding #2's silent-drop case into a diagnosable one.

### 4. `tests/diffusion/lora/test_lora_manager.py:580-619` — the new test cannot fail for the reason that matters

`test_lora_manager_discovers_unet_component` monkeypatches *both* `from_layer_diffusion` and `replace_submodule`, and builds a synthetic tree `pipeline.unet.down_block.proj = _FakeLinearBase()` (lines 602-604). The assertions at lines 616-619 therefore only verify that the literal string `"unet"` is present in `default_components` — they exercise none of SDXL's real leaf names and would still pass under every failure in finding #2.

**Fix:** add a case built from the live SDXL shapes — `attn1.to_qkv` (packed, 3-slice), `attn2.to_q/to_k/to_v`, `attn1.to_out.0`, `ff.geglu.proj`, `ff.out_proj` — and assert that `_get_lora_weights` resolves diffusers-format checkpoint keys (`…attn1.to_q`, `…attn1.to_out.0`, `…ff.net.0.proj`, `…ff.net.2`) for each. That test fails today on the FF names, which is the point.

### 5. `vllm_omni/diffusion/models/sdxl/sdxl_unet.py:829` — `stacked_params_mapping` set as a side effect of `load_weights`

Self-attention LoRA on SDXL works only through the packed path: `attn1.to_qkv` is a fused `QKVParallelLinear` (`sdxl_unet.py:145`), so `_replace_layers_with_lora` must expand it to `to_q`/`to_k`/`to_v` via `_get_packed_sublayer_suffixes` (`manager.py:409-417`, `534-537`). That expansion is derived from `stacked_params_mapping` (`manager.py:174-175`), which SDXL sets **as an instance attribute inside `load_weights()`** (`sdxl_unet.py:829`) rather than at class level.

`DiffusionLoRAManager.__init__` computes the mapping exactly once (`manager.py:73`). Any construction order where the manager is built before or without `load_weights` — dummy/random weight loading being the obvious one — leaves the mapping empty, at which point `attn1` is never replaced and, if it were, is silently `reset_lora`'d. That's a full self-attention LoRA drop with no warning.

**Fix:** hoist `stacked_params_mapping` to a class-level attribute on `SDXLUNet2DConditionModel` and have `load_weights` read it, rather than assigning it as a side effect.

### What I confirmed working (no action needed)

- `to_out.0` resolves correctly without normalization — the live module name `unet.…​.attn1.to_out.0` (`sdxl_unet.py:151-155`) matches the diffusers checkpoint key exactly, and `_match_target_modules` (`lora/utils.py:20-27`) matches target `to_out.0`. The `to_out` normalization reverted in `ac3a2ce5` was correctly dropped.
- The `attn1.to_qkv` packed path resolves for a normally-loaded model: `stacked_params_mapping` (`sdxl_unet.py:823-827`) yields `{"to_qkv": ["to_q","to_k","to_v"]}`, and `_expand_expected_modules_for_packed_layers` admits those suffixes. See #5 for the fragility caveat.
- Attention-only adapters (`to_q`/`to_k`/`to_v`/`to_out.0`) — the most common diffusers SDXL LoRA shape, and consistent with the PR's test plan — apply end-to-end.
