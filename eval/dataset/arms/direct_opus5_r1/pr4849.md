### Verdict: the fix is correct. Approve, with one cosmetic nit.

The diagnosis and the shape of the fix both hold up against the live code:

- `vllm_omni/engine/orchestrator.py:1209` builds `diffusion_source_outputs = [output, *companion_outputs]`, so the PR's "parent output is first" assumption is exactly what the producer guarantees — `source_outputs[0]` in the new bridge is the parent AR output, not an arbitrary element.
- The list return really was fatal: `vllm_omni/engine/stage_pool.py:951-955` (`submit_initial`) and `:1021-1026` (`submit_update`) both raise `ValueError("Diffusion list-prompt batch requests are no longer supported...")` on any `isinstance(request, list)`. The old single-element list only survived the streaming path, via the `already_submitted and len(...) == 1` unwrap at `orchestrator.py:1287-1288`; the initial-submit path had no unwrap, which matches the 500 in #4832.
- The new `None` return is a supported contract, not a new sink: `orchestrator.py:1238-1265` checks `if diffusion_prompt is None`, emits `OmniRequestOutput.from_error(...)` and cleans up parent + companion ids. It also mirrors `glm_image.ar2diffusion` (`glm_image.py:220-243`), which this file's module docstring already names as the reference signature.
- Dropping the CFG companion outputs is **safe**, and I checked this specifically because `orchestrator.py:1201-1207` warns that "downstream CFG conditioning may degrade" when companions are missing. CFG conditioning does not travel through the bridge payload — `orchestrator.py:859-875` (`_maybe_clone_diffusion_params_for_cfg`) attaches `params.cfg_kv_request_ids = companion_request_ids` to the diffusion sampling params instead. The companion outputs are `pop`-ed in `_forward_to_next_stage`, so ignoring them leaks nothing in `CfgCompanionTracker`. No bridge in `stage_input_processors/` reads `source_outputs[1:]`.
- Behaviour parity of the de-indented body is exact for index 0, including the prompt-normalization rewrite: old `prompt=[]` → `{}`, new `prompt[0] if prompt else {}` → `{}`; old scalar-wrap `[prompt][0]` ≡ new `original_prompt = prompt`.

### Comment

**`vllm_omni/model_executor/stage_input_processors/hunyuan_image3.py:151` and `:167`** — hardcoded `Request 0` in the log strings

```python
"[ar2diffusion] Request 0: ratio_index=%d out of range [0,%d), keeping prompt size %dx%d",
...
"[ar2diffusion] Request 0: AR generated %d tokens, text length=%d, ..."
```

The old `%d`/`i` was a batch index and meant something inside the loop. Now every request in the pipeline logs `Request 0`, at INFO on the hot AR→DiT transition. Concretely: two concurrent `/v1/images/edits` calls under request-level batching produce two interleaved `[ar2diffusion] Request 0: ...` INFO lines with no way to tell them apart, and the IndexError warning (`ratio_index out of range`) becomes unattributable to a request — which is the line you'd most want to correlate when triaging a bad ratio token. Smallest fix: drop the `Request 0:` prefix entirely (the log is already per-call), i.e. `"[ar2diffusion] AR generated %d tokens, ..."`. Threading the real `req_id` in would need a signature change and isn't worth it here.
