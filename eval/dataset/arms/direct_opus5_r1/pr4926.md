### P1

**`vllm_omni/platforms/cuda/platform.py:140-147` — `FLASH_ATTN_3_HUB` is admitted on Blackwell, where FA3 has no kernel.**

```python
fa3_hub_supported = compute_capability is not None and compute_capability.major >= 9
```

`major >= 9` matches sm_90 (Hopper) but also sm_100/sm_103/sm_120/sm_121 — the Blackwell SKUs this same function enumerates at lines 72 and 83. On a B200 or an RTX 5090 with `kernels` installed, `DIFFUSION_ATTENTION_BACKEND=FLASH_ATTN_3_HUB` passes this gate, reaches line 175, and returns `FlashAttention3HubBackend`; `kernels-community/flash-attn3` ships Hopper kernels, so this fails at launch instead of degrading. Note the sibling `SAGE_ATTN_3` check at line 160 already uses `major >= 10` precisely to separate Blackwell from Hopper, so the distinction is available. Change to `compute_capability.major == 9` (matching the doc's "CUDA Hopper (sm_90+) only" more honestly as sm_90-class), or explicitly exclude `major >= 10`.

**`vllm_omni/platforms/cuda/platform.py:124-147` — the hub backends bypass the `compute_supported` (sm ≥ 80) and Blackwell guards.**

The guard at line 149 is keyed on the literal `"FLASH_ATTN"`, so `FLASH_ATTN_HUB` never reaches it. Concrete path: Turing/T4 (sm_75) with `kernels` installed → `FLASH_ATTN_HUB` survives lines 124-147 untouched and is returned at line 177, while plain `FLASH_ATTN` on the same GPU correctly returns `TORCH_SDPA` (lines 149-158). Same for Blackwell, where the comment you're adding under at lines 64-71 states outright that "plain FA2 will crash there". The FA3→FA2 downgrade at line 147 makes this worse: it hands a pre-Hopper GPU a backend that was itself never capability-checked. Fold `FLASH_ATTN_HUB` into the existing `compute_supported` / `is_blackwell` checks rather than routing around them.

**`vllm_omni/diffusion/attention/backends/flash_attn_hub.py:95-103` (and `274-282`) — the version cascade silently defeats the reproducibility guarantee.**

```python
try:
    hub_module = get_kernel("kernels-community/flash-attn2", version=1)
except Exception as e:
    try:
        logger.info("Failed to load version 1, attempting version 2: %s", e)
        hub_module = get_kernel("kernels-community/flash-attn2", version=2)
    except Exception as e2:
        logger.info("Failed to load version 2, attempting default: %s", e2)
        hub_module = get_kernel("kernels-community/flash-attn2")
```

`except Exception` catches transient failures, not just "this version doesn't exist" — a network blip, an HF rate-limit (your own test log in the PR body shows the unauthenticated-rate-limit warning), or a 401 on a gated repo. When that happens the process silently loads a **different kernel major version**, and if that also fails, the third call passes neither `revision` nor `version`, so `select_revision_or_version` resolves to the floating default branch (verified against `kernels` 0.16.0: `get_kernel(repo_id, revision=None, version=None, ...)` → `select_revision_or_version(...)` → `install_kernel(...)`). The whole premise of this PR is that "tiny numerical differences compound across denoising steps"; a nondeterministic kernel version chosen by network weather is that failure, and it is reported at `logger.info`. Make the version a single explicit value (config or env), do not cascade, and on failure raise with the requested version named.

**`vllm_omni/diffusion/attention/backends/flash_attn_hub.py:147` and `:326` — `flash_attn_varlen_func` is called unconditionally but is allowed to be `None`.**

The constructor at lines 108-109 (and 287-288) only requires that *one* of the two handles resolve:

```python
if self.flash_attn_func is None and self.flash_attn_varlen_func is None:
    raise RuntimeError(...)
```

So a hub module exposing only `flash_attn_func` constructs fine. Then any request carrying a padding mask takes line 205's branch → `_forward_varlen_masked` → line 147 calls `self.flash_attn_varlen_func(...)` → `TypeError: 'NoneType' object is not callable`, mid-generation rather than at init. `_forward_varlen_dense` (lines 169, 348) has the same exposure via the piecewise fallback added in `332da8f2`. Either tighten the constructor to require both handles, or check `flash_attn_varlen_func is not None` before the varlen paths and degrade to the dense func.

### P2

**`flash_attn_hub.py:92-103` — `get_kernel` runs once per attention layer.** It's called from `__init__`, and `kernels.get_kernel` is not memoized (verified: `hasattr(kernels.get_kernel, 'cache_info') is False`; the body runs `select_revision_or_version` → `install_kernel` → `snapshot_download` on every call). A diffusion transformer instantiates one `AttentionImpl` per layer, so model init does dozens of Hub resolutions. Wrap in a module-level `@lru_cache`d `_load_hub_kernel(repo_id, version)` helper — which also gives you a natural place to put the single version pin from the P1 item above.

**`flash_attn_hub.py:103`/`:282` vs. `cuda/platform.py:126` — "falls back gracefully" only covers the import, not the load.** The platform check handles `kernels` being absent. The realistic failure — no network, `HF_HUB_OFFLINE=1`, Hub outage, gated repo — happens later, inside `__init__`, where the final `get_kernel` call is outside any `try`. It propagates and kills engine startup. The docs you're adding (`attention_backends.md`, "will log a warning and fall back gracefully") promise more than the code delivers. Either catch at construction and hand back `FlashAttentionImpl`, or narrow the doc claim to "if the `kernels` *library* is not installed".

**`cuda/platform.py:128` — `except ImportError` is too narrow, and this file already knows it.** Lines 111-120 in the same function deliberately catch broad `Exception` for the flashinfer probe, with the comment: *"A partially installed / ABI-mismatched wheel can raise OSError or RuntimeError from extension loading, not just ImportError. This runs during default backend selection, so a probe failure must not abort startup."* `kernels` imports torch and is subject to the identical failure mode. Widen to `except Exception` for consistency with the stated rationale.

**`tests/diffusion/attention/test_kernels_hub.py:57, 91-93` — the FA3 path never executes in CI.** `hardware_test(res={"cuda": "L4"})` pins an Ada L4 (sm_89), so `if major < 9: pytest.skip(...)` at line 92 fires unconditionally and section 3 of the test is dead on the declared runner — half the PR title is unverified by the suite. Separately, the only execution assertion uses `AttentionMetadata(attn_mask=None)` with no `full_attn_spans` (line 75), so only the plain `flash_attn_func` branch (lines 213-221) is covered; `_forward_varlen_masked`, `_forward_varlen_dense`, and the piecewise fallback have zero coverage. And with `k = v = q.clone()`, `causal=False`, `seq_len=32`, a dropped `softmax_scale` or an inverted `causal` flag would likely still land inside the `1e-2` tolerance. Request an H-class runner for the FA3 case, add a masked case and a `full_attn_spans` case, and use independent q/k/v with `causal=True`.

**`tests/diffusion/attention/test_kernels_hub.py:79-84` — errors instead of skipping when `kernels` is missing.** `kernels` is not declared in `requirements/` (confirmed — no match), so on a runner without it, `from kernels import get_kernel` inside the impl raises `ImportError` and the test *fails* rather than skips. Add `pytest.importorskip("kernels")` at the top of `test_kernels_hub_execution`.

### P3

**`docs/user_guide/diffusion/attention_backends.md` — `pip install kernels==0.14.1` may not match the API the code uses.** The code passes `version=1` / `version=2` as ints; that integer-major-version parameter is what `kernels` 0.16.0 exposes (`version: int | None`). If 0.14.1's `get_kernel` takes a different `version` type, both pinned attempts raise and every load silently lands on the unpinned third call — the P1 cascade issue, permanently on. Please confirm 0.14.1's signature and either raise the documented pin or express it as a floor (`kernels>=X`). A floor also belongs in an optional extra rather than only in prose.

**`vllm_omni/platforms/npu/platform.py:110-116`** — the downgrade routes to `FLASH_ATTN` without the `find_spec("mindiesd")` check the default path applies at line 123, so on an NPU without `mindiesd` the user gets a backend the auto-router would have refused. Matches existing explicit-`FLASH_ATTN` behavior, so it's pre-existing; noting it because this PR is what makes it reachable from a hub-backend request.
