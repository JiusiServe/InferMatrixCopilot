**Snapshot:** head `0128660809e150d5cc5546f7d9604e79dcb7fc2b` (base `ddba6de2ab65`) · state **MERGED** · CI: 2 failing gates — `buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci`.

**Verdict: approach is sound and matches the stated root cause; no blocking correctness defect found in the changed paths.** Reproduced the PR's test result at this SHA: `11 passed` (env fingerprint: vLLM **0.26.0**, torch 2.11.0+cu130, py3.12). The distributed change is well-scoped — diffusion coordinators stay diffusion-owned, and `destroy_model_parallel()` (`parallel_state.py:919-945`) correctly destroys the new vLLM-owned `_DP`/`_PCP` companions without double-freeing the diffusion originals. The pre-hook ordering is right: `MoERunner` reads `ctx.dp_metadata` inside `forward` (`vllm/model_executor/layers/fused_moe/runner/moe_runner.py:606-611`), so a `register_forward_pre_hook` is a valid place to populate it.

Findings below, most significant first.

### 1. `hunyuan_fused_moe.py:50` — construct `DPMetadata` by keyword, not position

```python
forward_context.dp_metadata = _vllm_fc.DPMetadata(torch.tensor(gathered_num_tokens, dtype=torch.int64))
```

This binds to whatever field happens to be declared first on `DPMetadata`. On the installed vLLM 0.26 that is `num_tokens_across_dp_cpu` (`vllm/forward_context.py:72-77`), so it works — and the new test asserts exactly that. But the PR targets vLLM **0.24**, and pytest itself warns here that omni `0.1.dev2408` and vLLM `0.26.0` are a mismatched pair. On older vLLM revisions `DPMetadata` carried `max_tokens_across_dp_cpu` as the leading field; there, this line silently populates the wrong field and every all2all consumer reads garbage token counts — a silent-correctness failure, not a crash.

Fix: `DPMetadata(num_tokens_across_dp_cpu=torch.tensor(...))`. One keyword makes the intended contract explicit and turns any upstream field reshuffle into a `TypeError` at the first forward instead of wrong dispatch sizes.

### 2. `hunyuan_fused_moe.py:41-46` — `all_gather_object` on a hot path in a perf fix

```python
gathered_num_tokens: list[int | None] = [None] * dp_group.world_size
torch.distributed.all_gather_object(gathered_num_tokens, int(num_tokens), group=dp_group.cpu_group)
```

This runs on the first MoE layer of every DiT forward — i.e. once per denoising step per CFG replica. `all_gather_object` pickles/unpickles through gloo and forces a CPU sync, which is materially heavier than the small-CPU-tensor collective vLLM uses for the same quantity. Given the PR exists to unblock the `tp2_cfgp2` / `tp2_sp2` **local perf** tests, paying a pickle round-trip per step to communicate one `int` per rank is worth avoiding.

Smallest fix: gather into a preallocated CPU int64 tensor over `dp_group.cpu_group` — e.g. build a zeroed `torch.zeros(world_size, dtype=torch.int64)`, set `[rank_in_group] = num_tokens`, and `all_reduce` it (or `all_gather_into_tensor`) — then hand that tensor straight to `DPMetadata`. Same result, no pickling, and it is already the shape `num_tokens_across_dp_cpu` wants.

### 3. `hunyuan_fused_moe.py:50` → latent mis-chunking if sequence-parallel MoE is ever enabled

Setting `dp_metadata` flips `MoERunner._sequence_parallel_context()` from `nullcontext()` to `dp_metadata.sp_local_sizes(self.moe_config.sp_size)` for every HunyuanImage3 MoE forward once DP > 1 (`moe_runner.py:606-611`). `sp_local_sizes` derives per-SP-rank sizes by dividing `num_tokens_across_dp_cpu` by `sp_size` (`vllm/forward_context.py:61-69, 101-113`), because upstream records the **pre-SP-shard** per-DP-rank token count. The value gathered here is `hidden_states.shape[0]` observed *inside* the MoE layer — already SP-sharded. With `moe_config.sp_size == 1` (the current diffusion configuration) the two coincide and nothing changes. With `sp_size > 1`, `local_sizes` comes out `sp_size×` too small and feeds `get_chunk_sizes_across_dp_rank()` in `prepare_finalize/flashinfer_nvlink_{one,two}_sided.py:17-20`.

Fix direction: no code change needed today, but add an explicit guard or comment in `_set_forward_context_dp_metadata` stating the helper is only valid while sequence-parallel MoE is off for the DiT — e.g. an `assert` or early return keyed on `is_sequence_parallel`, so enabling it later fails loudly rather than mis-chunking silently.

### 4. `hunyuan_fused_moe.py:37-38` — defensive `getattr` turns API drift into a silent no-op

```python
dp_group = getattr(_vllm_ps, "_DP", None)
if dp_group is None or getattr(dp_group, "world_size", 1) <= 1:
    return
```

If upstream ever renames or relocates `_DP`, the string lookup returns `None`, the function returns early, and MoE dispatch quietly runs without DP metadata — precisely the silent-failure mode this module's own docstring warns about for `num_tokens` (line 17-19). Use direct attribute access (`_vllm_ps._DP`, keeping the explicit `is None` check for the pre-init case) or `get_dp_group()`, so drift raises instead of degrading.

### 5. `hunyuan_fused_moe.py:41,47-48` — unreachable failure branch

`torch.distributed.all_gather_object` overwrites every slot in `object_list`, and the value contributed is `int(num_tokens)`, so no entry can survive as `None`. The `RuntimeError` is dead code, and it is the only reason line 41 is annotated `list[int | None]`. Delete lines 47-48 and narrow the annotation to `list[int]`.

### 6. `parallel_state.py:515-527` — the wrapper adds nothing over the upstream default

`init_vllm_model_parallel_group` forwards its four arguments unchanged and sets `use_device_communicator=True`, which is already the default in `vllm/distributed/parallel_state.py:1298-1305`. Inlining `vllm_parallel_state.init_model_parallel_group(...)` at the four call sites (lines 859, 869, 885, 904) removes an indirection without changing behavior. (`test_expert_parallel_layout.py:62` monkeypatches the wrapper, so it would need to patch the upstream symbol instead.) Optional — but if the wrapper stays, it is worth a one-line docstring saying *why* it exists, since as written the name implies it does more than it does.

### 7. Test coverage gap on the layout this PR actually fixes

`test_expert_parallel_layout.py` exercises only the `cfg_parallel_size=2` layout. The behavior change at `parallel_state.py:882` — `use_moe_parallel_mapping and cfg_parallel_size > 1` → `use_moe_parallel_mapping` — is exactly what makes `tp2_sp2` (cfg=1, dp=1) get a vLLM-owned `_DP` with `reduce_scatter` instead of the diffusion coordinator, and that branch has no unit test. Similarly, `TestSetForwardContextDPMetadata` (`test_hunyuan_fused_moe.py:53-91`) covers only "sets it" and "keeps existing"; the `world_size <= 1` early return — which is what `tp2_sp2` actually hits — is untested. Two small cases would pin both halves of the `tp2_sp2` fix that currently rest solely on the manual smoke run.
