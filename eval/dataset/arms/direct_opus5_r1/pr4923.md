### 1. `vllm_omni/deploy/qwen3_tts.yaml:41-46` — the comment now contradicts the value, and the async-output win silently depends on this flip

```yaml
# Prefix caching on by default. ... any text repetition across
# requests (same voice or shared ref_audio) is a net throughput win.
enable_prefix_caching: false
```

The comment argues prefix caching should be on; the line under it turns it off. That's not just cosmetic. `_should_use_async_omni_output` bails early on `if self.omni_prefix_cache is not None: return False` (`vllm_omni/worker/gpu_ar_model_runner.py:1540-1541`), and `omni_prefix_cache` is constructed exactly when `cache_config.enable_prefix_caching` is true (`vllm_omni/worker/gpu_model_runner.py:169-175`). So `use_async_omni_output = True` (`qwen3_tts_talker.py:351`) is inert unless prefix caching is off — the second half of this PR's title only takes effect because of this yaml line, and nothing in the file says so.

Knock-on: `requires_full_prefix_cached_hidden_states = False` (`qwen3_tts_talker.py:311`) and `deferred_prefix_cache_mm_keys = {"codes.audio"}` (`:321`), both introduced to make prefix caching cheap for this model, are now dead in the shipped deploy.

**Fix:** rewrite the comment to state the real reason (async omni output is mutually exclusive with `OmniTensorPrefixCache`, and the async path wins), and say explicitly that re-enabling prefix caching silently disables the async fast path. Ideally add a `logger.info_once` in `_should_use_async_omni_output` when a model requests async output but is refused because of `omni_prefix_cache`, so this isn't a config trap.

### 3. `vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:342-343` — the comment's batch-size claim is wrong, and the runner still builds generators that can't fire

```python
# ... This also means mtp seeding
# is silently dropped when the decode batch > 1 under full cudagraphs;
```

It's dropped at **every** batch size, not just `> 1`. Path: `_talker_mtp_forward` gates the multi-row scalar fallback on `talker_mtp_accepts_per_row_generators` (`gpu_model_runner.py:1851-1855`), but the single-row branch does not:

```python
if decode_batch_size == 1:
    if row_generators[0] is not None:
        talker_kwargs["generator"] = row_generators[0]   # gpu_model_runner.py:1884-1886
```

Once `talker_mtp` is a `CUDAGraphWrapper` (which this PR makes the GPU default), the call at `:1897` replays a graph captured in `_capture_talker_mtp_graphs` with no sampling kwargs at all (`gpu_ar_model_runner.py:562,570`). Python-level kwargs are inert on replay. **Triggering input:** a single in-flight request with `extra_args={"tts_local_seed": N}` on a default GPU deploy — before this PR the seed was honored; after it, it is accepted and ignored with no warning. `_row_generator` and the `_talker_mtp_generators` cache (`:1829-1849`) are also built and evicted every step on a path where they can never take effect.

**Smallest fix:** gate the `decode_batch_size == 1` branch on the same `talker_mtp_accepts_per_row_generators` flag, skip generator construction entirely when the flag is False, and `log_once` when a request supplies `tts_local_seed` on the graph-wrapped path. Then correct the comment to "at any decode batch size".

### 4. `qwen3_tts_code_predictor_vllm.py:39` + `qwen3_tts_talker.py:327` — NPU can still nest graphs; only the deploy yaml prevents it

`use_cuda_graphs=current_omni_platform.is_npu()` keeps the code predictor's internal graphs on NPU, but `talker_mtp_graph_safe = True` is set unconditionally, and the wrap decision at `gpu_model_runner.py:209-211` is shared by `OmniNPUModelRunner` (it inherits `_init_talker_mtp`; see `vllm_omni/platforms/npu/worker/npu_model_runner.py:48`) and uses `current_omni_platform.get_graph_wrapper_cls()` → `ACLGraphWrapper`. So on NPU with any `cudagraph_mode` satisfying `has_full_cudagraphs()`, you get an outer ACL graph around a code predictor that captures its own inner graphs — precisely the nested-capture bug this PR removes on GPU.

The only thing preventing it is the new `platforms.npu` override forcing `PIECEWISE` (`qwen3_tts.yaml:96-102`). Any NPU deploy that doesn't use this file, or that overrides `compilation_config`, re-enters the nested path. Given `buildkite/vllm-omni-npu-ci` is red on this PR, this is worth resolving in code rather than config: make the two mutually exclusive at the source, e.g. `self.talker_mtp_graph_safe = not current_omni_platform.is_npu()` in the talker, so the invariant holds regardless of yaml.

### Minor note, no change required

`_capture_talker_mtp_graphs` captures with `self.talker_mtp(ids, emb, hid, ts)` — no sampling kwargs — while runtime passes `do_sample/temperature/top_k/top_p` from `model_config.subtalker_sampling_params` (`gpu_model_runner.py:1878-1883`). This is safe today only because `talker_mtp` resolves the same `None` defaults from `self._subtalker_sampling_params` (`qwen3_tts_talker.py:1112-1120`), sourced from the identical `model_config.subtalker_sampling_params` (`:466-469`). That equality is now a load-bearing invariant under graph capture: if either side's defaults ever drift, the capture-time constants win and runtime sampling params become a silent no-op. A one-line comment at the capture site would make that explicit.

### Validation gap

Everything above is from static reading at `3b2d87c9c3bc`; I did not run the CUDA-graph capture or the NPU path (no NPU/matching accelerator here). The preflight confirmed the environment (vllm 0.26.0, torch 2.11.0+cu130) and that `CUDAGraphMode.PIECEWISE.has_full_cudagraphs()` is `False`, which is what makes the NPU yaml override effective. The claimed 39 ms → 9 ms `talker_mtp` improvement is unverified here.
