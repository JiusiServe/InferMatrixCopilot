# Review — PR #4859 `[BugFix][Ming-TTS] Improve Seed-TTS WER accuracy`

**Snapshot:** head `6ff4ce59ed87`, merge-base `a8b2bf11d2f2`, 6 files / +59 −45. PR state MERGED; `buildkite/vllm-omni-amd-ci` failing (gate already reported — not re-argued here).

## Verdict: Request changes

The instruction-handling and stop-gating alignment look intentional and the WER number is credible, but two changes are landmines: the benchmark PCM path now double-converts sample rate under the PR's *own* documented env settings, and the AudioVAE aggregator change silently truncates the encoder through an implicit shared-config mutation. Both are correctness issues rather than style.

---

### 1. `vllm_omni/benchmarks/data_modules/seed_tts_eval.py:179-194` — double sample-rate conversion in the WER path

`_pcm_s16le_to_f32_16k` now falls back to `stream_pcm_format_from_env()` when `pcm_sample_rate`/`channels` are not passed. Its only caller is line 616, `wav_16k = _pcm_s16le_to_f32_16k(pcm)` — no arguments — and `pcm` there is `out.tts_output_pcm_bytes` (line 586).

For the `openai-audio-speech` backend that buffer has **already** been normalized to 24 kHz mono by `patch/patch.py:1215` → `_pcm_s16le_to_seed_tts_wer_bytes(...)`, whose docstring at `patch.py:118` says exactly that ("Normalize streamed raw PCM to the 24 kHz mono PCM used by Seed-TTS WER"). Independent confirmation in the same file: `_save_seed_tts_eval_audio` writes that identical buffer with `sample_rate=24000` (`seed_tts_eval.py:116`).

Concrete trigger — the PR's own Test Plan:
```
export VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE=44100
```
The eval then treats 24 kHz mono samples as 44.1 kHz and resamples with ratio `16000/44100` instead of `16000/24000`, i.e. a ~1.84× time stretch and ~0.9-octave pitch drop before Whisper. That would inflate WER badly, so either the reported 1.83% was measured without this path active or the env var was not set for the eval run — either way the code as merged is wrong for the documented configuration. With `VLLM_OMNI_BENCH_AUDIO_CHANNELS=2` it also mixes down a second time, halving the sample count.

**Fix:** delete the env fallback here — the buffer's format is a fixed post-normalization contract, not a stream property. Either restore `pcm_sample_rate: int = 24000` with no env read, or make the call site explicit: `_pcm_s16le_to_f32_16k(pcm, pcm_sample_rate=24000, channels=1)`. The new docstring lines at `seed_tts_eval.py:42-43` should go with it; they contradict the "captured 24 kHz mono WAV" statement two lines above.

### 2. `vllm_omni/model_executor/models/common/ming/audio_vae.py:141` — mutating a config already owned by `self.encoder`

```python
config.num_hidden_layers = 4
self.aggregator = Qwen2Model(config)
```
`config` is the same object passed to `self.encoder = Qwen2Model(config)` ten lines earlier (`audio_vae.py:131`), and `PreTrainedModel.__init__` stores it by reference. `Qwen2Model.forward` iterates `self.layers[: self.config.num_hidden_layers]`, so the mutation retroactively shortens the encoder's forward pass. Verified against the installed transformers 5.14.1:

```
shared config: True   built layers: 8
after mutation m.config.num_hidden_layers = 4
layers actually executed: [0, 1, 2, 3]
```

The replaced code (`_qwen2_config({**encoder_args, "num_hidden_layers": 4})`) built an isolated config and left the encoder intact, so this is a real behavior change for every `patch_size != -1` build — which is the Ming default (`AudioVAEConfig.patch_size=4`, threaded through at `audio_vae.py:300-311`). It reaches both `ming_tts/prompt_encoder.py:137` and `ming_flash_omni/voice_presets.py:257`.

If truncating the encoder to 4 layers is the intended HF-parity behavior (plausible — it would explain the WER delta), then say so explicitly instead of relying on aliasing plus an HF-internal slicing detail that is not a stable contract. The encoder's remaining layers are still constructed and loaded as dead weight. **Fix:** build the aggregator from its own config copy and, if the encoder really should be 4 deep, set that in the encoder's config *before* constructing it, with a comment naming the HF reference. Today a transformers refactor to `for decoder_layer in self.layers:` silently changes encoder depth and regresses quality with no error.

### 3. `vllm_omni/model_executor/models/common/ming/audio_vae.py:349-351` — reparameterized sampling makes every request non-reproducible

```python
mean, scale = torch.chunk(h, 2, dim=1)
std = F.softplus(scale) + 1e-4
latent = (mean + std * torch.randn_like(mean)).transpose(1, 2)
```
`torch.randn_like` draws from the global (per-device) generator, not a request-local one. In the server path this means identical input + identical `seed` produces different reference-audio latents on every call, and the draw order depends on request interleaving across concurrent requests. It also makes `voice_presets.py:_build_wav_embeddings` non-deterministic, so cached preset embeddings differ per process start.

If HF parity requires sampling rather than taking the mean, thread a request-local `torch.Generator` through (`randn` with `generator=`) as the diffusion runner does for its per-request generators, or gate the sampling so deterministic/eval runs keep the `mean` path. As merged, WER/SIM benchmark reruns are no longer comparable and bug reports become non-reproducible.

### 4. `vllm_omni/model_executor/models/ming_tts/patch_emission.py:130` — short-duration requests now hard-fail

`min_required = max(min_stop_step + 2, min_steps)` with `STOP_HEAD_MIN_STEPS = 3` (`constants.py:51`) raises the floor from 4 to 5. `estimate_decode_step_window_for_duration` (`prompt_assembly.py:104-108`) returns `max_steps = target + 3`, so any prompt whose parsed duration yields `target_steps == 1` now produces `max_steps=4 < 5` and `_validate_ming_decode_window` raises `ValueError` where it previously passed. Same for a client sending `max_new_tokens=4` (`serving_speech.py:2678-2680`).

This is narrow (≈ one decode step of audio) but it turns a previously-served request into a 500. Either widen the estimator floor to `min_stop_step + 2` in `estimate_decode_step_window_for_duration`, or clamp instead of raising for the auto-derived window. The `+2` in `_resolve_ming_stop_decision:151` is fine on its own — it only shifts the earliest stop-head step by one, matching the HF gate.

### 5. `vllm_omni/entrypoints/openai/serving_speech.py:2623` / `2651` — `language` is now silently dropped for Ming

Removing `include_language` deletes the `instruction_dict["方言"] = request.language` branch, so an OpenAI-compatible client sending `language="粤语"` gets its request accepted and the field ignored rather than rejected. That's a user-visible API contract change with no note in the PR body and no test covering it — the existing test at `tests/model_executor/models/ming_tts/test_ming_shared_modules.py:96` passes `language="粤语"` but only asserts the flash-path dict, so it stays green either way.

If dialect control genuinely isn't supported by the Ming path, that's fine — but log or reject rather than dropping, and add an assertion to that test pinning the new behavior so it can't regress silently. The now-unused parameter removal itself is a clean subtraction; the concern is only the undocumented behavior change.

### 6. Minor — `vllm_omni/metrics/definitions.py:317-321`

`default_sample_rate` / `default_channels` are keyword-only parameters with no overriding caller (`patch.py:1163` and `seed_tts_eval.py:189` both use the defaults). Drop them and read the module constants directly. The move of `_audio_pcm_format` into `definitions.py` is a good dedupe otherwise; note it does add `max(..., 1)` clamping that the old helper lacked, which is an improvement but is an undocumented behavior change for `VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE=0`.
