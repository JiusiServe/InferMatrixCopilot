### 1. `vllm_omni/platforms/cuda/platform.py:251-253` — the docstring says "diffusion IR ops", but this hook is process-wide

```python
"""Prefer ``vllm_c`` CUDA kernels over ``native`` for diffusion IR ops."""
default = ["vllm_c", "native"]
```

`CudaOmniPlatform` is registered as the out-of-tree platform plugin (`vllm_omni/platforms/__init__.py:40`), so `vllm.platforms.current_platform` resolves to it for the whole process. `vllm/config/kernel.py:276` (`KernelConfig.set_platform_defaults`) calls `get_default_ir_op_priority` for **every** `VllmConfig`, not only the one built by the diffusion worker at `vllm_omni/diffusion/worker/diffusion_worker.py:175`.

Triggering path: any Omni deployment with an AR/LLM stage (Qwen3-Omni thinker, a Qwen2.5-VL text encoder) running under `CompilationMode.VLLM_COMPILE` with the inductor backend. Before this PR those stages got `rms_norm = ["native"]`; after it they get `["vllm_c", "native"]`. That is precisely the configuration upstream routes to `native` on purpose — `vllm/platforms/cuda.py:690-694`, *"Native used by default when compiling, use vllm_c kernels where available when no codegen"* — so inductor can codegen and fuse the norm rather than call an opaque custom op. No AR-stage measurement appears in the PR body.

Scope bound, so this doesn't read as bigger than it is: I checked `IrOpPriorityConfig` and it has exactly two fields, `rms_norm` and `fused_add_rms_norm`. Nothing else changes.

Smallest fix direction — express the divergence as "we pin the two rms_norm entries" instead of "we replace the whole default", so a future upstream field doesn't silently inherit `vllm_c`:

```python
cc = vllm_config.compilation_config
using_inductor = cc.backend == "inductor" and cc.mode != CompilationMode.NONE
default = ["native"] if using_inductor else ["vllm_c", "native"]

rms_norm = ["vllm_c", "native"]  # #4964: diffusion denoise loops are RMSNorm-heavy
if envs.VLLM_USE_OINK_OPS:
    rms_norm = ["oink"] + rms_norm

return IrOpPriorityConfig.with_default(default, rms_norm=rms_norm, fused_add_rms_norm=rms_norm)
```

That is behaviorally identical today. It does *not* address the AR-stage effect, which this hook has no per-stage seam for — so the real ask is: confirm the AR-stage flip is intended, and fix the docstring, which currently claims a narrower scope than the code has.

### 2. `qwen_image_transformer.py:557-558, 595-596, 1009` — Part 2 invalidates Part 1's headline evidence for Qwen-Image

After this diff there is no `vllm.model_executor.layers.layernorm.RMSNorm` left in the file (the import at line 20 is removed; grep confirms no remaining uses). `nn.RMSNorm` lowers to `torch.rms_norm`, which inductor decomposes — it does **not** reach the `_C::rms_norm` path Part 1 restores.

So the profiler numbers cited for Part 1 (`aten::mean` 2042 → 114, `stage_0_gen_ms` 1288 → 1080) were measured with Part 1 alone, back when the transformer still used vLLM `RMSNorm`. They no longer describe the merged state for Qwen-Image. In the merged tree, Part 1's actual beneficiaries are the 14 *other* diffusion transformers still importing vLLM `RMSNorm` — flux, flux2, flux2_klein, sd3, wan2_2_s2v, ltx2, hunyuan_video_15, omnigen2, longcat_image, ovis_image, ernie_image, t5_encoder, mistral_encoder, ming_flash_omni — none of which were benchmarked.

Why it matters: the platform-wide default change is currently justified by a measurement on the one model that Part 2 removes from that code path. Ask for a Part-2-only number, plus a no-regression check on one Flux or Wan config, so Part 1 carries independent justification.

### 3. `tests/platforms/test_cuda_ir_op_priority.py:31` — `monkeypatch.setattr` on `vllm.envs` leaks into the rest of the session

```python
monkeypatch.setattr(envs, "VLLM_USE_OINK_OPS", True)
```

`vllm.envs` resolves its variables through a module-level `__getattr__` that re-reads `os.environ` on each access — I verified `VLLM_USE_OINK_OPS` is not in `envs.__dict__` and that `setattr` materializes a real attribute there. Because `monkeypatch` captures the old value via `getattr` (which succeeds through `__getattr__`) and restores with `setattr`, the undo leaves a concrete attribute permanently shadowing the lazy lookup for the remainder of the pytest process. Any later test in the same worker that sets `VLLM_USE_OINK_OPS` via the environment will silently not take effect. Use `monkeypatch.setenv("VLLM_USE_OINK_OPS", "1")` instead — it restores cleanly and additionally exercises the real env plumbing that `platform.py:259` depends on.

### 4. `tests/platforms/test_cuda_ir_op_priority.py:11, 20` — test hygiene

- Line 11: `_vllm_config(*, backend: str = "inductor", mode)` — no caller ever passes `backend`. Inline `backend="inductor"` into the `CompilationConfig` literal and drop the parameter.
- Line 20: `CompilationMode.NONE` in the parametrize list is not a regression guard. Under the pre-fix code, `mode != CompilationMode.NONE` was already `False` for that case, so it returned `["vllm_c", "native"]` and the assertion passes on the buggy code too. Only `VLLM_COMPILE` and `STOCK_TORCH_COMPILE` actually guard #4964.
