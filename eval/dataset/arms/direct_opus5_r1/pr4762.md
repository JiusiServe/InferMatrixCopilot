## Review — PR #4762 `[Core / Bugfix] Add Mechanism for Endpoint Rejection`

**Snapshot:** head `cdc825f03b7d1c3848484a488a8fa9aa4ea6b2d4`, merge-base `1b0de21c552c` · state MERGED · CI: `buildkite/vllm-omni-amd-ci` and `buildkite/vllm-omni-npu-ci` failing (both are gates on the merged commit — not re-argued here).

### Verdict: Request changes

The endpoint-rejection mechanism itself (`endpoint_policy.py`) is small, correct, and well-tested — the route removal, the last-writer-wins overlap semantics, and the 400 shape all hold up. My concerns are almost entirely in the **`config_factory.py` rewrite that came along with it**. That rewrite is ~350 of the ~509 added lines, is not described in the PR body, and changes three behaviors unrelated to endpoint rejection. The one finding that undermines the PR's own security goal is #1.

---

### 1. `vllm_omni/engine/async_omni_engine.py:281-286` — restrictions and stage configs can resolve to *different* pipelines

```python
deploy_config_path = kwargs.get("deploy_config")
self.endpoint_restrictions = StageConfigFactory.get_pipeline_endpoint_restrictions(
    model=model, trust_remote_code=trust_remote_code, deploy_config_path=deploy_config_path,
)
```

The pipeline is now resolved **twice** from two different inputs. This call reads the raw `kwargs["deploy_config"]`. Stage resolution then re-resolves via `_resolve_stage_configs` (`async_omni_engine.py:1129-1130`) → `load_and_resolve_stage_configs`, and at `vllm_omni/entrypoints/utils.py:536-547` a `--stage-configs-path` pointing at a new-format YAML (`stages:` present, `stage_args:` absent) is **reassigned into `deploy_config_path`**.

Triggering path: `vllm serve <model> --stage-configs-path new_format.yaml` where that YAML sets `pipeline: <X>`. Stage resolution honours `pipeline: X` and serves pipeline X; `get_pipeline_endpoint_restrictions` saw `deploy_config_path=None`, fell through to auto-detection, and returns pipeline *Y*'s restrictions. The whole reason the `pipeline:` key exists is that auto-detection resolves the *wrong* pipeline for those models (the Ming-omni-tts rationale, whose comment this PR deleted at the old `config_factory.py` step 1). So exactly the models that need the override get the wrong endpoint restrictions — and for a Qwen3-Omni-shaped pipeline that means `/v1/completions` stays open and the server crash this PR exists to prevent is still reachable.

**Fix:** resolve the pipeline once. Have `_resolve_stage_configs` return the resolved `PipelineConfig` (or its `endpoint_restrictions`) alongside `config_path, stage_configs`, and set `self.endpoint_restrictions` from that. It also lets you delete `get_pipeline_endpoint_restrictions` and the extra cache layers entirely.

### 2. `vllm_omni/config/config_factory.py:75, 94, 189` — three uninvalidated process-lifetime caches

`@functools.cache` on `get_hf_config`, `try_infer_model_type`, and `get_pipeline_config`. `get_pipeline_config` keys on `(cls, model, trust_remote_code, deploy_config_path)` — the deploy YAML's **contents** are not part of the key, and `OMNI_PIPELINES` is not either.

Concrete failure: `register_pipeline()` (`vllm_omni/config/pipeline_registry.py:132`) is the documented out-of-tree plugin hook. Any lookup for a model *before* a plugin registers its pipeline caches `None` (or the wrong pipeline) for the process lifetime; the plugin's registration is then silently ignored, including its `endpoint_restrictions`. Same class of problem for a deploy YAML edited or rewritten at a stable path between two engine constructions in one process.

That this is real is visible in the PR's own tests: `tests/test_config_factory.py:47-49` had to add a fixture calling `get_hf_config.cache_clear()`, `try_infer_model_type.cache_clear()`, `get_pipeline_config.cache_clear()`. Production has no equivalent.

**Fix:** with #1 applied the model is resolved once per engine startup, so drop the caching entirely. If a cache is still wanted, scope it to the engine instance rather than the class, and include the registry generation / deploy-config mtime in the key.

### 3. `vllm_omni/config/config_factory.py:246-258` — malformed deploy config now crashes startup instead of degrading

```python
deploy_path = Path(deploy_config_path)
if deploy_path.exists():
    deploy_cfg = load_deploy_config(deploy_path)
```

The old highest-precedence deploy read was wrapped:

```python
try:
    explicit_pipeline = load_deploy_config(deploy_config_path).pipeline
except Exception:
    logger.exception("Failed to read 'pipeline' key from deploy config %s", deploy_config_path)
```

— it logged and fell through to auto-detection. The new helper is unguarded, so a malformed/unreadable YAML raises out of `AsyncOmniEngine.__init__`. Separately, the old step-1 read had **no `.exists()` gate**; the new one does, so any `deploy_config_path` that isn't a literal filesystem path (e.g. resolved through `_DEPLOY_DIR`) now silently skips the highest-priority override rather than being attempted.

If fail-fast on a bad deploy YAML is intended, say so and raise a clear error; right now it's an incidental change from a refactor. Either way the `.exists()` gate should match the resolution rules `load_deploy_config` actually supports.

### 4. `vllm_omni/config/config_factory.py:52-58` + `vllm_omni/entrypoints/utils.py:348` — `trust_remote_code` default silently flipped `True` → `False`

Old:
```python
trust_remote_code = cli_overrides.get("trust_remote_code", True)
if trust_remote_code is None:
    trust_remote_code = False
```
New: `create_from_model(..., trust_remote_code: bool = False, ...)`, and `entrypoints/utils.py:348` passes `cli_overrides.get("trust_remote_code", False)`.

Two changes, both unrelated to endpoint rejection:

- **Default flip.** For callers that omit the key, `get_config()` now runs with `trust_remote_code=False`, fails for custom-code checkpoints, and `get_hf_config` returns `None`. `get_pipeline_config` then skips the entire `if hf_config is not None:` architecture-matching fallback (`config_factory.py:~216`), so models resolved only by `hf_architectures` now return `None` and fall back to the legacy YAML path.
- **The `None` guard was dropped.** `.get("trust_remote_code", False)` returns `None` when the key is *present with value `None`* — that `None` now reaches `get_config(trust_remote_code=None)` and becomes a distinct `functools.cache` key from `False`. The deleted guard existed for that case.

Also at `async_omni_engine.py:288`, `kwargs["trust_remote_code"] = trust_remote_code` injects the key unconditionally. Since `_create_from_registry:341` builds `explicit_overrides = {k: v for k, v in cli_overrides.items() if v is not None}`, an injected `False` survives as an explicit per-stage override under the documented "caller-typed (non-None) value > deploy YAML" precedence — for callers that previously left the key absent. Worth confirming against the deploy YAMLs that set it (`vllm_omni/deploy/qwen3_tts.yaml:40,70`, `aura_omni.yaml:29,45,62,88`, `voxcpm2.yaml:24`, and ~10 top-level ones); I did not get to prove that end-to-end.

**Fix:** restore the `None` guard, and either restore the `True` default or state the flip explicitly in the PR description with the models it affects.

### 5. `vllm_omni/config/endpoint_policy.py:72` — layering inversion forces the whole serving stack into a config-module import

```python
def shutdown_unsupported_routes(app, endpoint_restrictions):
    from vllm_omni.entrypoints.openai.api_server import _remove_route_from_app
```

The deferred import exists only to break the cycle created by `api_server.py:94` importing `shutdown_unsupported_routes`. The cost is that `vllm_omni/config/` reaches into `vllm_omni/entrypoints/` at call time and pulls in the entire vLLM serving surface for a ~12-line starlette helper. Consequence: `tests/config/test_endpoint_policy.py` is not a unit test — on my checkout all four cases error at `api_server.py:63` with `ModuleNotFoundError: No module named 'vllm.entrypoints.serve.disagg'`, i.e. they can only run where the full serving import graph resolves.

**Fix:** move `_remove_route_from_app` into `endpoint_policy.py` (it needs only `starlette.routing.Route`) and have `api_server.py` import it from there. Cycle gone, deferred import gone, and the new tests become genuinely hermetic.

### 6. `vllm_omni/entrypoints/openai/api_server.py:514-517` — `hasattr` guard also disables the *global* restriction

```python
if hasattr(engine_client, "endpoint_restrictions"):
    shutdown_unsupported_routes(app, engine_client.endpoint_restrictions)
else:
    logger.warning("engine client has no endpoint restrictions attribute")
```

`UNSUPPORTED_ROUTES` is documented at `endpoint_policy.py:42-43` as "Routes that are not supported for any model" and is applied only *inside* `shutdown_unsupported_routes` (`:76`). So any engine client without the attribute leaves `/v1/chat/completions/batch` live and 500-ing — contradicting the "shutdown batch chat completions for all models" intent of commit `cdc825f0`. A warning-and-continue is also the wrong failure mode for a mechanism whose stated purpose is preventing a remote crash.

**Fix:** `shutdown_unsupported_routes(app, getattr(engine_client, "endpoint_restrictions", ()))` — unconditional, so the global set always applies and the branch disappears.

### 7. `vllm_omni/model_executor/models/qwen3_omni/pipeline.py:109` — unguarded `hf_config` dereference

```python
def resolve_qwen3_omni_pipeline(hf_config: Qwen3OmniMoeConfig) -> PipelineConfig:
    if not hf_config.enable_audio_output:
```

`get_pipeline_config` (`config_factory.py:~205`) calls `resolve_pipeline_config(model_type, hf_config)` where `model_type` may come from the raw `config.json` / `model_index.json` / basename fallbacks while `get_hf_config` returned `None` — so `hf_config=None` reaches this resolver and raises `AttributeError` during `AsyncOmniEngine.__init__`. Pre-existing, but this PR (a) widened reachability via finding #4 and (b) deleted the comment that documented the contract — `# Resolvers that get configs of the incorrect type should return None` was removed from the architecture-fallback loop. Either restore that comment and add `if hf_config is None: return QWEN3_OMNI_PIPELINE`, or make `resolve_pipeline_config` skip callable resolvers when `hf_config is None`.
