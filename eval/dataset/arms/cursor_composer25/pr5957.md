## Verdict

**Approve for the NVIDIA CUDA path, with follow-ups.** The IndexTTS 2.5 integration is thoughtfully structured: explicit two-stage contracts, fail-fast payload validation, request-end accumulation for the no-latent 2.5 path, native `speed` mapping, and broad unit coverage. I would not block on model correctness for the validated H200 path.

I would **not** treat the PR as fully merge-ready across platforms: AMD CI was still red at merge, there is no Buildkite coverage for IndexTTS 2.5, and connector-init allowlists omit the 2.5 architecture names.

## Strengths

1. **Stage contract is explicit and tested.** Stage 0 → Stage 1 handoff via `talker2s2mel_full_payload` fails fast on missing mel codes, latent mismatch, or empty conditioning (`S_ref`, `ref_mel`, `style`) instead of silently producing zero audio.

2. **2.5-specific runtime optimizations are opt-in and documented.** `omni_payload_at_request_end` and deferred D2H in the AR runner avoid per-decode host copies when `use_gpt_latent=false`; `omni_pooler_payload_include_hidden` is correctly disabled in that mode.

3. **Serving surface is coherent.** `IndexTTS25Adapter` maps OpenAI `speed` → `duration_factor = 1/speed`, validates `[0.5, 2.0]`, and opts into `native_speed_control` so serving does not double-apply torchaudio stretching.

4. **Test depth is unusually strong for a model PR.** Config/registry, adapter detection, duration bounds, payload partitioning, S2Mel CFM batching, EnhancedCodec, and scheduler whitelist drift tests give good contract coverage without requiring weights.

## Findings

### P1 — AMD CI gate still failing at merge

The PR merged with this check red. There is no ROCm-specific validation or fix in the diff for IndexTTS 2.5. Treat AMD readiness as unproven until that pipeline is green.

### P2 — IndexTTS 2.5 architecture names missing from connector-init allowlists

**Files:** `vllm_omni/worker/gpu_ar_model_runner.py:330-342`, `vllm_omni/worker/gpu_generation_model_runner.py:60-72`

The scheduler whitelist correctly includes both legacy and 2.5 consumer stages:

```62:63:vllm_omni/core/sched/omni_scheduling_coordinator.py
        ("IndexTTS2S2MelDecoder", "indextts2_s2mel_decoder"),
        ("IndexTTS25S2MelDecoder", "indextts2_5_s2mel_decoder"),
```

But worker connector init only lists the **2.0** arch strings (`IndexTTS2TalkerForConditionalGeneration`, `IndexTTS2S2MelDecoder`). The 2.5 pipeline uses `IndexTTS25TalkerForConditionalGeneration` / `IndexTTS25S2MelDecoder` (`vllm_omni/model_executor/models/indextts2/pipeline.py:56,80`).

Today this works only because `get_stage_connector_role()` returns non-`None` when deploy YAML wires connectors (`vllm_omni/deploy/indextts2_5.yaml`). Any custom stage layout that omits explicit connector role metadata would skip `init_omni_connectors()` and hang Stage 1 in `WAITING_FOR_INPUT`.

**Action:** Add the 2.5 arch names to both allowlists (and add a unit test mirroring `tests/core/sched/test_omni_scheduling_coordinator.py` so the two whitelists cannot drift again).

---

### P2 — `gpu_generation_model_runner` connector gate is narrower than AR runner

**File:** `vllm_omni/worker/gpu_generation_model_runner.py:73-75`

Stage 1 (S2Mel) gates on `model_arch in _OMNI_CONNECTOR_INIT_ARCHS` only. The AR runner also unions checkpoint `architectures` (`gpu_ar_model_runner.py:350-354`). For `IndexTTS25S2MelDecoder`, the generation runner depends entirely on `stage_connector_config.extra.role`; a blank `model_arch` override plus checkpoint `architectures=["IndexTTS25S2MelDecoder"]` would not match the 2.0-only allowlist.

**Action:** Align generation-runner gating with the AR runner’s `stage_archs & allowlist` logic.

### P3 — `duration_factor` validation is branded “2.5” but runs on shared IndexTTS2 paths

**Files:** `vllm_omni/model_executor/models/indextts2/indextts2_talker.py:565-569`, `vllm_omni/model_executor/models/indextts2/indextts2_s2mel_decoder.py:674-678`

Validation and error text reference IndexTTS 2.5 bounds in code shared with IndexTTS 2.0. Default `duration_factor=1.0` keeps legacy behavior unchanged, but a direct Omni caller passing e.g. `duration_factor=2.5` on an IndexTTS 2.0 deploy gets a misleading “IndexTTS 2.5” error, and S2Mel would apply speed scaling that legacy serving never documents.

**Action:** Gate validation and `_target_lengths` speed scaling on `config.model_type == "indextts2_5"`.
