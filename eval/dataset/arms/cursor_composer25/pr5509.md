## Verdict: **Approve with minor follow-ups**

This is a well-scoped kernel integration: typed `quant` config flows cleanly from `AttentionSpec` → `backend_kwargs()` → `TrtllmAttentionImpl`, SAGE kwargs are gated so the dense path stays compatible with older FlashInfer, and the init-time resolution of `trtllm_sage_attention_quantize` is the right fix for the Dynamo graph-break issue the authors already hit. Tests cover config round-tripping, init-time failures, quantize wiring, and (when hardware allows) numerical smoke checks. The main gaps are a silent ring-SP footgun, a docs regression, and backend-specific validation that is weaker than the documentation claims.

---

### Strengths

1. **Clean config layering** — `AttnQuantSpec` in `data.py` centralizes validation; `QuantConfig` in the backend is a thin runtime view. The shared `_coerce()` refactor for `skip_softmax` / `quant` is tidy.

2. **Backward compatibility** — `sage_kwargs` are only passed when `self.quant.enabled`, so dense `TRTLLM_ATTN` on older FlashInfer builds is unaffected (`trtllm_attn.py:292-299`).

3. **Fail-fast on missing deps** — Init checks for both the kernel signature (`sage_attn_sfs`) and the quantize routine are clear and actionable (`trtllm_attn.py:204-216`).

4. **Good test coverage** — Config serialization, dtype rejection, quantize call shapes, and optional GPU integration tests (`test_trtllm_attn.py:304-321`) with arch-dependent skip for int8 on non-SM100.

5. **SAGE + Skip-Softmax composition** — Both kwargs reach `trtllm_ragged_attention_deepseek` in the same call; config coexistence is tested.

### Issues to address

#### 1. **Ring SP + SAGE quant can silently ignore quantization** (medium)

`Attention._run_ring_attention` rejects configured skip-softmax because the ring path bypasses the backend impl, but there is no equivalent guard for SAGE quant:

```319:326:vllm_omni/diffusion/attention/layer.py
    def _run_ring_attention(self, query, key, value, attn_metadata):
        skip = getattr(self.attention, "skip", None)
        if skip is not None and getattr(skip, "configured", False):
            raise NotImplementedError(
                "Skip-Softmax (TRTLLM_ATTN) is not supported with ring sequence parallelism: "
                ...
            )
```

**What to change:** In `layer.py` around line 320, mirror the skip-softmax check for `getattr(self.attention, "quant", None)` and `quant.enabled`, raising `NotImplementedError` with the same “ring bypasses backend” rationale. Add a unit test analogous to `test_ring_sp_with_skip_softmax_rejected`.

#### 2. **Docs regression: removed sections + dangling cross-reference** (medium)

The PR adds a good SAGE section but also deletes unrelated content: “Known Limitations” (LTX-2 / FA4), “Validation Guidance”, “Reproducing the Benchmark Table”, and “Mixed backends across roles”. Worse, a stale reference remains:

```232:232:docs/user_guide/diffusion/attention_backends.md
- **Workaround for known issues**: see Known Limitations above.
```

**What to change:** Restore the removed sections (they are still accurate and useful), or at minimum fix the dangling link and move LTX-2 / validation guidance somewhere visible. The SAGE addition should not have come at the cost of unrelated doc deletions.

---

#### 3. **Docs overstate FLASHINFER_ATTN `quant` support** (low)

`attention_backends.md:185-188` says `FLASHINFER_ATTN` reads `dtype_qk` / `dtype_vo` / `flashinfer_backend`, and `AttentionSpec` allows `quant` on that backend (`data.py:1447-1450`). But `FlashInferAttentionImpl.__init__` never accepts or uses `backend_kwargs` — quant config is parsed and serialized but ignored at runtime.

**What to change:** Either (a) mark FLASHINFER quant as “reserved / not yet wired” in docs and restrict `AttentionSpec` validation to backends that actually consume it, or (b) implement consumption in `flashinfer_attn.py`. As merged, users can configure quant on `FLASHINFER_ATTN` and get a silent no-op.

---

#### 4. **Backend-specific `dtype_qk` validation is late and uses the wrong exception type** (low)

Docs say “A `dtype_qk` from the wrong set raises” (`attention_backends.md:188`), implying parse-time `ValueError` like other `AttnQuantSpec` checks. In practice, `bfloat16` / `float16` pass `AttnQuantSpec` and only fail at layer construction with `RuntimeError` (`trtllm_attn.py:199-203`). `test_quant_rejects_non_sage_dtype` covers this, but the UX is inconsistent with `skip_softmax` validation in `AttentionSpec.__post_init__`.

**What to change:** In `AttentionSpec.__post_init__` (around `data.py:1447`), when `backend == "TRTLLM_ATTN"` and `quant.dtype_qk` is set, require `dtype_qk in {"int8", "fp8_e4m3"}` and raise `ValueError`. Reserve `RuntimeError` for environment/kernel availability only.

---

#### 5. **Partial / misleading `quant` blocks silently no-op on TRTLLM** (low)

`AttnQuantSpec.enabled` is true if *either* `dtype_qk` or `dtype_vo` is set (`data.py:1424-1425`), so `quant: {"dtype_vo": "fp8_e4m3"}` or `quant: {"k_block_size": 4}` (without `dtype_qk`) serializes into `backend_kwargs` but `QuantConfig.enabled` stays false (`trtllm_attn.py:130-131`). User thinks quant is on; attention runs dense.

**What to change:** For `TRTLLM_ATTN`, require `dtype_qk` whenever the `quant` block is present and enabled. For `FLASHINFER_ATTN`, define the parallel rule once that backend actually consumes quant.

#### 7. **`torch.compile` + per-step quantize** (follow-up, not blocking)

Quantization runs inside `forward_cuda` on every call (`trtllm_attn.py:296-297`). The PR correctly resolves the function pointer at init to avoid the `lru_cache` graph break, but the quantize call itself may still force Dynamo recompiles or fall out of cudagraphs under regional `torch.compile` (the PR’s own benchmarks use compile). Worth a follow-up benchmark with `torch._dynamo.explain` or checking whether quantize should sit behind `@torch.compiler.disable` or be lifted to a custom op boundary — especially since the claimed 1.15–1.19× wins already include compile.

### Summary

Shippable core logic with sensible defaults and good backward compatibility. Before calling this fully production-ready, I'd want the ring-SP guard (issue 1) and the docs fix (issue 2). Issues 3–5 are polish that align behavior with documentation and prevent silent misconfiguration. None of these undermine the benchmark results on the intended path (single-GPU / Ulysses SP, Wan I2V, `torch.compile`), but they matter for users combining SAGE with ring parallelism or misreading the shared `quant` schema.
