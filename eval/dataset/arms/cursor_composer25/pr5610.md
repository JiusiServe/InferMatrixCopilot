## Specific comments

### 1. Add a reciprocal link from `async_chunk.md`
**File:** `docs/design/feature/async_chunk.md` (Related Files section, ~line 262)

The new page links to async chunk in the overview and related files, but `async_chunk.md` does not link back. Readers landing on the async-chunk doc will miss this companion optimization.

**Change:** Add a bullet such as:
`- [Async Omni Output Materialization](omni_async_output_materialization.md): Defers CPU payload construction off the AR decode critical path (requires async_chunk).`

---

### 2. Clarify the two CUDA copy streams in Architecture
**File:** `docs/design/feature/omni_async_output_materialization.md:145-150` and `:155-168`

The doc reads as if one dedicated stream handles all async copies. In code there are two:

- `_omni_payload_copy_stream` — hidden/multimodal payload D2H in `_snapshot_tensor_payload_to_cpu_async()`
- `async_output_copy_stream` — sampled-token (and logprob) D2H in `OmniAsyncGPUModelRunnerOutput.__init__()`

The lifecycle is still correct at a high level, but naming both streams would help operators debugging overlap or stream stalls.

---

### 3. Tighten lifecycle step ordering slightly
**File:** `docs/design/feature/omni_async_output_materialization.md:139-153`

Step 5 says the background thread “starts” after D2H enqueue; step 6 says sampled tokens are registered “immediately.” In practice, `OmniAsyncGPUModelRunnerOutput.__init__()` enqueues sampled-token D2H, starts the background thread, and then `sample_tokens()` calls `set_async_sampled_token_ids()` before returning. Consider reordering or noting that sampled-token registration happens after the async output object is constructed, not strictly before the background thread starts.

---

### 4. Qwen3-TTS example YAML is slightly under-specified
**File:** `docs/design/feature/omni_async_output_materialization.md:300-310`

The excerpt omits `async_scheduling: true` on Stage 1 (Code2Wav), which is present in `vllm_omni/deploy/qwen3_tts.yaml:81`. That is not wrong—the generation stage does not use async Omni output materialization—but a one-line note (“Stage 1 may still set `async_scheduling: true`; this feature applies only to the AR Talker”) would prevent readers from thinking the excerpt is incomplete or wrong.

---

### 5. Performance table could name the third enabling knob explicitly
**File:** `docs/design/feature/omni_async_output_materialization.md:108-112`

The baseline row is “CUDA Graph + async chunk.” The incremental row is “+ async output materialization.” That is fine given the blog attribution, but a footnote that the third row also assumes default Qwen3-Omni deploy settings (`async_scheduling` on AR stages, prefix caching off, model opt-in) would make the benchmark preconditions self-contained without rereading the Enabling section.

---

### 6. Consider listing other opt-in models (optional)
**File:** `docs/design/feature/omni_async_output_materialization.md:89-100` or Compatibility section

The doc correctly focuses on Qwen3-Omni and Qwen3-TTS. If the intent is to document the *mechanism* rather than the *product surface*, a short note that activation is per-model via `use_async_omni_output` (and that other models default to `False`, e.g. Moss TTS) would set expectations for contributors adding new pipelines.

---

### 7. `design/index.md` remains selectively curated (pre-existing)
**File:** `docs/design/index.md:9-16`

Adding this page is good. `async_chunk.md` and several other feature docs are still absent from the index. Not introduced by this PR, but if the index is meant to be a complete feature catalog, a follow-up pass would help.
