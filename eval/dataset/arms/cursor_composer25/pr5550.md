## Verdict: **Approve**

This PR delivers what it promises: a narrow W0 slice that defines the Scheduler→Worker allocation wire DTOs, threads them through `NewRequestData` and the multiproc RPC boundary, and validates identity/mode at the Worker entry without yet installing or consuming block tables. The scope matches the stated W0 boundary, dense-path backward compatibility is preserved (legacy 3-arg RPC when metadata is absent), and the new contract tests are targeted and pass locally (37 tests in `tests/diffusion/diffusion_kv/` plus the engine cleanup test).

The main follow-ups belong in W1 (allocator, BlockTable installer, step-state threading), not in this transport PR.

## Strengths

- **Clean ownership split**: Scheduler-mutable `DiffusionKVRequest` stays off the wire; `DiffusionKVMetadata` is a one-shot allocation snapshot on `NewRequestData` (`vllm_omni/diffusion/diffusion_kv/metadata.py`, `vllm_omni/diffusion/sched/interface.py:155-178`).
- **Fail-fast identity checks on the request RPC path**: `validate_new_request_data_identity` runs before dispatch and before the RPC error wrapper (`vllm_omni/diffusion/executor/multiproc_executor.py:454-460`), so bad envelopes never become worker outputs.
- **Backward-compatible RPC shape**: metadata is an optional 4th positional arg only when present (`multiproc_executor.py:544-546`); tests lock this (`tests/diffusion/diffusion_kv/test_worker_contract.py:204-221`).
- **Mode gating is conservative**: dense rejects unexpected metadata; paged accepts but does not require it (`diffusion_model_runner.py:163-178`).

## Findings

### 1. W1 follow-up — metadata is validated then dropped (step path)

**`vllm_omni/diffusion/worker/diffusion_model_runner.py:673-679`**

`execute_stepwise` validates `new_req.diffusion_kv_metadata` at entry (`:750-755`) but `_update_states` builds `StepRequestState` without capturing it—only `prepared_layout` is carried forward. Once W1 installs BlockTables, step mode will need either a field on `StepRequestState` or a Worker-side allocation registry keyed by `(request_id, allocation_generation)`.

**What to change (W1):** extend `StepRequestState` (or add a parallel registry) and thread metadata from the first `scheduled_new_reqs` envelope into subsequent step waves.

---

### 2. Low — `execute_batch` does not validate identity at the executor

**`vllm_omni/diffusion/executor/multiproc_executor.py:586-620`**

`execute_request` validates every `NewRequestData` before RPC (`:459-460`). `execute_batch` only does so indirectly when `len(scheduled_new_reqs) <= 1` (delegates to `execute_request`) or on the DLO-DP path (`:605-613`). The fused multi-request `execute_model_batch` RPC (`:615-619`) ships the scheduler output without executor-level identity checks; validation happens only inside `DiffusionModelRunner.execute_model_batch` (`diffusion_model_runner.py:636-641`).

**Impact:** Identity errors on multi-request batch waves fail on the worker and may surface through a different error path than request-mode identity failures (which are deliberately kept outside the per-request RPC `try/except`).

**What to change:** hoist the `validate_new_request_data_identity` loop to the top of `execute_batch` (and optionally `execute_step`) for parity with `execute_request`.

---

### 3. Low — DLO DP multi-concurrency silently falls back to serial RPC when any metadata is present

**`vllm_omni/diffusion/executor/multiproc_executor.py:462-471`**

`has_diffusion_kv_metadata` disables the fused DLO AllGather multi-request wave and forces per-request `execute_model` RPCs. That is functionally safe but is a performance regression once the Scheduler starts attaching metadata to concurrent DLO waves.

**What to change (W1):** document this in the executor dispatch comment or RFC; plan a metadata-aware DLO batching strategy if DP concurrency under paged KV is a requirement.

---

### 4. Low — custom runners/extensions will break once metadata is emitted

**`vllm_omni/diffusion/worker/diffusion_worker.py:462-465`**

When metadata is non-`None`, it is passed as a keyword to `model_runner.execute_model`. Custom `diffusion_model_runner_cls` implementations or worker extensions whose `execute_model` lacks `diffusion_kv_metadata` (and `**kwargs`) will raise `TypeError` once W1 starts producing metadata.

The existing test only covers the no-metadata dense path (`tests/diffusion/diffusion_kv/test_worker_contract.py:274-290`).

**What to change (W1):** add a migration note and a test that a runner accepting `**kwargs` survives metadata; update platform runner base signatures when the allocator lands.

---

### 5. Nit — RPC routing bypasses `WorkerWrapperBase.execute_model`

**`vllm_omni/diffusion/worker/diffusion_worker.py:1035-1036` vs `:1353-1374`**

Worker RPC calls `WorkerWrapperBase.execute_method`, which dispatches to `DiffusionWorker.execute_model` directly (`getattr(self.worker, method)`), not `WorkerWrapperBase.execute_model`. Both layers duplicate the optional-metadata kwargs logic. Not a W0 bug (positional 4th arg works on `DiffusionWorker`), but extensions overriding only the wrapper method would miss metadata.

**What to change:** in W1, either route RPC through the wrapper method or document that extensions must override `DiffusionWorker.execute_model`.

---

### 6. Nit — unrelated but good: engine init failure cleanup

**`vllm_omni/diffusion/diffusion_engine.py:191-208`**

Scheduler/executor teardown on init failure is a worthwhile fix, though orthogonal to KV plumbing. Test coverage is adequate (`tests/diffusion/test_diffusion_engine_cleanup.py:126-164`).

---

### 7. Test gap — no MP serialization roundtrip

Tests mock `collective_rpc` and call runners directly. There is no test that `DiffusionKVMetadata` survives the actual multiprocessing/pickle transport used by `MessageQueue`.

**What to change (W1):** add a small integration or executor-level test that enqueues metadata through the real RPC path.

---

### 8. Nit — DTO mutability

**`vllm_omni/diffusion/diffusion_kv/metadata.py:16-57`**

Scheduler-side `DiffusionKVContext` is frozen (`request.py:13`); wire metadata DTOs are mutable dataclasses. Consider `frozen=True` in W1 once construction sites are fixed, to prevent accidental mutation between Scheduler packaging and Worker installation.

## Summary

No merge-blocking defects for the stated W0 scope. The transport contract, validation placement, and dense-path compatibility are sound. The actionable work is mostly W1: consume/store metadata (especially in step mode), align executor validation across batch/step paths, and prepare custom runner/extension signatures before the allocator starts emitting snapshots.
