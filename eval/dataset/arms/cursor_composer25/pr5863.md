**Attention backend guidance is correct for SM120.** `platform.py` defaults datacenter Blackwell (SM100/SM103) to `TRTLLM_ATTN` and consumer Blackwell (SM120, RTX PRO 6000) to `CUDNN_ATTN`. Explicit `--diffusion-attention-backend CUDNN_ATTN` is the right call and matches the 5090 recipe pattern.

**API examples match the server contract.** T2VA’s required `aspect_ratio` is enforced in `pipeline_minimax_h3.py`. `/v1/videos/sync`, `extra_params.task`, and profiler headers `X-Stage-Durations` / `X-Peak-Memory-MB` match `api_server.py`.

**Benchmark methodology is credible.** Warmup before measurement, profiler-enabled stage times, `nvidia-smi` peak sampling, and the honesty about unmeasured Ref2VA / device-order tuning are all good practice.

## Issues to fix

### P1 — `numactl` flags presented as `vllm serve` arguments

```201:203:recipes/MiniMaxAI/MiniMax-H3-RTX-PRO-6000.md
Use `CUDA_VISIBLE_DEVICES=0,2,1,3`, `--cpunodebind=0 --membind=0`, and
`--port 8091` for the FL2VA server. Use `CUDA_VISIBLE_DEVICES=4,6,5,7`,
`--cpunodebind=1 --membind=1`, and `--port 8092` for the Ref2VA server.
```

`--cpunodebind` and `--membind` are **not** `vllm serve` flags (confirmed by searching the codebase; they appear only in this file). They are `numactl` options. A user copying this literally will get an argparse error.

**Change:** Wrap the command in `numactl`, e.g.:

```bash
numactl --cpunodebind=0 --membind=0 \
  env CUDA_VISIBLE_DEVICES=0,2,1,3 VLLM_OMNI_VIDEO_SYNC_TIMEOUT=1800 \
  vllm serve "${MODEL_ROOT}/FL2VA" ... --port 8091
```

### P1 — Dual-server layout omits `Ref2VA` model path

In the same section (lines 193–205), the Ref2VA server is described as using “the four-GPU configuration” but only `CUDA_VISIBLE_DEVICES`, NUMA binding, and `--port` are changed. The four-GPU commands all set `MODEL="${MODEL_ROOT}/FL2VA"` (lines 112–113). Without an explicit `MODEL="${MODEL_ROOT}/Ref2VA"` (or `--task-type ref2va` on the hub ID), the second server would still load FL2VA.

**Change:** State explicitly that the Ref2VA server uses `MODEL="${MODEL_ROOT}/Ref2VA"` (or equivalent `--task-type ref2va`), mirroring the single-server note at lines 215–216.

### P2 — Ref2VA curl example uses non-portable `/root/` paths

```336:345:recipes/MiniMaxAI/MiniMax-H3-RTX-PRO-6000.md
curl -X POST "http://127.0.0.1:${PORT}/v1/videos/sync" \
  ...
  -F "input_reference=@/root/hand.jpg;type=image/jpeg" \
  -F "audio_reference=</root/audio_ref.json" \
  ...
  -o /root/out_ref2va.mp4
```

Other recipes (`MiniMax-H3.md`) use `${REF_IMAGE}`, `${API_URL}`, etc. The `/root/` paths look like author-local artifacts.

**Change:** Replace with placeholders, e.g. `${REF_IMAGE}`, `${AUDIO_REF_JSON}`, `-o ref2va.mp4`, and add a one-line note that `audio_ref.json` should contain `{"audio_url": "..."}` (matching `_parse_form_json(audio_reference)` in `api_server.py`).

### P2 — Missing prerequisites and cross-links

### P3 — Ref2VA example parameters don’t match the validated workload

The benchmark table (lines 236–251) uses **50 steps**, **duration=5.0**, and **seed=1101**. The Ref2VA example (lines 343–344) uses **60 steps** and **duration=8**. That’s fine as an illustrative Ref2VA call, but readers may assume it’s validated on this hardware.

**Change:** Add “example only — not measured on this host” or align step count/duration with the T2VA benchmark and note expected latency scaling.

### P3 — Stage-time vs E2E reconciliation is slightly off for 2 GPUs

Lines 257–259 claim stage times sum to “roughly 0.75 s less than end-to-end in all three configurations.” That holds for 4-GPU (171.57 vs 172.32) and 8-GPU (89.73 vs 90.48), but for 2-GPU the sum is **284.99 s** vs E2E **284.76 s** (stages slightly *exceed* E2E by ~0.2 s).

**Change:** Soften to “within ~1 s” or note the 2-GPU case separately.

### P3 — Peak-memory measurement methods are mixed

The validation table (lines 254–255) uses `nvidia-smi` sampling, while lines 325–328 suggest reading `X-Peak-Memory-MB` from response headers. Those measure different things (`diffusion_model_runner.py` uses CUDA peak stats; the recipe uses driver-reported `memory.used`).

**Change:** Clarify that the table numbers come from `nvidia-smi`, and header `X-Peak-Memory-MB` is a separate CUDA-allocator metric.

### Nit — Template / metadata gaps

Per `recipes/TEMPLATE.md`, a Summary block (vendor, model, task, mode, maintainer) would improve consistency. The validated environment cites container image `vllm/vllm-omni:minimax-h3` without a digest or vLLM-Omni commit, which limits reproducibility.

**Change:** Add a Summary section; pin the image tag or record the vLLM-Omni commit used for the benchmarks.

### Nit — PR description vs documented latency

The PR description claims “~4 min” on 8×6000; the recipe’s validated **Client E2E is 90.48 s (~1.5 min)** for 8 GPUs (or ~4.7 min on 2 GPUs). The recipe numbers are more precise; consider updating the PR/issue blurb to match.
