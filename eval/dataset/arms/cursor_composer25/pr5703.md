## Verdict: **Approve with minor follow-ups**

The core change is small, correctly motivated, and aligned with PyTorch’s device-module API. Replacing hard-coded `torch.cuda.*` calls in the conditioned video-VAE encode paths fixes a real MUSA bug: on MUSA, `parameter.device.type` is `"musa"`, so the old `== "cuda"` guard skipped accelerator RNG seeding entirely and broke fixed-seed conditioned encoding. The `fork_rng` + `manual_seed(42)` structure is preserved, post-encode CPU FP32 normalization is untouched, and ROCm behavior is unchanged (`device.type` remains `"cuda"`). Reported MUSA smoke (deterministic latents, RNG restore, Ref2VA serving) is credible for this diff.

The main gaps are documentation accuracy, missing automated coverage for the RNG fix, and a slightly loose device binding — not correctness blockers for the stated CUDA/MUSA goal, but worth fixing in a follow-up.

**CI:** `buildkite/vllm-omni-amd-ci` is failing per PR gates. This diff does not touch AMD/ROCm paths (ROCm still reports `cuda`), so treat that gate as unrelated infrastructure noise rather than evidence against this change.

## Specific comments

### 1. Recipe copy-paste error: Ref2VA example serves `FL2VA` — `recipes/MiniMaxAI/MiniMax-H3-MUSA.md:72-76`

The prose describes the **validated Ref2VA TP4 profile**, but the shell block sets:

```bash
export MODEL="${MODEL_ROOT}/FL2VA"
```

For Ref2VA reproduction this should be `Ref2VA`, consistent with line 70 (“or to `Ref2VA` for Ref2VA”) and the validation section at lines 124–127. As written, users following the recipe will start the wrong checkpoint partition while expecting Ref2VA behavior.

**Change:** set `MODEL="${MODEL_ROOT}/Ref2VA"` in the Ref2VA example, or split into separate FL2VA and Ref2VA server blocks like `MiniMax-H3-NPU.md`.

### 2. Bind `device_module` to the VAE’s constructor device — `vllm_omni/diffusion/models/minimax_h3/vae.py:120`

```120:120:vllm_omni/diffusion/models/minimax_h3/vae.py
        self.device_module = torch.get_device_module()
```

`torch.get_device_module()` without an argument resolves the **current default accelerator**, not necessarily the `device` passed into `__init__`. On MUSA this likely works in practice because the pipeline is constructed on-device, but it is fragile if init ordering or offload ever diverges.

**Change:** use the constructor argument:

```python
self.device_module = torch.get_device_module(device)
```

Alternatively, resolve at encode time from `parameter.device` so the module always matches the tensor’s backend.

### 3. Device allowlist is broader than the PR claims — `vllm_omni/diffusion/models/minimax_h3/vae.py:170,214`

```170:170:vllm_omni/diffusion/models/minimax_h3/vae.py
        devices = [parameter.device] if parameter.device.type != "cpu" else []
```

The PR description says the allowlist is **CUDA and MUSA only**, but `!= "cpu"` also enables accelerator RNG for `"npu"`, `"xpu"`, `"mps"`, etc. Previously, only `"cuda"` (including ROCm) was seeded; NPU/Ascend encoding silently skipped accelerator seeding.

That may be desirable on NPU, but it is **unvalidated scope expansion** relative to the PR text and the existing NPU recipe. If the intent is truly CUDA/MUSA-only, tighten the guard:

```python
if parameter.device.type in ("cuda", "musa"):
```

If the broader behavior is intentional, update the PR/recipe wording and add NPU regression coverage.

### 4. PR description overclaims test additions

The description says this PR “adds coverage for the torchaudio, soundfile, and ffmpeg audio-loading paths,” but the diff contains **no test file changes**. Audio fallback logic lives in `reference_video.py` (`load_audio_file`, `load_video_audio`) and predates this PR; `grep` finds no tests exercising those paths under `tests/`.

The validation command also references `tests/diffusion/models/minimax_h3/test_minimax_h3_vae.py`, which **does not exist** in the tree. I ran the three existing focused modules and got **63 passed** — close to but not matching the claimed “36 passed” count, and none of those tests assert MUSA/CUDA RNG seeding.

**Change:** add a focused unit test that mocks `device_module.manual_seed` / `fork_rng` for a non-CPU device type (including `"musa"`), and optionally tests for `load_audio_file` fallback chains. Until then, soften the PR description to “validated manually on MUSA” rather than “adds coverage.”

### 5. Existing contract tests bypass the RNG path — `tests/diffusion/models/minimax_h3/test_minimax_h3_contract.py:344-353`

`test_video_vae_encode_uses_configured_parallel_tiling` constructs a bare `MiniMaxH3VideoVAE` via `object.__new__` without setting `device_module`.
