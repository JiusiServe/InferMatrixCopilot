### `vllm_omni/diffusion/attention/backends/flash_attn_hub.py:42-46` — medium / performance

The global `_hub_lock` is held during the entire `_load_hub_module` call, which performs potentially slow network/disk I/O (downloading kernels from HuggingFace Hub). In a multi-threaded environment, a thread loading `flash-attn2` will block another thread that needs `flash-attn3` — even though they don't share any state. Consider using a per-key lock pattern (e.g., a dict of locks keyed by `repo_id`, or a check-then-lock-then-recheck approach) so that only threads loading the *same* repo_id are serialized.

Anchored to:

```
def _get_hub_module(repo_id: str):
    with _hub_lock:
        if repo_id not in _hub_modules:
            _hub_modules[repo_id] = _load_hub_module(repo_id)
        return _hub_modules[repo_id]
```

Suggested:

```
import threading

_hub_modules: dict[str, object] = {}
_hub_lock = threading.Lock()
_key_locks: dict[str, threading.Lock] = {}


def _get_hub_module(repo_id: str):
    # Fast path: already cached, no lock needed
    if repo_id in _hub_modules:
        return _hub_modules[repo_id]
    # Serialize loads only for the same repo_id
    with _hub_lock:
        key_lock = _key_locks.setdefault(repo_id, threading.Lock())
    with key_lock:
        # Double-check after acquiring the per-key lock
        if repo_id not in _hub_modules:
            _hub_modules[repo_id] = _load_hub_module(repo_id)
        return _hub_modules[repo_id]
```

### `vllm_omni/diffusion/attention/backends/flash_attn_hub.py:22` — low / maintainability

The module-level `_hub_modules` dictionary grows without bound. While the current set of repo IDs is small and static (`flash-attn2`, `flash-attn3`), an unbounded global cache could accumulate stale entries if dynamic repo IDs are introduced in the future. Consider adding a size cap, LRU eviction, or using `functools.lru_cache` on `_load_hub_module` (with appropriate thread safety) if future growth is anticipated.

Anchored to:

```
_hub_modules: dict[str, object] = {}
```
