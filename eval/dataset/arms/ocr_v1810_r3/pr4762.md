### `vllm_omni/entrypoints/openai/api_server.py:263` — medium / bug

The type annotation for `methods` was changed from `set[str] | None` to `frozenset[str] | None`, but existing callers on lines 503-504 pass `set[str]` literals (`{"POST"}`, `{"GET"}`). Since `set` is not a subtype of `frozenset` (nor vice versa), this will cause static type checking errors. The runtime behavior is unaffected because Python doesn't enforce type annotations at runtime and the `&` operator works on both types. Consider widening the annotation to `set[str] | frozenset[str] | None` or using `AbstractSet[str]`/`Collection[str]` from `collections.abc`.

Anchored to:

```
def _remove_route_from_app(app, path: str, methods: frozenset[str] | None = None):
```

Suggested:

```
def _remove_route_from_app(app, path: str, methods: set[str] | frozenset[str] | None = None):
```

### `vllm_omni/config/config_factory.py:255-259` — high / bug

Missing try/except around `load_deploy_config` — regression from the old code. The original `create_from_model` wrapped the first deploy-config load in a try/except to gracefully handle malformed YAML or permission errors (logging the exception and falling through to auto-detection). The new consolidated `_get_deploy_override_pipe_config` calls `load_deploy_config` without any exception protection. If the deploy config YAML is malformed, inaccessible, or raises any exception, the entire process will crash with an unhandled error instead of falling back to pipeline auto-detection.

Suggestion: wrap `load_deploy_config` in a try/except that logs the failure and returns `None`, preserving the original resilience.

Anchored to:

```
        deploy_path = Path(deploy_config_path)
        if deploy_path.exists():
            deploy_cfg = load_deploy_config(deploy_path)
            if deploy_cfg.pipeline is not None:
                return cls.resolve_pipeline_config(deploy_cfg.pipeline, hf_config)
```

Suggested:

```
        deploy_path = Path(deploy_config_path)
        if deploy_path.exists():
            try:
                deploy_cfg = load_deploy_config(deploy_path)
            except Exception:
                logger.exception("Failed to load deploy config from %s", deploy_config_path)
                return None
            if deploy_cfg.pipeline is not None:
                return cls.resolve_pipeline_config(deploy_cfg.pipeline, hf_config)
```

### `vllm_omni/config/config_factory.py:267` — medium / bug

Backward-incompatible change: `trust_remote_code` now defaults to `False` (was `True` in the old code). The old logic extracted `trust_remote_code` from `cli_overrides.get("trust_remote_code", True)`, meaning models that needed remote code loading would get it by default. This means custom architectures that require `trust_remote_code=True` may silently fail to load unless the caller explicitly sets it. While this may be intentional, it is a breaking behavioral change worth documenting.


Suggested:

```
        trust_remote_code: bool = True,
```
