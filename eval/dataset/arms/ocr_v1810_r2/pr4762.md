### `vllm_omni/config/endpoint_policy.py:74-78` — high / bug

The comment states that when endpoint_restrictions and UNSUPPORTED_ROUTES overlap, the UNSUPPORTED_ROUTES reason message should be used. However, no deduplication logic is implemented. Since endpoint_restrictions entries are processed first (they appear before UNSUPPORTED_ROUTES in the concatenated tuple), their handlers are registered first in FastAPI, and the first matching route handles the request. This means the UNSUPPORTED_ROUTES handler for the overlapping capability would never be reached, contradicting the comment's intent. The overlap may be unlikely today (only CHAT_COMPLETIONS_BATCH is in UNSUPPORTED_ROUTES), but if a pipeline config adds that same restriction, the behavior won't match the documented intent.

Suggestion: Deduplicate by building a set or dict keyed on capability, giving UNSUPPORTED_ROUTES priority.

Anchored to:

```
    # Generally these should not overlap since there is no point. If they do,
    # we use the reason message in UNSUPPORTED_ROUTES, for consistent error messages.
    restricted_endpoints = (*endpoint_restrictions, *UNSUPPORTED_ROUTES)

    for end_restrict in restricted_endpoints:
```

Suggested:

```
    # Generally these should not overlap since there is no point. If they do,
    # we use the reason message in UNSUPPORTED_ROUTES, for consistent error messages.
    # Build a dict keyed by capability so UNSUPPORTED_ROUTES takes precedence.
    restricted_map: dict[OmniServingCapability, EndpointRestriction] = {}
    for restriction in endpoint_restrictions:
        restricted_map.setdefault(restriction.capability, restriction)
    for restriction in UNSUPPORTED_ROUTES:
        restricted_map[restriction.capability] = restriction

    for end_restrict in restricted_map.values():
```
