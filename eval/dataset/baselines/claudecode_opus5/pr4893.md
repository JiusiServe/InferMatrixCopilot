# Review of PR #4893 — [Bugfix] Fix HunyuanImage3 MoE groups for vLLM 0.24

## Verdict

**Approve with follow-ups.** The root-cause diagnosis is right and the shape of the fix is the correct one: diffusion coordinators keep the rank layout but don't implement vLLM's MoE runtime surface, so building vLLM-owned companion coordinators (rather than aliasing) is the proper split. I verified the mechanism against the installed vLLM: `FusedMoEParallelConfig.make` derives `dp_rank` from `get_dp_group().rank_in_group` and `pcp_rank` from `get_pcp_group().rank_in_group` (`fused_moe/config.py:1210-1213`), and `use_all2all_kernels` is on when `dp_size > 1 or pcp_size > 1` — which is exactly `tp2_cfgp2` and `tp2_sp2` respectively. `init_model_parallel_group(..., group_name=..., use_device_communicator=True)` matches the current signature, `_get_unique_name` auto-suffixes so re-init won't collide, and `group_name="ep"` is what sets `is_ep_communicator`. So the fix targets the right seams.

Two things I'd want addressed before this is load-bearing: the new DP-metadata hook is not gated on the MoE mapping actually being active, and it introduces a collective into a code path that is provably not rank-symmetric under CFG parallelism. Both are invisible to the DiT-only smoke test that was run.

The `buildkite/vllm-omni-amd-ci` and `buildkite/vllm-omni-npu-ci` gates are red — see comment 7 for why this change is a plausible cause rather than unrelated noise.

## Comments

### 1. `_set_forward_context_dp_metadata` fires outside the MoE mapping it was written for — `vllm_omni/diffusion/models/hunyuan_image3/hunyuan_fused_moe.py:37-39`

```python
dp_group = getattr(_vllm_ps, "_DP", None)
if dp_group is None or getattr(dp_group, "world_size", 1) <= 1:
    return
```

The guard is "is there a vLLM DP group bigger than 1", but the thing that makes this metadata meaningful is "did `initialize_model_parallel` build the vLLM-owned MoE mapping". Those are not the same set. `parallel_state.py:816` assigns `vllm_parallel_state._DP = _DP` (the *diffusion* DP coordinator) unconditionally, and your own test pins that this survives when EP is off — `test_expert_parallel_layout.py:247`, `assert parallel_state.vllm_parallel_state._DP is parallel_state._DP` with `world_size == 2`.

So a HunyuanImage3 run with `data_parallel_size: 2, enable_expert_parallel: false` now, per forward context, issues a gloo `all_gather_object` across diffusion DP ranks and installs a `DPMetadata` on the vLLM forward context. That flips `MoERunner._sequence_parallel_context()` (`fused_moe/runner/moe_runner.py:598-609`) from `nullcontext()` to `sp_local_sizes(...)` for a config where no vLLM DP semantics were ever intended — and it adds a cross-rank collective to a group whose ranks are processing *different requests*.

**Change:** gate on the mapping, not the world size. The most precise signal is on the module you're hooking — `module.moe_config.use_all2all_kernels` (or `moe_parallel_config.dp_size > 1`) — since that's exactly the code that will read `dp_metadata`. `vllm_omni.diffusion.distributed.parallel_state._EXPERT_PARALLEL_GROUP_RANKS is not None` also works and is cheap.

### 2. The new collective lands in a rank-asymmetric path under CFG parallel — hang risk

`hunyuan_image3_transformer.py:2800`:

```python
if cfg_parallel_ready and cfg_rank != 1:
    return
```

`_maybe_run_negative_cfg_prefill` then runs a full `self.model.forward_call(...)` — including every MoE layer — on `cfg_rank == 1` only. With CFG folded into vLLM DP (`parallel_state.py:885`, group = `cfg-dp`), the first MoE layer in that forward calls `all_gather_object` on the cfg-dp CPU group from one of the two ranks. The other rank is elsewhere. That is a gloo hang (default 30-min timeout), with a stack trace pointing at a pre-hook rather than at the asymmetry.

This is unreachable in the smoke test you ran because `_maybe_handle_ar_kv_reuse` returns early when `ar_kv_data is None` (`hunyuan_image3_transformer.py:2919`), which is always the case DiT-only. It *is* reachable via the AR+DiT pipeline with `--cfg-parallel-size 2`; the shipped `hunyuan_image_3_moe.yaml` leaves `cfg_parallel_size` at 1, so nothing is broken today.

Caveat in your favour: the EP all2all dispatch inside that same asymmetric forward spans both CFG ranks too, so this path is likely already broken pre-PR. I'd still want either an explicit `assert`/guard at the CFG-prefill site making the incompatibility loud, or a tracked follow-up — silently widening an existing hole is how it stays unfound.

### 3. `data_parallel_rank` is left at 0 on every rank — worth a comment or a fix — `vllm_omni/diffusion/worker/diffusion_worker.py:280-283`

The worker sets `vllm_config.parallel_config.data_parallel_size = dp * cfg` but never `data_parallel_rank`, so it reads 0 on all ranks. That is precisely why line 50 must hand-construct `DPMetadata(tensor)` instead of the sanctioned `DPMetadata.make(...)`, which asserts `num_tokens_across_dp_cpu[dp_rank] == num_tokens` (`vllm/forward_context.py:96`) and would fire on rank 1. Nothing in the MoE path reads `parallel_config.data_parallel_rank` today (the moe config uses `get_dp_group().rank_in_group`), so this is latent — but the next vLLM helper that does will produce silently wrong results rather than an error.

Either set `data_parallel_rank` alongside `data_parallel_size` in the worker, or add a one-line comment at `hunyuan_fused_moe.py:50` explaining why `.make()` is bypassed. Right now the bypass reads as arbitrary.

### 4. Reach for the accessor, not the private global — `hunyuan_fused_moe.py:34, 37`

`getattr(_vllm_ps, "_DP", None)` degrades to `None` if vLLM renames or relocates that global — the fix silently evaporates and the original launch failure comes back as an opaque kernel error. `_vllm_ps.get_dp_group()` (behind an `is not None` check if you want the soft path) makes a rename a loud failure. Same for `getattr(forward_context, "dp_metadata", None)`: `dp_metadata` is a declared field on `ForwardContext`, so plain attribute access is both clearer and load-bearing.

### 5. Dead branch, and a heavier collective than needed — `hunyuan_fused_moe.py:41-50`

`torch.distributed.all_gather_object` either fills every slot or raises; `if any(count is None ...)` cannot trigger, and the `list[int | None]` annotation exists only to support it. Drop both.

While you're there: vLLM's own path builds this as an `int32` tensor (`forward_context.py:307`). You use `int64`. Harmless today — every consumer I traced does `.tolist()`, `.max()`, or `.sum()` — but it's a gratuitous divergence. A `torch.zeros(world_size, dtype=torch.int32)` + `all_gather_into_tensor` on the CPU group avoids the pickle round-trip and matches upstream.

### 6. The new assertions test the mock, not the code — `tests/diffusion/distributed/test_expert_parallel_layout.py:121-126`

```python
assert parallel_state.vllm_parallel_state._PCP.device_communicator is not None
assert hasattr(parallel_state.vllm_parallel_state._PCP, "reduce_scatter")
```

These pass because `fake_init_vllm_model_parallel_group` (line 62-78) hands in `device_communicator=object()` and a `reduce_scatter` lambda. They'd pass just as happily if `init_vllm_model_parallel_group` dropped `use_device_communicator=True` — which is the entire fix. Have the fake capture its kwargs and assert on `group_ranks`, or spy on `vllm_parallel_state.init_model_parallel_group` and assert `use_device_communicator is True`.

The assertion that carries real signal is `vllm_group_names == ["vllm_pcp", "vllm_tp", "vllm_dp", "vllm_ep"]` (line 187-188) — that one pins both routing and creation order. Keep it.

Also uncovered: the `world_size <= 1` early return in `_set_forward_context_dp_metadata`, which is the branch that `tp2_sp2` actually takes.

### 7. Four new process groups per worker on every MoE config — and the red gates — `parallel_state.py:859-908`

Dropping `and cfg_parallel_size > 1` from the `_DP` condition (line 885) is defensible for consistency, but combined with the PCP/TP/EP changes it means that every `use_moe_parallel_mapping` run — including the plain `tp4` default in `hunyuan_image3_dit.yaml` — now constructs four vLLM `GroupCoordinator`s at init, each with a device communicator, and where `world_size > 1` a `PyNcclCommunicator` (plus a `CustomAllreduce` for the one named `"tp"`, since `cuda_communicator.py:48` keys off the substring). PCP in particular is now a second NCCL communicator over the same ranks as the diffusion SP group.

This is also the most likely reason the AMD and NPU gates are red: the NPU section of `hunyuan_image3_dit.yaml` sets `enable_expert_parallel: true`, so NPU init now goes down the vLLM-coordinator path where it previously used omni coordinators exclusively. Worth confirming against those job logs before merge rather than treating them as unrelated.

### 8. Vestigial teardown guards — `parallel_state.py:919, 931`

```python
if vllm_parallel_state._DP and vllm_parallel_state._DP is not _DP:
if vllm_parallel_state._PCP and vllm_parallel_state._PCP is not _SP:
```

After this change `_PCP` is never `_SP`, and in the MoE path `_DP` is never the diffusion `_DP`. The teardown is still correct — the identity checks just no longer describe anything reachable, so they read as though the aliasing still exists. Simplify, or the next reader will reconstruct the old design from them.

### 9. Design question: why keep two TP paths? — `parallel_state.py:869-881`

The `if use_moe_parallel_mapping / else` split means TP all-reduce for MoE diffusion models goes through vLLM's custom-op/CustomAllreduce path while non-MoE diffusion models keep omni's plain `torch.distributed.all_reduce`. If the vLLM coordinator is right for MoE, it's presumably right for everything, and the diffusion TP consumers I traced all go through vLLM's functional APIs (`tensor_model_parallel_all_reduce` / `..._all_gather`) rather than omni-specific coordinator methods. Not a blocker for this PR, but two TP paths is a maintenance cost worth retiring in a follow-up rather than growing.

## What I checked and found fine

- `DPMetadata(tensor)` positional construction is valid; `num_tokens_across_dp_cpu` is the sole required field.
- Index ordering is consistent: `all_gather_object` fills by `rank_in_group`, and every MoE consumer indexes with `get_dp_group().rank_in_group` via `FusedMoEParallelConfig`.
- `dp_metadata` doesn't leak across denoising steps — `pipeline_hunyuan_image3.py:1726` creates a fresh vLLM `ForwardContext` per `self.model(...)` call, so the cost is one collective per step, not per MoE layer.
- The EP rank ordering (`tp-sp-cfg-dp`) still matches vLLM's `flatten_tp_across_dp_and_pcp` formula. Pre-existing, but I re-derived it since the DP group changed hands.
- `pcp_size=None` at `hunyuan_image3_transformer.py:1639` resolves through `get_pcp_group().world_size`, so replacing the alias with a same-ranks vLLM coordinator preserves the world size the MoE sees.
