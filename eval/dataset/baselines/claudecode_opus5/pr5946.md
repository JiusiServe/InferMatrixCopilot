## Verdict: **Approve with changes** — the configuration is sound and every flag/env var/error string I checked is real, but several factual and numerical statements are wrong or unreconcilable and should be fixed before this is treated as a reference.

The serve command is entirely valid: `--num-gpus`, `--usp`, `--ring`, `--vae-patch-parallel-size`, `--text-encoder-tp-size`, `--vae-parallel-mode tile`, `--vae-use-tiling`, `--init-timeout`, `--diffusion-attention-backend` all exist in `vllm_omni/entrypoints/cli/serve.py`; `CUDNN_ATTN` is a registered backend (`diffusion/attention/backends/registry.py:63`) and is in fact the Blackwell default for sm_121 (`platforms/cuda/platform.py:73,226`), so pinning it explicitly is correct and harmless. `--enable-distributed-layerwise-offload` / `--enable-cpu-offload` (serve.py:638,648) and the `Enabling offloader backend` log line (`diffusion/worker/diffusion_model_runner.py:274`) are real. `vae_patch_parallel_size 1` and `text_encoder_tp_size 1` are legal. Both response headers exist (`api_server.py:3566-3567`), and the peak-memory semantics match `_sample_peak_memory_mb` (`diffusion_model_runner.py:361-388`), which does use `max_memory_reserved`.

### Blocking-ish (factually wrong)

**1. `MiniMax-H3-Spark-GB10.md:129-130` — the stated default timeout is wrong.**
> "the default 1800 s is shorter than a 50-step run"

`api_server.py:3023`: `VIDEO_SYNC_TIMEOUT_S = float(os.environ.get("VLLM_OMNI_VIDEO_SYNC_TIMEOUT", 600.0))`. The default is **600 s**, not 1800 s. 1800 is just what the other H3 recipes happen to set. Change to "the default 600 s". This matters because a reader who trusts "1800" may assume more slack than exists.

**2. `MiniMax-H3-Spark-GB10.md:28-30` — "A BF16 partition is 135 GiB and does not fit in 121 GiB" compares on-disk bytes to memory capacity, and the two aren't the same number here.**

135 GiB is the on-disk checkpoint. The pipeline does *not* load all of it: `diffusion/models/minimax_h3/encoder.py:42,793` truncates the Qwen3-VL backbone at `MINIMAX_H3_QWEN3VL_SELECTED_LM_LAYER = 50` (encoder.py:9 puts the retained encoder at ~51.5 GB BF16 ≈ 48 GiB). With the DiT at 62 GiB, BF16 *resident* weights are roughly 62 + 48 + VAEs ≈ 111 GiB — which nominally does fit in 121 GiB. The conclusion (FP8 is required) is right, but the stated reason is not; the honest version is "BF16 resident weights are ~111 GiB, leaving no room for activations, so FP8 is required." As written, someone who measures actual residency will think the recipe is wrong.

**3. `MiniMax-H3-Spark-GB10.md:38-51` vs `108-109` — the serve command omits the flag the measurements depend on.**

Line 108 says stage times come from `--enable-diffusion-pipeline-profiler`, but that flag is not in the serve command. Without it, `serving_video.py:825-827` returns `{}` and `X-Stage-Durations` is an empty object — a reader following the recipe verbatim gets no stage times at all. Either add `--enable-diffusion-pipeline-profiler` to the command block or add an explicit "add this flag to reproduce the table" line.

**4. `MiniMax-H3-Spark-GB10.md:143-146` — "keep the short edge at 576" is not achievable via `short_edge`.**

`pipeline_minimax_h3.py:472-473` hard-rejects any `short_edge != 768`:
```
raise OmniClientError(f"MiniMax H3 target.short_edge must be {MINIMAX_H3_OUTPUT_SHORT_EDGE}, got {short_edge}")
```
`MINIMAX_H3_OUTPUT_SHORT_EDGE = 768` (line 103). A Ref2VA user who reads this bullet and sends `-F 'short_edge=576'` gets a 400. The only way to get a 576 short edge is explicit `width`/`height`, since that path bypasses `_resolve_output_canvas` entirely (line 823-824). Reword to: "pass explicit `width`/`height` (e.g. `960x576`); `short_edge` must be `768` and is only consulted when `width`/`height` are omitted."

### Numbers that don't reconcile

**5. `MiniMax-H3-Spark-GB10.md:104` — the `Per step` column is divided by 49, not 50.**

2088 / 50 = 41.76. 2088 / 49 = **42.612** — an exact match for the stated 42.61 s. Either there's an off-by-one in how per-step was computed, or the denoise stage includes one extra step that should be explained. Please recheck.

**6. `MiniMax-H3-Spark-GB10.md:103` — the smoke row is internally inconsistent with the rest of the table.**

At 8.68 s/step × 10 steps = 86.8 s of denoise inside a 95.9 s end-to-end, only ~9 s remains for text encode + VAE decode + mux (0.49 s). But line 104 puts VAE decode for the 8 s clip at 70 s; halving the frames should land near ~35 s, not ~8 s. Tiled VAE decode isn't 8× superlinear in frame count. Two likely explanations, and the doc should say which: either "smoke shape" is a materially smaller geometry than the 960x576 the smoke `curl` at lines 60-72 actually pins (in which case name the real geometry, because the curl block contradicts the row label), or one of the numbers is mistranscribed.

**7. `MiniMax-H3-Spark-GB10.md:124-125` — "Repeated identical 10-step requests … (397 s to 490 s)" is ambiguous and reads as contradicting line 103.**

397–490 s over 10 steps is ~40–49 s/step, which matches the *8 s* geometry (42.61 s/step), not the 10-step smoke row's 8.68 s/step. Say explicitly that this variance was observed on the 8 s / 960x576 10-step runs, otherwise it looks like a 5× disagreement with the table directly above it.

### Smaller points

- **`MiniMax-H3-Spark-GB10.md:11`** — "128 GB LPDDR5X (~121 GiB usable)". If 128 GB is decimal that's 119.2 GiB *total*, so 121 GiB usable would exceed capacity. Since the entire FP8-is-mandatory argument hangs on this number, please state where 121 GiB came from (`free -g`? `nvidia-smi`?).
- **`MiniMax-H3-Spark-GB10.md:40`** — `FLASHINFER_DISABLE_VERSION_CHECK=1` is redundant; `engine/stage_engine_core_proc.py:122` already does `os.environ.setdefault("FLASHINFER_DISABLE_VERSION_CHECK", "1")`. Harmless, but if it was needed because of a real GB10 version-check failure, that's worth a sentence instead.
- **`MiniMax-H3-Spark-GB10.md:147-148`** — "the Cutlass FP8 kernel rejects" is inherited verbatim from `MiniMax-H3.md:385-388`, but on sm_121 FP8 linears go through FlashInfer, not Cutlass or quack (`quantization/quack_fp8.py:18-32`, `docs/user_guide/quantization/fp8.md:47-55`). Either drop the mechanism clause or say "the FP8 kernel". Low impact since the bullet already says it doesn't matter here.
- **No environment provenance.** Unlike `MiniMax-H3.md:180-185` (which pins vLLM 0.26.0, vLLM-Omni `0.26.1.dev14+gae6577ea`, PyTorch 2.11.0+cu130) and `MiniMax-H3-NPU.md`, this recipe reports specific latency and memory numbers with no vLLM-Omni commit, CUDA/PyTorch version, or driver. For a first-of-its-kind platform that's the single most useful thing to record. `recipes/TEMPLATE.md:32-38` asks for it.
- **No prerequisites section.** `ffmpeg`/`ffprobe` are required (the recipe calls `ffprobe` at line 88 and MP4 mux needs ffmpeg), and FP8 on this platform depends on FlashInfer being installed. `MiniMax-H3.md:61-62` states the ffmpeg requirement; a one-line pointer back to that recipe's Prerequisites would cover it.
