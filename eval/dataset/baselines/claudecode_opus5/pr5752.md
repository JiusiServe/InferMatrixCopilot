# Review: PR #5752 — [Feature] Align MiniMax H3 official input matrix

## Verdict: **Request changes** (merged — these should be follow-ups)

The core H3 work is good. The packing layer already supported `[0]/[-1]/[0,-1]` keyframes and `image`/`audio`/`video`/`video_audio` ref blocks (`packed_sequence.py:62`, `:338`), so most of this PR is plumbing that was genuinely missing, and the plumbing is coherent: `condition_labels` ordering matches `ref_blocks` ordering, the multi-output fan-out concatenates on the batch dim in a way that `_extract_audio_outputs`/`_minimax_h3_post_process` actually split correctly, the `ValueError → OmniClientError` sweep is the right call (and safe, since `OmniClientError` subclasses `ValueError`), and the rank-0/broadcast discipline in `_encode_audio_conditions` is correct with the `video_count`-vs-`prepared_videos` comment explaining the subtle part.

But the PR reaches outside MiniMax H3 into shared entrypoint code, and one of those changes breaks other models. Two required gates are also red (`buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci`) — those need to be green or explained regardless of everything below.

## Blocking

### 1. Typed `video_reference` now hands every model a file path instead of frames — breaks Wan VACE and Cosmos3 V2V
`vllm_omni/entrypoints/openai/api_server.py:3325-3345`, `vllm_omni/entrypoints/openai/video_api_utils.py:219-268`

`decode_video_url` now always writes the downloaded/data-URL bytes to a temp `.mp4` and sets `source_path`. `_parse_video_form` then unconditionally prefers that path and **throws the decoded frames away**:

```python
if media_data.source_path is not None:
    video_paths.append(media_data.source_path)
else:
    ...
    video_frames = list(media_data)
```

So for *all* models, `multi_modal_data["video"]` changes from `[PIL.Image, ...]` to `["/tmp/xxx.mp4"]`. Downstream:

- `vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2_vace.py:143` — `PIL.Image.open(f)` on each string entry → `UnidentifiedImageError` on an MP4.
- `vllm_omni/diffusion/models/cosmos3/pipeline_cosmos3.py:479` — `_pil_to_rgb(raw_video_frames[0])`, which for a `str` does `PIL.Image.open(value)` (`:301`) → same failure.

The rewritten test bakes this in: `tests/entrypoints/openai_api/test_video_server.py:513` changed from `assert input_video[0].size == (32, 24)` to `assert all(isinstance(item, str) ...)`. A fake engine passing doesn't mean Wan/Cosmos pass.

Secondary damage: `decode_spec` (`max_video_frames`, `keep="first"|"last"`, derived from stage configs) becomes a no-op for URL video references, since the frames it selected are discarded.

**Fix:** gate the path-vs-frames choice on capability. `VideoFrames` already carries `source_path`, so the information is available at the call site — pass paths only when `supports_mixed_reference_inputs` (or a dedicated `requires_source_container` flag) is set, and keep `ReferenceVideo(data=frames)` otherwise. Restore the frame-based assertions in `test_r9_typed_video_reference_form` for a non-H3 model and add the path assertions under an H3 model class.

### 2. `t2va` now rejects requests that fully specify the canvas
`vllm_omni/diffusion/models/minimax_h3/pipeline_minimax_h3.py:652-661`, `:210-212`

`_resolve_minimax_h3_aspect_ratio` is called *before* the `if height is None or width is None` branch, so the "t2va requires an explicit aspect_ratio" error fires even when width and height are both given. Verified against this checkout:

```
_resolve_shape('t2va', fps=24, num_frames=209, height=768, width=1344, extra={'task':'t2va'})
→ OmniClientError: t2va requires an explicit aspect_ratio
```

Over HTTP this means `-F 'width=1344' -F 'height=768'` returns 400 demanding a parameter that cannot affect the result. `tests/diffusion/models/minimax_h3/test_minimax_h3_e2e.py:65` had to add `"aspect_ratio": "16:9"` to a test that already sets `height=256, width=448` — that diff line is the regression.

**Fix:** move the ratio resolution inside the `height is None or width is None` branch (and keep the `short_edge` validation there too — right now `short_edge=720` is silently ignored when width/height are supplied but rejected when they aren't).

## Should fix

### 3. Hard 4 s output floor, and the bound is checked on the wrong quantity
`vllm_omni/diffusion/models/minimax_h3/pipeline_minimax_h3.py:636-640`

Measured on this checkout:

| input | result |
|---|---|
| `num_frames=29` | `OmniClientError: duration must be in [4, 15] seconds, got 1.208` |
| `duration=15.0` | 362 frames = **15.083 s** — accepted |
| `duration=4.0` | 107 frames = 4.458 s |

Two problems. First, the check is applied to `requested_frames` *before* `minimax_h3_align_frame_count`, so the function emits clips outside the very window it enforces. Second, an explicit small `num_frames` is now unusable — every smoke test or debug run must render ≥4 s. The e2e test's `num_frames=29` had to be replaced with `duration=4.0` for exactly this reason.

**Fix:** validate `num_frames / fps` after alignment (or clamp alignment downward at the top of the range), and consider treating an explicit `sampling.num_frames` as an opt-out from the API-level duration policy.

### 4. Image format/size contract is enforced on only one of three input paths
`pipeline_minimax_h3.py:161-171`, `api_server.py:3038-3060`

`_load_images` checks the 30 MiB cap and the JPEG/PNG/WEBP/HEIC/HEIF allowlist **only for path/PathLike inputs**. The multipart path enforces it in `_validate_minimax_h3_image_payload`. But typed `image_reference` (data URL or HTTP) is decoded to a `PIL.Image` in `decode_image_url` (`video_api_utils.py:170`) before it ever reaches the pipeline, so it hits the `isinstance(value, Image.Image)` branch and skips both checks. A BMP is a 400 via `input_references` (`test_h3_multipart_rejects_bmp_image_reference`) and a silent success via `image_reference` — and the 30 MiB limit documented in `recipes/MiniMaxAI/MiniMax-H3.md` is unenforced on that path entirely.

Also: HEIC/HEIF are in the allowlist and the docs, but there's no `pillow-heif` in `requirements/` or `pyproject.toml`, so Pillow can't decode them at all; and when it can, `Image.format` is `"HEIF"`, never `"HEIC"` — that allowlist entry is dead either way.

### 5. List-form references are silently dropped by the streaming endpoint
`vllm_omni/entrypoints/openai/serving_video_output_stream.py:563-577`

`image_reference` was widened to `ImageReference | list[ImageReference] | None` (`protocol/videos.py:119`), but this path passes it straight to `decode_input_reference`, which only matches `UrlImageReference`/`FileImageReference`. A list falls through every branch and returns `None` (`video_api_utils.py:356`) — the reference is dropped with no error and generation proceeds unconditioned. Either normalize with `_reference_list` here too, or reject lists explicitly.

### 6. H3-specific constraints hardcoded into the shared request schema
`vllm_omni/entrypoints/openai/protocol/videos.py:146-165`

`num_outputs_per_prompt` gets `le=10` — MiniMax H3's limit — applied to every video model. `aspect_ratio`, `short_edge`, and `start_time_seconds` are added as top-level fields whose descriptions all begin "MiniMax H3 …". This is the kind of thing `extra_params`/`video_params` exists for; the per-model bound belongs in the pipeline (where `_resolve_minimax_h3_num_outputs` already re-checks it), not in the generic schema.

## Minor

**7. `ref_audio_t` is clobbered by a loop variable.** `pipeline_minimax_h3.py:1510` — `for ref_audio_t in external_audio_lengths:` reuses the name of the value passed to `diffuse()` at `:1549`. After the loop it holds the last external audio length instead of `None`. Harmless today only because every path that reaches it also sets `ref_blocks`, which short-circuits the `ref_audio_t` fallback in `diffuse` (`:1191-1198`). Rename the loop variable.

**8. Audio-length bounds re-derived from VAE latents.** `pipeline_minimax_h3.py:1517-1523` rejects any reference whose encoded length is `<80 or >600` latent frames. Durations were already validated to 2–15 s upstream, so this re-derives the same constraint through resampling and VAE striding — a reference at exactly 2.0 s can land on 79 or 80 depending on rounding and 400 out. It also runs *after* every video/audio VAE encode, so bad input pays full encode cost. Validate the known durations in `prepare_reference_videos` / `validate_reference_audio_*` instead.

**9. Per-rank duplicated ffprobe and audio decode.** `pipeline_minimax_h3.py:1441-1444` — `validate_reference_audio_files` (an ffprobe subprocess per file) and `_load_audios` run on every DiT rank, but only rank 0 encodes (`_encode_audio_conditions:1024`). Video prep is already rank-0 gated via `_prepare_reference_videos:921`; audio should match. On 8 ranks that's 8× ffprobe + 8× decode per audio file.

**10. `_probe_video` lost `-select_streams v:0` but kept `-count_frames`.** `reference_video.py:46-60` — ffprobe now full-decodes and counts frames for *every* stream, including audio, on every reference. Use a targeted `-select_streams v:0 -count_frames` probe plus a separate cheap probe for the stream/format list.

**11. Dead code / inconsistencies.**
- `reference_video.py:317` — `target_frame_count` is a required keyword that is immediately `del`'d. Remove it and update the three call sites, or keep it and document why.
- `pipeline_minimax_h3.py:635` — `duration = requested_frames / fps` is assigned and never read.
- `pipeline_minimax_h3.py:1371` — `audio_is_waveform_pair` explicitly anticipates a list-form `[waveform, sample_rate]`, but `_load_audio:197` only accepts the *tuple* form, so that input is counted as one audio and then rejected as unparseable.

**12. FL2VA silently ignores `aspect_ratio`.** Documented and asserted (`test_minimax_h3_contract.py:659`), and defensible — but silently discarding an explicit client parameter is surprising. Rejecting a conflicting explicit ratio would be friendlier than ignoring it.

## Testing

The 403 new contract-test lines are almost entirely pure-helper tests: `_resolve_fl2va_keyframe_indices`, `_validate_ref2va_reference_counts`, `_resolve_output_canvas`, `_validate_reference_video_metadata` with hand-built metadata dicts. Those are useful and well-parameterized against the R1–R10/F1–F2/G1–G4 matrix.

What isn't covered is where the risk actually is: nothing exercises `forward()`'s new `condition_labels` + `ref_blocks` assembly (image blocks → video/video_audio blocks → standalone audio blocks), the two-keyframe FL2VA wiring into `minimax_h3_packed_sequence`, or the `num_outputs>1` concat/split round-trip. Those are all mockable at the same level as `test_distributed_video_vae_encodes_references_sequentially` already does — worth adding a `forward()`-level test with fake VAEs that asserts the emitted `ref_blocks` sequence for the R5 mixed case.
