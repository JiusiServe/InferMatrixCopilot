## Overall verdict

**Approve with reservations — the model integration is solid, but three things should be fixed before this is relied on, and one is already visible in CI.**

I read the changed LTX sources, the surrounding call paths (`ltx2_runtime` → `ltx2_denoise` → `ltx2_guidance`/`ltx2_latents`, `data.py` config enrichment, `serving_video`), and ran the CPU test suite (`tests/diffusion/models/ltx2/`, 246 passed). The architecture choice — extending the existing profile/recipe tables with a `2.5` key rather than forking new pipeline classes — is the right one, and the two genuine transformer bugs it uncovers (`RowParallelLinear` ignoring `bias`, `has_separate_cfg`) are real fixes. The parity harness is unusually rigorous (SSIM 0.99 / PSNR 40 against the official runtime for both T2V and I2V).

My concerns are: a repo-wide dependency bump made for one model, a recipe/latents contract mismatch that silently discards user input, a checkpoint guard that has been rendered inert, and an audio tolerance that suggests the ancestral sampler is not actually at parity.

## Blocking

### 1. `requirements/common.txt:12` — repo-wide `transformers` bump for one model; this is what the NPU gate is reporting

```
-transformers >= 5.5.3
+transformers >= 5.10.1, < 5.15
```

`requirements/npu.txt` is just `-r common.txt`, so this floor lands on every platform, and `buildkite/vllm-omni-npu-ci` is the one failing check. The removed comment said this constraint was deliberately *"kept exactly aligned with the upstream vLLM constraint"* — this PR silently drops that alignment invariant to add a model.

The code already degrades correctly without it: `ltx2_components.py:202-208` guards the `Gemma4UnifiedForConditionalGeneration` import, and `ltx2_components.py:583-584` raises a clear `ImportError` naming the required version at load time. That guard is the whole reason the floor doesn't need to move.

**Change:** revert `common.txt` to the upstream-aligned floor and express the LTX-2.5 requirement as an optional extra plus the existing runtime check. If the `< 5.15` ceiling is genuinely needed repo-wide (the comment says 5.15 has "a known construction regression"), land that as its own PR with the failing case cited — it doesn't belong to LTX-2.5.

### 2. `ltx2_recipes.py:130-141` — LTX-2.5 one-stage silently replaces caller-supplied latents with pure noise

`LTX25_FULL_RECIPE` sets `noise_scale=1.0` on its only phase but inherits `allow_request_latents=True` (only the two-stage and distilled recipes set it `False`).

Trace: `_run_recipe` → `run_phase(noise_scale=1.0)` → `LTXRuntime.prepare_latents` (`ltx2_runtime.py:326`) → `latent_ops.prepare_video_latents`, which on the provided-latents path does `create_noised_state(latents, 1.0, generator)` = `torch.lerp(latents, noise, 1.0)` — i.e. exactly `noise`. Same for `prepare_audio_latents`.

So `LTX2Pipeline` on an LTX-2.5 checkpoint accepts a `latents` argument and throws it away, with no error. LTX-2/2.3 one-stage (`noise_scale=0.0`) return the supplied latents unchanged, so this is a version-dependent contract break on the same class.

**Change:** either set `allow_request_latents=False` on `LTX25_FULL_RECIPE` (matching `LTX25_TWO_STAGE_RECIPE`), or leave the phase at `noise_scale=0.0` and apply the full re-noise only on the I2V branch in `ltx2_conditioning.py:667-676`, which is the only place that needs it.

### 3. `ltx2_components.py:678-689` — the regular-checkpoint guard is a no-op for LTX-2.5

```python
if profile.scheduler_use_dynamic_shifting:
    pipeline.scheduler = FlowMatchEulerDiscreteScheduler.from_config(
        pipeline.scheduler.config, use_dynamic_shifting=True, shift_terminal=profile.scheduler_shift_terminal)
validate_ltx_checkpoint(pipeline.scheduler.config,
                        expected_kind=resolve_ltx_checkpoint_kind(pipeline.pipeline_kind), ...)
```

`validate_ltx_checkpoint` (`ltx2_request.py:75`) for `expected_kind="regular"` checks exactly `use_dynamic_shifting` truthy and `shift_terminal is not None` — the two fields written one statement earlier. For LTX-2.5 one-stage/two-stage the assertion is satisfied by construction and can never fire.

Worse, the override tells us the shipped `Lightricks/LTX-2.5-Diffusers` `scheduler/` config is distilled-shaped, which means there is now *no* checkpoint guard at all on the 2.5 full path. Note `shift_terminal` is load-bearing (`_official_ltx_sigmas`, `ltx2_denoise.py:299-306`) but `use_dynamic_shifting` is written *only* to satisfy the validator that follows it.

**Change:** validate the config as loaded, before the override, and make the expected kind profile-driven (`LTXComponentProfile`) rather than derived from `pipeline_kind`, so LTX-2.5 full can declare "no scheduler-metadata guard, the profile pins the schedule" explicitly instead of by accident.

## Should fix

### 4. `ltx2_components.py:226-235` — newly rejects distilled checkpoints on `LTX2Pipeline`, undocumented

`resolve_ltx_checkpoint_kind("one_stage")` now returns `"regular"`; previously `expected_checkpoint_kind` was `None` for one-stage and the check was skipped. Anyone running `LTX2Pipeline` against `rootonchair/LTX-2-19b-distilled` or `diffusers/LTX-2.3-Distilled-Diffusers` will now get a hard `ValueError` at load. `LTX2DistilledOneStagePipeline` is the intended replacement, but `recipes/LTX/LTX-2.md`'s "API Migration" table — which lists every other rename — doesn't cover it. Add a row.

### 5. `ltx2_denoise.py:159-162, 166-203` — video and audio ancestral steps share one RNG stream

`_ancestral_generators` is built once in `LTXVideoAudioStepAdapter.__init__` and passed to *both* `_ancestral_euler_step_from_velocity` calls in `step()`. The video draw advances the generator, so the audio noise is a continuation of the video stream rather than an independent one. The official implementation carries a per-modality noiser.

The tolerances corroborate this: `test_ltx25_official_similarity.py:99` sets `LTX25_AUDIO_RELATIVE_L2_THRESHOLD = 0.32` against the LTX-2 baseline of `0.20` (line 89), while every *video* threshold was tightened (SSIM 0.95→0.99, PSNR 30→40). Video matches to 0.99 SSIM and audio needed a 60% looser bound — that asymmetry points at the shared noise stream, not at bf16 drift.

**Change:** give the audio step its own generator (e.g. a second `_make_ancestral_generators` result, or reconstruct per modality), then re-run the parity test and see whether `0.32` can come back down to the LTX-2 value. If the divergence is genuinely elsewhere, please note in the PR why 2.5 audio needs a looser bound than 2/2.3 — right now the PR body says "BF16 cuDNN official parity" with no caveat.

Related, lower stakes: `_make_ancestral_generators` (`ltx2_denoise.py:1046-1048`) always constructs on `pipeline.device`, so a CPU request generator yields CUDA-Philox ancestral noise and seeded output is not device-portable.

### 6. `ltx2_transformer.py:1533-1536` — `has_separate_cfg` True→False changes existing LTX-2/2.3 cached output

The reasoning is right (LTX fuses guidance into the batch and runs one forward per step, so `True` made Cache-DiT advance its counter every other step). But this changes cached results for already-shipped models, and it's landing inside a PR whose description only says Cache-DiT is *unsupported for 2.5*. Call it out as a behavior change in the description/release notes; a `tests/e2e/accuracy` datapoint for LTX-2 + Cache-DiT would be better still, since `tests/diffusion/cache/test_cache_dit.py:126` only asserts the flag value.

### 7. `serving_video.py:105-117` — blocking hub I/O in the async request path, no fallback

`preserves_reference_image_size` calls `should_preserve_reference_image_size` → `detect_ltx_model_version` → `hf_hub_download`. It's a `cached_property`, so once per process, but that once happens inside `_run_and_extract` on the first I2V request and blocks the event loop.

Two follow-ons:
- If `od_config` is unavailable, `model_class_name` is `None` and `should_preserve_reference_image_size` (`model_extras/registry.py:325-329`) falls through to `resolve_model_class_name(model, revision=...)` — a network lookup now on the I2V path for **every** diffusion model, not just LTX.
- `_load_ltx_metadata_json` swallows all exceptions and returns `{}`, so a hub timeout resolves to version `"2"` → the server resizes the image → but the worker's `model_version` (detected from local files at load) still defaults `image_crf` to 18. Different code paths reach different answers to the same question.

**Change:** resolve this once at handler construction from `od_config` (which already knows the answer without network I/O) rather than lazily per-request, and wrap the resolver so a hub failure can't 500 the request.

### 8. `ltx2_components.py:141-152` — 2.5 distilled two-stage has no upsampler fallback

`LTX25_DISTILLED_COMPONENT_PROFILE` keeps `"latent_upsampler"` in `resident_modules` but sets neither `artifact_repo_id` nor `latent_upsampler_filename`. So at `ltx2_components.py:648-652`, if `latent_upsampler/` isn't present as a subfolder, the `except (OSError, ValueError)` branch re-raises — unlike `LTX25_TWO_STAGE_COMPONENT_PROFILE`, which falls back to the single-file artifact from `Lightricks/LTX-2.5`. Is the x2 upsampler actually shipped under `latent_upsampler/` in `Lightricks/LTX-2.5-Diffusers`? If not, `LTX2DistilledTwoStagePipeline` on 2.5 can't load. Either way the asymmetry between the two 2.5 two-stage profiles deserves a comment.

## Minor / cleanup

- **`ltx2_guidance.py:304-311`** — `expand_for_sequence_parallel` has no production caller that passes `False`; `LTXRuntime._denoise_timestep_kwargs` (`ltx2_runtime.py:675-680`) is the only caller and always passes `True`. Dead knob; drop it or add the caller it was written for.
- **`ltx2_runtime.py:311`** — `_enter_phase` sets `self._guidance_plan`, but `_setup_forward_runtime` (line 461) overwrites it before any denoise use, and nothing between the two reads it (`_build_phase_inputs` doesn't). Either dead or load-bearing-by-accident; worth a comment or removal.
- **Two sources of truth for the transformer subfolder** — `LTXComponentProfile.transformer_subfolder` (`ltx2_components.py:222`) vs `ltx_transformer_config_subfolder` (`model_extras/ltx2.py:44`), the latter registered for only 2 of the 5 LTX classes (`model_extras/registry.py:258`). They agree today; nothing keeps them in sync. A parametrized test asserting `profile.transformer_subfolder == get_transformer_config_subfolder(cls_name, ...)` across all `(kind, version)` pairs would pin it.
- **`ltx2_conditioning.py:622`** — `elif not unpacked_latents and image is not None:` is inside an `if unpacked_latents:` chain; the first conjunct is always true.
- **`ltx2_components.py:433`** — `has_learned_registers` gained a default of `False`; it was previously keyword-required. A silently-wrong default is worse than a `TypeError` here.
- **`ltx2_components.py:398-400`** — the `ff_bias is False` → `"2.5"` heuristic runs *before* the LTX-2.3 vocoder checks, and adds a `transformer/config.json` hub fetch to the detection path for every LTX-2 checkpoint. Also, the `logger.info("Using LTX-2 defaults for checkpoint %s", model)` fallback line was dropped — that was useful when detection silently guesses.
- **`ltx2_conditioning.py:759`** — `getattr(self, "model_version", None) == "2.5"` here vs `getattr(self, "model_version", "2")` at line 745. Harmless but pick one.
- **`ltx2_conditioning.py:759-762`** — odd dimensions are cropped from the bottom/right (`image[:height, :width]`) rather than centered, so a CRF round-trip shifts geometry by up to a pixel before the aspect-preserving resize. Verified working (I round-tripped a 63×101 frame → 62×100), just noting the asymmetry.

- **`recipes/LTX/LTX-2.5.md:49, 56-67`** — the H100 FP8 row and the FP8 serve command carry no "experimental / unverified" caveat, while the B200/GB200 rows do and the PR checklist lists FP8 as *not* validated (`diffusion_features.md` marks it ❓). Label the FP8 recipe consistently with the rest of the PR.

The error message is good; the doc should say it up front.
- **`docs/user_guide/diffusion_features.md:161`** — the LTX-2.5 row introduces `❓` into a ✅/❌ table with no legend entry.
