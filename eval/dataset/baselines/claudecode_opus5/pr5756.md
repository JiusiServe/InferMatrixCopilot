# Review: [Frontend] Add ComfyUI support for r2v (MiniMax H3 as example) — PR #5756

## Verdict

**Approve with follow-ups.** The core design is sound and the wire format matches the server exactly: `input_reference` (image file), `audio_reference` (JSON `{"audio_url": data-url}`), repeated `input_references` (video files), `flow_shift` as a top-level form field, and `task`/`audio_flow_shift` inside `extra_params` — all line up with `_parse_video_form` (`vllm_omni/entrypoints/openai/api_server.py:2978`), `serving_video.py:189`, and `recipes/MiniMaxAI/MiniMax-H3.md`. The `extra_body` → `extra_params` rename is a real fix: the server never had an `extra_body` form field, so that payload was being silently dropped by FastAPI.

What I'd want addressed: one silent-failure risk from the `image` → `frame` rename, a validation hook that can never fire, a path-matching regression for a plausible H3 model string, two node inputs that always error, and an example workflow that ships a machine-specific path.

---

## Significant

### 1. `image` → `frame` rename silently degrades existing workflows to t2v
`apps/ComfyUI-vLLM-Omni/comfyui_vllm_omni/nodes.py:168`

ComfyUI stores input names in the saved workflow JSON. Every existing user workflow (and the pre-PR template, which used `Wan-AI/Wan2.2-TI2V-5B-Diffusers` with an `image` link) references an input that no longer exists. The link is dropped on load; because `frame` is `optional` and `generate()` has a `**kwargs` catch-all that only logs at INFO (`nodes.py:205-208`), nothing errors — the job just runs as text-to-video and returns a plausible-looking but wrong result. Silent wrong output is the worst failure mode here.

Suggested change: keep `image` as a deprecated optional alias and fold it in:
```python
"frame": ("IMAGE",),
"image": ("IMAGE",),  # deprecated alias for frame
...
if image is not None:
    if frame is not None:
        raise ValueError("Provide only one of frame or image (image is deprecated).")
    logger.warning("'image' input is deprecated; reconnect to 'frame'.")
    frame = image
```

### 2. `VALIDATE_INPUTS` override never fires, and it disables widget range checks
`apps/ComfyUI-vLLM-Omni/comfyui_vllm_omni/nodes.py:180-187`

Two problems:

- `frame` and `references` are link-only inputs. During validation ComfyUI calls `get_input_data(..., outputs=None)`, which marks linked inputs missing and passes `None`. So `frame is not None and references is not None` is unreachable — the exclusivity check never triggers. (The real enforcement is `api_client.py:277`, which does work, so behavior is correct — the override just adds nothing.)
- `**_kwargs` sets `varkw` on the argspec, and ComfyUI skips its own per-widget checks (`min`/`max`, combo membership) for *every* input whose name is covered by `VALIDATE_INPUTS`. With a catch-all that's all of them, so `width`/`height`/`fps`/`num_frames` lose their `min: 1` enforcement on this node.

Simplest fix: delete the override entirely and rely on `api_client.py:277`. If you want to keep it, at minimum drop `**_kwargs` and keep the signature to `(cls, url, model)`.

### 3. `lookup_model_spec` drops the first path component — `MiniMax-H3/Ref2VA` no longer matches
`apps/ComfyUI-vLLM-Omni/comfyui_vllm_omni/utils/models.py:126-131`

`normalized.split("/", 1)[-1]` discards the first component to strip the HF org prefix. That breaks two-component relative paths where the first component *is* the model — exactly the shape of the H3 partition dirs. I ran the new logic:

| model string | matched |
|---|---|
| `MiniMaxAI/MiniMax-H3` | ✅ |
| `/path/to/MiniMax-H3/Ref2VA` | ✅ |
| `./MiniMax-H3/Ref2VA` | ✅ |
| `MiniMax-H3/Ref2VA` | ❌ **no match** |

On a miss the `params_builder` is skipped, so `audio_flow_shift` goes out as a bare form field that FastAPI discards, and `task` is never sent — silent parameter loss, no warning.

Secondly, matching a multi-component remainder with `re.search` is now much looser than the old last-component match: `/data/MiniMax-H3/derived/Wan2.2-T2V-A14B` matches the H3 spec and would route a Wan model through `_minimaxh3_params_builder`, dropping `guidance_scale_2`/`boundary_ratio` with only a log warning. This function is also on the understanding path (`api_client.py:629`, `api_client.py:657`), so the blast radius covers BAGEL/Qwen too.

I'd just search the full normalized string — it fixes the miss and keeps every case in the `__main__` demo working:
```python
normalized = model.strip("/")
for pattern, spec in MODEL_PIPELINE_SPECS.items():
    if pattern.search(normalized):
        return spec, pattern.pattern
```
Either way, this needs a real unit test — `grep` shows zero test coverage for `lookup_model_spec`; the `__main__` block at `models.py:143` isn't run by CI.

### 4. `image_2` and `audio_2` are dead inputs that always raise
`apps/ComfyUI-vLLM-Omni/comfyui_vllm_omni/nodes.py:788,790` + `api_client.py:303-329`

The only accepted combinations are (videos only) and (exactly one image + exactly one audio). Any use of `image_2` or `audio_2` falls into the `else` at `api_client.py:325` and raises "Invalid references combination" — and only after the user hits Run. This matches the server (`pipeline_minimax_h3.py:1041-1050` takes a single image), so the restriction is right, but the UI shouldn't advertise sockets that can never be used. Drop `image_2`/`audio_2`, or rename to make the multi-video-only intent obvious (e.g. keep `image`/`audio` singular plus `video_1`/`video_2`).

## Worth fixing

### 5. Example template hardcodes a local snapshot path and drops the Wan example
`apps/ComfyUI-vLLM-Omni/example_workflows/vLLM-Omni Video Generation.json`

The `VLLMOmniGenerateVideo` model widget is `/workspace/models/hub/models--MiniMaxAI--MiniMax-H3/snapshots/428986c4aa5280855b9ac26eff8d1a46b5999cd0/FL2VA`. This ships to users via **sidebar → Template → vLLM-Omni Video Generation**; nobody else has that path or that snapshot hash. Use `MiniMaxAI/MiniMax-H3` (which the new tests use and which matches fine) or an obvious placeholder.

Also, this replaced the Wan example rather than adding to it, while `README.md:108` still says "(e.g., Wan, MiniMax-H3)" and the node default is still `Wan-AI/Wan2.2-T2V-A14B-Diffusers`. Consider shipping both, or updating the README to say the template is H3-specific.

One more on the MarkdownNote (node 22): "connect this Video Reference block ... then disconnect the `frame` input" is incomplete — you must *also* repoint `model` at the `Ref2VA` partition, since `_resolve_task` rejects `ref2va` against an FL2VA checkpoint (`pipeline_minimax_h3.py:387-390`).

### 6. No way to set `duration`, and `num_frames` default is badly wrong for r2v
`nodes.py:163` (`num_frames` default 41) + `README.md:120`

The recipe drives H3 length via `extra_params.duration` and explicitly warns: *"The requested duration should cover the complete audio. If duration is shorter, the reference soundtrack is truncated."* The node only exposes `num_frames`, defaulting to 41 — at H3's fixed 24 fps that's ~1.7 s. A user wiring a 15 s audio reference with defaults gets a ~2 s clip with the audio chopped, no warning. (`_resolve_shape` at `pipeline_minimax_h3.py:403-410` only falls back to `num_frames` when `duration` is absent.)

Related: the node's `fps` default is 16, but H3 hard-errors on anything but 24 (`pipeline_minimax_h3.py:400`). That one at least fails loudly.

Minimum: document both in the README r2v tip. Better: add `duration` to `VLLMOmniMiniMaxH3Params` and let the builder forward it into `extra_params` (the commit message says duration/num_frames were "conflicting" — worth revisiting, since duration is the parameter the recipe actually recommends).

### 7. Dead code and an inaccurate comment
`nodes.py:223-225` and `nodes.py:777`

The comment says `model_params["type"]` "is used in api_client" — it isn't. `api_client.py:359` and `models.py:44` both pop and discard it, and the builder is selected from the model name via `lookup_model_spec`, not from `type`. So `params["type"] = "minimax_h3"` at `nodes.py:777` writes state nothing reads, and the commented-out pop is confusing. Remove both; if you'd rather keep `type` for future dispatch, say so in the comment instead of claiming a use that doesn't exist.

## Nits

- `models.py:103` — `r"MiniMax-H3(/FL2VA|/Ref2VA)?"`: under `re.search` the optional group is a no-op (`MiniMax-H3` alone already matches every string the group would). Simplify to `r"MiniMax-H3"`.
- `api_client.py:71` — bumping `max_poll_duration` 5 → 30 min is reasonable for H3, but it's a global default change for all video jobs. Consider exposing it as a node widget rather than a constant.
- `api_client.py:341-345` — the audio reference goes out as a base64 data URL inside a multipart body (~33 % inflation) after a lossy 128 kbps MP3 re-encode (`format.audio_to_base64` default). For a lip-sync driving signal that's a lossy round-trip on the one input that matters most; consider a higher bitrate or a lossless container, since the server accepts any data URL.
- `models.py:36` — `for key in ("audio_flow_shift",):` over a one-element tuple; either add the other extras H3 accepts (`duration`) or write it as a plain `if`.
- Naming: PR text says "Video Reference", display name is "Video References" (`__init__.py:56`), template note says "Video Reference block". Pick one.

## Tests

The two new cases are good — they assert the *decoded server-side* shape (`multi_modal_data["image"]` is a PIL image, `["audio"]` is a path, `["video"]` is a 2-element path list) plus `task=ref2va` in the extras, which is exactly the contract that matters. Gaps I'd close:

- No coverage of the three `ValueError` branches in `generate_video` (`api_client.py:277`, `:310`, `:325`) — cheap to add and they're the only thing enforcing exclusivity now that `VALIDATE_INPUTS` can't (item 2).
- Nothing asserts `task=fl2va` for the `frame` path. `test_video_generation_node` uses Wan, which has no `params_builder`, so H3 first-frame routing is untested.
- No test for `lookup_model_spec` (item 3) — this PR changed matching logic shared with BAGEL/Qwen and there's no regression net under it.
