## Substantive comments

### 2. `vllm_omni/diffusion/lora/manager.py:369-382` — hardcoding `unet` duplicates metadata the pipeline already declares

`StableDiffusionXLPipeline` already declares `_dit_modules: list[str] = ["unet"]` (`pipeline_sdxl.py:46`). Every pipeline in the tree declares `_dit_modules` — it's the established convention for "which submodules are the denoiser", and `vllm_omni/diffusion/offloader/module_collector.py:110` already consumes it. This PR instead grows a fifth entry on a hardcoded tuple that must be manually kept in sync with 69 pipelines.

That the two are already drifting is visible in the list itself: the manager hardcodes `"bagel"`, while `pipeline_bagel.py:159` declares `_dit_modules = ["language_model.model"]`. Two sources of truth for the same fact.

Reinforcing this: `_lora_components` (line 382) — the documented opt-in escape hatch — has **zero users in the entire repo**. It's a dead extension point, which is why contributors reach for the hardcoded tuple instead.

Suggested direction (follow-up PR is fine, this one is a valid stopgap):

```python
components = tuple(getattr(self.pipeline, "_dit_modules", ()) or ()) or default_components
```

with dotted-path resolution (a small `getattr` chain) so `"language_model.model"` works, keeping the hardcoded tuple only as a fallback for pipelines that don't declare `_dit_modules`. That makes new pipelines LoRA-capable by default instead of requiring a manager edit each time.

### 3. `vllm_omni/diffusion/lora/manager.py:688` — the real bug is the silence, and it's still there

Your own NOTE comment nails it: *"adapters can load/activate while effectively applying to zero layers, producing base-identical output."* That is a framework defect, not an SDXL defect. Trace it: `_replace_layers_with_lora` matches nothing → `_lora_modules` stays empty → `_activate_adapter` (line 527) iterates an empty dict → line 631 sets `_active_adapter_id = adapter_id` → the log says `"Activating adapter: id=%d"` → the user gets base-model output and a clean log.

The next pipeline whose denoiser attribute isn't in the tuple hits exactly this again, and debugging it costs the same day it cost here. Add the diagnostic in `add_adapter`, right after line 688:

```python
before = len(self._lora_modules)
self._replace_layers_with_lora(peft_helper)
if not self._lora_modules:
    logger.warning(
        "Adapter %d (%s) matched zero layers in the pipeline; output will be "
        "identical to the base model. Scanned components=%s, target_modules=%s.",
        adapter_id, lora_request.lora_name, scanned_components,
        getattr(peft_helper, "target_modules", None),
    )
```

(Requires `_replace_layers_with_lora` to return or record which components it actually scanned — cheap.) This is the change that would have made the original SDXL bug self-diagnosing in one log line, and it generalizes to every future pipeline.

### 4. FF-layer LoRA weights are silently dropped on SDXL — the fix is incomplete for many real adapters

`sdxl_unet.py:836-847` renames diffusers' FF names at load time:

```python
if ".ff.net.0.proj." in name:
    name = name.replace(".ff.net.0.proj.", ".ff.geglu.proj.")
...
elif ".ff.net.2." in name:
    name = name.replace(".ff.net.2.", ".ff.out_proj.")
```

The LoRA path has no equivalent mapping — `_load_adapter` explicitly passes `weights_mapper=None` (`manager.py:309`). So for an SDXL LoRA whose `target_modules` include `ff.net.0.proj` / `ff.net.2` (extremely common):

- `_matches_target("unet....ff.geglu.proj")` is False against target `ff.net.0.proj` → the module is never replaced;
- and even if it were, `_get_lora_weights` (lines 499-509) would look up `unet....ff.geglu.proj`, `....ff.geglu.proj`, then `proj` — none of which is the checkpoint's `....ff.net.0.proj`.

Result: attention LoRA applies, FF LoRA vanishes, no warning. The output *changes* (so the manual test in the PR description looks like a pass) but it's wrong-by-omission. The adapter you tested is presumably attention-only.

Fix: build a `WeightsMapper` from the same rename table `load_weights` uses and thread it into both `from_local_checkpoint` and the target matching — ideally by having the model own the mapping rather than duplicating the string literals in two places. At minimum, please note this limitation in `docs/user_guide/diffusion/lora.md`.

I confirmed the paths that *do* work, for the record: `attn1.to_qkv` resolves via `stacked_params_mapping` → `to_q/to_k/to_v` (`sdxl_unet.py:825-827`, consumed by `_get_packed_sublayer_suffixes`), and `to_out` being an `nn.ModuleList` (`sdxl_unet.py:151`) means the module name is `to_out.0`, matching diffusers verbatim. That's why the `to_out.0` → `to_out` normalization from 632efb42 was correctly reverted in ac3a2ce5 — good call, don't reinstate it.

### 5. SDXL LoRAs containing text-encoder weights will hard-fail

`pipeline_sdxl.py:93-108` builds `text_encoder`/`text_encoder_2` as stock HF `CLIPTextModel`/`CLIPTextModelWithProjection` — plain `nn.Linear`, not `LinearBase`. So `get_supported_lora_modules` (called at `manager.py:124`) never picks up `q_proj`/`k_proj`/`v_proj`/`fc1`/`fc2`, and vLLM's `check_unexpected_modules` raises:

```
While loading ..., expected target modules in {...} but received [text_encoder.text_model.encoder.layers.0.self_attn.q_proj, ...]
```

A large share of published SDXL LoRAs ship TE weights, so "SDXL LoRA compatibility" will still look broken to those users — just with a confusing exception instead of a silent no-op. Not a regression from this PR (the load path predates it), but it's squarely in this PR's stated scope. Either skip/warn on `text_encoder*`-prefixed modules rather than raising, or document the unet-only limitation.

## Test comments

### 6. `tests/diffusion/lora/test_lora_manager.py:580-619` — 40-line copy of the bagel test; parametrize instead

`test_lora_manager_discovers_unet_component` is character-for-character `test_lora_manager_discovers_bagel_component` (line 538) with `bagel`→`unet` and the leaf path changed. Adding a sixth component will mean a third copy.

Collapse both into one parametrized test over the full default tuple. That is strictly stronger: it pins *every* default component, so silently dropping one from the list fails a test, whereas today only `bagel` and `unet` are covered.

```python
@pytest.mark.parametrize(
    ("component", "inner"),
    [("transformer", "foo"), ("transformer_2", "foo"), ("dit", "foo"),
     ("bagel", "language_model.qkv_proj"), ("unet", "down_block.proj")],
)
def test_lora_manager_discovers_default_component(monkeypatch, component, inner):
    ...
```

### 7. `tests/diffusion/lora/test_lora_manager.py:613` — the stub `peft_helper` skips the code path that actually matters

`type("_PH", (), {"r": 1})()` has no `target_modules`, so `getattr(peft_helper, "target_modules", None)` returns `None` at `manager.py:343` and **everything** is replaced unconditionally. The test therefore proves only "the loop visits `pipeline.unet`" — it never exercises target matching, which is precisely where SDXL is fragile (issue #4).

Add one test with a realistic SDXL shape: `target_modules=["to_q", "to_k", "to_v", "to_out.0"]` against a module tree containing a packed `to_qkv` (with a `stacked_params_mapping` on the component) plus a `to_out.0`, asserting both get replaced. That would regression-guard the packed-sublayer resolution SDXL depends on, and a variant with `ff.net.0.proj` would encode issue #4 as a known gap.
