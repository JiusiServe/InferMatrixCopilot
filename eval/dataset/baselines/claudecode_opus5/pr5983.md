### 1. `vllm_omni/diffusion/diffusion_engine.py:559,576,579,588` — the identical race is still live one file over, with the same zombie-engine outcome (**most important**)

`_process_rpc_queue` runs on the singleton busy-loop thread and uses the exact check-then-act pattern this PR is removing:

```python
if not fut.done():
    fut.set_result(result)
```

The cancels are not hypothetical here — they're explicit and on the hot path:
- `collective_rpc` (`diffusion_engine.py:993-995`) calls `task.future.cancel()` on timeout, from a different thread than the busy loop.
- `async_collective_rpc` (`diffusion_engine.py:1015-1019`) does the same on `asyncio.TimeoutError`, and its `return await aio_fut` (no-timeout branch) propagates ordinary task cancellation into `concurrent.Future.cancel()` as well — so a client disconnect is enough.

These futures are never put in RUNNING state, so `cancel()` always succeeds. `_busy_loop` (`diffusion_engine.py:439-490`) has no `try/except` around its body, so an `InvalidStateError` there kills the busy loop outright — same symptom as #5793 (`/health` 200, jobs accepted, GPU idle), and worse in one respect: it also skips the `_fail_pending_rpcs(...)` shutdown drain at line 489, so queued RPC callers hang instead of erroring.

The comment at `diffusion_engine.py:570-573` even names `InvalidStateError` and "which would kill the busy loop" — and then guards with the racy check. Since commit c18f956d deliberately moved the helpers into `diffusion/utils/future_utils.py` to be shared, this is the obvious second consumer. **Change:** import `try_set_result`/`try_set_exception` and apply at lines 559, 576, 579, and 588.

### 2. `tests/diffusion/test_result_pump.py:441,455` — two of the three tests pass with the fix reverted

`test_compute_done_racing_cancel_does_not_crash_pump` and `test_output_ready_racing_cancel_does_not_crash_pump` assert only `fut.cancelled()`, which is true whether the pump survived or died. The pump runs in a daemon thread (`_feed_one_msg_to_pump`, line 62), so its exception never reaches the test body. I checked the installed pytest (9.0.3): `_pytest/threadexception.py` raises the thread traceback as `PytestUnhandledThreadExceptionWarning` and only escalates it to an error under `-W error` — and `pyproject.toml:242-251` sets `addopts = ["--strict-markers", "--strict-config"]` with no `filterwarnings = error`. So under repo CI config those two tests go green against a reverted fix. Only `test_batch_split_racing_cancel_does_not_crash_pump` genuinely gates it (the loop in `_deliver_batch_split` dies on the first entry, leaving `healthy_fut` unresolved).

The PR description's "with the fix reverted: all 3 fail" is therefore only true under `-W error`.

**Change:** cheap and exact — `_feed_one_msg_to_pump`'s mock only sets `executor._pump_stop` on its *second* dequeue call (line 57-59), so surviving the message is directly observable. Add to each racing test:

```python
assert executor._pump_stop.is_set(), "pump thread died on the late resolve"
```

or have `_feed_one_msg_to_pump` return `call_count[0]` and assert `>= 2`.

### 3. `vllm_omni/diffusion/executor/multiproc_executor.py:868-916` — the fix is per-exception, not per-thread (follow-up)

`InvalidStateError` is one of several ways this thread can die with no operator-visible signal. `self._deliver_batch_split(...)` at line 883 is not wrapped, and `batch_output.get_request_output(req_id)` (line 923) is untrusted worker-shaped data; an unexpected message shape does the same. Wrapping the whole post-dequeue dispatch body in `except Exception: logger.exception(...)` would retire the entire class rather than this instance. Separately, the issue's real complaint — "no way to see the difference between queued and dead" — is untouched: consider setting `self._is_failed` (or otherwise failing `check_health`, line 953) if a pump thread exits while `_pump_stop` is clear, so a zombie can't keep returning 200.

### 4. `vllm_omni/diffusion/utils/future_utils.py:19-20,26-27` — the recovery is invisible, and conflates two very different states

`logger.debug` at default INFO means the next occurrence of this race leaves no trace, which is unfortunate for a bug that took two production reproductions to characterize. Suggest `logger.warning` (it is rare by construction) plus an optional `context: str` the executor can populate with `rpc_id`/`async_output_id`.

Also worth splitting the two cases: a cancelled future is expected and benign; an *already-resolved* future would mean a genuine bookkeeping bug (impossible today given the pop-under-lock, which is why it's worth surfacing if it ever happens):

```python
except concurrent.futures.InvalidStateError:
    if fut.cancelled():
        logger.debug("Dropping late result for cancelled future (%s)", context)
    else:
        logger.warning("Double resolution of future (%s)", context)
```

### 5. `vllm_omni/diffusion/executor/multiproc_executor.py:910-916, 938-941` — the abort path still leaks (pre-existing, but directly adjacent)

In the *common* abort ordering the cancel lands well before the late result, so `pending.done()` is already `True` and control never reaches the new helpers — it falls into the `else` branch and stashes the output in `self._completed_outputs[...]` forever. Nothing evicts it: it's popped only by `wait_output_ready` (line 966) and line 650, and `shutdown()` (lines 1007-1009) clears `_rpc_futures`/`_output_futures`/`_batch_split_map` but **not** `_completed_outputs`. SHM has already been unpacked by then, so this pins real memory per aborted request — under exactly the #5793 workload. It also makes the two orderings inconsistent: the racy path drops the result, the non-racy path caches it forever.

**Change (follow-up PR):** don't cache when the popped future was cancelled, and clear the dict on shutdown:

```python
if pending is not None and pending.cancelled():
    pass  # consumer is gone; drop instead of caching forever
elif pending is not None and not pending.done():
    ...
```
