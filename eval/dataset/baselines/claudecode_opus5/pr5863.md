# Review: PR #5863 — `[doc]Add recipe for MiniMax-H3 on RTX PRO 6000`

## Verdict

**Approve, with follow-ups.** This is one of the better recipes in `recipes/` — it separates measured from unmeasured, states its methodology, and the flag sets are actually valid for this model. I re-derived every number in the tables and the internal arithmetic is clean (per-step divisions, both speedup ratios and their efficiencies, all three headroom subtractions, the stage-sum-vs-E2E residual of ~0.75 s in all three configs, the 19% warmup delta, and the two-point fit's 0.25% prediction error all check out). The flags validate against the code: 56 DiT heads (`minimax_h3_transformer.py:54`) give 7 heads/rank under both TP2×USP4 and TP4×USP2; `--text-encoder-tp-size 8` divides Qwen3-VL's 64/8 heads (`pipeline_minimax_h3.py:648`); `--vae-patch-parallel-size` equals the DiT group size in every config; and the rank-grouping claim at line 58 matches `order="tp-sp-pp-cfg-dp"` in `parallel_state.py:840`.

**One finding is significant enough to fix in a follow-up**: the "Per-GPU memory model" section attributes the memory reduction to the wrong variable, and its central factual claim is contradicted by the code. Two other items (the Ref2VA restart command, and Ref2VA on the two-GPU profile) will bite readers.

## Major

### 1. The memory model attributes the reduction to Ulysses, but `--text-encoder-tp-size` was scaled in lockstep — lines 43–46, 277–291

`MiniMax-H3-RTX-PRO-6000.md:281` states:

> because all three configurations shard the DiT with TP2 and **hold identical weights per GPU**

This is false. The three configs use `--text-encoder-tp-size 2`, `4`, and `8` respectively (lines 96, 126, 155). In `pipeline_minimax_h3.py:656-661`, only ranks `< text_encoder_tp_size` load the encoder, and `MiniMaxH3Qwen3VLTextModel` shards it across the encoder group — so per-GPU encoder weights are `E/2`, `E/4`, `E/8`. Per-GPU weight residency is therefore *not* "set by the tensor-parallel degree alone" (line 43) either.

The consequence is that the fit is unidentifiable. Ulysses degree and encoder TP degree double together across the sweep, so these two formulas fit all three points *identically*:

```
doc:  peak ≈ 55.4 + 22.1 / ulysses_degree
also: peak ≈ 55.4 + 44.2 / text_encoder_tp_size
```

Two independent checks say the second is the real mechanism:

- `E/2 = 22.1 GiB` implies `E ≈ 44.2 GiB`. `MiniMax-H3.md:312` documents the retained-50-layer Qwen3-VL encoder as **~51.5 GB = 48.0 GiB**. That's an 8% match on a quantity that was never fitted.
- For the Ulysses reading to hold, 22.1 GiB would have to be shardable DiT activation memory at USP1. At 1344×768×124f the latent sequence is ~31k tokens; one `[31k, 5376]` bf16 tensor is ~0.33 GiB. Getting to 22.1 GiB of *shardable* activation is off by roughly an order of magnitude.

**Why this matters practically:** the doc tells readers per-GPU memory is a function of TP and Ulysses degree. A reader on eight GPUs who sets `--text-encoder-tp-size 2` — legal, and the natural choice if they only read the parallelism table — lands ~16–17 GiB above the predicted 61.07 GiB, i.e. near 78 GiB rather than 61 GiB.

**Change:** either re-plot with `--text-encoder-tp-size` held fixed to actually isolate the Ulysses term, or (cheaper, honest) state that the two were varied together, that the sweep cannot separate them, and that the encoder-sharding term dominates. Add `--text-encoder-tp-size` to the list of things that invalidate the numbers (line 293–294 currently lists only reference length, concurrency, and output shape).

### 2. Line 291: "adding GPUs past eight will not reduce the per-GPU requirement further"

This contradicts the doc's own formula one paragraph earlier: `55.4 + 22.1/8 = 58.2 GiB`, a further 2.9 GiB below the eight-GPU measurement. As written the paragraph refutes itself.

Under the encoder model there *is* a real floor at eight GPUs, for a much more useful reason: `text_encoder_tp_size` must divide Qwen3-VL's **8 KV heads** (`pipeline_minimax_h3.py:648-653`), so 8 is the hard maximum regardless of world size. That's the sentence worth writing — it's an actionable constraint, not an extrapolation.

### 3. Line 216: the Ref2VA restart command fails for the documented download path

> For Ref2VA on a single-server layout, stop the FL2VA server and restart the same command with `MODEL="${MODEL_ROOT}/Ref2VA"`.

`pipeline_minimax_h3.py:563` sets `model_path = model_root / "Ref2VA"` for that partition, and `:629-670` then loads `tokenizer/`, `processor/`, `text_encoder/`, `video_vae/`, and `audio_vae/` from *under that path*. But the default download pattern (`MINIMAX_H3_DOWNLOAD_PATTERNS`, `:114-118`) fetches only:

```
FL2VA/**, Ref2VA/model_index.json, Ref2VA/transformer/**
```

So anyone who obtained the checkpoint through the pipeline's own combined download has no `Ref2VA/text_encoder` and this restart dies at load time. It only works with a full `Ref2VA/**` subtree (whole-repo `hf download`, or an HF-id download with `--task-type ref2va`). Given lines 28–32 actively steer readers toward single-partition downloads, this is a likely landing spot.

**Change:** state the prerequisite explicitly — "requires the complete `Ref2VA/**` subtree, not the combined-download subset" — and note the `~270 GiB` storage implication for a host that wants both.

### 4. Two GPUs + Ref2VA is a foreseeable OOM with no warning at the point of use

The recipe establishes that (a) the two-GPU profile peaks at 77.49 GiB with 18.5 GiB headroom, (b) Ref2VA "drives the Qwen3-VL presentation from tens of tokens ... to several thousand" (line 298), and (c) Ref2VA was never measured. It then hands the reader an unqualified restart instruction (line 216) and a Ref2VA example at **60 steps and `duration=8`** (lines 343–344) — both above the measured 50-step/5.0 s workload.

The warning exists at lines 78–79, but it's in the two-GPU section, ~140 lines from where the reader actually acts. Repeat it at line 216 and in the Ref2VA example, and say plainly that the two-GPU profile is the one most likely to OOM on Ref2VA.

## Moderate

### 5. Line 4: dangling reference to a nonexistent profile

> The additional HBM over the **RTX PRO 5000 profile** removes the **four-GPU minimum**

Neither exists in the repo. `grep -rn "RTX PRO" recipes/` returns only this file. The nearest sibling is `recipes/MiniMaxAI/MiniMax-H3-5090.md`, and no "four-GPU minimum" is documented anywhere — `MiniMax-H3.md` gives a 1-GPU CPU-offload profile, a 2-GPU DLO profile, and a 4-GPU *no-offload* profile. Presumably the intent is "removes the need for offload below four GPUs." Rewrite against a real target and link it: `[MiniMax-H3.md](MiniMax-H3.md#four-gpus-throughput-oriented-combined-service)`.

### 6. Lines 201–203: `numactl` flags presented as server flags

> Use `CUDA_VISIBLE_DEVICES=0,2,1,3`, `--cpunodebind=0 --membind=0`, and `--port 8091`

`--cpunodebind`/`--membind` are `numactl` options, and `numactl` appears nowhere in the section. Listing them inline with `--port` reads as if they were `vllm serve` flags; a reader copying them onto the server command gets an argparse error. Show the actual invocation:

```bash
CUDA_VISIBLE_DEVICES=0,2,1,3 numactl --cpunodebind=0 --membind=0 \
  vllm serve "${MODEL_ROOT}/FL2VA" --omni --port 8091 ... 
```

### 7. Lines 180–191: the device-order table doesn't hold for the headroom variant

The "Rank ordering across two sockets" table (lines 170–173) is derived for TP2×USP4 — TP pairs `(0,1)…(6,7)`, Ulysses groups `(0,2,4,6)`/`(1,3,5,7)`. The headroom variant immediately below changes TP to 4, which makes TP groups `(0,1,2,3)`/`(4,5,6,7)` and Ulysses groups `(0,4)`, `(1,5)`, `(2,6)`, `(3,7)`. The recommended `0,4,1,5,2,6,3,7` order then does the opposite of what the table's first row claims. One sentence scoping the table to TP2×USP4 fixes it.

### 8. Lines 10–16: no vLLM-Omni version or commit

`MiniMax-H3.md:182-185` pins "vLLM 0.26.0, vLLM-Omni `0.26.1.dev14+gae6577ea`, PyTorch 2.11.0+cu130" for its validation. This recipe gives driver/CUDA but identifies the software only as `vllm/vllm-omni:minimax-h3` — a tag referenced nowhere else in the repo (the repo uses `v0.26.0` and `cosmos3`). If that's a local build, these numbers aren't reproducible. Add the vllm-omni version/commit and PyTorch version, and confirm whether the tag is actually published.

### 9. Lines 253–259: the peak-memory method undersamples the eight-GPU config

`nvidia-smi --query-gpu=memory.used` at **1 Hz** across a request whose entire VAE decode window is **1.798 s** on eight GPUs gives 1–2 samples inside that window. If decode is the peak, the 61.07 GiB figure is an undersample — and it's the point the "0.25% error" validation rests on. Two things:

- `MiniMax-H3.md:181` carries the caveat "the sampled `nvidia-smi` peak is also not a CUDA allocator high-water mark." This recipe drops it while making stronger quantitative claims.
- The recipe *documents* `X-Peak-Memory-MB` at lines 326–328 but doesn't use it. That header is `max_memory_reserved` with per-request reset (`diffusion_model_runner.py:343-370`) — the allocator high-water mark including fragmentation. Sampling `nvidia-smi` across all devices is a defensible choice (it catches CUDA context and NCCL buffers the allocator can't see), but reporting both would be strictly better, and would settle whether the peak is in denoise or decode.

Either way, drop "a 0.25% error" — that precision isn't supported by 1 Hz sampling, and it's a two-parameter fit validated on one point.

### 10. "HBM" and the 96 GiB baseline

RTX PRO 6000 Blackwell is **GDDR7**, not HBM. The word appears 9 times (lines 3, 4, 22, 26, 250, 251, 279, 285, plus the table header). `MiniMax-H3-5090.md` has the same habit, so this is a pre-existing repo convention rather than something this PR introduced — but a recipe whose entire value is precise memory sizing on one specific card is the wrong place to keep it.

Relatedly, `nvidia-smi` reports ~97,887 MiB ≈ **95.6 GiB** total on this card, not 96 GiB, so every "Headroom below 96 GiB" value (line 251) is ~0.4 GiB optimistic. Since the row is quoted to 0.1 GiB, use the real total.

### 11. Lines 28–32: the `--task-type` paragraph doesn't apply to any command here

Every command block points `MODEL` at `${MODEL_ROOT}/FL2VA` — a single-partition directory. `_resolve_minimax_h3_model_root` (`:143-165`) returns early for a local `is_dir()` path, so `--task-type` triggers no download at all in this recipe's flow, and `_minimax_h3_partition_for_task` (`:125-140`) already auto-detects `fl2va` from the directory name. The "start one server at a time" constraint is likewise already satisfied by every command in the file, since none of them loads both DiTs. As written it reads as an unmet constraint the reader must work around. Reword to: these commands already load one partition; the combined-service warning in `MiniMax-H3.md` doesn't apply.

### 12. Line 338: `--max-time 1200` is below the server timeout

The T2VA example uses `--max-time 1800`, matching `VLLM_OMNI_VIDEO_SYNC_TIMEOUT=1800`. The Ref2VA example drops to 1200 for a *larger* workload (60 steps, `duration=8`). Extrapolating the two-GPU denoise (278.55 s at 50 steps / 5.0 s) gives ≥535 s before any reference-token cost — plausibly over 1200 s on two GPUs. curl would abort client-side while the server keeps generating. Use 1800.

### 13. Line 340: `audio_reference=</root/audio_ref.json` is uncopyable as written

`-F "field=<file"` makes curl read the field value from the file, so this needs `audio_ref.json` to contain the exact JSON the server expects — and the recipe never says what that is. `MiniMax-H3.md:510` shows the inline form:

```bash
-F "audio_reference={\"audio_url\":\"${AUDIO_URL}\"}"
```

Either use the inline form or show the file's contents. While there: `/root/hand.jpg` and `/root/out_ref2va.mp4` are hardcoded absolute paths, inconsistent with the `export`-variable style used in every other block in the file.

## Minor

- **Line 275** — "denoise is 96-98% of end-to-end." The table gives 97.8%, 97.9%, 97.1%. Say 97–98%.
- **Lines 108–109** — "an unsharded BF16 partition does not fit in 96 GiB" conflates the 135 GiB *on-disk partition* (which includes the separately-shardable text encoder and the tiled VAEs) with unsharded DiT weights. The conclusion looks right — solving the fit's constant for the TP2 DiT shard puts the full DiT near 90–95 GiB — but quote that number instead of the partition size.
- **Lines 220–224** — "does not depend on the experimental SM120 kernel": nothing in the repo goes by that name (`benchmarks/diffusion/bench_attention_backends.py:323` notes trtllm-gen and FA4 4.0.0b10 are broken on sm_120 — possibly the intent). Either name it or drop it. Worth adding that `CUDNN_ATTN` is already the sm_120 **auto-route**, not an override (`platforms/cuda/platform.py:219-225`; `docs/user_guide/diffusion/attention_backends.md:114-118`) — so the flag pins the default. Link that doc; it also has an sm_120 RTX PRO 6000 benchmark table showing `FLASHINFER_ATTN` competitive on lighter-mask DiTs, which is a reasonable untested alternative to mention.
- **Lines 226–232 (FP8)** — on sm_120 the fused quack GEMM is unavailable (`tcgen05` absent) and FP8 falls back to FlashInfer's unfused path (`docs/user_guide/quantization/fp8.md:48-56`). Readers should not expect a latency win here, and `flashinfer` must be installed. Cross-link `MiniMax-H3.md`'s FP8 quality evidence (LPIPS 0.1156 / PSNR 23.63) so FP8 isn't presented as free.
- **`recipes/README.md:33`** — not added to the "Available Recipes" table. `MiniMax-H3.md` and `MiniMax-H3-MUSA.md` are listed; the 5090 and NPU recipes aren't, so indexing is already inconsistent, but a new 2/4/8-GPU 96 GB profile is exactly what someone would scan that table for. Suggested row: `| MiniMaxAI/MiniMax-H3-RTX-PRO-6000.md | MiniMax H3 T2VA on workstation Blackwell | 2x / 4x / 8x RTX PRO 6000 96GB |`
- **Lines 62–67** — the four-GPU device order is stated prescriptively ("the order is `0,2,1,3`") while the equivalent eight-GPU guidance is explicitly labeled unvalidated (lines 177–178) and lines 69–71 say all measurements were taken without pinning. The mapping is correct (rank pairs `(0,2)`/`(1,3)` land inside physical pairs `(0,1)`/`(2,3)`), but it should carry the same "not compared on this host" caveat.
- **No change needed** — the omission of `VLLM_WORKER_MULTIPROC_METHOD=spawn` relative to every sibling H3 recipe is harmless: `engine/stage_init_utils.py:509-511` forces it. Noting so it doesn't get flagged in a follow-up.

## Worth keeping

The `t2va requires an explicit aspect_ratio even when width and height are supplied` gotcha (line 306) is correct and non-obvious — `_resolve_minimax_h3_aspect_ratio` is called unconditionally at `pipeline_minimax_h3.py:791`, before the `height is None or width is None` branch, and raises at `:348`. The `ref2va` counterpart (line 332) is also right (`:346-347` defaults to 16:9). The explicit separation of measured from unmeasured, and the "Not yet measured" section naming exactly what wasn't run, is a standard the other recipes in this directory should be held to.
