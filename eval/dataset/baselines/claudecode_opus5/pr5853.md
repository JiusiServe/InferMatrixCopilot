## Verdict

**Approve with follow-ups.** The architecture here is sound: a declarative `CacheDiTRequestSpec` + reconciling runtime is the right shape for request-boundary hook swaps, the `installation_key` trick to force a reinstall when `force_refresh_step_hint` changes is a genuinely correct workaround for Cache-DiT's "`None` means keep" merge semantics (confirmed in `cache_dit==1.3.0`: `BasicCacheConfig.empty()`/`update()` skip `None`), and re-arming the `once` hint at each request boundary is necessary (`cache_manager` clears the hint after it fires). Batch-key isolation is wired correctly — both `*BatchSamplingParamsKey` classes are populated by field-name reflection (`request_scheduler.py:23`, `base_scheduler.py:32`), so adding the field is enough. Tests are real and pass locally (27 passed on the policy/runtime/inputs subset).

What holds me back from an unqualified approve is one concrete un-recoverable failure path in the install/uninstall lifecycle, a landmine in the newly-public `CacheDiTBackend.disable()`, and a cross-cutting API field that only one model implements. Note the `buildkite/vllm-omni-amd-ci` gate is red on the merged commit — that's the gate to look at, not something to re-litigate here.

## Major

### 1. A partially-failed install leaves hooks nothing can remove
`vllm_omni/diffusion/cache/cachedit/runtime.py:71-74`

```python
if self._backend is None:
    backend = CacheDiTBackend(spec.cache_config)
    backend.enable(self._pipeline)          # <-- may raise mid-way
    self.adopt(backend, installation_key=spec.installation_key)
```

`CacheDiTBackend.enable()` (`backend.py:246-264`) loops over `_dit_modules` and only sets `self.enabled = True` after the last one. H3 in combined mode has two (`transformer`, `transformers_ref`, `pipeline_minimax_h3.py:618-629`). If the second `enable_cache_for_dit` raises, hooks are already installed on `transformer`, but:

- the local `backend` is dropped, so `self._backend` stays `None` and `_installation_key` stays `None`;
- `CacheDiTBackend.disable()` early-returns on `if not self.enabled` (`backend.py:270`), so even a retained handle couldn't clean up.

Failure scenario: request A (`quality=high`) fails during install → 500. Request B (`quality=lossless`) sees `desired_key is None == self._installation_key`, skips `disable()`, and denoises **with the leftover Cache-DiT hooks on `transformer`** — the exact opposite of the documented "reference path". Request C (`quality=high`) builds a new backend, but `cache_dit`'s `cachify()` returns early on `BlockAdapter.is_cached(...)`, so the new profile is never applied and C silently runs the stale one. `is_cache_dit_enabled()` reports `False` throughout, so `cache_summary` is suppressed and there's no observable trace.

Suggested fix, two small changes:
- In `backend.py:251-260`, append to `self._cache_targets` **before** calling `enable_cache_for_dit` (the target object is already computed at line 250), and have `disable()` tear down `_cache_targets` regardless of `self.enabled`.
- In `runtime.py:72-74`, wrap the install: `try: backend.enable(...) except Exception: backend.disable(self._pipeline); raise`.

### 2. `disable()`'s target list is wrong for every custom-enabler pipeline
`vllm_omni/diffusion/cache/cachedit/backend.py:241-244`

```python
self._refresh_funcs = [custom_enabler(pipeline, self.config)]
self._cache_targets = [_default_get_pipeline_transformer(pipeline)]
```

The custom enablers don't necessarily cache `pipeline.transformer`:
- `enable_cache_for_wan22` (`model_specific.py:110-147`) caches a `BlockAdapter` over **both** `transformer` and `transformer_2`; `disable()` would release only the first, leaving `transformer_2` hooked and `enabled = False`.
- `enable_cache_for_wan22_s2v` (`model_specific.py:167-180`) *permanently* replaces `after_transformer_block` with a no-op ("we permanently replace it… to prevent double injection"). Releasing the cache hooks there doesn't restore the model — audio injection is gone for good.

Nothing today calls `disable()` on those pipelines (only the H3 runtime does), so this isn't a live bug — but `disable()` is now a public method on the shared backend, and the opt-in protocol is a two-method duck type (`models/interface.py:150-160`), so the next model that adds `adopt_cache_dit_backend` inherits silent corruption. Either have `CacheDiTEnabler` return its cache targets alongside the refresh func, or raise `NotImplementedError` from `disable()` on the custom-enabler path until they're audited.

### 3. `quality` is a global request field that exactly one model honors
`vllm_omni/inputs/data.py:215`, `entrypoints/openai/protocol/videos.py:168`, `serving_chat.py:172`

The field is validated, plumbed through three entrypoints, and made part of both batch keys — but only `MiniMaxH3Pipeline` reads `sampling.quality`. For every other diffusion model, `quality=high` returns 200, changes nothing, *and* splits the request into its own worker batch (`sched/interface.py:58,117`), so users pay a throughput penalty for a no-op. That's the worst combination: silent semantically, non-silent operationally.

Recommend gating at the entrypoint on a model capability (the registry already knows `model_class_name`; `get_extra_body_params` is precedent) and returning 400 for unsupported models — or at minimum `logger.warning_once` when a non-supporting model receives it. The docs only cover H3, so today the only way a user learns is by measuring.

### 4. `lossless` doesn't mean "reference path" when a non-Cache-DiT backend is configured
`vllm_omni/diffusion/models/minimax_h3/quality_policy.py:149-158`

`resolve()` branches on `quality == "high"` **without consulting `self._configured_backend`**. So with `--cache-backend mag_cache` (or `tea_cache`/`step_cache`) on H3:
- `high` installs Cache-DiT hooks *stacked on top* of the already-installed backend;
- `lossless` returns `cache_dit=None`, which only uninstalls Cache-DiT — the other accelerator survives, so the documented "Remove Cache-DiT hooks and run the reference path" (`docs/.../cache_dit.md`) is false.

Both other backends happen to fail H3 at startup under default config (`TeaCacheConfig.__post_init__` raises `KeyError` without coefficients; MagCache raises without `mag_ratios`), so this needs a deliberate config to hit — but it's a one-line guard: raise `OmniClientError` in `resolve()` when `_configured_backend` is a non-`cache_dit`, non-`none` accelerator and `quality` is set.

## Moderate

### 5. PR description contradicts the shipped behavior
The description says "Without startup Cache-DiT capability… `high` returns an error." The final code does the opposite — `quality_policy.py:149` installs on demand with no deployment gate, and `test_high_quality_policy_emits_cache_profile_without_deployment_gates` asserts exactly that. The `docs/` table matches the code, so this is description-only staleness from commit `8bc8bfaa`, but anyone reading the PR for the contract gets the wrong mental model.

### 6. Conflicting hardware in the two published measurement tables
`recipes/MiniMaxAI/MiniMax-H3.md` says the numbers were measured on "4× NVIDIA H200"; the PR body reports the same latencies (85.49 / 63.36 s, same SSIM/PSNR) on "4x NVIDIA L20X". One of the two is wrong, and the wrong one is now in a shipped recipe. Worth correcting the recipe.

### 7. `quality` doesn't round-trip through the video API
`vllm_omni/entrypoints/openai/api_server.py:2814` sets `quality=req.quality or "default"` on a response whose field already defaults to `"default"` (`protocol/videos.py:349`). But `"default"` is not in `DIFFUSION_QUALITY_LEVELS`, so a client that echoes a previous response's `quality` back into a new request gets a 422. Either accept `"default"` as an alias for omitted in the request validator, or leave the response field alone and don't advertise a value clients can't reuse.

### 8. A `once` refresh hint only applies to the first output
`pipeline_minimax_h3.py:1758-1764` calls `prepare()` once, then loops `_minimax_h3_output_seeds(seed, num_outputs)`. Cache-DiT auto-refreshes when `current_step >= num_inference_steps`, and that same path clears the hint when `force_refresh_step_policy == "once"` — so with `num_outputs_per_prompt > 1`, outputs 2..N silently lose the hint. (Cache state itself does reset per output, so this is a hint-semantics gap, not cross-seed contamination.) Either move `prepare()` inside the loop or document the restriction next to the recipe's `force_refresh_step_hint` row.

## Minor / nits

- **`refresh()` on a silently-disabled backend**: `runtime.py:77` calls `refresh` without checking `is_enabled()`. `CacheDiTBackend.refresh` logs a warning and returns (`backend.py:287-289`), so a request would proceed uncached while the runtime still reports `is_enabled == True`. An assert or a re-install would be more honest than a log line.
- **Validation in three places**: pydantic validator (`videos.py:177`), `normalize_diffusion_request_args` (`diffusion_request_utils.py:96`), and `__post_init__` (`inputs/data.py:347`). All consistent and all reachable from different entrypoints, so it's defensible — but a single shared `validate_quality(value)` helper would keep the error strings from drifting.
- **Per-request INFO logging**: `backend.py:273` (disable) and `backend.py:292` (refresh) log at INFO on every request boundary once H3 owns the lifecycle. Consider DEBUG for the refresh path.
- **Layering**: `pipeline_minimax_h3.py:25-28` now imports the Cache-DiT package at module import time, inverting the previous runner→cache direction. `cache-dit==1.3.0` is a hard dep in `requirements/common.txt` so it won't break imports, but a lazy import inside `adopt_cache_dit_backend`/`prepare` would keep model modules independent of the cache package.
- **Style**: `adopt_cache_dit_backend`/`is_cache_dit_enabled` are defined above `__init__` in the class body (`pipeline_minimax_h3.py:546-556`) while the attribute they touch is created at line 697 — moving them below `__init__` would make that dependency easier to see.
- `logger.debug("MiniMax H3 request quality=%s", quality)` at `pipeline_minimax_h3.py:1574` is ~180 lines away from where `quality` is used; folding it into the `prepare()` call site would make the log more useful.

## What's good

The `installation_key` design (`quality_policy.py:103-117`) with its comment explaining *why* a hint change needs a reinstall rather than a refresh is exactly the kind of note that survives a year. `test_startup_cache_follows_omit_lossless_high_omit_state_machine` asserting the full event sequence — including that a repeated `high` refreshes rather than reinstalls — is the right way to test a state machine. And the recipe's explicit "these values apply to this deployment and are not universal guarantees" note is a good norm for perf claims.
