## Verdict

**Approve** — the change is correct, well-scoped, and fixes a real problem. I verified the premise: `Attention.__init__` constructs one impl per layer (`vllm_omni/diffusion/attention/layer.py:95`) with no try/except around it, so pre-PR every diffusion attention layer did its own `get_kernel()` round-trip, and `get_kernel` does a live Hub ref-resolution call each time (no memoization inside `kernels`). Caching per repo_id is the right fix, at the right layer.

I ran the code with a stubbed `kernels` module and confirmed: two `_get_hub_module()` calls → one load, the module object is shared, the lock is released on exception, and `RuntimeError` chains the last error. The lock-over-dict pattern also matches the existing convention at `vllm_omni/diffusion/postprocess/rife_interpolator.py:29,370`, and moving off `@cache` (commit 0f2516f2) was the right call — `lru_cache` doesn't hold its lock across the wrapped call, so N threads could still all download.

Comments below are follow-ups, not blockers. Two are worth acting on.

---

### 1. Transient failures are now sticky — `flash_attn_hub.py:31-38`

```python
for version in (1, 2, None):
    try:
        ...
    except Exception as exc:
```

`except Exception` doesn't distinguish "this repo has no v1 tag" from "HTTP 429 / connection reset" — and 429 is precisely the error this PR exists to defend against (per 528804e8's commit message). Previously each layer retried independently, so a blip while building layer 0 self-healed by layer 1. Now the first layer's degraded choice (v2, or the unpinned default revision) is cached for the whole process and every subsequent layer silently inherits it.

To be fair, caching also *fixes* a worse pre-existing bug in the same area: different layers could previously land on different kernel versions within one model. Net improvement — but I'd narrow the `except` to the version-resolution error and let network errors propagate, and log at `warning` (not `info`) when a fallback actually takes effect, since it's now a process-wide decision.

### 2. The third fallback is dead code on kernels ≥ 0.15 — `flash_attn_hub.py:35`

Verified against the installed `kernels` 0.16.0: `get_kernel(repo_id)` with neither `version` nor `revision` raises `ValueError("A kernel version or revision must be specified.")` in `select_revision_or_version`, before any network call. So on ≥0.15 the `None` branch can never succeed, and every startup logs at least one alarming `Failed to load ... version 1` INFO line.

Compounding this, the pins disagree: `docs/user_guide/diffusion/attention_backends.md:228` says `pip install kernels==0.14.1`, `pyproject.toml:70` pins `kernels<0.15.0`, and the environment I checked has 0.16.0. On 0.14, where `version` had different semantics, you'd be relying solely on the bare call — which resolves to the moving `main` branch. That directly undercuts the documented purpose of these backends (bit-exact train/rollout alignment, docs line 217). Since the loop was being rewritten anyway, this was the moment to pin an explicit version/revision or gate the probe on the installed `kernels` version rather than probe by exception.

### 3. The cited test doesn't exercise the changed file — `tests/diffusion/attention/test_kernels_hub.py:19`

`test_kernels_hub_platform_fallback` only compares `get_path()` strings from the platform selector (`registry.py:68`, pure string lookup); it never imports `flash_attn_hub`. It passes here, but it passed before the PR too. The new cache and fallback loop have zero coverage.

A cheap unit test is feasible — I prototyped it: inject a stub `kernels` into `sys.modules` (give it a real `__spec__`; transformers' `is_kernels_available()` raises on `__spec__ is None`), then assert (a) two `_get_hub_module()` calls → one `get_kernel` call, (b) attempt order is `(1, 2, None)`, (c) total failure raises `RuntimeError` chained from the last exception.

### 4. Cache has no reset hook — `flash_attn_hub.py:22`

Dropping `@cache` also dropped `cache_clear()`. Once a test stubs `kernels`, the stubbed module leaks into every later test in the same process. Add a `_clear_hub_module_cache()` helper for fixtures.

### 5. Nits

- `flash_attn_hub.py:37` — logs `version None` for the default attempt; the old code said "attempting default". Worth a explicit label.
- `flash_attn_hub.py:22` — `dict[str, object]` → `dict[str, ModuleType]`, and annotate the two helpers `-> ModuleType`; the rest of the file annotates returns. No lint rule forces it (ruff config has no `ANN`), just consistency.

### 6. PR description is stale relative to head

It still claims "adding `trust_remote_code=True` for more reliable Hub access", but 9947f414 removed it — correctly, since `kernels-community` is already a trusted org and older `get_kernel` doesn't accept the kwarg, which would have made *every* fallback attempt fail. Anyone reading the merged history will be misled about what shipped.

The diff can't plausibly affect NPU — `vllm_omni/platforms/npu/platform.py:110` rejects both hub backends before the module is ever imported — so it's most likely unrelated, but that should be confirmed against a known-failure list rather than assumed.
