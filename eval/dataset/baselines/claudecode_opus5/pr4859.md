## High

### 1. `vllm_omni/benchmarks/data_modules/seed_tts_eval.py:188-200` — double sample-rate conversion after the upstream merge; breaks WER

`out.tts_output_pcm_bytes` is **already normalized to 24 kHz mono** by every producer:
- `patch/patch.py:1215` → `_pcm_s16le_to_seed_tts_wer_bytes(...)` resamples to 24 kHz and down-mixes to mono (added upstream in `a8b2bf11` — *after* this branch forked at `0455bffc`);
- `patch/patch.py:945-957` → resamples to 24 kHz / loads `sr=24000, mono=True`.

Making the decoder fall back to `stream_pcm_format_from_env()` therefore re-applies the *stream* rate to already-normalized bytes. With the PR's own Test Plan (`VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE=44100`, correct for Ming's 44.1 kHz stream and required for `audio_duration`/`audio_rtf` at `patch.py:1193-1194`), line 200 computes `target_len = len*16000/44100` on 24 kHz data — a 24000/44100 = 0.544× length, i.e. speech fed to Whisper ~1.84× too fast. Same file, same bytes, line 116 still writes the saved WAV at a hardcoded `sample_rate=24000`, so the function is internally inconsistent.

The `channels > 1` branch (195-199) is likewise dead-or-harmful: capture already mixed to mono, so `VLLM_OMNI_BENCH_AUDIO_CHANNELS=2` would silently halve the samples.

**Change:** revert this hunk — keep `pcm_sample_rate: int = 24000` and drop the env lookup and the channel fold, or make the contract explicit (`_pcm_s16le_to_f32_16k(pcm, pcm_sample_rate=SEED_TTS_WER_PCM_RATE)` with a comment that the capture path guarantees 24 kHz mono). Also drop the new module docstring lines at 42-43, which now assert the opposite of what the pipeline does. Please re-run the 1088-utterance EN sweep on the merged head before quoting the WER table.

### 2. `vllm_omni/model_executor/models/common/ming/audio_vae.py:141` — mutating the shared config truncates the encoder to 4 layers

```python
config = _qwen2_config(encoder_args)
self.encoder = Qwen2Model(config)     # builds N layers, stores `config` by reference
...
config.num_hidden_layers = 4          # <-- also rewrites self.encoder.config
self.aggregator = Qwen2Model(config)
```

`Qwen2Model.forward` iterates `self.layers[: self.config.num_hidden_layers]`, so after this line the **encoder** executes only its first 4 of N blocks. Verified locally against the installed transformers:

```
len(m1.layers)=8  m1.config.num_hidden_layers=4
output changed after mutation: True   (max abs diff 0.083)
```

Nothing catches it: `prompt_encoder.py:97-102` validates that all `encoder.encoder.*` params were *loaded*, not that they are *used*, so the extra layers load fine and are then skipped at runtime.

If this is deliberate bug-for-bug parity with the HF reference (plausible — it would explain the WER delta), it must not look like a cleanup. **Change:** restore the explicit second config and set the layer count there, or keep the mutation with a comment that spells out the consequence and cites the HF file/line, e.g.:

```python
# NOTE: intentional — HF's audio_vae mutates the shared config, so
# self.encoder also runs only its first 4 layers (transformers slices
# self.layers[:config.num_hidden_layers]). Do not "fix" this: the
# checkpoint's latents were produced under this behavior.
```

Either way add a unit test asserting the intended effective depth, otherwise the next cleanup pass silently regresses WER. And please state which behavior Ming-flash-omni's VAE (`ming_flash_omni_talker.py:256,267`) was validated under — it constructs the same class.

## Medium

### 4. `audio_vae.py:349-351` — third parameterization of the posterior, only one model validated

This is not simply "restore sampling": `#2906` shipped `logvar → clamp(-30,20) → exp(0.5·logvar)`, `#4341` made it deterministic mean-only, and this PR introduces `softplus(scale) + 1e-4` (the stable-audio-tools bottleneck form). At most one of the three matches the checkpoints. Please cite the reference implementation in a comment and say which variants were checked — the Test Plan covers only Ming-TTS MoE 16.8B EN; the dense 0.5B path (`ming_tts_audio_vae.py:44`, `prompt_encoder.py:137`) and Ming-flash-omni are unverified.

Blast radius worth calling out explicitly: `voice_presets.py:257` encodes preset waveforms once at startup and caches the latents for the process lifetime, so preset voices now vary between server restarts and a bad draw is frozen for the whole run. `flowloss_head.py:39` / `fm.py:48` already consume the global RNG, so this isn't a new class of problem — but it is a new unseeded draw whose output conditions the *entire* utterance rather than one step. Consider gating with an env/config flag if determinism is needed for regression tests.

### 5. `ming_tts/patch_emission.py:130,151` — unexplained `+2`, no test, and one newly-rejected request size

`min_stop_step + 2` makes the effective floor `stop_head_min_steps + 2` (= 5 with `STOP_HEAD_MIN_STEPS = 3`), while the error strings still print `min_stop_step=3`, so the arithmetic reads as arbitrary. If the intent is HF's `if step > min_stop_step`, either write it that way or bump `STOP_HEAD_MIN_STEPS` to 4 and keep `+1`; either way add a one-line comment.

Side effect: `max_new_tokens == 4` was accepted before (API floor is `_TTS_MAX_NEW_TOKENS_MIN = 1`, `serving_speech.py:1529`) and now raises `ValueError` from inside `forward` rather than returning a 400. Tighten the server-side check to `stop_head_min_steps + 2`. There are no tests for `_resolve_ming_stop_decision`; a boundary test (`step == min_stop_step` continues, `step == min_stop_step + 1` may stop) is cheap and would pin this.
