## Overall verdict

**Approve with reservations / request changes on a few points.** The core fix is right and well-targeted: the executor now takes a reader handle from *every* worker and runs one result pump per worker queue (`multiproc_executor.py:123-124`, `:789-802`), which is genuinely what was broken — the old code created a reader only for rank 0 while `WorkerProc.__init__` had always created a per-rank writer queue (`diffusion_worker.py:816-821`). The `collect_rank_status` split (`:667`), the recursive envelope pack/unpack in `ipc.py:226-229` / `:262-265`, the async-output-thread sentinel shutdown, and the shared compatibility key extraction are all clean improvements, and the test suite added here is substantial (85 tests pass locally).

My reservations are about three things: (1) the fault-isolation model — one malformed request reliably fails a co-scheduled stranger's request; (2) the fail-closed timeout, which tears down the entire worker group at a 600s default that is well under realistic video generation time; (3) the headline per-DP-primary queue routing is gated on a condition that is unreachable in production, and the test that "proves" it only exercises the dead branch.

## Specific comments

### 1. `multiproc_executor.py:469-491`, `:504`, `:516-527`, `:759-760` — one bad request fails every request in the wave

Three separate paths collapse per-request faults into wave-wide faults:

- Preflight `raise ValueError` (`:471`, `:481`, `:488`) aborts the whole wave before dispatch.
- `except Exception` (`:516`) writes `DiffusionOutput(error=str(exc))` for **every** `new_req`.
- `collected_errors` (`:759`) raises `RuntimeError(collected_errors[0])`, discarding the successful peer response that is sitting right there in `tagged`.

Wave membership is decided by the scheduler, not the user, so in a served deployment this means user B gets a 500 because user A sent an empty prompt. The example script codifies this — `dlo_dp2_lifecycle.py:194-197` asserts *both* requests fail. The worker already tags errors with `dp_rank` (`diffusion_worker.py:1145-1150`) and that attribution is thrown away.

**Change:** on preflight rejection, fail only the offending request and return the remainder to the waiting queue (or execute the wave serially). At `:751-758`, map each error to `results[dp_rank]` and only fail the requests whose own rank errored; reserve the wave-wide failure for the case where a rank never replied.

### 2. `multiproc_executor.py:41-49` and `:486-491` — `_is_empty_dp_prompt` encodes model-specific policy in the generic executor

An empty prompt is legitimate in this repo: `vllm_omni/benchmarks/data_modules/sound_effect_dataset.py:114` emits `prompt=""` with the comment "SoundEffect ignores text", and `pipeline_wan2_2_vace.py:599` / `pipeline_flux2.py:690` use `prompt=""` internally for unconditional branches. This check will hard-fail those requests (and their wave peers) on any DLO+AllGather model, not just MiniMax-H3.

It's also incomplete: a list of prompts, a `TextPrompt`-like object, or `{"prompt": None, "multi_modal_data": ...}` all fall through to `return False`, so the guard doesn't cover the shapes it would need to.

**Change:** move this behind a pipeline capability hook (`requires_non_empty_prompt`, alongside `supports_request_batch`) rather than hardcoding it in `MultiprocDiffusionExecutor`.

### 3. `multiproc_executor.py:35`, `:497`, `:414-433` — 600s wave timeout tears down the entire engine

`_DLO_DP_WAVE_TIMEOUT_S` defaults to 600s and a breach calls `_fail_closed_on_dp_wave_timeout` → `self.shutdown()`, killing every worker. But the single-request path at `:533-538` passes `timeout=None`. So the same model, same resolution, same step count is unbounded when run serially and gets a 10-minute engine-death cap when run as a DP wave. The repo's own example sets `VLLM_OMNI_VIDEO_SYNC_TIMEOUT=14400` (4h) in the same env block as `VLLM_OMNI_DLO_DP_WAVE_TIMEOUT=600` — a 5s 1344×768 video with audio at production step counts will blow through 600s and take the server down.

Also, `float(os.environ.get(...))` at module import (`:35`) means a malformed value raises `ValueError` during import with no context; the repo has an env-var module convention this should use.

**Change:** default the wave timeout to `None` (or derive it from the same family as `VLLM_OMNI_VIDEO_SYNC_TIMEOUT`) and make the aggressive value opt-in; route the env read through the standard envs module.

### 4. `multiproc_executor.py:726-741` — the per-DP-primary queue routing is unreachable

This block is gated on `self.od_config.step_execution`, but the only caller that reaches the multi-rank-reply path is `execute_request`, reachable only via `execute_batch`, which is only assigned to `execute_fn` when the mode is **not** `STEP_BATCH`, i.e. when `step_execution is False` (`diffusion_engine.py:275-278`). In the real DLO DP path `result_mqs` stays `[None] * num_responses` and `_dequeue_one_with_failure_polling` reads from the shared `_sync_result_buffer` (`:188-194`), which works because every pump feeds it and the results are sorted by `dp_rank` afterwards.

Consequences: the `RuntimeError("Missing result queues for DP primary ranks…")` guard can never fire, and `test_step_execution_reads_each_dp_primary_result_queue` (`test_multiproc_engine_concurrency.py:311`, config `step_execution=True`) validates a branch production never takes. The DP tests that *do* mirror production (`:268`, `:440`) set `step_execution=False` and stub `_sync_result_buffer` directly.

**Change:** either delete the branch and state plainly that pump-mode DP collection goes through `_sync_result_buffer`, or key it on "no pump running" so it is a real fallback. Don't leave a passing test asserting behavior of unreachable code.

### 5. `multiproc_executor.py:504` — silent cross-request output substitution

```python
res = results[i] if i < len(results) else results[0]
```

If the response count ever undershoots the request count, request B is handed request A's generated video/image and marked `finished=True`. That is a wrong-recipient data delivery, not a degradation. Raise instead of falling back.

Related: the DP branch condition at `:459-463` omits the `dp_size > 1` check that `execute_batch` has at `:591-595`. Unreachable today, but if it ever is reached with `dp_size == 1`, `num_responses` is 1 and this exact fallback fires. Add the check.

### 6. `diffusion_engine.py:243-254` — removing the implicit 500ms batch wait silently disables DP concurrency

`request_batch_max_wait_ms` defaults to `0.0` (`data.py:845`, `arg_utils.py:190`), and `_wait_for_request_batch_admission_locked` returns immediately when it's zero (`:478-480`). With async request arrival the busy loop will therefore schedule one request per wave, so `dp_concurrent=True` becomes a no-op for anyone who doesn't set the flag — and the info log at `:250-254` still announces `batch_wait=0ms` as though it were configured. The example defaults `--batch-wait-ms` to 500 (`dlo_dp2_lifecycle.py:56`), which suggests the value is in fact required.

If the removal is deliberate (avoiding a hidden 500ms latency tax — reasonable), log a **warning** when `dp_concurrent and request_batch_max_wait_ms == 0` saying DP concurrency will not batch, and document the requirement.

### 7. `diffusion_engine.py:215` + `:246-249` — `max_num_seqs` is silently clamped to `dp_size`

`_resolve_execution_mode` was relaxed to accept `max_num_seqs > 1` under DLO DP, but `_init_runtime_state` then overwrites `scheduler.max_num_running_reqs = dp_size` unconditionally. A user asking for `max_num_seqs=8` on DP2 gets 2 with no diagnostic. Log the clamp.

### 8. `multiproc_executor.py:283-286` + `:517` — stale-response exhaustion is misdiagnosed as a wedged collective

`_validate_wave_id` raises `TimeoutError` after 16 stale discards. `execute_request` treats *any* `TimeoutError` as "a rank is stuck in AllGather" and shuts down the entire worker group. Discarding 16 stale responses is a different condition and should not kill the engine. Use a distinct exception type for the discard-exhaustion case.

### 9. `multiproc_executor.py:923-952` — `shutdown()` has no reentrancy guard

`_fail_closed_on_dp_wave_timeout` (busy-loop thread) and `_monitor` (`:403`) can both call `shutdown()` and then both iterate `_failure_callbacks`. `_mark_engine_dead` happens to be idempotent, so it's benign today, but the double join over `_result_pump_threads` and the concurrent list clears are racy. The same PR added exactly this guard to `InlineStageDiffusionClient` (`:302-305`) — mirror it here.

### 10. `multiproc_executor.py:71-85` — survivors are never `kill()`ed, and the global budget can SIGTERM healthy workers

After the 15s join budget and `terminate()`, the 5s terminate budget expires and survivors are simply abandoned while `self._processes = []` drops the last reference. The example asserts `multiprocessing.active_children()` is empty after shutdown (`dlo_dp2_lifecycle.py:222-225`), so add a `proc.kill()` escalation.

Separately, the budget is global across all processes: with 8 workers, if worker 0 consumes the full 15s, workers 1–7 get `join(0.0)` and are terminated even if they'd have exited cleanly a millisecond later. A small per-process floor would avoid that.

### 11. `multiproc_executor.py:924-927` vs `diffusion_worker.py:937-945` — pumps stop before workers are told to stop

`shutdown()` sets `_pump_stop` first, then the finalizer sends `SHUTDOWN_MESSAGE`. So there's a window where no one is draining the result ring buffers while workers are still producing. If a worker's `_async_output_loop` is blocked in `result_mq.enqueue()`, the sentinel `None` is never consumed, the 10s join at `diffusion_worker.py:940` expires, `result_mq` cleanup is skipped, and `context.term()` (`:1249`) can then block — eating the executor's 15s budget. Consider stopping the pumps *after* the workers have acknowledged shutdown.

### 12. `inline_stage_diffusion_client.py:110` — unconditional `deepcopy` of a heavyweight dataclass

`clone()` is `copy.deepcopy(self)` (`vllm_omni/inputs/data.py:372-373`), and `OmniDiffusionSamplingParams` can carry `latents`, `timesteps`, `past_key_values`, `cfg_*_past_key_values`, `trajectory_latents`, `output`, and `modules: dict[str, Any]` (`inputs/data.py:213-338`). At this entry point those are normally empty, but for multi-stage flows that thread KV cache or latents through sampling params this is a per-request deep copy of tensors — and if `modules` ever holds live `nn.Module`s it would copy weights. Note that the entrypoint layer already clones via `stage_params.clone_sampling_params`.

The isolation goal is real, but a targeted copy of the fields that normalization actually mutates would be safer and cheaper. At minimum, add a comment stating which fields are known to be empty here and why deepcopy is bounded.

### 13. `ipc.py:153-164` — ndarray SHM segments leak on the fail-closed path

Segments are created in the worker and unlinked only by the reader in `_array_from_shm` (`:87-88`). After a wave timeout the executor stops reading, so every in-flight packed output's segments survive until the `resource_tracker` exits. Previously these ndarrays were pickled inline, so this is new exposure. Bounded in practice (fail-closed kills the engine anyway), but worth a note — and `_ndarray_from_shm` (`:137-139`) is a pure alias for `_array_from_shm` with no added behavior; either drop it or make it symmetric with `_ndarray_to_shm`.
