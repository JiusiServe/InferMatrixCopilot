### 2. The stated ownership invariant is stronger than the code guarantees — `omni_async_output_materialization.md:193-196`

> Correctness therefore depends on that builder being the only consumer that drains connector signals for its output cycle.

`get_omni_connector_output()` is drained from three other places on the same runner, all via `attach_omni_connector_output()`:

- `gpu_ar_model_runner.py:1104` — EC-transfer early return in `execute_model()`
- `gpu_ar_model_runner.py:1129` — the `num_scheduled_tokens <= 0` early return
- `gpu_ar_model_runner.py:1920` — the `execute_model_state is None` path in `sample_tokens()`

Under async scheduling, step `N+1`'s `execute_model()` runs before step `N`'s `get_output()` joins the builder — that overlap is the entire point of the feature — so an empty-token or PP step can in principle drain while a builder is still in flight. Either state why that can't happen (if e.g. a zero-token step can't be scheduled while an output is outstanding, say so — that's the load-bearing fact), or soften to something like "the builder is the only consumer that drains connector signals for a step that produced model output; the early-return paths in `execute_model()`/`sample_tokens()` drain for steps that produced none."

### 3. No TP > 1 caveat, though the background builder issues a collective — `omni_async_output_materialization.md:189-198` and the guard table at `336-354`

`get_omni_connector_output()` is not purely CPU-local: with `async_chunk` and TP world size > 1 it calls `tp_group.broadcast_object(...)` (`omni_connector_model_runner_mixin.py:1521-1527`, via `_broadcast_tp_payload_packet` at `:622-628`). Under this feature that collective now executes on the `omni-async-output-builder` thread while the main thread is running the next decode step.

`_should_use_async_omni_output()` has no TP guard, and the doc's compatibility table is presented as exhaustive ("only when **all** of the following runtime conditions hold"). Meanwhile the validated configuration is TP=1 throughout (bundled CUDA profiles, one replica per stage), while `qwen3_omni_moe.yaml` uses `tensor_parallel_size: 4` for stage 0 on XPU and `2` on NPU. Worth one sentence in *Live Runner State and Ownership* noting that the builder participates in a TP collective when TP > 1, plus stating that the validation was TP=1 — that scopes the "validated on CUDA and ROCm" claim honestly.
