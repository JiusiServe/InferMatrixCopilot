## Verdict

**Request changes.** The intent is right — the CUDA-only gate in the H3 conditioned-VAE encode paths genuinely blocked seeded RNG on MUSA — but the implementation only fixes half the problem and, in doing so, most likely breaks a second supported platform.

`torch.random.fork_rng()` takes a `device_type` argument that defaults to `"cuda"`, and this PR never sets it. The gate was widened from `== "cuda"` to `!= "cpu"`, so non-CUDA device objects now flow into `fork_rng` while the save/restore inside it still goes through `torch.cuda`. The seeding loop was made device-aware; the fork was not. Everything else (the recipe) is documentation and has one copy-paste bug.

The PR also merged with `buildkite/vllm-omni-amd-ci` red. On ROCm `device.type` is `"cuda"`, so this diff is a semantic no-op there and the failure is probably unrelated — but that's for the gate to confirm, not for the diff to assume.

## Blocking

### 1. `fork_rng` still forks the CUDA RNG for non-CUDA devices
`vllm_omni/diffusion/models/minimax_h3/vae.py:172` and `:216`

From `torch/random.py` (verified against the installed torch 2.11):

```python
def fork_rng(devices=None, ..., device_type="cuda"):
    device_type = torch.device(device_type).type
    device_mod = getattr(torch, device_type, None)
    ...
    device_rng_states = [device_mod.get_rng_state(device) for device in devices]
```

`device_mod` comes from `device_type`, **not** from the entries of `devices`. Passing `devices=[device(type='musa', index=0)]` without `device_type="musa"` means `torch.cuda.get_rng_state(musa_dev)` on entry and `torch.cuda.set_rng_state(...)` on exit. I confirmed the behaviour empirically with a foreign device object:

```
$ python -c '...'
foreign-device state == cuda:0 state -> True
fork_rng(devices=[xpu:0]) silently routed through torch.cuda
```

Two outcomes, both wrong:

- Box with no usable CUDA (an MTT S5000 host): `torch.cuda.get_rng_state` calls `_lazy_init()` → `RuntimeError`, so `encode_image()`/`encode_video()` raise.
- Box where `torch.cuda` resolves to something: the *CUDA* generator is saved and restored, and the MUSA generator seeded at `:176`/`:220` is **left mutated after the context exits** — the exact leak `fork_rng` is here to prevent.

The recipe asserts the opposite at `recipes/MiniMaxAI/MiniMax-H3-MUSA.md:110` ("restores both CPU and MUSA RNG states"), and the PR body repeats it. Nothing in this tree supports that: `vllm_omni/platforms/musa/platform.py:145,155,169` call `torch.musa.*` directly, i.e. `torch.cuda` is *not* aliased to MUSA in this stack. Please re-check what the MUSA smoke test actually exercised.

Fix is one keyword:

```python
device = parameter.device
devices = [device] if device.type != "cpu" else []
with torch.random.fork_rng(devices=devices, device_type=device.type):
```

`device_type="cpu"` is safe when `devices == []`: `getattr(torch, "cpu")` resolves and the state list stays empty.

### 2. Widening to `!= "cpu"` regresses NPU, which is a documented H3 target
`vllm_omni/diffusion/models/minimax_h3/vae.py:170` and `:214`

The PR body says "The device allowlist is limited to CUDA and MUSA." The code implements a *deny*list of one entry. `vllm_omni/platforms/` ships `cuda`, `rocm`, `musa`, `npu`, `xpu` — so `npu` and `xpu` devices now take the accelerator branch too.

On NPU this is a straight regression, not just an unvalidated path. Before: `device.type == "npu"` → `devices = []` → CPU-only fork, works. After: `devices = [npu:0]` → `torch.cuda.get_rng_state` → `_lazy_init()` on a CUDA-less torch_npu build → raise. Nothing in the tree imports `torch_npu.contrib.transfer_to_npu`, so `torch.cuda` is not patched. And `recipes/MiniMaxAI/MiniMax-H3-NPU.md:10,87,117` documents exactly the FL2VA and Ref2VA serving modes that call `encode_image()`/`encode_video()`.

Fixing #1 makes this moot for correctness (`device_type=device.type` works for `npu`/`xpu` too). If you'd rather keep the conservative posture the PR body describes, make the allowlist literal:

```python
_RNG_DEVICE_TYPES = ("cuda", "musa")
devices = [device] if device.type in _RNG_DEVICE_TYPES else []
```

Either is fine — but the code and the description should agree.

### 3. `self.device_module` is resolved from the global accelerator at construction time
`vllm_omni/diffusion/models/minimax_h3/vae.py:120`

`torch.get_device_module()` with no argument resolves `torch._C._get_accelerator()`, not the device this VAE actually lives on, and freezes that at `__init__`. Derive it from the parameter instead — `torch.get_device_module` is `@functools.cache`d upstream, so there is no cost to calling it per-encode:

```python
for d in devices:
    device_module = torch.get_device_module(d)
    with device_module.device(d):
        device_module.manual_seed(MINIMAX_H3_KEYFRAME_ENCODE_SEED)
```

Two side effects of caching it as an attribute, both avoided by the above:

- A Python module object on an `nn.Module` makes the instance unpicklable (`TypeError: cannot pickle 'module' object`). `deepcopy` is fine (modules are atomic), `state_dict` is unaffected, but any future `spawn`/cloudpickle path over the pipeline object breaks.
- `tests/diffusion/models/minimax_h3/test_minimax_h3_contract.py:342` builds the VAE via `object.__new__` and never sets `device_module`. It passes today only because the fake parameter is on CPU and the loop body is skipped; the moment anything exercises a device parameter it becomes an `AttributeError`.

## Should fix

### 4. No tests, and the stated validation command doesn't run
The diff touches only `vae.py` plus two markdown files. The PR body claims it "adds coverage for the torchaudio, soundfile, and ffmpeg audio-loading paths" — no test file is added or modified. And the quoted command references `tests/diffusion/models/minimax_h3/test_minimax_h3_vae.py`, which does not exist at this head (the directory has `contract`, `e2e`, `packing`, `parallel`, `quantization`, `quantization_quality`); pytest would exit 4 on it, so the reported "36 passed" can't come from that invocation. I ran what does exist — `test_minimax_h3_contract.py` + `test_minimax_h3_packing.py` → **57 passed** — so the CPU behaviour is unregressed, but that's the pre-existing suite, not new coverage.

A cheap CPU-only regression test would have caught #1 and #2 outright: monkeypatch `torch.random.fork_rng` with a recorder, drive `encode_video` with a fake parameter whose `.device` is `torch.device("musa", 0)`, and assert the recorded call carries `device_type == "musa"`. No accelerator required.

### 5. The "validated Ref2VA configuration" block starts an FL2VA server
`recipes/MiniMaxAI/MiniMax-H3-MUSA.md:72-76`

Line 72 introduces "The validated Ref2VA configuration", line 76 is `export MODEL="${MODEL_ROOT}/FL2VA"`. Copy-pasting the block yields the wrong partition and every `ref2va` request fails. The NPU recipe handles this correctly with two blocks (`MiniMax-H3-NPU.md:87` and `:117`) — mirror that, or set `Ref2VA` here and note the FL2VA substitution.

### 6. Recipe line 110 overstates what is verified
`recipes/MiniMaxAI/MiniMax-H3-MUSA.md:110` — "restores both CPU and MUSA RNG states" is the claim contradicted by #1. Please don't land it until `device_type` is passed and the restore is re-measured on hardware (seed MUSA, capture `torch.musa.get_rng_state()`, run `encode_image`, assert the state is byte-identical afterwards).
