## Verdict

**Approve with required follow-ups.** The core diagnosis is right and the fix is the correct shape: H3's alignment padding is structural, not a second document, and excluding it before quantization is the only way to keep SAGE from folding garbage into a block scale. The prefix-mask validation is genuinely strict, the trailing-empty-sequence normalization handles the zero-padding case, and the hardware tests cover the case that actually matters (`used=194`, a partial trailing K block). I ran the CPU-testable subset locally: `7 passed, 2 skipped`.

Two things should not have shipped as-is: the packed path adds ~10 host↔device syncs per attention call in exactly the code path whose caller documents "do not do this," and `max_seqlen_q/k` went from a guaranteed-safe upper bound to unvalidated producer metadata. I verified both against the code rather than by inspection alone.

## Required

### 1. ~10 device syncs per attention call, and the metadata to avoid them is already in `extra`

`vllm_omni/diffusion/attention/backends/trtllm_attn.py:300-341,364`

Per call, on CUDA tensors: two `.item()` at :300, two more in the `while` condition at :305-308, `flat_mask.sum().item()` at :320, `torch.equal` at :322, two `.nonzero()` at :325-326 (nonzero is a synchronizing op), two `.item()` at :329-330, and `torch.all(...).item()` at :364. Each drains the launch queue. Plus a full-length `arange` allocation and elementwise compare over 58,816 elements at :321.

The caller says exactly this, one frame up:

```
vllm_omni/diffusion/models/minimax_h3/minimax_h3_transformer.py:394-396
# max_seqlen is already the first (real) packed document length. Do
# not read the CUDA cu_seqlens scalars here: this function runs once
# per layer and .item() would serialize every attention launch.
```

The PR moves those reads one layer down, where they run once per layer per step per rank. And the value being reconstructed is already sitting in the metadata as a plain Python int:

```
vllm_omni/diffusion/models/minimax_h3/minimax_h3_transformer.py:417
"valid_kv_length": used,
```

`valid_tokens` at :320 *is* `used`. Read `extra["valid_kv_length"]` instead of deriving it from the mask; the mask then only needs a shape check, not a reconstruction. Same for the SAGE gate — have the producer publish `min_seqlen` rather than reducing `seq_lens` on device. The `while` loop at :305-311 is producer-side normalization that belongs in the producer.

This matters for the PR's own claim: the recipe asserts TRTLLM and FA4 are "within 2% of each other," while the PR body says the TRTLLM run was cold and "its end-to-end latency is not reported as steady-state backend performance." The sync cost was never measured.

### 2. `max_seqlen_q/k` reach the kernel unvalidated

`vllm_omni/diffusion/attention/backends/trtllm_attn.py:342-343,384`

Before this PR, `max_q_len`/`max_kv_len` were `q_len`/`kv_len` — always an upper bound on any sequence in the batch. Now they are producer metadata, passed straight through. I confirmed the gap:

```
cu_seqlens = [0, 2, 8], max_seqlen_q = max_seqlen_k = 2
→ no error; max_kv_len=2 reaches the kernel while seq_lens = [2, 6]
```

Not reachable from H3 today — `packed_sequence.py:224` and `:543` both emit exactly `[0, used, seq_len]`, so `cu[1]` happens to be the max. But `minimax_h3_transformer.py:394` documents `max_seqlen` as "the first (real) packed document length," which is not "the maximum," and this backend is generic. Add a check after :341:

```python
if max_kv_len < int(seq_lens.max().item()):
    raise ValueError(...)
```

or just derive both from `seq_lens` (you have already paid for the sync).

### 3. An all-False mask silently launches a zero-token kernel

`vllm_omni/diffusion/attention/backends/trtllm_attn.py:320-338`

Confirmed:

```
attn_mask = all False, cu_seqlens = [0, 6, 8]
→ no error; batch_size=0, seq_lens=[], cum_seq_lens_q=[0], query has 0 tokens
```

`valid_tokens == 0` matches `cu_seq_lens_q[0]`, so the boundary check passes and everything downstream degenerates. Worse, `torch.all(empty >= k_block_size)` is `True`, so `use_sage` stays on and quantizes empty tensors. Every other malformed input in this block raises a clear `ValueError`; this one shouldn't be the exception. Add `if valid_tokens == 0: raise ValueError(...)` after :320.

## Should fix

### 4. The SAGE gate adds a sync to the dense (non-packed) path

`trtllm_attn.py:364` — in the `else` branch, `seq_lens` is built at :346 from the Python int `kv_len`, then `torch.all(...).item()` syncs to answer `kv_len >= k_block_size`. That's a new per-call sync for every Wan/other TRTLLM+SAGE user, for a comparison that is host-side. Compute `use_sage` from `kv_len` directly in that branch.

### 5. The SAGE gate ignores `q_block_size`

`trtllm_attn.py:364` — `q_block_size` may be 4 or 16 (`data.py:1447`, `_VALID_BLOCK_SIZES`), but the guard only inspects KV sequence lengths. For a role where `q_len != kv_len` that's the wrong tensor. Gate on both.

### 6. The AllGather-KV reject is unrelated scope, name-based, and untested

`vllm_omni/diffusion/attention/layer.py:96-100` — a hard `ValueError` in the shared `Attention.__init__`, keyed on `get_name() == "TRTLLM_ATTN"`, now firing for models that never asked for TRTLLM (it is their platform default). The TODO above it already acknowledges the name-based dispatch. For non-causal attention with no joint tensors, local-Q × gathered-KV is what TRTLLM already computes correctly; the real gap is that TRTLLM ignores `attn_metadata.query_ranges`, which only `flash_attn.py:274` and `flash_attn_hub.py:216,383` honor. Either narrow the check to `query_ranges is not None` at forward time — which also removes the backend-name coupling — or keep it and add a test plus a line in `docs/user_guide/diffusion/attention_backends.md`, since this is a new user-visible hard error.

### 7. Documentation claims outrun the evidence

`recipes/MiniMaxAI/MiniMax-H3.md:247-248` — "Stable measurements … within 2% of each other" is contradicted by the PR body's own caveat that the TRTLLM run was cold and not steady-state. Cite a steady-state measurement or drop the number.

Same section: this flips H3's *default* backend on the strength of a comparison that produced PSNR 27.10 dB / SSIM 0.888 versus FA4. That is a visible output change for existing users and the recipe doesn't mention it. One sentence noting outputs differ from the previous FA4 default would be honest.

`recipes/MiniMaxAI/MiniMax-H3.md:44` — `uv pip install -e .` does not pull flashinfer; it's in neither `pyproject.toml` nor `requirements/*.txt`. So ":239 defaults to dense BF16 TRTLLM_ATTN; no attention backend flag is required" holds only on images that already ship it. The SAGE example additionally needs flashinfer ≥ 0.6.16rc1 or the server hard-fails at init (`trtllm_attn.py:216`). State both.

## Minor

The field's only consumer is `allow_trtllm_default` (`layer.py:83`), so nothing breaks, but the name asserts something untrue and a future reader could use it to skip mask plumbing. - **Skip-Softmax has no short-sequence guard.** `trtllm_attn.py:356` — SAGE warns and falls back below one K block; skip-softmax silently applies `threshold * 14` to the 14-token refiner under a bare `default` spec. The recipe tells users to override `per_role`, but the asymmetry with the SAGE handling is surprising. A matching `warning_once` would be consistent.
- **Padding-row semantics diverge from CUDNN.** TRTLLM now zeroes padding rows (:398-405); CUDNN slices K/V only (`cudnn_attn.py:76-77`) and leaves padding queries with real outputs. Both are fine for H3, which discards those rows, but the shared `valid_kv_length` contract in `abstract.py:122` doesn't say which is intended. Worth pinning down in that comment.
