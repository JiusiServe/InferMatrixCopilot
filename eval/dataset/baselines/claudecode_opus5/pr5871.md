### [P1] The in-repo recipe requirement contradicts the repo's own model guides — `.claude/skills/review-pr/references/process/general-checks.md:91`

Rule 11 requires "every new model PR to add or update its in-repository model-family recipe under `recipes/`", and `references/checks/model-addition-checklist.md:62` reinforces that "the external recipes repository is a structural reference, not a substitute."

But all three official contribution guides at this head tell authors the opposite:

- `docs/contributing/model/adding_omni_model.md:547` — "please add a model recipe to the [vllm-project/recipes] repository", repeated as summary step 7 at `:583`
- `docs/contributing/model/adding_diffusion_model.md:1062` — same
- `docs/contributing/model/adding_tts_model.md:950,969` — same

`recipes/README.md:7-14` does say in-repo, so the repository genuinely contradicts itself. The skill silently picks a side and promotes it to a review requirement, so a reviewer running it will file a finding against an author who followed the documented process. Either resolve the conflict in this PR (update the three guides), or make rule 11 cite `recipes/README.md` as its sole basis, downgrade it to non-blocking while the guides disagree, and have the skill surface the doc conflict instead of the author's omission.

### [P1] Rules 6–12 create merge gates that the skill's own finding bar and severity ladder disclaim — `.claude/skills/review-pr/references/process/general-checks.md:57`

Rules 6–12 are written as unconditional mandates ("Require every performance PR…", "Require every bug-fix PR…", "Require every new model to compare accuracy…"). Two paragraphs down, `general-checks.md:127` says to treat missing evidence as a validation gap "unless the repository contract makes that evidence a merge requirement", and `references/process/review-routing.md:69-72` defines P0/P1/P2 purely as security/data-loss, reachable runtime failure or compatibility break, and non-blocking defect with a concrete failure mode. "No A/B table" and "no recipe" fit none of those bands, so the agent has to either invent a severity or drop the rule.

The author-side sibling skill grades the same items softer and explicitly permits deferral: `precheck-pr/references/checklists.md:127-128` marks missing accuracy/perf evidence as "⚠ if missing and not explicitly deferred to a follow-up PR or RFC section; — if explicitly deferred". Reviewer and author checklists disagreeing on the same PR is the failure mode to avoid here.

Smallest fix: annotate each of rules 6–12 with (a) its severity band and (b) whether it is documented repository policy or reviewer preference — of the set, only the `>500 LOC` RFC gate and the `docs/` update rule are actually backed by `docs/contributing/README.md` — and mirror precheck-pr's deferral allowance.

### [P2] Module references carry no code paths, so routing can't be executed from a diff — `.claude/skills/review-pr/references/modules/ar-runtime.md:3` (and the other 15 files in `references/modules/`)

`references/process/design-contracts.md:16-19` routes by matching changed behavior against each page's `primary_code_paths`, `primary_path_exceptions` and `depends_on`. That metadata exists upstream (`ar_runtime.md` frontmatter lists `vllm_omni/core/**`, `vllm_omni/worker/**`), but not at this PR's own merge base: `docs/design/index.md` at `62bf8d63` lists only 4 module pages — `ar_module.md`, `dit_module.md`, `async_omni_architecture.md`, and `entrypoint_module.md`, which is a one-line "update soon" stub — none with frontmatter. Meanwhile `design-contracts.md:27` forbids importing a newer published contract into an older branch, and every module reference links only to `…/en/latest/…`.

So for any branch cut before the docs reorg, the reviewer is told to read the head's page first, finds nothing, and is barred from using the only page that exists. `rg` over all 1,639 added lines returns zero occurrences of `vllm_omni/`, so there is no fallback mapping from a changed file to one of the 16 contracts.

Fix: inline each module's `primary_code_paths` globs and the repo-relative page path into the reference header, e.g. in `ar-runtime.md`:

```
Primary design: docs/design/module/ar_runtime.md (published: …/design/module/ar_runtime/)
Owns: vllm_omni/core/**, vllm_omni/worker/**  (related: vllm_omni/model_executor/**)
```

That makes routing work from the diff alone and makes "inspect the matching `docs/` file in the reviewed checkout first" (`SKILL.md:48`) actually followable.

### [P2] "The reviewed head's CODEOWNERS" links to `main` — `.claude/skills/review-pr/references/delivery/review-requests.md:9`

The sentence promises the reviewed head's file but the link is `https://github.com/vllm-project/vllm-omni/blob/main/.github/CODEOWNERS`, and lines 18-21 then insist on resolving ownership from the frozen head and never letting published state override it. An agent following the link gets `main`. Point at the head-relative read (`git show <head_sha>:.github/CODEOWNERS`) and label the GitHub URL as discovery-only.

### [P2] The snapshot fingerprint is unbounded and collides with the 60-second status report — `.claude/skills/review-pr/references/process/review-execution.md:52`

"Before the first source read, record a pristine snapshot fingerprint … including tracked, untracked, and ignored paths with file type, mode, symlink target, and content hash", recomputed "before each validation group and delivery" (also `SKILL.md:181`). In a local review the working tree routinely holds `.venv/`, build outputs and cached checkpoints, all git-ignored; content-hashing them several times is minutes to hours of I/O — and `SKILL.md:112` requires the status report within 60 seconds, *before* source reads. The local-branch procedure at `review-execution.md:63-85` also disagrees with itself here: it fingerprints tracked, index and in-scope untracked state, but not ignored files.

Fix: bound the fingerprint — content-hash tracked/index/in-scope-untracked, and cover ignored paths by path+size+mtime (or exclude them with the assumption stated) — and say explicitly that the fingerprint follows the status report rather than preceding it.

### [P2] Routing tables are duplicated between `SKILL.md` and `review-routing.md` — `.claude/skills/review-pr/SKILL.md:63`

`SKILL.md:63-106` and `references/process/review-routing.md:12-56` carry the same 16 module rows, 4 feature rows and 5 evidence rows with parallel trigger wording. Any routing change has to be made twice, and the wordings have already begun to drift (`SKILL.md:74` "Diffusion runtime, models, batching, parallelism, or offload changes" vs. the routing table's "Diffusion Family / Diffusion runtime, models, batching, parallelism, or offload"). This is exactly the subtraction pass the skill asks of others at `SKILL.md:176-178`. Keep the trigger table in `SKILL.md` (progressive disclosure needs it there) and reduce `review-routing.md` to what it uniquely owns: the one-primary/second-module selection rule, the change-type guidance, and the P0–P2 calibration.
