# Review: PR #5884 — "Fix Cache-DiT nested module discovery"

## Verdict: **Approve with follow-ups** (one of which I'd want addressed before this lands, see #1)

The diagnosis and the fix are correct. I confirmed the regression history: before #5720 (`48298030`), `enable()`/`cache_summary()` went through `_default_get_pipeline_transformer` → `pipeline.transformer`, and `BagelPipeline` sets `self.transformer = self.language_model.model` (`pipeline_bagel.py:254`), so Cache-DiT worked. #5720 switched to `_dit_modules`-driven discovery with plain `getattr`, which cannot resolve Bagel's declared `"language_model.model"` — hence the `ValueError: ... has no declared DiT modules` in issue 5879 and the red `single_card_cache_dit` case in `tests/e2e/online_serving/test_bagel_expansion.py:92`. Using `attrgetter` restores it, matches what `ModuleDiscovery._collect_modules` (`module_collector.py:107-131`) already does for the offloader, and the change is minimal and in the right place.

Local verification: `tests/diffusion/cache/` + `tests/diffusion/offloader/test_module_collector.py` → **132 passed**. Note `buildkite/vllm-omni-amd-ci` is red on this PR; that gate needs to be green or explicitly triaged — I'm not re-litigating it here.

## 1. This also silently activates Cache-DiT for SoulX Singer, which looks unsafe — `vllm_omni/diffusion/cache/cachedit/backend.py:43`

`"language_model.model"` (Bagel) is not the only nested declaration. The complete set of nested `_dit_modules` is:

| pipeline | path | before | after |
|---|---|---|---|
| `BagelPipeline` | `language_model.model` | `ValueError` | fixed ✅ (the intent) |
| `Cosmos3OmniDiffusersPipeline` | `transformer.language_model` | skipped | has a custom enabler, so `enable()` is unaffected; only `cache_summary` sees it (guarded) ✅ |
| `FlowMatchingAudioPipeline` (SoulX Singer) | `cfm_decoder.model.diff_estimator` | `ValueError` | **newly enabled, untested** ⚠️ |

SoulX has never run through this path: pre-#5720 `pipeline.transformer` raised `AttributeError`, post-#5720 it raised the "no declared DiT modules" `ValueError`. After this PR it resolves, `DiffLlama._cache_dit_adapter_config` (`modules/llama.py:115`) is found, and `cache_dit.enable_cache` is applied for the first time. That config declares `has_separate_cfg=False` (the dataclass default, `cachedit/config.py:29`), but `_run_flow_matching_loop` (`pipeline_soulx_singer_base.py:317`) runs **two** `diff_estimator` forwards per denoising step — and the two branches have *different sequence lengths*: positive is `x=torch.cat([prompt, xt])`, negative is `x=xt` (`:329`/`:333`). DBCache stores `Fn`/`Bn` residual buffers across consecutive forwards and subtracts them, so the first post-warmup forward compares tensors of mismatched sequence length. That's a crash or silently wrong audio, not just degraded caching. `FlowMatchingAudioPipeline` is not in `_NO_CACHE_ACCELERATION` (`registry.py:332`).

**What to change:** either verify `--cache-backend cache_dit` end-to-end on SoulX in this PR, or add the SoulX pipeline to `_NO_CACHE_ACCELERATION` here so the discovery fix doesn't ship an activation nobody has exercised. A one-line addition is much cheaper than a user hitting it. (Bagel itself also does 1–3 forwards/step with `has_separate_cfg=False`, but that is exactly the pre-#5720 behavior the E2E gate passed under, so it's out of scope.)

## 2. Resolution failures are still silent — `backend.py:47-50`

```python
try:
    module = attrgetter(name)(pipeline)
except AttributeError:
    continue
```

This is the exact failure mode that produced issue 5879: a declared path doesn't resolve, nothing is logged, and the user gets `ValueError: Pipeline BagelPipeline has no declared DiT modules for Cache-DiT` with no indication of *which* declaration failed or why. The sibling implementation you're mirroring does log it — `module_collector.py:114-118` warns *"Pipeline declares '%s' as offloadable but the attribute does not exist or is None"*.

Two reasons this matters more than a nit: (a) the bare `except AttributeError` also swallows `AttributeError`s raised *inside* a property or a partially-initialized `nn.Module.__getattr__`, so "component built lazily and not yet present" is indistinguishable from "typo in `_dit_modules`"; (b) the next person to declare a nested DiT path gets the same undebuggable error you just spent a PR diagnosing.

**Suggested:** `logger.warning("Pipeline %s declares DiT module '%s' but it does not resolve; skipping", type(pipeline).__name__, name)` in the `except` branch.

## 3. The `is_cached` guard doesn't do what the PR description says — `backend.py:61-62`

`cache_dit.summary()` already no-ops for uncached transformers: `summary.py:82-89` returns `[CacheStats()]` when the module is not cached, not parallelized, and not quantized. So this guard is not what suppresses the Cosmos3 UND summary — that was already suppressed inside cache_dit.

What the guard *does* change is the other two disjuncts: `cache_dit.summary` also reports **parallelism and quantization** stats for transformers that aren't Cache-DiT-cached (`summary.py:85-86`, `:120-127`), and those are now dropped. vllm-omni doesn't set `_is_parallelized`/`_is_quantized` today (I grepped — no hits), so there's no user-visible impact, but the guard is stricter than cache_dit's own condition and the rationale in the PR description doesn't match.

**Suggested:** either drop the guard (redundant), or widen it to match cache_dit and say so in a comment:
```python
if not (BlockAdapter.is_cached(t) or BlockAdapter.is_parallelized(t) or BlockAdapter.is_quantized(t)):
    continue
```
Related: when the guard skips *every* declared DiT, `cache_summary` now logs nothing at all — the `if not transformers` warning at `:65` doesn't fire because the list is non-empty. A user who explicitly set `enable_cache_dit_summary` gets total silence. A `logger.debug` on the skip path would close that.

## 4. Each path is resolved twice, and identical modules aren't deduped — `backend.py:53` / `backend.py:59`

`_dit_module_names` walks every dotted path, discards the resolved modules, and returns names; `cache_summary:59` then re-walks each one with an unguarded `attrgetter(name)(pipeline)`. Returning `tuple[tuple[str, nn.Module], ...]` (or having `cache_summary` consume resolved modules) removes the redundant traversal.

It would also make deduping natural. `ModuleDiscovery._collect_modules` dedupes on `id(module)` (`module_collector.py:107`, `:127-130`); this function doesn't. Bagel exposes the same module under two names (`self.transformer` *is* `self.language_model.model`), and today only the nested one is declared, so nothing breaks. I checked the double-enable case and cache_dit's `CachedAdapter.apply` short-circuits on `is_cached` (`cache_adapter.py:111-112`), so it's safe — but a duplicate declaration would still print the same summary twice, and the two discovery helpers behaving differently on the same `_dit_modules` list is a trap.

## 5. Test gaps — `tests/diffusion/cache/test_cache_backends.py:137-161`

- `test_enable_and_refresh_nested_declared_dit` patches `BlockAdapter` wholesale, so `BlockAdapter.is_cached(transformer)` returns a truthy `Mock`. The `mock_cache_dit.summary.assert_called_once_with(...)` at `:161` therefore passes regardless of the new guard — it's testing nested resolution only, which is fine, but it shouldn't be read as covering the guard.
- **Nothing covers "nested module *is* cached → summarized" under the real `is_cached`** — i.e. the actual Bagel scenario this PR exists for. In `test_summary_skips_uncached_nested_dit` (`:121`) the cached module is the top-level `transformer` and the nested one is the uncached one. Adding a case where the *nested* module has `_is_cached = True` would pin the fix.
- Both new tests use `SimpleNamespace`/`Mock`, which fall through `BlockAdapter.is_cached`'s final `else` branch (`block_adapters.py:618-619`) rather than the `torch.nn.Module` branch (`:610-613`) that runs in production. Same result today, but a trivial `nn.Module` stub would exercise the real branch.

## 6. Follow-up (out of scope, worth an issue): the other `_dit_modules` consumers still use plain `getattr`

The same class of bug remains in three places, all of which silently no-op for nested declarations:

- `worker/diffusion_model_runner.py:153` — `_compile_transformer` does `getattr(self.pipeline, "language_model.model", None)` → `None` → returns. `torch.compile` is silently skipped for Bagel and SoulX (`:282-286` feeds it `_dit_modules` directly).
- `registry.py:437-450` — SP hook application; partially rescued by the `find_module_with_attr` fallback at `:445`.
- `lora/manager.py:382-388` — `hasattr(self.pipeline, component_name)` on declared components; nested-declared DiTs are skipped for LoRA scanning, which the surrounding comment explicitly warns produces "base-identical output".

Not this PR's job, but the fix here makes it obvious these are the same bug, and a linked issue would keep it from being rediscovered a third time.
