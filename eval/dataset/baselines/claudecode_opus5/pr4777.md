# Review: PR #4777 — Qwen-Image-Layered: allow `layers=2`

## Verdict

**The core change is correct and I agree with the rationale — but it is incomplete: one stale test elsewhere in the tree still asserts the old bound and will fail, and the PR ships zero CI-runnable coverage that `layers=2` is actually *accepted*.** Since this is already merged, the two items below want a follow-up patch.

I verified the substance rather than taking the description at face value:

- The lower bound really is encoded in exactly one place. `SUPPORTED_LAYERED_LAYERS_RANGE` (`vllm_omni/entrypoints/openai/image_api_utils.py:17`) feeds all three enforcement points — `protocol/images.py:93`, `api_server.py:2070` (`/v1/images/edits`), `serving_chat.py:3287` (diffusion chat) — and the error string is derived from `.start`/`.stop`, so no message goes stale. No doc or recipe states a `3-10` range (I grepped; the only prose was `protocol/images.py:63`, which the PR updated).
- Nothing downstream assumes `layers >= 3`. `pipeline_qwen_image_layered.py` treats it symbolically: `prepare_latents` allocates `layers + 1` planes (`:543`, `:580`), `_unpack_latents` mirrors it (`:623`), and the combined first frame is stripped at `:856`, yielding exactly `layers` images. The offline path (`examples/offline_inference/image_to_image/image_edit.py:262`) never validated `layers` at all, so `layers=2` was already reachable there — the API gate was the sole inconsistency. `sched/interface.py:113` defaults to 4, unaffected.
- I ran the validator directly (importing the module standalone): `range(2, 11)` now rejects 0/1/11 and accepts 2/3/10, exactly as the PR claims. I could not run the pytest suites — this checkout's env has vLLM 0.26.0 against a repo expecting 0.24.x, so `tests/entrypoints/openai_api/test_image_server.py` fails at import on `vllm.entrypoints.serve.disagg` (pre-existing env mismatch, unrelated to this PR).

Also: `buildkite/vllm-omni-amd-ci` is red on this PR. I'm not re-litigating it — that gate needs a green run or an explicit unrelated-flake note in the merge record.

## Comments

### 1. Stale rejection case will break weekly CI — `tests/dfx/reliability/invalid_param_test/test_invalid_image_editing.py:63`

This is the real miss. The PR updated two test files; a third still encodes the old bound:

```python
        pytest.param(
            True,
            {"prompt": "edit", "model": _IMAGE_EDITS_SERVER_MODEL, "layers": "2"},
            ("Invalid layers", "3", "1"),
            400,
            id="invalid_layers",
        ),
```

`/v1/images/edits` validates `layers` unconditionally, not just for layered models (`api_server.py:2068-2074` sits outside any model-type branch), so this case posts `layers="2"` against a live `Qwen/Qwen-Image-Edit` server and expects HTTP 400. After this change `layers=2` validates fine, the edit proceeds, and no 400 is raised. `assert_http_error` requires **all** tuple elements as substrings *and* the exact status (`tests/helpers/assertions.py:801-806`), so it fails on the status check.

Why it wasn't caught here: this directory only runs in the weekly pipeline — `.buildkite/test-weekly.yml:156`, `pytest -s -v tests/dfx/reliability/invalid_param_test/ -m "slow and H100"`, gated on `WEEKLY==1` or the `weekly-test` label. The `ready` label used on this PR never touches it. It will fail on the next weekly run.

Fix — mirror what the PR did in the other two files:

```python
            {"prompt": "edit", "model": _IMAGE_EDITS_SERVER_MODEL, "layers": "1"},
            ("Invalid layers", "2", "10"),
```

(The new message is `Invalid layers value 1. layers must be between 2 and 10 inclusive.` — all three substrings match. Note the old expectation `("Invalid layers", "3", "1")` was already fragile: `"1"` matched only via the `10` in the message. Using `"2"`/`"10"` is no worse, but a single `"between 2 and 10 inclusive"` substring would be sturdier.)

### 2. No CI-runnable test asserts that `layers=2` is *accepted* — `tests/entrypoints/openai_api/test_image_server.py:1245`, `:1595`

Every test this PR touched still only exercises *rejection*; the lower boundary moved from 2 to 1 on both sides, so the suite is exactly as green with `range(3, 11)` restored as with `range(2, 11)`. The only acceptance coverage is `layers=4` (`test_image_edit_layers_and_resolution:1611`) and the L2 e2e case, which needs a single H100 with the full model and — by the author's own note — was never run. The whole point of the PR is unprotected against a silent revert.

These are mocked-client tests, so this is nearly free. In `test_parameter_validation` (`:1245`), alongside the `layers=1` / `layers=11` rejections:

```python
    # Boundary acceptance: 2 is the upstream minimum, 10 the OOM guard.
    assert ImageGenerationRequest(prompt="test", layers=2).layers == 2
    assert ImageGenerationRequest(prompt="test", layers=10).layers == 10
```

And parametrize `test_image_edit_layers_and_resolution` (`:1595`) over `layers` in `(2, 4, 10)`, asserting `captured_sampling_params.layers == layers` — that covers the HTTP/Form path at the new boundary without hardware.

### 3. Record the policy in the constant — `vllm_omni/entrypoints/openai/image_api_utils.py:17`

The bounds are now a bare `range(2, 11)` whose two ends have entirely different justifications, both living only in PR descriptions. #2334 tightened to 3 with a one-line commit message and no rationale, which is precisely how this bug got in; the next person has nothing stopping them from re-tightening. One comment fixes that permanently:

```python
# Lower bound 2 matches the upstream Qwen-Image-Layered demo's slider minimum;
# upper bound 10 is an OOM guard (see issue #2331, layers=1000).
SUPPORTED_LAYERED_LAYERS_RANGE = range(2, 11)
```

### 4. The e2e rewind `3 → 2` is fine — `tests/e2e/online_serving/test_qwen_image_layered_expansion.py:119`

I checked that the guard doesn't lose its teeth at the new value. `test_layered_output_image_count` asserts `len(image_items) == expected_layers` (`:199`), and the #1969 failure mode was collapsing the layer list into a single image — `2 != 1`, so the regression is still caught, and an off-by-one returning 3 would also still fail. The header docstring (`:10`) and the param id (`:120`) were both updated consistently. No objection.

### 5. Things I checked and found clean (no action)

- Float/bool coercion into the `in range(...)` check (`2.0 in range(2, 11)` is `True`) is unreachable in practice: both entry points are typed `int | None` (`api_server.py:1958` Form, `protocol/images.py:61`) and coerce before validation. Pre-existing, not worth touching.
- No CI config selects the e2e case by its `layers_guard_001_layers3` node id, so the id rename breaks nothing (`layers_guard` appears only inside the test file itself).
- `serving_chat.py:2720` reads `layers` from `extra_body` on a separate path without calling `validate_layered_layers` — pre-existing and out of scope here, but worth knowing that the "OOM guard" upper bound isn't uniformly enforced either.
