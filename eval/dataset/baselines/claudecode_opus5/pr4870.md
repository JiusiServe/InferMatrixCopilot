## Verdict

**The worker fix is right and is the real fix for #4851 — approve that half.** Switching the multimodal split length from `hidden_states.shape[0]` to `scheduler_output.total_num_scheduled_tokens` is not just correct, it makes the no-prefix-cache path finally agree with the prefix-cache path, which has been using the scheduled-token total all along (`vllm_omni/core/prefix_cache.py:591-603`, whose docstring already claims it "mirrors the no-prefix-cache path" — before this PR that claim was false).

**The bundled `serving_speech.py` streaming change is under-validated and should not have ridden along unexamined.** It changes behavior on paths the PR neither describes nor tests (WebSocket realtime streaming), and it routes a payload shape into `_generate_audio_chunks` that the sibling non-streaming reducer explicitly treats differently. The E2E evidence in the description is a `stream=False` probe; the code changed is the `stream=True` path.

Also: `buildkite/vllm-omni-amd-ci` is red on this head. All validation cited is NVIDIA H20. That gate needs to be accounted for before this is trusted on AMD.

## Findings

### 1. `vllm_omni/worker/gpu_ar_model_runner.py:1734` — correct fix, but the stated root cause is narrower than the actual one

The PR explains the failure as "tail-only hidden states." The likelier production trigger is **cudagraph padding**: the forward runs on `num_tokens_padded` (`gpu_ar_model_runner.py:1207`, `set_forward_context(..., num_tokens=num_tokens_padded)`), so `hidden_states.shape[0]` is the *padded* width — the same code already truncates it at line 1308 (`hidden_states[:num_tokens_unpadded]`) and line 1711-1714 (`min(total_num_scheduled_tokens, hidden_states.shape[0])`). `to_payload_element` gates slicing on the exact match `element.shape[0] == seq_len` (`vllm_omni/utils/mm_outputs.py:131`), so any padded step silently disabled the per-request split and handed the whole batched `codes.audio` to every request. That explains the observed profile precisely: only concurrent requests corrupt, single-request tests pass, and it's intermittent (steps that go through the prefix-cache merge at `gpu_ar_model_runner.py:746-750` took the already-correct path).

Action: update the PR description and the test name — and add a padded-hidden case (`hidden_states.shape[0] > total_num_scheduled_tokens`) alongside the tail-only one, since that is the shape that actually shipped the bug.

### 2. `vllm_omni/platforms/npu/worker/npu_ar_model_runner.py:905` — identical bug left unfixed

```python
seq_len = hidden_states.shape[0]      # line 905
...
seq_len=seq_len,                      # line 1144, into to_payload_element
```

This is a copy of the GPU path (same `partition_payload_list` / `pooler_inter, pooler_client` structure, same `#4527`/`#4792` comments) with the same defect. Qwen3-TTS on Ascend will corrupt concurrent `no_async_chunk` audio exactly as CUDA did. Either apply the same one-line change here (`int(scheduler_output.total_num_scheduled_tokens)`) or file a follow-up issue and say so in the PR — silently fixing one of two identical call sites is how this comes back.

### 3. `vllm_omni/entrypoints/openai/serving_speech.py:3505-3510` — FINAL_ONLY streaming is riskier than described

Two concrete problems:

**(a) The two consumers of the final payload disagree on list-valued audio.** `_generate_audio_bytes` treats a list under `async_chunk=False` as *cumulative history snapshots* and keeps only the last non-empty element (`serving_speech.py:3823-3838`, comment at 3832). `_generate_audio_chunks` treats a list as disjoint chunks and emits `audio_val[prev_count:]` (`serving_speech.py:2749-2752`). Before this PR the streaming path ran under DELTA, where each output carries a single freshly-drained tensor (the output processor pops `DRAINABLE_MODALITIES` at `vllm_omni/engine/output_processor.py:393-396`), so it always hit the per-step tensor branch. After this PR both paths receive the same FINAL_ONLY object. If the list form the non-stream branch defends against ever reaches the stream path, the client gets every cumulative snapshot concatenated — repeated audio, an even worse symptom than the one being fixed. Either route both through one reducer, or state in the PR why the list form cannot survive `_consolidate_multimodal_tensors` under FINAL_ONLY.

**(b) The WebSocket realtime path is affected and unmentioned.** `serving_speech_stream.py:273` calls `_prepare_speech_generation` directly and streams via `_generate_pcm_chunks` (lines 284 and 365). Under `--no-async-chunk`, a WS client now receives one `audio.chunk` after full generation instead of progressive chunks — TTFB becomes total synthesis time, and `_stream_audio_with_alignments` gets a single chunk for its timestamp windowing. If that's intended, say so; if not, scope the change to the HTTP path.

**Missing validation:** `tests/e2e/online_serving/test_qwen3_tts_customvoice_expansion.py:65` `test_voice_001[no_async_chunk]` runs `stream: True` with 3 concurrent requests — literally the path this hunk changes, in CI. Run it (and its Base counterpart) before/after and put the result in the PR, or drop the serving hunk from this bugfix and land it separately. The worker fix stands on its own; the issue's two reported failures were both `stream=False`.

### 4. `vllm_omni/entrypoints/openai/serving_speech.py:3507` — inconsistent default for a missing `async_chunk`

`getattr(self.model_config, "async_chunk", True)` here vs `getattr(self.engine_client.model_config, "async_chunk", False)` at line 3823. Same attribute, same object (`self.model_config` *is* `engine_client.model_config`, set in vLLM's `models/serving.py:120`), opposite fallbacks — so a config missing the attribute makes the request-prep and the audio-reduction paths disagree about what mode they're in. Pick one default and use it in both places.

### 5. `vllm_omni/entrypoints/openai/serving_speech.py:3509` — misleading variable name

`is_streaming_request = request.is_streaming() and not qwen3_full_payload` no longer answers "is this request streaming." Rename to `use_delta_outputs` (it feeds only `coerce_param_message_types`) so a future caller doesn't reuse it as a streaming predicate.

### 6. `tests/worker/test_gpu_ar_model_runner.py:438` — good regression test, two gaps

- Assert `output.multimodal_outputs` as well as `inter_stage_outputs`. The client-side payload is the other half of the corruption: `talker2code2wav_token_only` sizes the stage-1 placeholder from `output.multimodal_output["codes"]["audio"]` (`vllm_omni/model_executor/stage_input_processors/qwen3_tts.py:428-435`), so an unsliced client payload mis-sizes the code2wav prompt independently of the connector payload. Under `_async_chunk=False` the two lists are the same object, so this costs one line.
- Add the padded case per finding #1; `hidden = [[1.0]]` with `total=3` exercises `shape[0] < total`, not the `shape[0] > total` shape that padding produces.

### 7. Hardening (optional, `vllm_omni/utils/mm_outputs.py:131`)

The split remains inferred from an exact `element.shape[0] == seq_len` match and is all-or-nothing per batch: if any request in a step contributes a row count different from its scheduled tokens, the match fails and *every* request in that step silently receives the whole batched tensor again — the identical failure class, with no log. For Qwen3-TTS the invariant currently holds (prefill writes `zeros(span_len, Q)` at `qwen3_tts_talker.py:715-717`, MTP decode writes one row per request), but e.g. the non-prefill `span_len > 1` branch at `qwen3_tts_talker.py:719-725` returns no `codes.audio` at all. A `logger.debug`/`warning_once` when a token-rank-looking mm tensor matches neither `seq_len` nor the per-request list convention would turn the next occurrence into a log line instead of a 0.228-cosine mystery.
