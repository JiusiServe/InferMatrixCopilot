## Overall verdict: **Approve with changes** — the batching core is sound; a few config/inheritance edges need fixing before this is safe in production

I traced the whole path: `pre_process_func` → `batch_compatibility_key` → `RequestBatchSamplingParamsKey` → `RequestScheduler` grouping → `execute_model_batch` → `_execute_request_list` → `pipeline.forward(batch)` → `split_diffusion_output_by_request`, plus the S2V/VACE transformers' batch handling. The new tests pass locally (86 scheduler/helper + 76 wan2_2 pipeline tests).

**What's right, and non-trivially so:**
- The `repeat_interleave(num_outputs_per_prompt, dim=0)` ordering on user-supplied embeds/images matches `encode_prompt`'s `repeat(1, n, 1) + view(B*n, ...)` interleave semantics, matches `collate_sampling_param_generators`' flat ordering, and matches the `[idx*n : (idx+1)*n]` slicing in `split_diffusion_output_by_request`. All four axes line up.
- Dropping `latent_condition.repeat(batch_size, …)` in favour of `repeat_interleave` on `image_tensor` before the VAE is the correct fix, and the `first_frame_mask` shape change from `1` to `batch_size` is consistent with it.
- VACE's per-request `prepare_video_latents(request_generator)` inside the loop, followed by `prepare_latents([gen0, gen1])`, preserves the *per-generator consumption order* of the single-request path — so single-vs-batch determinism is genuinely preserved there. That's easy to get wrong and wasn't.
- Removing the `squeeze(0)`/`unsqueeze(0)` pairs in S2V `predict_noise`/`diffuse` is correct; the S2V transformer's `forward` was already batch-shaped.
- The known-limitation section in the description is honest and I agree with the diagnosis: the batch-shape BF16 divergence is upstream of anything this PR controls.

The findings below are ordered by severity.

### 1. `od_config.max_num_seqs = batch_size` clobbers configured values — breaks in both directions

`vllm_omni/engine/stage_init_utils.py:1444` and `vllm_omni/engine/stage_engine_startup.py:1561`

```python
od_config = build_diffusion_config(model, stage_cfg, metadata)
od_config.max_num_seqs = batch_size
```

`max_num_seqs` is a real `OmniDiffusionConfig` field (`vllm_omni/diffusion/data.py:852`) settable from `engine_args` via `from_kwargs`, and stage configs already expose it (`vllm_omni/config/stage_config.py:310`). `batch_size` here traces back to `AsyncOmni(diffusion_batch_size=...)`, which **defaults to 1** (`vllm_omni/engine/async_omni_engine.py:113`). Two consequences:

- A diffusion stage that sets `engine_args.max_num_seqs: 4` is now silently forced back to `1` unless the caller also passes `diffusion_batch_size` — i.e. the exact knob this PR exists to enable is disabled by this PR for YAML-configured deployments.
- Conversely, `diffusion_batch_size=4` with a non-batching pipeline now hard-fails engine startup at `vllm_omni/diffusion/diffusion_engine.py:229-234` (`raise ValueError(... does not support request-level batching)`), where previously that argument only sized the client.

**Change to:** reconcile rather than overwrite, e.g.

```python
od_config.max_num_seqs = max(int(getattr(od_config, "max_num_seqs", 1) or 1), int(batch_size or 1))
```

and state the new precedence in the docstring of `initialize_diffusion_stage`. The two new tests (`test_initialize_diffusion_stage_applies_client_batch_size_to_engine`, `test_launch_diffusion_stage_replica_applies_batch_size_to_config`) pin the clobbering behaviour, so they'd need updating too.

### 2. S2V: `scheduler.step(generator=…)` is now unconditionally `None`

`vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2_s2v.py:1081`

```python
generator=clip_generator if isinstance(clip_generator, torch.Generator) else None,
```

`clip_generator` is always the **list** returned by `_make_clip_generators` (`:1317` → `:1390`), so `isinstance(..., torch.Generator)` is always `False` and the generator is never forwarded — including for a batch of one, where it used to be. This is inert today because `FlowUniPCMultistepScheduler` (`:548`) is deterministic and ignores `generator`, but it's a silent trap: the moment a stochastic solver is wired in, S2V loses reproducibility with no signal.

**Change to** either drop the parameter entirely with a comment explaining that the S2V scheduler is deterministic, or thread per-sample generators properly (`clip_generator[0]` when `len(clip_generator) == 1`, otherwise a per-sample step).

### 3. DMD2 Wan variants silently inherit `supports_request_batch = True`

`vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2.py:1055` (`WanT2VDMD2Pipeline`) and `vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2_i2v.py:1027` (`WanI2VDMD2Pipeline`)

Adding `supports_request_batch = True` to the base classes propagates to both DMD2 subclasses, which are not exercised by any test in this PR. That matters because `DMD2PipelineMixin.__init_dmd2__` installs `DMD2EulerScheduler(stochastic_sampling=(solver == "sde"))` (`vllm_omni/diffusion/models/dmd2/mixin.py:31-36`), and `Wan22Pipeline.diffuse` calls `scheduler_step_maybe_with_cfg(noise_pred, t, latents, do_true_cfg)` (`pipeline_wan2_2.py:564`) with **no** generator. For the SDE solver the step noise is therefore drawn from the global RNG as one draw over the whole batch tensor, making each request's output depend on batch composition — the exact isolation property this PR claims to establish.

**Change to:** set `supports_request_batch = False` explicitly on `WanT2VDMD2Pipeline` and `WanI2VDMD2Pipeline` until validated, or plumb per-request generators into `scheduler_step_maybe_with_cfg`.

(Separately and pre-existing: `DMD2PipelineMixin.forward` at `mixin.py:85-93` passes `guidance_scale=`/`num_inference_steps=` to `super().forward()`, which `Wan22Pipeline.forward(self, req)` does not accept. Those classes look untested end-to-end — worth a follow-up issue, not this PR.)

### 4. Admission keys are coarser than forward-time validation, so one bad pairing kills both requests

The condition keys admit requests that `forward` then rejects, and the resulting `ValueError` propagates out of `_execute_request_list` for the *whole* batch — an individually-valid request gets failed because of its batch-mate.

Most concrete instance, `vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2_i2v.py:142`:

```python
request.batch_compatibility_key = ("wan22_i2v_last_image", last_image is not None)
```

`_normalize_i2v_last_image` (`:88-110`) explicitly accepts a raw `torch.Tensor`, and the pre-processor never resizes `last_image`. Two requests with differently-shaped tensor last-images share this key, pass admission, and then blow up in `DiffusionRequestBatch.collate_tensors` at `:669`.

**Change to:** mirror the VACE approach — reuse `_vace_condition_structure` (or an equivalent) so the key carries shape/size/dtype, not just presence. The same reasoning applies to S2V's forward-time `raw_audio_waveforms`/sample-rate check (`pipeline_wan2_2_s2v.py:1263`) and VACE's reference-count check (`pipeline_wan2_2_vace.py:657-660`): prefer keeping incompatible requests out of the same batch over aborting the batch.

Worth deciding explicitly (and documenting) whether `execute_model_batch` should isolate per-request failures at all, or whether whole-batch abort is the accepted contract.

### 5. `output_type="latent"` payload key changed — an output-contract change bundled into a perf PR

`vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2.py:207-208` and `pipeline_wan2_2_i2v.py:68-69`

```python
if sampling_params is not None and sampling_params.output_type is not None:
    output_type = sampling_params.output_type
```

This is a genuine bug fix — previously `sampling_params.output_type` was ignored and `postprocess_video` ran on raw latents. But the fixed path now returns a bare tensor, which `normalize_diffusion_postprocess_output` (`vllm_omni/diffusion/output_formatter.py:76-79`) wraps as `{"output": tensor}` with `primary_key="output"` instead of `"video"`. Latent-mode clients will see a different payload key.

**Change to:** nothing in the code — but call this out explicitly in the PR description / release notes. It's unrelated to batching and will surprise someone.

### 6. `sampling.extra_args` accessed without `getattr` guard

`vllm_omni/diffusion/sched/request_scheduler.py:48`

```python
extra_args = sampling.extra_args or {}
```

The surrounding lines are defensive (`getattr(sampling, "lora_request", None)`, `getattr(request, "batch_compatibility_key", None)`), and `resolve_wan_sample_solver`/`resolve_wan_flow_shift` both use `getattr(req.sampling_params, "extra_args", {}) or {}`. This inconsistency already forced a fix to an existing stub-based test (`tests/diffusion/test_diffusion_engine_rpc_routing.py:126` adds `sampling_params["extra_args"] = {}`), which is the signal.

**Change to:** `extra_args = getattr(sampling, "extra_args", None) or {}`.

### 7. `None` in the solver key means "current pipeline default", but that default is mutable

`vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2.py:689-694`

```python
sample_solver = resolve_wan_sample_solver(first_request, default=self._sample_solver)
...
    self._sample_solver = sample_solver
    self._flow_shift = flow_shift
```

The key deliberately preserves `None` for "unspecified" so that it resolves against the pipeline default — but that default *drifts*: once any request overrides `sample_solver`, `self._sample_solver` is permanently rebound, and all later `None`-key batches silently run the previously-overridden solver. Pre-existing, but the new key design now depends on this being stable.

**Change to:** resolve `None` against an immutable `self._default_sample_solver` / `od_config.flow_shift` captured at init, rather than the mutable current value.

### 8. No shape validation on collated explicit `latents`

`req.collate_request_tensors("latents", None)` concatenates on dim 0 and the result flows straight into `prepare_latents`, which only does `.to(device, dtype)` (`pipeline_wan2_2_i2v.py:904-907`; S2V bypasses `prepare_latents` entirely at `pipeline_wan2_2_s2v.py:1319-1320`). The implicit convention — visible only in the new tests (`latents_a = torch.zeros(2, 4, 1, 2, 2)` for `num_outputs_per_prompt=2`) — is that each request supplies a leading `num_outputs_per_prompt` dim. Anything else silently yields a wrong-shaped batch or a confusing failure deep in the transformer.

**Change to:** assert `request_latents.shape[0] == batch_size` right after collation in each of the four `forward`s, and document the convention on `collate_request_tensors`. Given the test plan leans on `--explicit-latents`, this path deserves a guard.

### 9. `_vace_condition_structure` fallthrough loses shape for unknown types

`vllm_omni/diffusion/models/wan2_2/pipeline_wan2_2_vace.py:55`

```python
return (type(value).__name__,)
```

An `np.ndarray` condition returns `("ndarray",)` regardless of shape, so two differently-shaped numpy conditions get the same key and collide at collation time (see finding 4). **Change to:** add an `np.ndarray` branch carrying `(shape, dtype)`, and for genuinely unknown types be conservative rather than optimistic.

### 10. Wasted full text-encoder pass in the negative-embed fallback

`pipeline_wan2_2.py:674-682`, `pipeline_wan2_2_i2v.py:582-590`, `pipeline_wan2_2_vace.py:619-627` all do:

```python
_, negative_prompt_embeds = self.encode_prompt(
    prompt=[""] * req.num_reqs, ..., do_classifier_free_guidance=True, ...
)
```

That's a full UMT5 forward over `num_reqs` empty prompts whose positive result is discarded, on every batch that supplies `prompt_embeds` without `negative_prompt_embeds`. In a perf PR this is worth a small negative-only encode helper.

### Minor / nits

- **`pipeline_wan2_2_s2v.py:1257`** — `astype(np.float32, copy=False)` returns the caller's array unchanged when it's already float32, and the new test asserts `np.shares_memory(outputs[0].output[1], audio_a)`. Handing a view of request-owned input back out in the output payload is surprising; confirm it's intentional.
- **`_make_clip_generators` production path is untested.** `OmniDiffusionRequest.__post_init__` (`vllm_omni/diffusion/request.py:58-59`) always assigns a seed when both seed and generator are absent, and the runner materializes a generator from it (`diffusion_model_runner.py:445-453`). So in production `seed is not None` and the *request* generator is discarded in favour of `Generator().manual_seed(seed + clip_index)`. The new test sets `seed=None`, exercising only the other branch. Add a seeded case.
- **`request_batch.py:48`** — `stage_durations` is shared by reference across every split output, so per-request timing metrics for a batch are actually batch aggregates. A comment would stop that being misread downstream.
- **`pipeline_wan2_2.py:238`** — for the base T2V pipeline the image key splits batches even when `self.expand_timesteps` is `False`, in which case the image is ignored entirely. Harmless, slightly reduces batching opportunity.
