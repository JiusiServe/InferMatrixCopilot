# Review: PR #4817 — Gate quack FP8 to datacenter Blackwell (sm_100.x) only

## Verdict

**The one-character fix is right, and the diagnosis is sound** — `>= 10` matched cc 12.x, quack's GEMM class is literally `GemmSm100` with `arch = 100` (`quack/gemm_sm100.py:139`), and the try/except-per-GEMM fallback on the DiT hot loop is exactly the catastrophic path described. Ship the behavior change.

**But the PR as written treats the symptom and leaves the mechanism intact**, and its headline mitigation — the new regression test — does not run in CI. Two things I'd ask for before merge (#1 is a hard blocker on the stated goal of the PR, #2 is a one-liner), plus a design point (#3) that would make this class of bug self-limiting instead of requiring an arch-allowlist chase.

Also: 2 required checks are red (`buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci`). Nothing in this diff is exercised by either pipeline — `test-amd-ready.yaml:19` runs only `tests/diffusion tests/model_executor`, and `test-npu-ready.yaml:21` runs a TTS e2e — so these look pre-existing/flaky rather than caused here. Still a gate: get them green or explicitly waived, don't merge through them.

## Blocking

### 1. The new test is deselected in every CI job — the regression guard doesn't guard anything

`tests/quantization/test_quack_fp8_gate.py:19` (top of module — no `pytestmark`)

The repo selects CPU unit tests by marker, not by path. `.buildkite/test-ready.yml:29` is the job that would pick up `tests/quantization/`:

```
pytest -sv -m 'core_model and cpu' --ignore=tests/diffusion --ignore=tests/model_executor
```

The new file carries no markers, so it is collected and then dropped. Verified locally:

```
$ pytest tests/quantization/ -m 'core_model and cpu' --collect-only
no tests collected (18 deselected)

$ pytest tests/quantization/test_quack_fp8_gate.py -q
18 passed in 0.10s
```

The tests are good and they pass — they're just never run. Every sibling CPU test declares markers explicitly (`tests/test_arg_utils.py:19`, `tests/config/test_omni_config.py:42`, `tests/test_outputs.py:11`). Add, after the imports:

```python
pytestmark = [pytest.mark.core_model, pytest.mark.cpu]
```

Since a `>= 10` → `== 10` edit is trivially re-introducible by a future refactor, this line is the entire value of the test file.

**Related coverage gap:** the tests only exercise `_is_quack_capable` / `quack_enabled`, which are pure arithmetic. The behavior that actually broke users is the *wiring* — `install_quack_fp8_patch()` must not patch `FlashInferFP8ScaledMMLinearKernel` when the gate is off. Worth one more test that monkeypatches capability to `(12, 0)`, calls `install_quack_fp8_patch()`, and asserts `apply_scaled_mm` is unpatched (`not getattr(..., "_omni_quack_patched", False)`).

### 2. `warmup_quack_fp8()` bypasses the gate entirely — and it's the documented public API

`vllm_omni/quantization/quack_fp8.py:131-142`

```python
def warmup_quack_fp8(shapes, device="cuda", out_dtype=torch.bfloat16) -> None:
    if _load_quack() is None:      # <-- checks import, never checks quack_enabled()
        return
```

`_load_quack()` succeeds on sm_120 — nothing in the import path probes the arch; the rejection happens later inside `gemm_tuned`. And `quack_scaled_fp8_mm` (line 97) does **not** wrap the call in try/except, unlike the patched `apply_scaled_mm` (line 122). So on an sm_120 box, the snippet this PR leaves in `docs/user_guide/quantization/fp8.md:73-75` —

```python
from vllm_omni.quantization.quack_fp8 import warmup_quack_fp8
warmup_quack_fp8([(14040, 2048, 6144), ...])
```

— will burn JIT time and then raise `OpError` out to the caller (typically a Docker build step, per the doc's "at image build time" framing), on precisely the GPUs this PR just declared unsupported. The docs say "quack is not auto-enabled there"; the helper disagrees.

Fix at line 136:

```python
def warmup_quack_fp8(...) -> None:
    if not quack_enabled():
        return
    if _load_quack() is None:
        return
```

## Should fix

### 3. The arch allowlist is the only line of defense; the per-call retry loop is untouched

`vllm_omni/quantization/quack_fp8.py:117-124`

```python
def apply_scaled_mm(self, *, A, B, ...):
    try:
        out = quack_scaled_fp8_mm(...)
        ...
    except Exception as exc:
        logger.warning_once("Quack FP8 GEMM failed (%s); using FlashInfer.", exc)
    return original(...)
```

Nothing here remembers that quack failed. Every GEMM, every layer, every denoising step re-enters CuteDSL, re-attempts config selection/compile, and re-raises. That is what turned an arch mismatch into a >400 s request — the `== 10` gate removes today's trigger but not the amplifier. Any future trigger (a quack version whose admissible archs narrow, an unsupported shape, a dtype the tuner rejects, a transient compile failure) reproduces the identical pathology on a *supported* GPU, where no capability check will save you.

A sticky disable makes the failure cost O(1) instead of O(GEMMs):

```python
_quack_gemm_failed = False

def apply_scaled_mm(self, *, A, B, ...):
    global _quack_gemm_failed
    if not _quack_gemm_failed:
        try:
            out = quack_scaled_fp8_mm(A, B, As, Bs, out_dtype, bias)
            if out is not None:
                return out.view(*output_shape)
        except Exception as exc:
            _quack_gemm_failed = True
            logger.warning("Quack FP8 GEMM failed (%s); using FlashInfer for all subsequent calls.", str(exc))
    return original(...)
```

FlashInfer is a correct fallback, so permanently latching to it on first failure costs at most some fused-bias perf in an already-degraded run — vastly better than the current behavior. With this in place the arch gate becomes an optimization (skip the one wasted attempt) rather than the sole thing standing between users and an unusable server.

### 4. `warning_once` isn't once here — it keys on the exception *object*

`vllm_omni/quantization/quack_fp8.py:123`

vLLM's implementation is `@lru_cache`-backed (`_print_warning_once(logger, msg, *args)` in `vllm/logger.py`), so the cache key includes `exc` itself. Each call raises a *fresh* exception instance → new key → new log line. That is why the reporter saw the log "flooded by `Quack FP8 GEMM failed (...)`" despite `warning_once` — it's not a contradiction in the bug report, it's a real defect. Passing `str(exc)` makes the dedup work (identical arch-rejection messages collapse to one line). Moot if you take #3, which fires exactly once by construction.

## Minor / docs

- **`quack_fp8.py:19-27` — the docstring's stated reason doesn't match the code.** It says `tcgen05` is "datacenter-Blackwell only (`sm_100a`/`sm_101a`/`sm_103a`, cc `10.x`)", but the PR body itself notes PTX `tcgen05.mma` also targets `sm_110a` (cc 11.x), which `== 10` excludes. The gate is fine — it's just that the real constraint is *quack's kernel is sm_100-family* (`GemmSm100.arch = 100`; CuteDSL's `admissible_archs` per CUTLASS #2800), not tcgen05 availability. Reword to say so; otherwise the next reader "fixes" the docstring's inconsistency by widening the gate. Same wording in `docs/user_guide/quantization/fp8.md:47-50`.
- **`docs/user_guide/quantization/fp8.md:53-54`** now advertises `VLLM_OMNI_USE_QUACK_FP8=1` to "force quack on" without saying what happens on 12.x. As written, a user on an RTX PRO 6000 who sets it walks straight back into the >400 s failure this PR exists to prevent. Add: on cc 12.x this is expected to fail per-GEMM and be far slower until CuteDSL ships `sm_120a` support.
- **Stale "Blackwell" language the PR didn't sweep:** `docs/user_guide/quantization/fp8.md:31` ("Faster FP8 GEMM on Blackwell") and `:33` ("On Blackwell (SM 100+), vLLM runs FP8 linears through the FlashInfer kernel") still imply all Blackwell; `pyproject.toml:102` still says "Optional Blackwell-only fused-bias FP8 GEMM". Cheap to align while you're here.
- **`(10, 3) → True` is asserted but unverified.** By the CUTLASS #2800 reasoning quoted in the PR body (`admissible_archs = [Arch.sm_100a]`), B300/sm_103a could raise the same `OpError` and hit the same fallback path. `GemmSm100` declares `arch = 100` and CuteDSL family semantics (`sm_100f`) vary by version, so it may well be fine — but the test now enshrines it as expected behavior on no evidence. Either confirm on a B300 or soften the test comment. Fix #3 makes being wrong here survivable.
