# Review: PR #5991 — Distilled 4-step sigma schedule for MiniMax H3

## Verdict

**The core mechanism is correct and I verified it end-to-end**, but I'd request changes before merge. The math is right (I checked every shifted sigma by hand), the schedule/step-count plumbing into `minimax_h3_denoise_loop` is consistent, and all 144 relevant tests pass locally. What I'd push back on is (a) the new `num_inference_steps` convention silently disagreeing with the one the same pipeline uses for non-distilled checkpoints, (b) a hard 400 where this repo's existing DMD2 path warns-and-overrides, (c) `sigma_schedule.py` landing in `diffusion/sched/`, which is the *request* scheduler package, not the noise-schedule package, and (d) a `ClassVar` that is assigned and mutated per-instance.

Note both merge gates are red (`buildkite/vllm-omni`, `buildkite/vllm-omni-amd-ci`) and this was merged anyway. Locally `tests/diffusion/models/minimax_h3` (132 passed) and `tests/diffusion/sched` (12 passed) are green and no line exceeds the 120-char limit, so the failure is likely `ruff format`/an unrelated job — worth reading the gate rather than assuming it's noise.

## Major

### 1. `num_inference_steps` now means two different things on the same pipeline
`vllm_omni/diffusion/models/minimax_h3/pipeline_minimax_h3.py:1783-1797`

The legacy path treats `num_steps` as **sigma boundaries**: `_time_shift_sigmas` builds `linspace(1, 0, num_steps)`, and `minimax_h3_denoise_loop` runs `len(sigmas) - 1` iterations (`denoise_loop.py:201`). Verified:

```
num_steps=50 -> 50 sigmas -> 49 denoise steps
num_steps=4  -> 4 sigmas  -> 3 denoise steps
```

The distilled path treats it as **intervals**: a 5-entry `base_schedule` also produces 5 sigmas / 4 model evals, but reports `num_steps = 4`. So the identical physical schedule is called "5" on one checkpoint and "4" on the other, and the new error message (`must be 4 or omitted`) instructs users toward a number that would give 3 steps on any other H3 checkpoint. It also means the PR's headline comparison is really 49-step teacher vs 4-step student.

The distilled convention is the honest one; the legacy one is off by one. But shipping both silently is worse than either. Either fix the legacy boundary count in the same PR, or add an explicit comment at `pipeline_minimax_h3.py:1787` naming the divergence, and pin it with a test asserting `minimax_h3_time_shift_sigmas(num_steps=5)` and the 5-entry distilled schedule produce the same number of model evaluations under different reported step counts.

### 2. Hard `OmniClientError` contradicts the repo's existing DMD2 policy
`pipeline_minimax_h3.py:1793-1797` vs `vllm_omni/diffusion/models/dmd2/mixin.py:41-50`

`DMD2PipelineMixin._sanitize_dmd2_request` already handles exactly this case for distilled checkpoints — it logs a warning and forces the checkpoint's step count:

```python
if sp.num_inference_steps and sp.num_inference_steps != self.dmd2_config.num_inference_steps:
    logger.warning("DMD2: ignoring num_inference_steps=%d, forcing %d.", ...)
sp.num_inference_steps = self.dmd2_config.num_inference_steps
```

This PR rejects instead. That's a real availability problem: `serving_video.py:145` starts from `_resolve_default_sampling_params()`, so any deployment that sets a stage-level `default_sampling_params` with a step count — and any client UI that always sends `num_inference_steps` — gets a 400 on every request, with no way to distinguish a server default from a user's explicit value. Recommend matching the existing mixin (warn + override). If you deliberately want strictness, say so in a comment explaining why H3 differs from `DMD2PipelineMixin`.

### 3. `flow_shift` can silently defeat the pinned trajectory
`pipeline_minimax_h3.py:1798-1799`

```python
video_shift = float(extra.get("flow_shift", self.default_video_shift))
audio_shift = float(extra.get("audio_flow_shift", self.default_audio_shift))
```

These still apply when a distilled schedule is active, and the shift is what turns `0.15` into `0.679` — a different shift moves the student off the exact trajectory this PR exists to reproduce. Note `DMD2PipelineMixin` explicitly strips `extra_args.flow_shift` for this reason (`mixin.py:71-75`). If you reject a mismatched `num_inference_steps`, rejecting/warning on `flow_shift` is the consistent choice; silently honoring it is not.

### 4. Wrong package, and it makes a leaf module expensive to import
`vllm_omni/diffusion/sched/sigma_schedule.py:1`, `time_request.py:6`

`vllm_omni/diffusion/sched/` is the request/step scheduler package (`request_scheduler.py`, `step_scheduler.py`, `interface.py`). Noise/sigma schedules already have a home: `vllm_omni/diffusion/models/schedulers/`, which contains `scheduling_dmd2_euler.py` — and `DMD2Config` lives in `vllm_omni/diffusion/models/dmd2/config.py`. Putting `DMD2SigmaSchedule` in `sched/` splits DMD2 knowledge across three packages.

It's also measurable. `time_request.py` previously had zero module-level imports (`import torch` is deliberately function-local at `time_request.py:57` to keep it cheap). Importing `vllm_omni.diffusion.sched.sigma_schedule` executes the package `__init__`, which pulls in `OmniDiffusionRequest` and the whole scheduler stack:

```
vllm_omni root import: 10.50s
then time_request:      6.49s   (sched + request_scheduler now loaded)
```

Moving the file to `vllm_omni/diffusion/models/dmd2/sigma_schedule.py` (or `models/schedulers/`) fixes both the layering and the import cost, and puts it next to the `DMD2Config` its own docstring (`sigma_schedule.py:21-27`) spends five lines disambiguating itself from.

## Medium

### 5. `ClassVar` is assigned and mutated per-instance
`pipeline_minimax_h3.py:550-552`, `621-623`

```python
_base_schedule_by_partition: ClassVar[Mapping[str, DMD2SigmaSchedule | None]] = {}
...
self._base_schedule_by_partition = {expected_partition: _read_base_schedule(release)}
self._base_schedule_by_partition["ref2va"] = _read_base_schedule(ref2va_release)
```

Two type errors in three lines: you can't assign a `ClassVar` through an instance, and `Mapping` has no `__setitem__`. mypy isn't in pre-commit or the ready pipeline so CI won't catch it, but the annotation actively misdescribes the code. Make it an ordinary instance attribute typed `dict[str, DMD2SigmaSchedule | None]`, and if the partially-constructed fallback is genuinely wanted, express it in the accessor: `getattr(self, "_base_schedule_by_partition", {}).get(partition)` at `pipeline_minimax_h3.py:757-760`. As written, the class-level default exists only so `test_partially_constructed_pipeline_falls_back_to_the_uniform_schedule` can pass on an `object.__new__` instance — that test pins the workaround, not a real path.

### 6. `num_steps` and `base_schedule` are redundant and can disagree
`pipeline_minimax_h3.py:1410-1413`, `1512-1521`, `time_request.py:54-55`

`diffuse()` takes both, but once `base_schedule` is non-None, `num_steps` is dead for sigma generation (`time_request.py:54` returns before touching it) and is used for nothing else in `diffuse`. So the call site passes `num_steps=4` alongside a 5-entry list, and nothing checks they agree. Pass the `DMD2SigmaSchedule` object (it already exposes `num_inference_steps`) or the resolved sigma list, or add `assert len(base_schedule) - 1 == num_steps`.

### 7. The only new production wiring that reads JSON is untested
`pipeline_minimax_h3.py:621-623`

Every new pipeline test injects `_base_schedule_by_partition` by hand via `_distilled_pipeline`, so the per-partition mapping built in `__init__` — including the combined-mode `ref2va_release` branch, the actual behavior the "must not drag Ref2VA onto its schedule" comment is defending — is never exercised. `__init__` loads real weights so it isn't directly testable, but extracting `_base_schedules_from_releases(expected_partition, release, ref2va_release)` as a pure function would make it a three-line test. There's already a `_write_partition_index` helper at `test_minimax_h3_contract.py:103` you could extend with an optional `base_schedule`.

Relatedly, `_read_base_schedule` (`pipeline_minimax_h3.py:173-175`) is a pass-through to `DMD2SigmaSchedule.from_metadata` that exists only so `test_absent_base_schedule_key_differs_from_an_empty_list` can import it — and that test duplicates `test_absent_metadata_key_means_undistilled_but_empty_is_malformed` in `tests/diffusion/sched/test_dmd2_sigma_schedule.py:47-52`. Drop the wrapper and the duplicate test; call `from_metadata(release)` directly.

### 8. Question: is deterministic Euler right for this student?
`denoise_loop.py:235` (`minimax_h3_euler_eta0_step`)

DMD2 multi-step generators are frequently sampled with fresh-noise re-injection at each intermediate level rather than a deterministic ODE step — which is why the repo's own DMD2 contract carries `solver: "ode" | "sde"` (`models/dmd2/config.py:11,19`) and `DMD2EulerScheduler` accepts `stochastic_sampling`. The attached 4-step video suggests eta=0 works for this checkpoint, so I'm not claiming a defect — but "no changes required to the denoising solver" is a checkpoint-specific fact, not a property of DMD2. Consider recording the solver in the `_minimax_h3` block now so a future SDE-trained student doesn't need another metadata migration.

## Minor

- **`sigma_schedule.py:63-64`** — `from_metadata` returns `None` for both an absent key and an explicit `null`, but raises for `[]`. The docstring only describes the absent case; either normalize or say so.
- **`sigma_schedule.py:44`** — `from_positions` raises `TypeError` (not `ValueError`) for a non-iterable `base_schedule` (e.g. `"base_schedule": 4`), so it escapes the `ValueError` contract the tests pin. One `isinstance(raw, (list, tuple))` check in `from_metadata` covers it.
- **`sigma_schedule.py:50-52`** — `values[0] != 1.0 or values[-1] != 0.0` is an exact float comparison and requires checkpoint authors to include the trailing `0.0` boundary. Fine as a contract, but it's a new public checkpoint contract with nothing documenting it — `_minimax_h3.base_schedule` (like `sigma_shift_scales`) appears in no doc. At minimum state in the docstring that entries are **pre-shift** rectified-flow positions; a checkpoint author who recorded post-shift sigmas would get a silently wrong trajectory with no error.
- **`diffusion_model_runner.py:445-464`** — the PR tells users to omit `num_inference_steps`, which makes the runner log `Failed to refresh the diffusion transformer cache` on every request under `tea_cache`/`step_cache`. That path already probes `getattr(self.pipeline, "num_inference_steps", 0)`; exposing that property on the pipeline for distilled checkpoints would make the omit-it workflow clean.
- **`test_minimax_h3_contract.py:504-507`** — `assert video != pytest.approx(uniform)` is a weak assertion (differing in any one element passes). Comparing against the concrete uniform values, as `test_shifted_sigma_schedule_matches_reference_values` does, would be sharper.

## What I verified

- Shifted values in both new test files are arithmetically correct for `s·u/(1+(s−1)u)` at s=12 and s=3.
- `minimax_h3_denoise_loop` steps `len(sigmas) - 1` times and the progress bar total matches, so a 5-entry schedule really does run 4 model evals — the plumbing is sound.
- Monotonicity/NaN validation ordering in `__post_init__` is correct (finiteness checked before the ordering comparison, as the comment says), and the shift map is strictly increasing on [0,1] for `s>0`, so the new path can't produce duplicate sigmas — dropping the legacy `unique_consecutive` is safe.
- Only one caller of `MiniMaxH3Pipeline.diffuse` exists, so the new required kwarg breaks nothing.
- `tests/diffusion/sched/` is picked up by `.buildkite/cuda/test-ready.yml:18` (`tests/diffusion -m 'core_model and cpu'`) and the new markers are registered — no CI wiring is missing.
- `OmniDiffusionSamplingParams.num_inference_steps` defaults to `None` (`vllm_omni/inputs/data.py:271`), so the plain `vllm-omni serve` + omit-the-flag workflow in the PR description does work; the exposure in finding #2 is via stage defaults and clients.
