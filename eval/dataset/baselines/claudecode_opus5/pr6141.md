## Substantive

### 1. `docs/usage/faq.md:17` — the AWQ answer points at a page with zero AWQ content

The answer says AWQ *is* available and tells the reader to "see the [quantization overview] for validated combinations." But `docs/user_guide/quantization/overview.md` never mentions AWQ — not in the Quantization Modes table, not in Hardware Support, not in any of the three Model Type Support tables, and there is no `awq.md` in `docs/user_guide/quantization/`. The only AWQ evidence in the repo is config pass-through (`tests/model_executor/models/test_encoder_quant_config.py:69`, `tests/diffusion/quantization/test_fp8_config.py:224` assert an `"awq"` method string is accepted/preserved) plus a ModelOpt checkpoint that happens to use `awq_clip` calibration (`docs/user_guide/quantization/modelopt.md:107`).

So a user asking the exact question this FAQ entry exists to answer gets "yes" and is then sent to a page that is silent. That's arguably worse than the old (stale) answer, which at least named a concrete thing.

Fix either way:

- Preferred: add a line to `overview.md` stating that AWQ/GPTQ configs are accepted through vLLM's inherited quantization registry but are not validated or documented for vLLM-Omni model types, then the FAQ link pays off; **or**
- Reword faq.md:17 to say so directly, e.g. "AWQ checkpoints are accepted through the inherited vLLM quantization registry, but AWQ is not among the combinations vLLM-Omni validates — see the quantization overview for the methods that are."

Don't leave the current pairing: the assertion and its cited source disagree.

### 2. `docs/community/contact_us.md:9` — the security route isn't actionable as written

"Send a direct message to one of the [lead maintainers] in vLLM Slack" — but `governance.md:28-30` lists lead maintainers as GitHub handles only (`@Gaohan123`, `@hsliuustc0106`, `@ywang96`). A reporter has no way to map those to Slack identities, and Slack DMs to non-connected members can be restricted depending on workspace settings. The fallback ("post a detail-free request in `sig-omni`") is thoughtful, but it makes the *first* step of a security report a public message, which is exactly the friction that causes people to just file the issue instead.

Given the PR description acknowledges this is an interim route, I'd suggest at least one of:

- Add a security contact address (a `security@`-style alias or the maintainers' preferred email) so there's a channel that works without Slack membership.
- List the Slack display names next to the GitHub handles under `### Lead Maintainers`.
- Point to the upstream vLLM project's vulnerability-reporting process, which is available today, as the primary route while omni's own private reporting is disabled.

Also worth checking before merge: `vllm-project` may publish an org-level default `SECURITY.md` (via the org `.github` repo), which GitHub would already surface on this repo's Security tab. If so, this page and the repo's own Security tab will tell reporters two different things. There is no `SECURITY.md` in this repo (I checked), so whatever GitHub currently shows is inherited.

### 3. `.github/ISSUE_TEMPLATE/config.yml` — no security contact link (unchanged by this PR, but in scope)

`blank_issues_enabled: false` and the only `contact_links` entry is Slack/questions. The "New issue" chooser is precisely where a would-be reporter lands, and `docs/contributing/README.md:125` now tells them *not* to open an issue — but nothing at the point of decision says where to go instead. Adding:

```yaml
  - name: Security vulnerability
    url: https://docs.vllm.ai/projects/vllm-omni/en/latest/community/contact_us/#security-disclosures
    about: Do not open a public issue. Follow the private disclosure instructions.
```

would actually complete the "reconcile contact guidance" goal. Small, and it's the highest-traffic surface of the three.

## Smaller

### 4. `docs/community/meetings.md:3-8` — all cadence information is now gone from the repo

Previously `docs/contributing/README.md` gave "every Tuesday at 19:30 PDT" and `governance.md` stated committers meet bi-weekly. Both are deleted; the replacement page states no cadence at all. I understand the motivation (the old times were wrong), but the result is that a contributor cannot learn *whether meetings are weekly or monthly* without opening a Google Doc, and the docs site is no longer searchable for it. Suggest one line like "Meetings run roughly every two weeks; see the documents below for the current time and dial-in." Even a coarse cadence is more useful than none, and it degrades gracefully if the exact slot moves.

Related: making two Google Docs the sole source of truth is a link-rot and access-control risk for a repo whose whole point is reproducible docs. Not a blocker, but if there is an ICS or a page on `vllm.ai/events`, prefer it.

### 5. `docs/community/governance.md` — the removed `## Meetings` section leaves governance with no pointer to the new page

Committer meeting cadence was a governance statement, and `governance.md` is the first Community nav entry. Add a one-line link to `meetings.md` where the section was, rather than dropping it silently.

### 6. `docs/.nav.yml:166-167` — replacing `community/*` with an explicit list is a maintenance trap

awesome-nav will simply omit any future `docs/community/*.md` from the sidebar, with no build error (there's no markdown link checker in `.pre-commit-config.yaml`, so nothing catches it either). Since the only reason to go explicit was to control the ordering of two pages, keep the glob as a tail:

```yaml
- Community:
  - Governance: community/governance.md
  - Contact Us: community/contact_us.md
  - Community Meetings: community/meetings.md
  - community/*
```

That preserves the intended order and still auto-picks-up new pages.

### 7. Nits

- `docs/community/meetings.md:5-6`: the `?tab=t.0` query parameter on both Google Docs URLs is a UI artifact from copying the address bar. Strip it.
- `docs/community/contact_us.md:7`: the "Security Disclosures" section is explicitly interim per the PR description, but the page doesn't say so. A short "(GitHub private vulnerability reporting is not yet enabled for this repository; this page will be updated when it is.)" both sets reader expectations and creates a natural trigger to revisit.
