## Verdict

**Approve with follow-ups.** The extraction is directionally right and I could not find a configuration reachable through `_init_scheduler` where behavior changes: `step_execution=True` → `StepScheduler` → base no-op (replacing the old `self.step_execution` guard), and `supports_request_batch=False and not dp_concurrent` implies `max_num_seqs==1` (enforced at `diffusion_engine.py:215`) → the new `max_num_running_reqs <= 1` short-circuit. So the two removed engine-side guards are correctly re-expressed.

What I'd have pushed back on before merge: one of the four new scheduler tests is vacuous (verified), the policy is only half-moved (the engine still owns what "stable" means), and `_AdmissionWaitDecision` is a private name in a public extension point. The bundled TTS changes are unrelated but I verified they're safe.

Ran locally: the 7 new `-k admission` scheduler tests, `TestRequestBatchAdmission`, `tests/entrypoints/test_async_omni_diffusion_config.py`, `test_tts_detection.py` + `test_check_tts_adapter.py` (129), and a smoke build of the mkdocs argparse hook — all green.

## Comments

### 1. `tests/diffusion/test_diffusion_scheduler.py:281` — this test proves nothing (highest-value fix)

`test_admission_wait_disabled_while_wave_is_running` initializes with `max_num_seqs=1`, so `max_num_running_reqs == 1` and `request_scheduler.py:49` returns `should_wait=False` **before** ever reaching the `num_running_requests() > 0` check. Verified directly:

```
initialize(max_num_seqs=1, request_batch_max_wait_ms=1000.0), zero requests
  -> _AdmissionWaitDecision(should_wait=False, ...)
```

The assertion holds with the running-wave guard deleted. Change `max_num_seqs` to `2`; then after `add_request` + `schedule()` you get `running=1, waiting=0` and the decision is `should_wait=False` *because of* the guard under test (confirmed). Conversely, the new `max_num_running_reqs <= 1` short-circuit — the one genuinely new condition this refactor introduces — has no test of its own; add one.

### 2. `should_end_admission_wait` is in the wrong class — `vllm_omni/diffusion/sched/request_scheduler.py:63-75`

The body reads only `decision` fields and `self.num_waiting_requests()`. Nothing in it is `RequestScheduler`-specific, so it belongs in `BaseScheduler` next to the decision type, with `RequestScheduler` overriding only `get_admission_wait_decision`. Three things this fixes:

- `base_scheduler.py:172-181` currently defaults to `return True`, so any out-of-tree scheduler that overrides `get_admission_wait_decision` and forgets the second hook silently gets a zero-length wait. Making the base implementation the real one removes the footgun.
- `tests/diffusion/test_diffusion_engine.py:88-104` duplicates the expression verbatim in `MockScheduler`, so the engine-level test now asserts against a *copy* of the policy rather than the policy. Once the logic is on the base, the mock can inherit it or be dropped.
- `request_scheduler.py:74`'s `decision.deadline is not None` is dead as written — `RequestScheduler` always sets a deadline when `should_wait=True`.

### 3. The policy is only half-moved — `vllm_omni/diffusion/diffusion_engine.py:484-503`

The PR description says the waiting decision should "reside in scheduler," but the engine still owns the definition of *stable*: `last_waiting` / `stable_since` (i.e. "the waiting count stopped growing") and the hardcoded 2 ms poll are policy, and they stayed put. The scheduler contributes only the window length, then gets handed the engine's state back as a parameter. Consider giving the decision object the mutable observation state, or a single `scheduler.observe_admission(now) -> bool` that reads its own queue, so the engine owns only the condition variable, `stop_event`, and clock. As it stands the state machine straddles the boundary the PR set out to draw.

### 4. `dp_concurrent` is engine state pushed into the scheduler API — `request_scheduler.py:41-55`

`_uses_dlo_dp_concurrency` (`diffusion_engine.py:114`) is a pure function of `od_config`, which the scheduler already holds. Moving that helper into a shared module (the scheduler can't import `diffusion_engine` without a cycle) would let `get_admission_wait_decision` derive it and drop the parameter entirely — that's what would make this a real abstraction rather than a relocation. Secondary: `dp_concurrent: bool = False` as a default means a caller that forgets to pass it silently gets the 50 ms window instead of 300 ms, with no error.

### 5. `_AdmissionWaitDecision` is private but public-facing — `vllm_omni/diffusion/sched/interface.py:34`

It is the declared return type of `BaseScheduler.get_admission_wait_decision` (`base_scheduler.py:167`) and the parameter type of `should_end_admission_wait`, yet it is underscore-prefixed and absent from `sched/__init__.py`'s `__all__`. Custom scheduler injection is a documented extension point (`SchedulerInterface`, `base_scheduler.py:346`), so a third-party subclass has to import an underscore name from a submodule to type its override — and the tests already do exactly that (`test_diffusion_engine.py:28`). Rename to `AdmissionWaitDecision` and export it from `vllm_omni/diffusion/sched/__init__.py`.

### 6. `assert` + direct attribute access breaks the file's convention — `request_scheduler.py:47-48`

```python
assert self.od_config is not None
max_wait_ms = self.od_config.request_batch_max_wait_ms
```

Every other config read in this hierarchy is defensive: `base_scheduler.py:62-72` uses `getattr(od_config, ..., default)` for `max_num_seqs`, `omni_kv_config`, `diffusion_kv_mode`, and even the engine uses `getattr(od_config, "request_batch_max_wait_ms", None)` at `diffusion_engine.py:285`. Under `python -O` the assert is stripped and this becomes `AttributeError` on `None`. The blast radius is visible in this very diff: `test_diffusion_engine_rpc_routing.py:149` and `test_diffusion_scheduler.py:247` had to grow the attribute, while ~15 other `initialize(SimpleNamespace(max_num_seqs=2))` call sites in the same file survive only because they never reach this method. Resolve it once in `initialize()` via `getattr(od_config, "request_batch_max_wait_ms", 0.0)` and store it.

### 7. `deadline=None` + `should_wait=True` is an unbounded loop — `diffusion_engine.py:502`

```python
remaining = decision.deadline - now if decision.deadline is not None else 0.002
```

If a scheduler returns `should_wait=True` without a deadline, the engine polls every 2 ms until `stop_event` or `should_end` — the pre-refactor code could not do that because the deadline was always computed locally. Either make the field mandatory when `should_wait` is set (a `__post_init__` check on the frozen dataclass is two lines) or bound the loop engine-side.

### 8. Undeclared behavior change: `stable_since` now resets before the end check

Old order was *check-then-update*; new order (`diffusion_engine.py:491-500`) is *update-then-check*. Concretely: with a 50 ms window, if a request arrives at t=49 ms, the old code still broke out at t=50 ms; the new code resets the window and keeps coalescing. That's arguably the more correct semantics, but it changes admission latency and is presented as a pure refactor with no test covering it. Add a test and a line in the PR description.

### 9. Docs are now stale — `docs/design/feature/diffusion_continuous_batching.md:125-134`

The listed gating conditions ("the pipeline supports request batching; step execution is disabled; no requests running; wait > 0") no longer match the code. The gate is now "the installed scheduler is a `RequestScheduler`" plus the new, undocumented `max_num_running_reqs > 1`. The "Related Implementation" list at line 225 points only at the engine and should now name `sched/request_scheduler.py`.

Related, worth a docstring note: swapping the `supports_request_batch`/`step_execution` flags for "which scheduler class is installed" is right for the default wiring, but `DiffusionEngine(od_config, scheduler=...)` (`diffusion_engine.py:232`) lets a caller install a `RequestScheduler` with `step_execution=True`, where the old `self.step_execution` guard suppressed the wait and nothing does now.

### 10. CLI/docs plumbing — `vllm_omni/entrypoints/cli/serve.py:47`, `docs/mkdocs/hooks/generate_argparse.py:126`

`_nonneg_finite_float` is fine and the `try/except ValueError` earns its keep (without it argparse would surface the private helper's `__name__` in the error). Two notes: it duplicates `data.py:951` with a differently-worded message, and only the CLI path gets it — the YAML/`engine_args` path relies on the config check, so keep the two messages recognizably identical. More importantly, `mkdocs.yml:62` is the *only* reference to the docs hook — it has no test, so a missing entry in `exec_globals` shows up as a Read-the-Docs build failure, which is precisely what commit `92f00f4a` was cleaning up. A five-line test calling `extract_omni_serve_subparser_init()` would move that into CI. I confirmed the hook builds correctly as-is.

### 11. Scope: the TTS changes don't belong in this PR (but are safe)

- `tools/pre_commit/check_tts_adapter.py:34` (29→27) was **necessary**. `_check` (line 132) errors when `actual < budget`, `serving_speech.py` has exactly 27 branches, and this PR doesn't touch that file — so the ratchet was already red on `main` at the merge base. Legitimate drive-by unblock.

It is nevertheless a true no-op: `MingFlashOmniTTSAdapter` (`ming_flash_omni_tts.py:18-20`) already owns `stage_keys={"ming_tts"}` at the default `detect_priority=100`, ahead of `MingTTSAdapter`'s arch fallback at 200, and `detect_tts_model_type` returned the identical name `"ming_flash_omni_tts"` either way. 129 detection/ratchet tests pass.
