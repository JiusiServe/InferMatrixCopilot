## Comments

### 1. `vllm_omni/entrypoints/openai/video_api_utils.py:315` — the now-dominant peak is untouched (medium, follow-up)

`_coerce_video_to_uint8_frames` streams frames, but `_coerce_video_to_frames` still materializes the whole normalized float video first. `video_tensor.float().clamp(-1, 1) * 0.5 + 0.5` keeps **two live full-size float32 temporaries** (`clamp` result alive while `*0.5` allocates, then that alive while `+0.5` allocates).

Measured on this checkout, 120×768×768×3 float32 (810 MiB video), peak RSS delta over the whole `_coerce_video_to_uint8_frames` call:

| variant | peak delta | ×video |
|---|---|---|
| this PR as merged | 1623 MiB | 2.00× |
| + in-place normalize (below) | 1029 MiB | 1.27× |

```python
video_tensor = video_tensor.float().clamp(-1, 1)
video_tensor.mul_(0.5).add_(0.5)
```

Output is bit-identical (`np.array_equal` → True). This is safe: `.clamp()` always returns a fresh tensor, so the in-place ops can never reach the caller's tensor even when `.float()` returned `self`. Same pattern applies to the numpy path at `video_api_utils.py:338` (`np.clip(...) * 0.5 + 0.5` → `arr = np.clip(...); arr *= 0.5; arr += 0.5`) and to `:317` (`.to(torch.float32).div_(255.0)`).

At the PR's own 362-frame 1344×768 scale that's roughly **3.3 GiB more off the peak — larger than what this PR already saved**. Not blocking, but it should be the immediate follow-up, and the PR description shouldn't read as if the conversion path is now bounded: the remaining 1.27× is one full float copy plus the uint8 output.

Minor, same area: for the tensor path, `_normalize_single_video_array:337` re-scans the array with `.min()`/`.max()` even though `_normalize_video_tensor` just guaranteed `[0, 1]` — two wasted full passes.

### 2. `video_api_utils.py:444` — uint8 fast path contradicts the promotion the next lines emulate (low)

```python
if frame.dtype == np.uint8:
    frames_u8[index] = frame
    continue
```

The gate is per-frame, but the old `np.stack` behavior it claims to preserve was per-video. For a mixed `[uint8, float32]` list the old path promoted to float32, so uint8 values 0–255 clipped to `[0, 1]` → 0 or 255; the new path copies them through verbatim. My fuzz shows `maxdiff 250` on exactly that input — the single divergence found.

It's **not a live bug**: `_normalize_frames:373-374` and `_normalize_single_video_array:339-340` convert every integer dtype to float32, so no uint8 frame ever reaches here and the branch is dead in both old and new code. But it's odd to have a branch that silently picks per-frame semantics ten lines above a comment explaining why per-frame promotion had to be avoided. Either gate on `common_dtype == np.uint8`, or drop the branch and leave a comment that integer frames are normalized upstream.

### 3. `video_api_utils.py:441-442` — new error path is untested, and validation runs after allocation (low)

`ValueError("All video frames must have the same shape.")` replaces `np.stack`'s message. It's a nicer message, but no test covers it, and it fires *after* `np.empty` (`:434`) and `np.result_type` (`:435`) — a ragged input now allocates the full output buffer before failing. Cheap fix: validate shapes in the `common_dtype` pass before allocating, and add a test asserting the `ValueError`. A uint8-passthrough test would also be worth having if finding 2 keeps that branch.

### 4. `video_api_utils.py:451` — one heap allocation per frame remains (nit)

`np.clip(...)` allocates a fresh temporary every iteration (F allocations). A single reusable scratch buffer keeps the semantics exactly and allocates once:

```python
scratch = np.empty(output_shape, dtype=common_dtype)
...
np.clip(frame, 0.0, 1.0, out=scratch)   # widening cast into out is safe
scratch *= 255.0
np.rint(scratch, out=scratch)
frames_u8[index] = scratch
```

Small, but it's free and it's the same idea the PR is already applying.

### 5. `tests/entrypoints/openai_api/test_video_api_utils.py:63` — this patches the global numpy module (nit)

`video_api_utils.np` **is** the `numpy` module object, not a module-local alias, so `monkeypatch.setattr(video_api_utils.np, "stack", fail_stack)` breaks `numpy.stack` process-wide for the duration of the test. It's restored by `monkeypatch` and pytest-xdist isolates by process, so it passes today — but it's a global mutation used to assert an implementation detail, and it will fail spuriously if a future refactor legitimately uses `np.stack` on a bounded slice. Prefer asserting the observable property (e.g. `tracemalloc` peak stays well under the full-video float size), or at minimum add a comment that the global patch is deliberate.
