## Verdict

The approach is sound and the transform is provably correct — I stubbed `torch_npu.npu_rotary_mul` with the rotate-half reference and confirmed the BSND round-trip is **bit-identical** to the BNSD path, and that the inbound `.contiguous()` is a no-op for the real caller (q/k arrive as `.view(B,S,N,D).transpose(1,2)` views, so transposing back recovers the original contiguous buffer). So the fix is cheap and safe for the path it targets.

But it ships a hand-transcribed CANN tiling rule as the gate for a fast path, and that rule doesn't hold up against a sibling call site in the same model. Combined with a `_load_source_module` shim in the test that leaves the actual new logic untested, this is **approve-with-required-follow-ups** rather than clean. It's already merged, so the items below are follow-up work.

## Blocking-severity follow-ups

### 1. The "shared" helper has exactly one caller; two identical BNSD sites are untouched — and one of them contradicts the predicate

`vllm_omni/model_executor/models/common/qwen3_code_predictor.py:260-261`

```python
cos = cos.unsqueeze(1)  # [batch, 1, seq_len, head_dim]
sin = sin.unsqueeze(1)
if current_omni_platform.is_npu():
    q = torch_npu.npu_rotary_mul(q, cos, sin)
    k = torch_npu.npu_rotary_mul(k, cos, sin)
```

This is the same fused op, same BNSD layout, same rotate-half mode. The code predictor re-prefills the full growing sequence each AR step (`qwen3_code_predictor.py:444` — "len 2 -> num_code_groups+1"), with `head_dim=128`, `num_attention_heads=16` (`configuration_qwen3_tts.py:198-200`), and batch = concurrency. At the **first** AR step, `seq_len=2`:

- `batch*heads = 4*16 = 64` vs `seq_len*8 = 16` at concurrency 4
- `batch*heads = 16*16 = 256` vs `16` at concurrency 16

`head_dim//2 = 64` is 32-byte aligned in bf16, so `_bnsd_rotary_shape_is_supported` returns `False` here — a *far worse* violation than the tokenizer decoder's (head_dim 64, 16 heads at `hidden_size=1024`). Yet the PR's own benchmark table shows c=4/8/16 completing without a `DoRotateHalfTiling` abort.

Exactly one of these is true, and the PR should state which:

- **The predicate is not CANN's real condition.** Then the fast path is being disabled for shapes that are fine, and the tokenizer crash's actual trigger is something else (or narrower) than `B*N <= S*8`.
- **The code predictor carries the same latent crash** and just wasn't exercised in this configuration. Then it needs the helper wired in — which is what the commit "Extract shared rotary fallback helper" implies but does not do.

`vllm_omni/platforms/npu/_310p/patch/qwen3_tts.py:184-185` is the same pattern on the 310P path and should be dispositioned alongside.

### 2. The tiling rule is uncited and silently version-coupled

`vllm_omni/platforms/npu/layers/rotary_embedding.py:15-17`

```
For the aligned-head-dimension branch, CANN requires
``batch * num_heads <= seq_len * 8``.
```

Both magic numbers — the `* 8` and the `32 // element_size` half-dim alignment — are reverse-engineered from `rope_rotate_half_tiling.cpp` with no reference to a CANN version, doc, or source line. The PR body says CANN 9.0.0; the code doesn't. Failure modes if CANN changes the tiler: the crash silently returns, or every shape permanently takes the transpose path, with no signal either way.

Please add the CANN version + source/doc reference to the docstring, and a `logger.warning_once` on the fallback branch so a perf regression is diagnosable from logs.

## Correctness

### 3. `ndim != 4` is conflated with "use BSND" and produces a garbage failure

`rotary_embedding.py:19-20` returns `False` for non-4D input, and `:44` treats `False` as "take the transpose path". For a 3-D tensor with `unsqueeze_dim=1`, `:51` transposes dims 1/2 and `:54` unsqueezes `cos` at dim 2 — I confirmed this raises `RuntimeError: The size of tensor a (4) must match the size of tensor b (8) at non-singleton dimension 3`, and for shapes where the broadcast happens to succeed it would return silently wrong numbers.

The current caller always passes 4-D, but this is now a shared module. Fix in `npu_rotary_mul_with_bsnd_fallback`:

```python
if unsqueeze_dim != 1 or hidden_states.ndim != 4 or _bnsd_rotary_shape_is_supported(hidden_states):
    return torch_npu.npu_rotary_mul(...)
```

so "shape I can't reason about" degrades to today's behavior rather than into the transpose path.

### 4. `rotary_embedding.py:57` returns a non-contiguous tensor

`output_bsnd.transpose(1, 2)` — verified non-contiguous. The current consumers tolerate it (`modeling_qwen3_tts_tokenizer_v2.py:365` HF `Cache.update`, and the eager/SDPA matmuls), but any NPU fused-attention consumer needs contiguous BNSD and will either copy implicitly or fail. Since the inbound `.contiguous()` at `:51` is already a no-op for the real caller, the symmetric and actually-useful placement is on the output. At minimum, document that the returned tensor is a view.

## Test coverage

### 5. The new logic has no direct test; the one assertion changed doesn't cover the bug being fixed

`tests/platforms/npu/test_310p_patches.py:538-547`

The test's `q = torch.zeros(1, 2, 3, 2)` is fp32 with `head_dim=2`, so `head_dim//2 = 1` against a `half_dim_alignment` of 8 — it takes the fallback because of the **alignment** clause, never reaching `batch*heads <= seq_len*8`. The `B*N` rule that is the entire point of this PR has zero coverage, and the fast BNSD path is no longer covered either.

The value assertions can't catch a broken transpose round-trip: `q` is all zeros and `k` all ones, so `assert_close(q_out, q + 1)` holds under any permutation of dims 1/2.

Add a dedicated test module (e.g. `tests/platforms/npu/test_npu_rotary_embedding.py`) with:
- `_bnsd_rotary_shape_is_supported` boundary cases: `B*N == S*8` (supported) vs `B*N == S*8 + 1` (not), across fp16/bf16/fp32 and aligned/unaligned `head_dim` (64 and 80 in bf16 are a good pair — I verified they split True/False).
- A fallback round-trip with **asymmetric** random data, asserting the result equals the reference `x*cos + rotate_half(x)*sin` computed in BNSD.
- One case that stays on the BNSD fast path, asserting `cos` reaches the op as `[B,1,S,D]`.

### 6. Minor: the module-loading shim

`test_310p_patches.py:492-498` loads `rotary_embedding.py` by path and injects it into `sys.modules`. It works (the tokenizer test passes locally: `1 passed, 6 deselected`), but it means the test is validating a hand-loaded copy of the module rather than the import graph. Acceptable given the file's `import torch_npu` at `:9`, but a real unit test that fakes `torch_npu` once and imports normally would be more durable.
