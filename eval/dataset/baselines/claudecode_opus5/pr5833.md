# Review: PR #5833 — docs: reorganize vLLM-Omni design navigation

## Verdict

**Approve with changes** — the reorganization is a net improvement and the scope discipline is good (only `.nav.yml` + `index.md`, no doc content touched, no URLs moved). It also quietly fixes two real orphans: `design/metrics.md` and `design/qwen3_omni_tts_performance_optimization.md` were previously not in `.nav.yml` at all, and `design/feature/vae_parallel.md` was listed twice.

But there is **one concrete rendering bug** in `design/index.md` that puts three unrelated docs under a "Quantization" heading, and **one nav entry that duplicates a page already in the nav**, which is both a semantic and a MkDocs-mechanics problem. Both are small fixes.

## Must fix

### 1. `docs/design/index.md:49-55` — Cache-DiT / TeaCache / Diffusion Continuous Batching render *inside* the Quantization section

```markdown
49  #### Quantization
50
51  - [Quantization Overview](../user_guide/quantization/overview.md)
52
53  - [Cache-DiT](feature/cache_dit.md)
54  - [TeaCache](feature/teacache.md)
55  - [Diffusion Continuous Batching](feature/diffusion_continuous_batching.md)
```

The blank line at L52 does not close the list — in CommonMark and Python-Markdown a blank line between items just makes the list *loose*. So all four bullets render as a single (extra-spaced) list under the `#### Quantization` heading, and the page ToC will show Cache-DiT / TeaCache / Diffusion Continuous Batching as children of "Quantization". Even if you read it as two separate `<ul>`s, they still fall under that heading, since the next heading is `## Infrastructure and Performance` at L57.

This also **contradicts `.nav.yml:133-136`**, where those three are siblings of Quantization under Diffusion Acceleration — so the sidebar and the landing page disagree about the structure this PR is establishing.

Fix — give the trailing three a heading of their own and put Quantization last so it doesn't swallow them:

```markdown
#### Caching and Batching

- [Cache-DiT](feature/cache_dit.md)
- [TeaCache](feature/teacache.md)
- [Diffusion Continuous Batching](feature/diffusion_continuous_batching.md)

#### Quantization

- [Quantization Overview](../user_guide/quantization/overview.md)
```

and mirror the same grouping in `.nav.yml:133-136`. As a side benefit this removes the loose-list spacing, so the list matches the tight lists elsewhere on the page.

### 2. `docs/.nav.yml:133` — `user_guide/quantization/overview.md` is now in the nav twice

It is already at `.nav.yml:76` under **User Guide → Features → Quantization → Overview**. Listing the same source file at a second nav location is problematic on two counts:

- **Semantics:** `docs/user_guide/quantization/overview.md` is a usage page (config entrypoints, hardware support matrices, per-model status tables). Placing it under **Developer Guide → Design Documents → Feature Design → Diffusion Acceleration** puts a user-guide page inside the design tree — exactly the "mixed documents with different audiences" problem the PR description says it is fixing. With `navigation.tabs` enabled (`mkdocs.yml:41`), clicking it also throws the reader out of the Developer Guide tab into the User Guide tab.
- **Mechanics:** MkDocs keeps a single `File → Page` back-reference, so a file listed twice is rendered once, under whichever nav occurrence constructed the surviving `Page`. The practical symptom is that the Quantization Overview page's breadcrumb/parent and its prev/next footer links get taken from the Design section (Skip-Softmax ← → Cache-DiT) instead of its User Guide siblings. I could not build to confirm this end-to-end (`mkdocs` isn't installed in this checkout and I have no network), so please verify by building and checking the footer nav on that page — but the fix below sidesteps it either way.

**Recommendation:** drop `.nav.yml:133` entirely. The cross-reference in `design/index.md:51` already gives readers the pointer, and that's the right place for a cross-audience link. Note also that `fail_on_warning: true` in `.readthedocs.yml` means it's worth knowing whether this emits a warning on RTD rather than finding out later.

If you keep it, at minimum retitle it so it's obviously a cross-link (e.g. `Quantization (User Guide)`), and confirm the rendered breadcrumb on the target page.

## Should fix

### 3. `docs/.nav.yml:116-121` — enumerating the connector directory loses auto-discovery

The previous entry was `design/feature/omni_connectors/` — a directory reference that awesome-nav expanded to whatever was in the directory. Replacing it with six hardcoded paths means the next connector doc added there will silently not appear in the sidebar (it'll only surface as an INFO-level "omitted from nav" line in the build, which nobody reads). This repo already has the idiom for keeping the glob while nesting it — see `.nav.yml:94`:

```yaml
      - Communication:
        - OmniConnector Implementations:
          - glob: design/feature/omni_connectors/*
```

The hand-written titles here (`Yuanrong Store Connector` for `yuanrong_connector.md`, etc.) are nicer than the H1s (`YuanrongConnector`), so if you want to keep them, put a `.nav.yml` inside `docs/design/feature/omni_connectors/` instead — that keeps the titles *and* keeps new files from being dropped.

### 4. `docs/.nav.yml:106-146` — hardcoded titles now shadow page H1s, and two already diverge

Before this PR the design nav carried no explicit titles; MkDocs derived them from each page's H1, so the sidebar could never drift. Every entry now has a hardcoded title, and two are already out of sync with the documents they point to:

- `.nav.yml:109` `Ray-based Execution` → `design/feature/ray_based_execution.md` H1 is **"Distributed utils"**
- `.nav.yml:146` `AsyncOmni Architecture` → H1 is **"AsyncOmni Architecture (Qwen3-Omni Example)"**

The nav titles are the better ones in both cases — but the effect is that the sidebar now *masks* a stale page title rather than fixing it. Clicking "Ray-based Execution" lands on a page titled "Distributed utils". Worth a one-line follow-up issue to fix those two H1s so the nav override becomes redundant rather than load-bearing.
