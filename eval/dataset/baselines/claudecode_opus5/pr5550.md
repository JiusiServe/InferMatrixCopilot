# Review: PR #5550 — Worker contracts and RPC plumbing for Scheduler-managed paged KV cache

## Verdict

**Approve with required follow-ups.** The scoping is genuinely well done: the transport shape (`NewRequestData.diffusion_kv_metadata` → optional 4th RPC arg → runner) is the right seam, the dense path is left byte-identical, and the "what W0 does not validate and who owns it later" section of the description is the kind of thing most staged PRs skip. The 16 new tests pass locally (`pytest tests/diffusion/diffusion_kv/ -q` → 16 passed).

Two things should be fixed before the W1 producer lands, because both are latent-until-then and will surface as confusing runtime failures rather than contract violations: the un-updated `ARDiffusionModelRunner.execute_model` override, and the total absence of DTO-local invariants on the new metadata classes (which the sibling DTOs from #5541 do enforce). Everything else is polish.

---

## Required

### 1. `ARDiffusionModelRunner.execute_model` was not updated — `vllm_omni/experimental/ar_diffusion/runner.py:237`

```python
def execute_model(self, req: OmniDiffusionRequest, kv_prefetch_job: KVPrefetchJob | None = None) -> DiffusionOutput:
```

This is the only `DiffusionModelRunner` subclass in-tree, and it overrides `execute_model` without the new parameter. `DiffusionWorker.execute_model` (`diffusion_worker.py:463-465`) injects `diffusion_kv_metadata=` as a keyword when metadata is present, so a `paged_scheduler` request routed to the AR-Diffusion runner raises `TypeError: execute_model() got an unexpected keyword argument 'diffusion_kv_metadata'`. That TypeError is then swallowed by the executor's blanket `except Exception` at `multiproc_executor.py:574` and returned as `DiffusionOutput(error="execute_model() got an unexpected keyword argument...")` — a stringified signature error surfacing as a user-facing generation failure.

It's unreachable today (no producer emits metadata), which is precisely why it will be missed until W1. Fix now: add the parameter to the override and forward it to `super().execute_model(...)`, or raise an explicit `NotImplementedError("ARDiffusionModelRunner does not support Scheduler-managed paged KV")` mirroring the style already used at `runner.py:281` and `runner.py:287`.

### 2. The new DTOs drop every invariant their Scheduler-side twins enforce — `vllm_omni/diffusion/diffusion_kv/metadata.py:24-57`

Compare with `diffusion_kv/request.py:13-89` from the merged #5541. `DiffusionKVContext` is `frozen=True` with a `__post_init__` that rejects empty `context_id`/`cache_role` and non-positive `num_tokens`; `DiffusionKVRequest.__init__` rejects negative `prefix_len`, non-positive `target_len`/`seq_len`, `prefix_len + target_len > seq_len`, and duplicate `context_id`s. The new `DiffusionKVSequenceMetadata`/`DiffusionKVContextMetadata` carry literally the same fields and check none of it, and are not frozen despite being described as "one allocation snapshot."

The description's validation-ownership argument is correct for *cross-object* checks — comparing against `SchedulerRequestState.diffusion_kv_requests` or rank-local `KVCacheConfig` really does need state W0 lacks. It does not cover *DTO-local* checks. The clearest example is referential integrity: `DiffusionKVSequenceMetadata.context_ids` is documented at `metadata.py:36-37` as referencing "request-scoped context allocations from the enclosing `DiffusionKVMetadata`," and nothing enforces it. That check needs zero external state — it is a set membership test inside one object. A typo'd or stale `context_id` today produces a silently wrong (or empty) context block table in W1, at attention time, far from the cause.

Suggested minimum on `DiffusionKVMetadata`:

```python
@dataclass(frozen=True)
class DiffusionKVMetadata:
    ...
    def __post_init__(self) -> None:
        context_ids = [c.context_id for c in self.contexts]
        if len(context_ids) != len(set(context_ids)):
            raise ValueError(f"contexts must have unique context_id values, got {context_ids}")
        sequence_ids = [s.sequence_id for s in self.sequences]
        if len(sequence_ids) != len(set(sequence_ids)):
            raise ValueError(f"sequences must have unique sequence_id values, got {sequence_ids}")
        known = set(context_ids)
        for seq in self.sequences:
            unknown = [cid for cid in seq.context_ids if cid not in known]
            if unknown:
                raise ValueError(f"sequence {seq.sequence_id} references unknown context_ids {unknown}")
```

plus the same local length/emptiness checks the twins already apply. `frozen=True` on all three also makes the "snapshot" claim real (note `block_ids: tuple[list[int], ...]` still has mutable inner lists — worth `tuple[tuple[int, ...], ...]` if immutability matters).

### 3. Field semantics are undocumented, and the tests model them inconsistently — `metadata.py:41-45`

`prefix_len`, `target_len`, `seq_len` have no field docs. `DiffusionKVRequest` documents them (`request.py:41-44`) and enforces `prefix_len + target_len <= seq_len`; the new tests use `prefix_len=4, target_len=2, seq_len=8` (`test_metadata.py:22-29`, `test_worker_contract.py:32-39`), leaving a W1 implementer unable to tell whether `seq_len` is meant to equal the sum, bound it, or be independent. Similarly, nothing in the class says the outer dimension of `block_ids` is native KV **cache-group** order — that's only in the PR description, which won't survive into the codebase. Add field docstrings.

Two smaller consistency points in the same block: `cache_role: str` is free-form where the set of roles is closed enough to be an enum, and `context_id: str` vs `sequence_id: int` is an unexplained asymmetry between two sibling identifiers.

## Should fix

### 4. The DLO fallback is silent and untested — `multiproc_executor.py:462,471`

`has_diffusion_kv_metadata` disables the DLO+AllGather DP broadcast for the entire wave whenever any request carries metadata. The fallback is functionally correct (the serial loop uses `exec_all_ranks=True`, so every rank still participates in each weight AllGather) but costs `dp_size`× redundant compute, with no log line and no test — `make_executor()` at `test_worker_contract.py:62-65` sets `enable_distributed_layerwise_offload=False`, so this branch is never exercised. Add a `logger.warning` on the fallback and a test. The inline comment should also state *why* (the broadcast RPC has one args tuple for N requests and no per-request metadata slot).

### 5. `cache_mode.value` assumes a normalized enum — `diffusion_model_runner.py:169-173`

`DiffusionKVCacheMode` is a `str, Enum`, and `OmniDiffusionConfig.__post_init__` (`data.py:933`) normalizes the field — so this is correct on the production path. But if a config ever reaches the runner unnormalized (a duck-typed config, as the tests themselves use at `test_worker_contract.py:45`, or a config path that skips `__post_init__`), the `is not` identity check is a false negative for the string `"paged_scheduler"` → it wrongly raises, and then `cache_mode.value` raises `AttributeError` instead of the intended `ValueError`. Normalize once (`DiffusionKVCacheMode(cache_mode)`) or use `==` and `getattr(cache_mode, "value", cache_mode)` in the message.

### 6. Batch path validates against a different config than it executes with — `diffusion_model_runner.py:638` vs `645`

`_validate_diffusion_kv_metadata` reads `self.od_config`, while `_execute_request_list` is called with the `od_config` argument. If those ever diverge, the mode gate is checked against the wrong config. Thread `od_config` into the validator.

### 7. Two overlapping identity checks with two different messages

`validate_new_request_data_identity` (`sched/interface.py:191-197`) and `_validate_diffusion_kv_metadata` (`diffusion_model_runner.py:175-178`) both assert `metadata.request_id == req.request_id`, and both run in the batch (`:637-641`) and step (`:751-754`) paths. Two error strings for one condition. Collapse into one helper.

### 8. The comment at `multiproc_executor.py:454-456` overstates what raising buys

Raising out of `execute_request` doesn't avoid conversion into worker output — the engine busy loop catches it at `diffusion_engine.py:461` and fabricates an error `DiffusionOutput` for **every** `scheduled_request_id` in the wave. So one malformed envelope fails all co-scheduled requests. Either fail just the offending request (append its `RunnerOutput` and continue) or reword the comment to say the goal is a distinguishable engine-level error rather than a per-request RPC error.

Worth noting: in-tree, envelope `request_id` always equals `req.request_id` (`base_scheduler.py:76`, `:114`, `step_scheduler.py:54`), so the first branch is purely defensive against injected schedulers. That's fine; it's cheap.

## Minor

9. **`multiproc_executor.py:457`** — the function-local import is unnecessary. `sched.request_scheduler` is already imported at module level (`:26`) and itself imports `sched.interface` at module level, so there is no cycle to break. Move it to the top-level block; it currently re-runs on every dispatch.

10. **Conditional-arg pattern** (`multiproc_executor.py:544-546`, `diffusion_worker.py:462-464`, `:1371-1373`) — three branches to append a positional/keyword arg only when non-`None`, in an RPC where both ends are always the same build. `kv_prefetch_job` is already passed unconditionally even when `None`. Always passing `diffusion_kv_metadata=metadata` would delete all three branches — and would turn finding #1 into an immediate loud failure instead of a latent one. If the conditional exists specifically to tolerate third-party runners with narrower signatures (which `test_dense_worker_call_does_not_extend_model_runner_signature` hints at), say so in a comment, because it isn't self-evident.

11. **`tests/diffusion/diffusion_kv/test_metadata.py:15-110`** — all three tests construct a dataclass and assert its attributes equal the constructor arguments; they exercise `@dataclass`, not this code. If #2 lands, rewrite them as invariant tests (unknown `context_id` rejected, duplicate `sequence_id` rejected, bad lengths rejected) — the CFG shared-context and branch-context scenarios are the right *scenarios*, they just need an assertion with teeth.

12. **Design asymmetry worth recording in a comment** — request mode transports metadata as an explicit 4th RPC arg (`multiproc_executor.py:546`), batch mode transports it implicitly inside `scheduler_output` where the runner validates and then discards it (`diffusion_model_runner.py:636-642`). Two transports for one payload. The description acknowledges this; the code should too, so W1 doesn't have to rediscover it.

13. **`diffusion_engine.py:191-208`** — a real fix (init failure previously leaked worker processes), well tested, but unrelated to "Worker contracts and RPC plumbing" and would have been cleaner as its own PR. Two notes on it: when the caller injects `scheduler=`, the engine now calls `close()` on an object it does not own (`:201`) — surprising ownership, worth documenting or restricting to self-created schedulers. And `_init_executor` (`:190`) sits outside the `try`, which is correct but reads as an oversight; a one-line comment would preempt the question.
