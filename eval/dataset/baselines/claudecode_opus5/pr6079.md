## Verdict

**Request changes** — the wiring is mechanically sound, but the change does not do what the PR says it does.

I verified the mechanical claims: the JSON parses, and both mark expressions from the test plan collect exactly one case (I ran both `--collect-only` commands in this checkout; `1 test collected` each). The `num_prompts`/`max_concurrency` pairing is valid under `tests/dfx/perf/scripts/run_benchmark.py:204-214` — with no `request_rate`, the QPS loop is a no-op and only the two-point concurrency sweep runs.

But the stated purpose — "a per-PR performance regression is not visible until the next nightly run" — is not achieved. Nothing in this repo compares perf metrics against a baseline, and the results this step produces are thrown away. As merged, the step is an expensive functional smoke test that largely duplicates the existing `Omni · MiniCPM-o 4.5 Online Test` ready step, at ~1 H100 slot + ~1 A3 slot per PR.

Also: `buildkite/vllm-omni-amd-ci` and `buildkite/vllm-omni-intel-ci` are red. Neither pipeline is touched by this diff and neither runs this config (the new JSON is only reachable through the CUDA/NPU mark expressions), so they're likely unrelated — but they're the gate and need to be green or explicitly waived.

## Major

**1. The step cannot detect a perf regression at all.**
`tests/dfx/perf/scripts/run_benchmark.py:266,283` — the only assertion is `assert_result`, i.e. `result["completed"] == num_prompt`. The `baseline` block is merely *recorded* into the result JSON (`tests/dfx/conftest.py:729-736`). And `--assert-baseline` (`tests/dfx/conftest.py:755`) is registered but **read by nothing** — grepping `getoption` across `tests/` turns up only `--run-level` and the accuracy options. So "we gate on request failures rather than baseline deltas" is accurate about behavior, but the implication that adding `--assert-baseline` later would close the gap isn't: that path doesn't exist yet.

Either land the metric-comparison path first (so this step earns its runtime), or retitle/redescribe this as what it is — a MiniCPM-o TTS serving smoke test with latency logging — and justify it against the online e2e step that already covers serving health.

**2. No artifact upload — the numbers are discarded.**
`.buildkite/cuda/test-ready.yml:238-239` and `.buildkite/npu/test-npu-ready.yml:27-28` export `BENCHMARK_DIR` but never upload. Every nightly perf step does (`.buildkite/cuda/test-nightly.yml:122-128`):

```yaml
- |
  set +e
  pytest -s -v tests/dfx/perf/scripts/run_benchmark.py --test-config-file tests/dfx/perf/tests/test_minicpmo_4_5_ready.json -m 'core_model and cuda'
  EXIT=$$?
  buildkite-agent artifact upload "tests/dfx/perf/results/*.json"
  exit $$EXIT
```

Without this, `BENCHMARK_DIR` buys nothing and there is no way to compare a suspect PR against a good run. Apply the same pattern in both files.

## Should fix

**3. The baseline block is copied from a different sweep and is wrong here.**
`tests/dfx/perf/tests/test_minicpmo_4_5_ready.json:53-79` takes the first two elements of each nightly array, but nightly's sweep points are (c=1, n=32) and (c=4, n=64) while this config runs (c=1, n=10) and (c=4, n=40). `request_throughput` in particular is not the same quantity, and a 10-request mean/p99 over shuffled seed-tts rows is a different sample. Nothing asserts these today, so it's latent — but whoever wires up assertion inherits thresholds that were never measured for this config.

Related: there is no `"A3"` bucket, yet this config is now actually run on A3 for the first time. `resolve_baseline_for_sweep` keeps every hardware bucket (`tests/dfx/conftest.py:631-641`), so the NPU run records H100 thresholds next to A3 numbers. Either regenerate H100 values from a real run of *this* config and add an A3 bucket, or drop `baseline` from the ready config entirely — it's documented as optional (`docs/contributing/ci/test_examples/l4_performance_tests.inc.md:193`).

**4. `num_prompts: [10, 40]` at `max_concurrency: [1, 4]` — the c=1 point is too small to mean anything.**
`test_minicpmo_4_5_ready.json:31-38`, with `percentile-metrics` including p99 (`:52`) over 10 samples. If the goal is regression detection, sample count buys more than concurrency breadth: one point at c=4 / n=40, or c=1 raised back toward nightly's 32, would be both cheaper and less noisy than the current two points.

**5. CUDA `source_file_dependencies` omits the harness the case depends on.**
`.buildkite/cuda/test-ready.yml:232-236` lists the JSON, deploy yaml, model dir and stage input processor — but not `tests/dfx/perf/scripts/run_benchmark.py`, `tests/dfx/conftest.py`, or `vllm_omni/benchmarks/` (the seed-tts dataset module and the `openai-chat-omni` backend this case exercises). The PR description claims the runner is gated on; it isn't. Consequence: a PR that breaks the benchmark harness skips this step, and the breakage surfaces on someone else's model PR. Add those three paths.

**6. NPU run on A3 is unproven, and the dataset fetch is a new cost there.**
The test plan's "Full run on A3 (1x)" box is unchecked. `test_minicpmo_4_5.json` is CUDA-only in nightly, and no NPU perf job uses `zhaochenyang20/seed-tts-eval` — the NPU TTS perf job deliberately uses the smaller `linyueqian/seed-tts-eval-subset`. `resolve_seed_tts_root` snapshot-downloads the whole `en/**` subtree (`vllm_omni/benchmarks/data_modules/seed_tts_dataset.py:133-137`) regardless of `num_prompts`, and the `a3_npu_2` preset mounts no HF cache volume (`.buildkite/common/ci_mirror_hardwares.yml`), unlike `h100_1` which mounts `/mnt/hf-cache`. Please land an actual A3 run before this gates PRs, or use the subset repo for the ready config.

## Minor

**7. NPU step has no diff gating.** `.buildkite/npu/test-npu-ready.yml:20-28` — no `source_file_dependencies`, so it takes an `a3_npu_2` node on *every* ready build, while its CUDA twin only runs when MiniCPM-o files change. `upload_pipeline.py` applies the same filtering to both pipelines (`_process_test_steps` is pipeline-agnostic), so the same dep list works. Add it unless always-on A3 coverage is intentional.

**8. Timeout convention.** `.buildkite/cuda/test-ready.yml:231` — every other step in that file wraps pytest in `timeout 20m bash -c "..."`; `timeout_in_minutes` appears exactly once in each ready file, both added here. A hung multi-stage server holds an H100 or A3 for a full hour and surfaces as a canceled job rather than a test failure. Prefer `timeout 30m bash -c "..."` to match neighbors, keeping `timeout_in_minutes` only as a backstop.

**9. Documented convention says perf JSON is L4.** This is the first `core_model` case in `tests/dfx/perf/tests/` (I checked all 27 configs). `docs/contributing/ci/test_writing_guide.md:57` states perf JSON uses `full_model` + a type marker, and `:145` heads the mark-field section "(L4 perf configs)". If perf configs are now allowed at L2, update those docs in this PR — otherwise this file reads as a mistake to the next contributor.

**10. Double execution on nightly main.** The step sits in the `E2E Test` group (`.buildkite/cuda/test-ready.yml:110`), and on `main` with `NIGHTLY=1` the ready pipeline is uploaded with `--e2e`, which keeps all E2E steps and disables diff filtering (`.buildkite/cuda/bootstrap-upload-steps.yml`). So nightly main builds run this on `h100_1` alongside the nightly MiniCPM-o perf job on `h100_1`. Small, but avoidable H100 time.

**11. Nit:** `"name"` is not set on the `benchmark_params` entry (`test_minicpmo_4_5_ready.json:24`); `l4_performance_tests.inc.md:193` item 4 recommends it for stable pytest ids and result keys. The nightly config omits it too, so purely optional.
