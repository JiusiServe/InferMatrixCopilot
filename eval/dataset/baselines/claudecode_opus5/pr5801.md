## Verdict

**Request changes (as a follow-up — this is merged with a red gate).**

The H3-side change is correct and a real win. I verified the RoPE rewrite numerically against an fp64 reference on GPU: the new path is not just equivalent, it's marginally *more* accurate than the code it replaces (max err vs fp64: `0.02297` new vs `0.02468` old, bf16, T=1000/H=8/D=128), and it's 2.5× faster on the op (1420 µs → 567 µs eager at T=16384/H=56/D=128; 320 µs → 220 µs under `torch.compile`, which is the default since `_compile_transformer` runs unless `--enforce-eager`). No dynamo graph break is introduced — I checked with `torch._dynamo.explain`, `graph_count 1, break_count 0`.

Two things need fixing, one of which is a cross-model regression that this PR introduces silently:

1. `norm.py:68` changes the default weight dtype from *ambient* to *hard fp32*, which disables the fused RMSNorm kernel for every other diffusion model that uses this layer.
2. `minimax_h3_transformer.py:361-365` leaves ~2.7× of the RoPE win on the table with an unnecessary slice+cat.

Everything else below is smaller.

## Blocking

### 1. `vllm_omni/diffusion/layers/norm.py:68` — new default `dtype=torch.float32` silently regresses every other model

Before: `nn.Parameter(torch.ones(hidden_size))` — `torch.ones` follows `torch.get_default_dtype()`, and the diffusion loader builds models inside `set_default_torch_dtype(self.od_config.dtype)` (`vllm_omni/diffusion/model_loader/diffusers_loader.py:358`). So in production the weight was **bf16**. After this PR it is **always fp32**, regardless of that context:

```
with set_default_torch_dtype(torch.bfloat16):
    RMSNorm(64).weight.dtype   ->  torch.float32     # was bfloat16 pre-PR
    torch.ones(4).dtype        ->  torch.bfloat16
```

That matters because `_forward_fused` → `vllm._custom_ops.rms_norm` requires weight dtype == input dtype. I confirmed on GPU:

```
rms_norm(out_bf16, x_bf16, weight_fp32, eps)
  -> RuntimeError: const_data_ptr<c10::BFloat16>, expected scalar type BFloat16 but found Float
```

which is swallowed by the bare `except Exception` at `norm.py:96` and falls through to `forward_native`. Measured cost at `[8192, 3072]` bf16 on this box: **fused 32 µs vs native 347 µs (~10×)**; at `[32768, 3072]`, 111 µs vs 1303 µs.

Affected call sites, all of which construct with the default: `z_image_transformer.py:291,292,438,439,441,442,764`, `wan2_2_transformer.py:395,396,528,529,555`, `hunyuan_image3_transformer.py:1757,1758`, `transformer_cosmos3.py`, `indextts2/.../gpt_fast/model.py`. Some of these are outside `_repeated_blocks` and therefore never compiled — e.g. `z_image_transformer.py:764` (`cap_embedder`, `_repeated_blocks = ["ZImageTransformerBlock"]`) — so they run eager and eat the full 10×.

There is also a plausible harder break on NPU: `forward_npu` (`norm.py:116`) now hands `torch_npu.npu_rms_norm` an fp32 `gamma` with a bf16 `x` for those same models, where it previously got bf16. And an fp32 param sitting among bf16 params can upset FSDP2 mixed-dtype all-gather groups under `use_hsdp`.

**Change to:**

```python
def __init__(self, hidden_size: int, eps: float = 1e-6, dtype: torch.dtype | None = None) -> None:
    super().__init__()
    # ``dtype=None`` follows ``torch.get_default_dtype()``, i.e. the loader's
    # ``set_default_torch_dtype(od_config.dtype)`` context. Pass an explicit
    # dtype only to pin gamma independently of that context.
    self.weight = nn.Parameter(torch.ones(hidden_size, dtype=dtype))
```

`torch.ones(n, dtype=None)` uses the default dtype, so this restores the old behaviour exactly while keeping H3's explicit `dtype=_BF16_DTYPE` working. Please also add the `dtype` param to a docstring — it controls both checkpoint storage *and* kernel selection, which is not obvious.

While you're in here: `norm.py:92-97` / `99-108` catching bare `Exception` per call is how this stayed invisible. A `logger.warning_once` in the `except` branch (or an explicit `self.weight.dtype == x.dtype` precondition instead of try/except) turns a silent 10× into a discoverable one, and stops real kernel bugs from being masked.

## Perf (the point of the PR)

### 2. `minimax_h3_transformer.py:361-365` — the slice + `cat` costs 2.7× of the RoPE win

`apply_rotary` already handles partial rotary: `vllm/vllm_flash_attn/ops/triton/rotary.py:188-190` allocates `empty_like(x)` and copies `x[..., rotary_dim:]` itself. `apply_rotary_emb_torch` (`rope.py:31-37`) does the same for the native path. So the manual split and re-concat is pure overhead — it materialises a second full `[T, H, 128]` tensor per call, twice per layer, 50 layers.

Measured, T=16384/H=56/D=128 bf16, bit-identical output (`maxdiff 0.0`, and `torch.equal` on the native path):

| | µs |
|---|---|
| current (`x[..., :96]` → rope → `cat`) | 566.5 |
| pass full `x` (rotary_dim inferred from cos) | **212.6** |

```python
def _apply_rope(self, x: torch.Tensor, freqs: torch.Tensor) -> torch.Tensor:
    """Rotate the first freqs.shape[-1] head dims; the kernel passes the rest through."""
    cos = torch.cos(freqs).to(x.dtype)
    sin = torch.sin(freqs).to(x.dtype)
    return self.rope(x, cos, sin)
```

Caveat: I could not verify that `mindiesd.rotary_position_embedding` supports `rotary_dim < head_dim`. If it doesn't, keep the split for the NPU branch only and say so in a comment.

### 3. `rope.py:124-127` + `minimax_h3_transformer.py:335,362` — `half_head_dim=False` buys nothing on CUDA/HIP

On CUDA the new flag only *undoes* itself: `_prepare_half_head_dim_cos_sin` slices the 96-wide cos back to 48 before handing it to a kernel that wants half-dim anyway. So the model computes `cos`/`sin` over 96 dims to throw half away, and the resulting `cos[..., :48]` is **non-contiguous** (`is_contiguous() == False`), which forces the `cos.contiguous()` copy at `vllm_flash_attn/ops/triton/rotary.py:180` on every call.

Using the existing default path (`RotaryEmbedding(is_neox_style=True)` with `cos = torch.cos(freqs[..., :rot_dim // 2])`) is bit-identical (`maxdiff 0.0`) and marginally faster (557 µs vs 567 µs). The flag's only genuine payoff is the mindiesd branch, where full-dim cos skips the `repeat` at `rope.py:64-65`. That's a legitimate reason to keep it — but please say so in the `half_head_dim` docstring, because as written it reads like a CUDA optimisation and it isn't.

## Correctness / robustness

### 4. `rope.py:168-177` — `forward_npu` never normalises `x` to 4D, unlike `forward_cuda`/`forward_hip`

`forward_cuda` and `forward_hip` both call `_ensure_batch_dim` (`rope.py:69-76`) precisely because omni call sites pass `[S, H, D]`. `forward_npu` → `apply_rotary_emb_mindiesd` does not, and H3 passes 3D (`x: [T, heads, head_dim]`). `rotary_position_embedding(..., head_first=False)` presumably wants `[B, S, H, D]`.

The new test at `tests/diffusion/layers/test_rope_broadcast.py:255-260` passes a 3D `x` of shape `(11, 3, 96)` and asserts it is forwarded verbatim — so it *locks in* the 3D contract against a stub, without establishing that mindiesd accepts it. Either add `_ensure_batch_dim`/`_restore_batch_dim` to `forward_npu`, or state explicitly that H3's fused RoPE is CUDA/HIP-only.

Related, pre-existing but now inherited by the base class: `apply_rotary_emb_mindiesd` hands the same op a 4D `[1, S, 1, D]` cos when `half_head_dim=True` and a 2D `[S, D]` cos when `False`.

### 5. `rope.py:124-127` — the halving assumption is silent

For `half_head_dim=False, interleaved=False` the code takes `cos[..., :D//2]`, which is only valid because `MiniMaxH3Rope.forward` returns `cat((half, half), -1)`. I confirmed the failure mode is silent: feed a non-duplicated 96-wide `freqs` and the output diverges by 10.97 with no error. Worth a one-line comment stating the layout contract (a debug assert is probably too hot for the inner loop).

### 6. `rope.py:125-126` — the `interleaved` branch is unreachable in-tree

`cos[..., ::2]` only runs for `interleaved=True and half_head_dim=False`. The only base-class user with `half_head_dim=False` is H3 (`is_neox_style=True`), and `RotaryEmbeddingWan` overrides every forward except `forward_xpu`/`forward_musa`, which route to its own `forward_native`. Untested and unused — cover it or drop it.

### 7. `rope.py:220-222` — `RotaryEmbeddingWan.__init__` shadows the base field

```python
super().__init__(is_neox_style=is_neox_style)   # sets self.half_head_dim = True
self.half_head_dim = half_head_dim              # then overwrites it
```
Works, but now that the base owns the field, forward it: `super().__init__(is_neox_style=is_neox_style, half_head_dim=half_head_dim)` and delete the second line.

## Comments and tests

- **`minimax_h3_transformer.py:174-176`** — stale: "torch.nn.RMSNorm upcasts reduced-precision inputs for the variance reduction, matching that accumulation semantic." `_norm` no longer returns `nn.RMSNorm`. The fp32-accumulation claim still holds (the vllm kernel accumulates variance in float; I measured identical max error vs fp64 for `nn.RMSNorm` and the fused path, `0.01562` both), but the comment should name `vllm_omni...norm.RMSNorm` and note that native multiplies gamma in fp32 while the fused kernel does it in bf16.
- **`minimax_h3_transformer.py:357-358`** — "In the unfused path, cos/sin are cast to the activation dtype before the elementwise math" is now unconditional, and the `# [T, rot_dim]` annotation on line 362 is misleading since the rope halves it internally.
- **`test_minimax_h3_parallel.py:73`** — `attention.rope._forward_method = attention.rope.forward_native` means the test never exercises `forward_cuda`, which is the path this PR exists for. Reasonable for a `cpu`-marked test, but there's no GPU-marked counterpart. A tolerance-based equivalence test against the old formula would pass — I measured max abs diff `0.03125` in bf16, well inside `rtol=2e-2`.
- **`test_rope_broadcast.py:242`** — the test calls `apply_rotary_emb_mindiesd` directly, so the actual new plumbing (`self.half_head_dim` threaded through at `rope.py:175`) is not covered. Route it through `RotaryEmbedding(is_neox_style=True, half_head_dim=False).forward_npu(...)` instead.
- **No test asserts the fused CUDA path is actually reached with `dtype=bf16`.** The NPU test checks gamma dtype; the CUDA path — the one H3 runs — has no equivalent, which is exactly why finding #1 slipped through. A test that monkeypatches `vllm._custom_ops.rms_norm` and asserts it was called (and that a default-constructed `RMSNorm` under `set_default_torch_dtype(bf16)` also reaches it) would pin both.
- **`test_norm.py:330,340`** — `captured["epsilon"] = torch.tensor(epsilon)` then `.item()`; just store the float.
- **Nit, `rope.py:104,111`** — `RotaryEmbedding.__init__` runs two `find_spec` calls per instance; H3 now creates 50 of them. `norm.py:12` already does the module-level `_HAS_MINDIESD = find_spec(...) is not None` pattern — worth matching.
