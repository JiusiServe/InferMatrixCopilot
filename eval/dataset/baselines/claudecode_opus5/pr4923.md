## Verdict

**Directionally right, with two behavioral regressions worth a follow-up.** Mirroring the Qwen3‑Omni graph layout is the correct fix for the nested-graph problem, and the async-output opt-in is a clean reuse of an existing, already-exercised path (`_should_use_async_omni_output` → `_maybe_run_eager_omni_postprocess_before_async_output`). I verified the pieces that usually break here and they hold: `("codes","audio")` and `("hidden_states","last")` are in `gpu_resident_buffer_keys`, so `_store_value` clones them (qwen3_tts_talker.py:426, gpu_model_runner.py:1953) — the graph's `weak_ref_tensors` outputs are not leaked into the per-request buffers; capture-time sampling params come from the same `subtalker_sampling_params` dict as the runtime kwargs, so the baked-in graph matches; and `cudagraph_num_of_warmups` is forced to 1 whenever not eager (vllm/config/vllm.py:1398), so the code predictor's lazy `_setup_compile()`/`_stacked_codec_embed` build always lands in warmup, not inside capture.

What I'd push back on: (1) any request carrying `seed` silently defeats the whole point of the PR and still isn't reproducible; (2) the `use_cuda_graphs` flip is unconditional while the outer wrap is conditional, so non-full-cudagraph GPU deployments lose MTP graphs with nothing replacing them; (3) `talker_mtp_graph_safe = True` is unconditional but the model is not graph-safe on NPU — and both the NPU and AMD gates are red. The yaml also carries an unexplained capacity retune plus comments that now contradict their own values.

## Comments

### 1. Seeded requests still take the N-scalar-calls path — and the seed is ignored anyway (blocking-ish)

`vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:346-350`

Setting `talker_mtp_accepts_per_row_generators = False` does **not** produce "a single batched MTP call" when a seed is present. It selects the opposite branch in the runner:

```python
# vllm_omni/worker/gpu_model_runner.py:1851
if (decode_batch_size > 1
    and any(generator is not None for generator in row_generators)
    and not getattr(self.model, "talker_mtp_accepts_per_row_generators", False)):
    ...  # one recursive scalar _talker_mtp_forward per row
```

`tts_local_seed` is populated for *every* request that passes `seed` through the OpenAI speech API (`vllm_omni/entrypoints/openai/serving_speech.py:3694`). So one seeded request in a batch of 64 turns each decode step into 64 sequential single-row graph replays — precisely the pathology this PR removes. And the reproducibility it buys is zero: `CUDAGraphWrapper.__call__` replays without re-reading `args/kwargs` (vllm/compilation/cuda_graph.py:346-361), so the `generator` handed to the size-1 call at gpu_model_runner.py:1884-1886 is discarded.

Suggested fix — make the *runner* drop generators when the call will be replayed, rather than making the model advertise a capability:

```python
# _talker_mtp_forward, after _cudagraph_mode is resolved
if _cudagraph_mode == CUDAGraphMode.FULL:
    if any(g is not None for g in row_generators):
        logger.warning_once(
            "talker_mtp is replayed from a captured graph; per-request "
            "tts_local_seed is not honored under full cudagraphs.")
    row_generators = [None] * decode_batch_size
```

This is strictly better than the static flag (large batches that fall back to eager keep their per-row seeding), and it lets you delete the `cudagraph_mode` read from the model *now* instead of deferring it to the `TODO(#4923)`.

Relatedly, the comment at lines 342-345 is inaccurate: seeding is dropped at **every** batch size under FULL replay, not only "when the decode batch > 1"; what batch > 1 additionally costs you is the batching itself. Existing test `tests/worker/test_omni_gpu_model_runner.py:317` documents exactly the fallback you're now opting into.

### 2. `use_cuda_graphs=is_npu()` is unconditional; the outer wrap is not

`vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_code_predictor_vllm.py:39`

"outer full-graph capture owns MTP" only holds when full cudagraphs are actually on. Cases where it isn't, on GPU:

- `enforce_eager: true` → `cudagraph_mode = NONE` (vllm/config/vllm.py:1391-1393). This is the configuration the bundled e2e tests run (`tests/e2e/offline_inference/test_qwen3_tts_base.py:40-42`).
- explicit `cudagraph_mode: PIECEWISE`.
- vLLM downgrading FULL→PIECEWISE/NONE in `initialize_cudagraph_capture` for attention backends whose `AttentionCGSupport != ALWAYS` (vllm/config/compilation.py:1399-1423) — a very plausible ROCm path.

In all of these, MTP now has *neither* inner device graphs nor an outer graph — a straight regression against main. Since the talker already computes the answer, plumb it down:

```python
# qwen3_tts_talker.py
graph_wrapped = self.talker_mtp_graph_safe and cudagraph_mode is not None and cudagraph_mode.has_full_cudagraphs()
...
# qwen3_tts_code_predictor_vllm.py
use_cuda_graphs=current_omni_platform.is_npu() or not graph_wrapped,
```

### 3. `talker_mtp_graph_safe = True` is not true on NPU

`vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:327`

On NPU the code predictor keeps its internal ACL graphs (`use_cuda_graphs=is_npu()`), and `npu_ar_model_runner._capture_talker_mtp_graphs` (vllm_omni/platforms/npu/worker/npu_ar_model_runner.py:136-187) will wrap and capture `talker_mtp` for any mode with `has_full_cudagraphs()` — i.e. the exact nesting this PR exists to remove, just moved to NPU. The only thing preventing it is the new `cudagraph_mode: PIECEWISE` pin in the bundled yaml, which does not cover CLI launches or custom deploy configs. Make the capability flag match reality:

```python
self.talker_mtp_graph_safe = not current_omni_platform.is_npu()
```

(keep the yaml pin as belt-and-braces). Note that `buildkite/vllm-omni-npu-ci` and `buildkite/vllm-omni-amd-ci` are both failing — those gates are the ones this change touches, and the capture path re-raises with a very identifiable message ("talker_mtp graph capture failed for a model that declared talker_mtp_graph_safe=True", gpu_ar_model_runner.py:576). Worth checking the AMD log against one more difference: `fish_speech_slow_ar.py:254` turns *off* torch.compile in its inner MTP module when `talker_mtp_graph_safe` is set (`_disable_compile_for_graph = True`) and skips `warmup_compile`; Qwen3‑TTS deliberately keeps Inductor on inside the captured region. If ROCm capture is failing, that's the first knob I'd try.

### 4. `enable_prefix_caching: false` is load-bearing but documented as the opposite

`vllm_omni/deploy/qwen3_tts.yaml:41-46`

The comment block still reads "Prefix caching on by default … any text repetition across requests … is a net throughput win", directly above `enable_prefix_caching: false`. Worse, this is not a tuning knob here: `_should_use_async_omni_output` bails when `self.omni_prefix_cache is not None` (gpu_ar_model_runner.py:1540), and `omni_prefix_cache` is constructed iff `cache_config.enable_prefix_caching` (gpu_model_runner.py:169). So anyone who re-enables prefix caching silently loses the async-output fast path this PR adds. Please rewrite the comment to say that, and consider a `logger.info_once` in `_should_use_async_omni_output` naming the reason it declined — a silent perf cliff keyed on an unrelated flag is the kind of thing that gets rediscovered in a profile six months later.

Same file, lines 6-8: "Stage 0 (talker) sets `max_num_batched_tokens=512` … small per-step batches keep first-chunk latency low" now sits above `max_num_batched_tokens: 32768`.

### 5. The capacity retune looks orthogonal and unexplained

`vllm_omni/deploy/qwen3_tts.yaml:38, 48, 70`

`max_num_seqs` 10→64 (both stages) and stage-0 `max_num_batched_tokens` 512→32768 are not graph/async changes. Two things make me want a justification in the PR rather than just a table:

- `qwen3_tts_high_concurrency.yaml:54`, the profile explicitly "validated for the c64 / PROMPTS=512 performance experiments", keeps stage-0 `max_num_batched_tokens: 512`. The new default now exceeds the tuned high-concurrency profile. Which one is right?
- Stage 1 goes to `max_num_seqs: 64` while still sharing `devices: "0"` with stage 0 at `gpu_memory_utilization: 0.3` and `max_num_batched_tokens: 65536` — the 2‑GPU high-concurrency profile deliberately uses S1=10 on a separate GPU. The line comment above it ("Tuned for Base voice clone; CustomVoice / VoiceDesign are TTFA-optimal at 1") is now stale too.

Second-order effect worth knowing: `max_num_seqs=64` raises `max_cudagraph_capture_size` to `min(max_num_seqs*2, 512) = 128` (vllm/config/compilation.py:703), so `_capture_talker_mtp_graphs` (gpu_ar_model_runner.py:533-541) now captures ~18 MTP graphs per boot, including sizes 72…128 that can never be dispatched for a 64-seq decode batch and that fall outside the code predictor's warmed power-of-2 buckets — `_padded_bsz`/`_bucket_pos_ids` miss (qwen3_code_predictor.py:558-563, 615-621), producing extra `dynamic=False` Inductor recompiles plus graph-pool memory for nothing. Clamping the capture loop to `size <= self.max_num_reqs` would be a cheap win.
