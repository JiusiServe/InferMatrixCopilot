# Review: [Perf][Qwen3-TTS] Drop default seed from qwen3_tts.yaml

## Verdict: **Correct fix, right diagnosis — approve on the substance, with one gate question and two things I'd add before calling it done.**

I traced the whole chain and it holds up:

- `serving_speech.py:3696-3706` copies any stage-0 deploy-level `seed` into `extra_args["tts_local_seed"]` (added by #4869), unconditionally for `_tts_model_type == "qwen3_tts"`.
- `gpu_model_runner.py:1821-1844` turns that into a per-row `torch.Generator`, and `qwen3_code_predictor.py:746-764` then takes the `generators is not None` branch: a Python loop of `torch.multinomial(probs[row:row+1], ...)` per row **per residual codebook group per step**, instead of one batched `torch.multinomial`. That is a real, structural cost, exactly as described.
- The default seed was the *only* trigger: nothing else in the repo writes `tts_local_seed`, `benchmarks/tts/model_configs.yaml` sends no `seed` in `task_extra_body` for either Qwen3-TTS entry, and no `seed` appears anywhere in `vllm_omni/config/`. So with the YAML lines gone, the nightly genuinely returns to `generators=None`.
- No test depends on the removed value: `tests/entrypoints/openai_api/test_serving_speech.py:3347` injects `seed=42` into a `SimpleNamespace` itself, and `tests/test_config_factory.py:1270` only asserts `model_arch`. The e2e Qwen3-TTS tests make no determinism/quality assertions. YAML still parses; stage 0 params are now `{temperature, top_k, max_tokens, min_tokens, repetition_penalty}`.

Comments below, most important first.

### 1. Two red platform gates run *this exact file* — confirm they're pre-existing

`buildkite/vllm-omni-npu-ci` and `buildkite/vllm-omni-amd-ci` are failing. That's the gate to point at, and it isn't obviously orthogonal here: `.buildkite/test-npu-ready.yaml:21` runs `tests/e2e/online_serving/test_qwen3_tts_customvoice.py`, which loads this deploy config at `tests/e2e/online_serving/test_qwen3_tts_customvoice.py:22-25`. A config-only diff is *usually* inert, but this diff changes the RNG state of the very job that's red, so "2-line YAML deletion, must be unrelated" isn't sufficient. Please link the pre-existing failures on `main` (or a re-run) rather than reasoning from diff size.

### 2. `vllm_omni/deploy/qwen3_tts.yaml:61` — leave a comment where the seed was

This is my main ask. The value has now survived three PRs (#1161 → #2383 → #4869) precisely because nothing in the file said why it was there, and nothing now says why it must not come back. Two aggravating factors:

- The file documents every other non-obvious choice in exactly this style — lines 41-46 (prefix caching), 57-59 (`min_tokens`, #4962), 76-82 (`max_num_batched_tokens`). A bare deletion is the one un-annotated decision in the file.
- `docs/configuration/stage_configs.md:274`, `:298`, and `:325` — the canonical `default_sampling_params` example users copy from — all ship `seed: 42`. Since the propagation is `qwen3_tts`-gated with no runtime signal, a copy-paste re-adds a ~40% throughput cliff that is only observable in the nightly, days later.

Suggested, at the end of the stage-0 `default_sampling_params` block:

```yaml
      # No default seed on purpose. #4869 propagates any deploy-level seed into
      # every request's extra_args["tts_local_seed"], which forces the residual
      # code predictor onto the per-row multinomial path (~40% audio_throughput,
      # ~2x TTFP/RTF at c>=16 — #4963). Per-request `seed` still gives
      # deterministic output and stays batched via #4889's per-row generators.
```

### 3. The PR body understates the scope — it also unseeds vLLM's own stage-0 sampler

The description frames this as returning to "the exact pre-07-04 hot path," but it's a superset of that. Pre-07-04, `seed: 42` was still set on `SamplingParams`, so stage 0 was already on vLLM's seeded sampler path. In the installed vLLM (0.26.0), any request with a seed puts an entry in `generators`, which (a) disables the FlashInfer and aiter fast paths outright (`vllm/v1/sample/ops/topk_topp_sampler.py:158-165` and `:230-236`, both falling back to `forward_native` with a warning) and (b) runs a per-row `q[i].exponential_(generator=...)` loop (`:201-202`).

That's *extra upside* — the recovery may beat the 07-03 baseline on the talker sampler, not just match it. But it's also a default-behavior change the body doesn't state: **the shipped profile's talker token stream is no longer reproducible run-to-run.** Please say that explicitly in the PR body / release notes, since it's user-visible for anyone who has been relying on the default profile's stability since #1161. (Per-request `seed` remains the documented escape hatch — `examples/online_serving/text_to_speech/README.md:425`.)

Two sub-points worth stating in the body while you're there:
- The stage-1 deletion (old line 92) is a strict no-op — `temperature: 0.0` means `all_greedy`, and `vllm/v1/sample/sampler.py:261` returns before touching generators; `qwen3_tts_code2wav.py` contains no `randn`/`Generator`/`manual_seed` at all. Good to include for consistency, but it recovers nothing.
- Consequence to accept knowingly: when a Qwen3-TTS e2e job goes red on the default profile, "same seed, same output" is no longer a debugging step. Given `min_tokens: 2` only guards the first two frames (#4962), short/degenerate generations now vary per run instead of being pinned. I don't think that blocks this — the throughput win dominates — but it should be a stated trade, not a side effect.

### 4. Add a cheap regression guard — there is none

This is the fourth PR to touch this value and the first three all moved it in the wrong direction. A ~6-line unit test costs nothing (no GPU, no model) and converts a silent nightly regression into a red PR. Next to `tests/test_config_factory.py:1270`:

```python
def test_qwen3_tts_deploy_has_no_default_seed(self):
    """A deploy-level seed puts every request on the per-row MTP
    multinomial path (#4869 / #4963). Keep it request-level only."""
    deploy = load_deploy_config(
        Path(__file__).parent.parent / "vllm_omni" / "deploy" / "qwen3_tts.yaml"
    )
    for stage in deploy["stages"]:
        assert "seed" not in (stage.get("default_sampling_params") or {})
```

Without this, "verified no test references the deploy-level seed" is true but cuts the wrong way — it means nothing stops the next reintroduction either.

### 5. Follow-up (not for this PR): the cliff is still silently reachable

`vllm_omni/entrypoints/openai/serving_speech.py:3696-3706` keeps #4869's propagation; this PR only removes its trigger in the shipped profile. Any custom deploy YAML with a `seed` still lands on the slow path with zero user-visible signal. A `logger.warning_once` in that block ("deploy-level seed forces per-row residual-MTP sampling; expect materially lower audio throughput — prefer request-level `seed`") would make a future reintroduction visible in server logs instead of in a nightly chart. Similarly, `examples/online_serving/text_to_speech/README.md:425` advertises `--seed 42` for determinism with no perf caveat — one sentence there would be honest about the cost. Both are cheap and complementary to the #4261 Gumbel-max work you cite.
