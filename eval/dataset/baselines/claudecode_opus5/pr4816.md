### 1. `vllm_omni/entrypoints/openai/api_server.py:754` — the fix is incomplete in pure-diffusion mode (blocking-ish, small fix)

In pure-diffusion mode this line sets `state.serving_tokenization = None`. `_create_speech_error_json_response` (`api_server.py:369`) does:

```python
err = base(raw_request).create_error_response(...)
```

`base()` now returns `None` instead of raising `AttributeError` — the exception type changed, the 500 did not. And this path is live in diffusion mode: `omni_init_app_state` installs a real speech handler at `api_server.py:784` via `OmniOpenAIServingSpeech.for_diffusion`, which calls `_init_speaker_storage()` (`serving_speech.py:438`). So `Omnispeech(raw_request)` is non-`None`, the 404 guard doesn't trigger, and the PR's own repro — `POST /v1/audio/voices` with undecodable audio → `ValueError` → `api_server.py:1483` — still returns a 500 on a diffusion server.

Same for `upload_voice`'s generic `except` (`:1486`), `delete_voice` (`:1518,1529,1539,1542`), and `list_voices` (`:1374`).

Fix it at the helper rather than at nine call sites:

```python
def _create_speech_error_json_response(raw_request, message, *, err_type="BadRequestError",
                                       status_code=HTTPStatus.BAD_REQUEST):
    base_server = getattr(raw_request.app.state, "serving_tokenization", None)
    if base_server is None:
        # Pure diffusion mode has no tokenization handler; build the OpenAI-shaped
        # error payload directly instead of 500-ing on a missing/None handler.
        resolved = int(getattr(status_code, "value", status_code))
        return JSONResponse(
            content={"error": {"message": message, "type": err_type, "param": None, "code": resolved}},
            status_code=resolved,
        )
    err = base_server.create_error_response(message=message, err_type=err_type, status_code=status_code)
    return _error_response_to_json_response(err, status_code=status_code)
```

This also makes the helper consistent with the defensive `getattr(..., None)` pattern the PR already applies at `:1157`, `:1248`, `:1286`, `:1329`.

### 2. `tests/entrypoints/openai_api/test_serving_speech.py:2352` — the regression this PR fixes is still untested

`_patch_api_server_base` does `mocker.patch.object(api_server_module, "base", return_value=fake_base)`. Every test that goes through `_create_speech_error_json_response` therefore never touches `app.state` at all — which is exactly why the original bug shipped, and why nothing here would catch it recurring on the next upstream rename.

The three lines this PR edits (`:2533`, `:2546`, `:2615`) do carry weight — they cover the direct `getattr` reads in `create_speech` / `create_speech_batch` / `create_audio_generate`. But no test exercises the real `base()`.

Add one test that does not patch `base`, pinning the contract to upstream:

```python
def test_api_server_upload_voice_value_error_returns_400_with_real_base(mocker):
```

The cheapest possible variant is a single assertion that `vllm.entrypoints.serve.instrumentator.basic.base(raw_request)` returns the object `omni_init_app_state` stored — that's the whole invariant, in one line. If you add the guard from item 1, pair it with a diffusion-mode case (`serving_tokenization = None` → still 400, not 500).

### 3. Version coupling — worth a sentence in the PR, and it points at the failing gates

The three failing gates — `buildkite/vllm-omni-{amd,intel,npu}-ci` — are precisely the non-CUDA platforms, and NPU is the one with a divergent pin: `docker/Dockerfile.npu.ci:2` uses `vllm-ascend:v0.23.0-4885d8e` while `docker/Dockerfile.ci:5`, `Dockerfile.rocm:1`, and `Dockerfile.xpu:91` all target v0.24.0. I couldn't verify v0.23.0's `basic.py` from this sandbox (no network), so I can't tell whether the NPU failure is this change or the usual platform noise — but that's a question for the gate, not for me to hand-wave. AMD and Intel both sit on v0.24.0 like the passing CUDA job, so those two are more likely unrelated. Please confirm the three red checks against this branch before merge, and note that `serving_tokens` at `api_server.py:1066` already uses the new-style name — so the target vLLM is at least partly post-refactor, which is consistent with this change being right.
