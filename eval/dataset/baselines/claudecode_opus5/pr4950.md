# Review: docs(recipe) — fix MiniCPM-o 4.5 curl TTS example

## Verdict: **Approve** (correct fix; three accuracy tightenings worth a follow-up)

The core claim is right, and I verified it against the code rather than taking it on faith:

- `chat_template_kwargs` is a declared top-level field on `ChatCompletionRequest` (confirmed via `vllm.entrypoints.openai.chat_completion.protocol.ChatCompletionRequest.model_fields`), and `model_config["extra"] == "allow"` — so the old payload's root-level `extra_body` key was silently swallowed as an extra field and never read.
- The only consumer of the flag is `request.chat_template_kwargs` (`vllm_omni/entrypoints/openai/serving_chat.py:373`, `:381`), via `_effective_chat_template_kwargs(request)` → `_preprocess_chat(default_template_kwargs=...)`. Nothing on that path looks at `extra_body`. So the old example genuinely could not set `use_tts_template`, and the new one does.
- Downstream, `llm2tts` only populates `tts_token_ids` / `tts_hidden_states` when it finds a `<|tts_bos|>` (151703) in `prompt + generated` (`vllm_omni/model_executor/stage_input_processors/minicpmo_4_5_omni.py:97-108`), and the talker short-circuits to a dummy forward without them (`.../minicpmo_4_5/minicpmo_4_5_omni_tts.py:406-409`). The causal chain in the PR description holds.

This is a real user-facing bug fix in a "known-good starting point" recipe, and it's the kind of thing that costs someone an afternoon. Good catch.

## 1. `recipes/OpenBMB/MiniCPM-o-4_5.md:221-222` — "returns silent audio" isn't what the code does

> `Without it, Stage-1 talker receives no TTS token span and returns silent audio (not text-only).`

The traced path doesn't produce silent audio — it produces no audio object at all:

1. `minicpmo_4_5_omni_tts.py:406-409` — missing `tts_token_ids` → returns `self._dummy_hidden_states(...)`, a bare tensor.
2. `minicpmo_4_5_omni.py:324-331` — the wrapper only fills `mm_out["model_outputs"]` when the talker returned a 2-tuple. A bare tensor fails `isinstance(talker_result, tuple)`, so `multimodal_outputs=None`.
3. `serving_chat.py:2506-2513` — `mm_output.get("audio")` is then `None`, and `_create_audio_choice` returns `self._create_error_response("Audio generation completed but no audio was produced.")`.

Worse, that error object is fed to `choices.extend(choices_data)` at `serving_chat.py:2174` — extending a list with a pydantic model iterates it into `(key, value)` tuples, which then fail `OmniChatCompletionResponse` validation. So the expected symptom is a 500, not a zero-amplitude WAV.

**Change:** either state the symptom you actually reproduced verbatim, or soften to something non-committal, e.g. *"Without it, the talker gets no TTS span and the request yields no usable speech."* The current sentence will be used as a diagnostic ("I got an error, so this can't be my problem"), so a wrong specific symptom is worse than a vague correct one.

**Worth a separate issue:** if you really did measure a 0-amplitude 12s WAV rather than an error, the likely mechanism is `minicpmo_4_5_omni.py`'s sibling at `stage_input_processors/minicpmo_4_5_omni.py:91-100` — when no 151703/151704 is present it falls back to the **MiniCPM-o 2.6** ids `151691/151692` and scans for them in a **4.5** token stream. If some unrelated 4.5 special token occupies 151691, that builds a bogus span and hands garbage to `generate_speech`. That's a latent bug independent of this docs PR, and it would explain the discrepancy above.

## 2. `recipes/OpenBMB/MiniCPM-o-4_5.md:107` and `:223-224` — the `extra_body` rule is stated too broadly

> `(curl does not flatten nested extra_body)` … `nested extra_body.chat_template_kwargs is ignored.`

The second sentence is exactly right. The first, as a general rule, is not: vLLM-Omni deliberately reads a root-level `extra_body` dict for the diffusion/image path — `serving_chat.py:441`:

```python
extra_body = getattr(request, "extra_body", None) or request.model_extra or {}
```

with the comment right above it making the curl-vs-SDK distinction explicit. Other recipes depend on that (`recipes/GLM/GLM-Image.md:75` sends `"extra_body": {"height": ..., "width": ...}` in raw curl and it works).

**Change** line 107 to scope the claim, e.g.:

> `field — the server reads chat_template_kwargs from the request root only, and does not unwrap a nested extra_body for it (unlike the image-generation params).`

Otherwise a reader will "fix" the GLM-Image recipe next.

## 3. `recipes/OpenBMB/MiniCPM-o-4_5.md:124-127` — response-shape note is correct; add the `index` trap and a way to actually check the WAV

The two-choices claim is confirmed: `chat_completion_full_generator` appends one batch of choices per finished stage output (`serving_chat.py:2124-2174`) — a text choice from stage 0 and an audio choice from stage 1.

Two additions that would make this section carry its weight:

- **Both choices are emitted with `index: 0`** (`serving_chat.py:2453` and `:2570`, each using `output.index`). Clients that key off `choice.index` will collide. Say so — "select the choice by whether `message.audio` is present, not by index" — which is exactly what the demo does at `examples/online_serving/minicpmo/gradio_demo.py:340-346`.
- The curl example as written dumps a multi-MB base64 blob into the terminal, so nobody can tell if it worked. Append the extraction step:

  ```bash
  ... | jq -r '.choices[] | select(.message.audio) | .message.audio.data' | base64 -d > out.wav
  ```

  That turns the smoke test into something with a pass/fail signal, which is the whole point of the "Verification" section.

## 4. Optional: mention the server-side default

`--default-chat-template-kwargs` is plumbed through (`vllm_omni/entrypoints/openai/api_server.py:904`), so an operator who always wants speech can serve with `--default-chat-template-kwargs '{"use_tts_template": true}'` instead of touching every client. One line in the **TTS trigger** note would save real integration pain.
