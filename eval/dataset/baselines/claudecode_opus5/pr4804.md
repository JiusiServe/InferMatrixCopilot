# Review of PR #4804 — [Feature] Support MOSS-TTS-Local-v1.5 Streaming

## Verdict

**Request changes (for the Realtime variant and the codec-selection/slot-lifecycle logic); the Local-v1.5 path itself looks reasonable.**

The core idea is right and the Local-v1.5 restructuring is a genuine improvement: moving the depth transformer into the runner-owned `talker_mtp` path, emitting per-step raw frames instead of re-sending the whole accumulation each step, and adding a persistent codec streaming session. The numbers in the test plan back it up.

What worries me is blast radius. Three things in this PR are not scoped to `moss_tts_local`:

1. `MOSS_TTS_REALTIME_PIPELINE` is switched onto the same always-streaming path, but `moss_tts_realtime.yaml` was not updated for it — that config gives the codec **one** stream slot against **eight** concurrent stage-0 requests, and the new code's response to slot exhaustion is to silently drop the request's audio.
2. `_build_codec` now tries the v2 class first for **every** MOSS-TTS variant, and `load_weights` was simultaneously made fatal — so a v1 checkpoint that mis-parses as v2 now hard-fails at load instead of falling back.
3. The codec's `forward` now *requires* `seq_token_counts`, and only the GPU dummy-run path was taught to supply it; the NPU twin was not. `buildkite/vllm-omni-npu-ci` is red — please confirm whether that's this.

None of the new streaming logic (chunk thresholds, slot lifecycle, finish sentinel) has a unit test, even though `tests/model_executor/models/moss_tts/` already has the CPU-only, weight-free pattern that would cover it — and the bug class here (a shared 8-slot batch) is exactly the cross-request audio-corruption class that `test_per_request_codes.py` was written to guard.

## Blocking

### 1. Realtime: one stream slot vs. eight concurrent requests → audio silently dropped

`vllm_omni/model_executor/models/moss_tts/pipeline.py:65` moves Realtime to `talker2codec_raw_async_chunk`, which unconditionally sets `codec_streaming=True` (`stage_input_processors/moss_tts.py:301,334`), so every Realtime request now takes `_decode_streaming_batch`.

`vllm_omni/deploy/moss_tts_realtime.yaml:42` still has stage-1 `max_num_seqs: 1` and no `codec_stream_slots`, so `_ensure_stream_session` (`modeling_moss_tts_codec.py:436-450`) allocates **1** slot — while stage 0 admits 8.

Failure path for requests 2..8: `modeling_moss_tts_codec.py:466-484` — no slot, so codes are buffered with a one-time warning; when the request finishes with no slot ever granted, `_finish_stream_request(request_id, session, None)` drops the buffer. The client gets a 200 with an empty/truncated audio stream and a `logger.warning` on the server. That's a silent wrong answer, not a degraded one.

Please either (a) bump Realtime's `codec_stream_slots`/`max_num_seqs` in the yaml to match stage 0, and (b) make exhaustion non-silent — fall back to the offline `batch_decode` path or fail the request. The comment at `:396` explains why offline decode is wrong for a delta stream, which is fair, but dropping is worse than erroring.

### 2. Realtime + legacy codec: `_MossCodecStreamSession` calls an API the v1 codec doesn't have

`_MossCodecStreamSession.__init__` (`modeling_moss_tts_codec.py:37-53`) calls `codec.streaming(batch)`, and `step()` calls `_set_streaming_exec_mask` / `_decode_frame`. The legacy vendored `MossAudioTokenizerModel` in `audio_tokenizer.py` has none of these (only `decode` / `decode_codes`). So if `_build_codec`'s fallback ever fires for a pipeline that now sets `codec_streaming=True`, the first streaming chunk dies with `AttributeError`.

Guard the streaming path on the codec actually supporting it (`hasattr(codec, "_decode_frame")`) and fall back to offline decode, rather than assuming v2.

### 3. `_build_codec` tries v2 first for all variants, and `load_weights` is now fatal

`modeling_moss_tts_codec.py:727-740` attempts `MossAudioTokenizerV2Config.from_pretrained(codec_path)` for every variant. Both config classes declare `model_type = "moss-audio-tokenizer"` (`configuration_moss_audio_tokenizer_v2.py:68`, `audio_tokenizer.py:37`), and HF's `from_pretrained` doesn't reject a mismatch — it warns. So a v1 checkpoint will very likely *parse* as v2, with v2-shaped defaults (`sampling_rate=48000`, `downsample_rate=3840`, `number_channels=2`, `quantizer_type="rlfq"`) filling in anything its `config.json` omits. The `except` never fires, the fallback is unreachable, and the new fatal check at `:679-688` turns the mismatch into a hard `RuntimeError` at load.

I'd make the class choice explicit rather than exception-driven — the config already carries a `version` field (`configuration_moss_audio_tokenizer_v2.py:88`, currently accepted and ignored), or add `codec_version` to the hf config / deploy yaml. If you keep the strict weight check (it's a good check — the old silent 50%-loaded behaviour produced structurally garbage audio), scope it so a failure can still fall back to the legacy builder instead of aborting.

Relatedly, `modeling_moss_tts_codec.py:701` — `inferred_channels = 2 if "v2" in codec_path.lower() else 1` sniffs the checkpoint *path string*. It's also effectively dead: both config classes always define `number_channels`, so the `getattr` default can only be reached if the value is falsy. Drop it or read it from the config properly.

### 4. Stream slots leak on abort because the finish hook uses a different id space

`on_requests_finished` (`modeling_moss_tts_codec.py:564`, called from `gpu_generation_model_runner.py:79-82`) receives **stage-1 internal** `finished_req_ids`. But `_stream_req_slots` is keyed by `_runtime_request_key`, which deliberately prefers `meta.req_id` (`modeling_moss_tts_codec.py:420-429`) — and the processor sets that to stage-0's `external_req_id` (`stage_input_processors/moss_tts.py:239-240`).

Those two are not guaranteed equal: `Orchestrator._build_next_stage_request` (`engine/orchestrator.py:1029-1039`) runs the stage-1 request through `processor.process_inputs` and then sets `external_req_id = req_id`, and the connector mixin treats internal vs. external as distinct throughout (`omni_connector_model_runner_mixin.py:272-287` cleans under *both* keys for exactly this reason). If they diverge, `on_requests_finished` finds no state, `continue`s, and the hook that exists to prevent slot leaks does nothing. After 8 client disconnects, every subsequent request hits finding #1's silent-drop path permanently.

Suggest making the two lookups agree — prefer `info["request_id"]` (the runner sets this at `gpu_model_runner.py:1729`, same id space as `finished_req_ids`), or resolve through `_request_ids_mapping` in the hook.

While there: the positional fallback key `f"moss-codec-stream-{index}"` (`:429`) is unsafe in streaming mode — batch index isn't stable across steps, so two requests can alias onto one slot. Raise instead of inventing a key when `codec_streaming` is set.

### 5. NPU dummy-run not updated for the new mandatory `seq_token_counts`

`modeling_moss_tts_codec.py:260-265` now raises when `seq_token_counts` is absent. `gpu_generation_model_runner.py:793-799` supplies it for the GPU dummy run; the NPU twin at `platforms/npu/worker/npu_generation_model_runner.py:773-783` was not given the same line, so profiling raises there. The real-execution paths are fine on both (`gpu_generation_model_runner.py:316`, `npu_generation_model_runner.py:299`) — it's only the dummy path that diverged. `buildkite/vllm-omni-npu-ci` is failing; please check whether this is the cause before merging further work on top.

## Should fix

### 6. `_finish_empty_streaming_requests` can never return anything

`modeling_moss_tts_codec.py:369-401` declares `outputs: dict[int, torch.Tensor]`, never assigns to it, and returns it. The three `for i, wav in ...items()` loops at `:249-250` and `:299-300` are dead. Make it return `None` and drop the loops — as written it reads like it might emit audio, which is the opposite of the documented intent.

### 7. `talker_mtp` hardcodes sampling params and silently ignores the ones it accepts

`modeling_moss_tts_talker.py:1521-1527` fixes `1.7 / 25 / 0.8` and takes only `do_sample` from the caller — `temperature`, `top_k`, `top_p` are accepted in the signature and discarded. The comment explains *why* the generic stage params shouldn't apply, which is reasonable, but silently dropping arguments is a trap. Read them from `subtalker_sampling_params` with these as defaults, or remove them from the signature.

Note this also changes audio sampling versus the old `make_omni_output` (`0.8 / 30 / 0.6`, `repetition_penalty=1.1`). That's a quality-affecting change riding along with a refactor — worth a line in the PR description.

### 8. Per-step GPU→CPU sync building a history that's never used

`modeling_moss_tts_talker.py:1548-1554` does `acc[-50:].long().cpu().tolist()` every decode step for every request, but `repetition_penalty=1.0` is passed at `:1568`, and `generate_frame` skips the history entirely when it's 1.0 (`modeling_moss_tts_local_depth.py:210-214`). So it's a blocking device sync per request per frame for nothing. Guard it: `if repetition_penalty != 1.0`.

Same area: `updated_acc = torch.cat([acc, new_codes])` at `:1590` reallocates the full accumulation every frame (O(T²) copies over an utterance), and `accumulated` now has no other consumer on this path. If it's only there for the (disabled) history, keep a bounded deque of the last 50 rows instead.

### 9. `codes.ref` is computed every step and ignored

`modeling_moss_tts_talker.py:1658-1673` builds `per_req_ref_codes` on every `make_omni_output` call, and `talker2codec_raw_async_chunk` explicitly declines to use reference codes (`stage_input_processors/moss_tts.py:263-268`). Drop the producer, or wire it up — right now it's per-step work with no consumer.

### 10. Hardcoded stop token in the pipeline config

`pipeline.py:97` — `"stop_token_ids": [151645]`, while `im_end_token_id` is config-driven everywhere else (`configuration_moss_tts.py:260`, `modeling_moss_tts_talker.py:1285`). A checkpoint with a different id gets no stop constraint and runs to `max_tokens`. The new warning at `modeling_moss_tts_talker.py:1381-1390` is a good canary, but the constraint should be derived from the config rather than duplicated as a literal.

### 11. Stream-session KV cache is allocated after memory profiling

`_ensure_stream_session` allocates lazily on the first streaming request, and `RingKVCache` (`audio_tokenizer_v2.py:436`) allocates `2 × slots × heads × capacity × dim` in **fp32** for every transformer layer in the codec, with `capacity = frame_rate × 10 s` at each stage's rate. For the decoder stack that is a large, slot-proportional allocation that lands *outside* the window vLLM profiled for `gpu_memory_utilization: 0.15`. With `codec_stream_slots: 8` this can be multiple GB. Please pre-allocate the session during `load_weights`/warmup so it's inside the profiled peak, and document the `codec_stream_slots` ↔ stage-1 `max_num_seqs` relationship in the yaml.

### 12. Benchmark: normalization failure produces a bogus WER instead of an error

`benchmarks/patch/patch.py:1243-1251` — on exception it falls back to the raw captured PCM, which for this model is 48 kHz stereo, and the WER path then treats it as 24 kHz mono (`seed_tts_eval.py:568` → `_pcm_s16le_to_f32_16k`). The result is a plausible-looking but meaningless WER. Prefer leaving `tts_output_pcm_bytes = None` so the item is counted as `no_pcm`.

## Minor

- `modeling_moss_tts_talker.py:1462`: `info_dict.get("max_new_frames", [-1])[0]` drops the defensive parsing the sibling Realtime path still has (`:471-477`) — a scalar value now raises `TypeError`. All current producers pass a list (`serving_speech.py:1886,1905,1994`), so this is latent, but the asymmetry is easy to re-break.
- `audio_tokenizer_v2.py`: the `@auto_docstring` decorators emit six `[ERROR] Config not found for moss-tts` lines to stderr on import — verified by importing the module standalone; the config module alone emits none. Worth dropping the decorators in the vendored copy.
- `configuration_moss_audio_tokenizer_v2.py:18` uses `PreTrainedConfig` (transformers v5 spelling) while the rest of the repo uses `PretrainedConfig` (`config/stage_config.py:17`, `config/config_factory.py:12`). Both resolve on the installed 5.14.1; picking one keeps grep honest.
- `stage_input_processors/moss_tts.py:20`: `_MOSS_AUDIO_PAD_CODE = 1024` duplicates the config-driven `audio_pad_token_id`.
- `modeling_moss_tts_codec.py:128-143`: docstring still says "24 kHz mono" and "all five variants share the same codec checkpoint" — stale after this PR.
- `audio_tokenizer_v2.py:508`: `MHAState.reset` zeroes the batch-shared `offset_cpu` regardless of `reset_mask`, so releasing one slot resets it for all. Inert with `weights_per_step=0` (the only consumer is `apply_weights_per_step`, which short-circuits at `len(modules) == 1`), but it's a real cross-slot leak if a checkpoint ever uses per-step weights. Likewise `RingKVCache.complete` scatters k/v for masked-out slots. If this is a faithful upstream port, a comment noting the divergence risk would help the next reader.
- The `qwen3_tts_request_seed` → `tts_local_seed` rename is applied consistently (grep finds no stragglers), and dropping the `qwen3_tts` model-type gate is a sensible generalization — but the new name reads model-specific for what is now a generic talker seed. `tts_talker_seed` would age better.

## Tests

`tests/worker/test_omni_gpu_model_runner.py` only tracks the key rename. Nothing covers: the initial-vs-steady chunk threshold (`stage_input_processors/moss_tts.py:287-292`), the empty-finish sentinel round trip, slot acquire/release/starvation, or `on_requests_finished`. Items #1 and #4 above are both testable CPU-only with a stub codec, in the same style as `test_per_request_codes.py`. Given that a slot mix-up here corrupts *another user's* audio, I'd want at least the slot-lifecycle test before this carries more traffic.
