# Review: PR #4849 — `[image][bugfix] Fix HunyuanImage3 bridge request batching`

## Verdict: **Approve** (correct, minimal, well-targeted) — with follow-ups that should not be dropped

The diagnosis is right and the fix is the right shape. I verified the failure path end-to-end:

- `StagePool.submit_initial` rejects list requests for `stage_type == "diffusion"` (`vllm_omni/engine/stage_pool.py:951-955`), which is the exact `ValueError` in issue #4832.
- The orchestrator only unwraps a single-element list on the *update* path — `if already_submitted and len(diffusion_prompt) == 1` (`vllm_omni/engine/orchestrator.py:1290`). On the first forward, `_next_stage_already_submitted` is `False` (`orchestrator.py:968`), so the old `[payload]` went straight into `submit_initial` and blew up. First AR→DiT hop for every HunyuanImage3 request — matches "0/96 requests completed" in the benchmark half of #4832.
- `c45ac74d` (#4079) converted `glm_image.ar2diffusion` to `dict | None` but left `hunyuan_image3` behind. This PR is literally the missing half of that commit, and the new code is a faithful mirror of `glm_image.py:215-243`.

I also confirmed the two things that could have made this fix lossy, and neither applies:

1. **Collapsing `prompt` to `prompt[0]` is safe.** `AsyncOmni.generate` rejects list prompts up front for any pipeline containing a diffusion stage (`vllm_omni/entrypoints/async_omni.py:310-316`), so `req_state.prompt` is always a single prompt here. Multi-image `/v1/images/edits` packs N images into *one* prompt's `multi_modal_data`, not N prompts (see the contract pinned by `tests/entrypoints/openai_api/test_image_server.py:2085`), so the multi-image IT2I case is unaffected.
2. **Dropping companions loses nothing today.** `HUNYUAN_IMAGE3_PIPELINE` has no `prompt_expand_func` (`vllm_omni/model_executor/models/hunyuan_image3/pipeline.py:19-48`), so `CfgCompanionTracker` never registers companions for this model; `diffusion_source_outputs` (`orchestrator.py:1211`) is always `[output]`. Worth noting the *old* code was actively wrong here anyway: a companion at index `i>0` would have been given `original_prompt = {}`, i.e. a 1024×1024 payload with an empty prompt.

Tests: both changed files pass locally — `tests/model_executor/stage_input_processors/test_hunyuan_image3_bridge.py` 7 passed, `tests/diffusion/models/hunyuan_image3/test_multi_resolution.py` 93 passed. No other caller or test references the old list contract (`ar2diffusion` grep is clean).

## Comments

### 1. The same bug is still live in `ming_flash_omni` — fix it centrally, not per-bridge

`vllm_omni/model_executor/stage_input_processors/ming_flash_omni.py:351` / `:435`

```python
) -> list[dict[str, Any]]:
    ...
    return [{"prompt": "", "extra": extra}]
```

`thinker2imagegen` is the `custom_process_input_func` for a stage whose `execution_type` is `StageExecutionType.DIFFUSION` (`vllm_omni/model_executor/models/ming_flash_omni/pipeline.py:127-138`). It takes the identical path — `already_submitted=False` → `submit_initial` → `ValueError: Diffusion list-prompt batch requests are no longer supported`. This PR fixes Hunyuan; Ming image-gen is still broken by #4079 in exactly the same way (and `return []` at `ming_flash_omni.py:379`/`:389` is the only branch the orchestrator handles today).

The per-bridge fix is fine as the hotfix, but this is now the second bridge to hit the same landmine and there is nothing preventing a third. Recommend a follow-up that makes it structural, in preference order:

- Drop the `already_submitted` condition at `orchestrator.py:1290` so a single-element list is unwrapped on both paths, and raise a bridge-attributed error (naming the processor) for `len > 1` instead of the generic `StagePool` message; **and**
- Convert `thinker2imagegen` to `dict | None`; **and**
- Add one shared contract test that walks every `StageExecutionType.DIFFUSION` stage's `custom_process_input_func` and asserts the annotated return type is not a list. That is what would have caught both.

### 2. `"Request 0"` in the log messages is now stale

`vllm_omni/model_executor/stage_input_processors/hunyuan_image3.py:165` and `:175`

```python
"[ar2diffusion] Request 0: ratio_index=%d out of range [0,%d), keeping prompt size %dx%d",
"[ar2diffusion] Request 0: AR generated %d tokens, ...",
```

The `%d`-for-`i` was meaningful when the function looped; the literal `0` is now pure noise and actively misleading in a multi-request log — every request logs "Request 0". The orchestrator already emits `req=%s` for this transition (`orchestrator.py:1233`), so just drop the prefix: `"[ar2diffusion] AR generated %d tokens, ..."`. (`glm_image.py` has the same wart at `:346`, `:353`, `:385` — pre-existing, don't feel obliged, but don't propagate it either.)

### 3. Companions are dropped silently; the docstring implies they're handled

`vllm_omni/model_executor/stage_input_processors/hunyuan_image3.py:101-104`

> `source_outputs` may include companion outputs, but the parent output is expected first

This reads as "companions are accounted for" when they are in fact discarded unread. For HunyuanImage3 that's correct-by-construction today (no `prompt_expand_func`, so companions can't exist), but if CFG expansion is ever added for this model the negative conditioning will vanish with no signal — compare `ming_flash_omni.py:392-401`, which does consume its `cfg_text` companion into `negative_thinker_hidden_states`. Either say so explicitly ("HunyuanImage3 does not register CFG companions; any extra outputs are ignored") or add a one-line `logger.debug` when `len(source_outputs) > 1`. Cheap insurance.

### 4. Test name overclaims relative to what it asserts

`tests/model_executor/stage_input_processors/test_hunyuan_image3_bridge.py:58-68`

`test_ar2diffusion_uses_parent_output_when_companions_are_present` builds two `SimpleNamespace` outputs with no `request_id`, so nothing about them is companion-like — the test asserts "index 0 wins", nothing more. That's a fine assertion, but under this name a future reader will believe CFG-companion semantics are covered. Either rename to `..._uses_first_source_output`, or give the second output a `request_id` carrying the CFG suffix so it becomes a real contract test. The `_source_output` helper at `:22-32` would need `request_id` added.

### 5. Minor: developer docs still teach the list contract

`docs/contributing/model/adding_omni_model.md:323-395` still shows `process_engine_inputs(...) -> list[...]` and `for next_input in next_inputs:` as the stage-transition model, and `docs/design/feature/diffusion_request_level_batching.md` documents the `forward()`/`DiffusionOutput` shape but never states the *input-processor* return contract. Stale docs are part of why #4079 missed two bridges. One sentence in the batching design doc — "a diffusion stage's `custom_process_input_func` must return a single prompt dict, or `None` to fail the request" — would pay for itself.
