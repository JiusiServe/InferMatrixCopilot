# Review: PR #5713 — [CI/Build] Speed up omni sleep-mode entrypoint tests with shared engines

## Verdict

**Approve with follow-ups.** The core idea is right and the measured win is real (2100s → 901s). Class-scoped engines paired with `loop_scope="class"` are the correct pytest-asyncio 1.4 construction, removing the per-test `engine.shutdown()` from `finally` blocks is the right consequence of the fixture owning lifecycle, and the renames leave no dangling references (`grep` for every removed symbol comes back clean). The CPU file passes locally (`16 passed`).

But the refactor buys some of its speed with assertions that can no longer fail, and it introduces cross-test coupling with no guard rail. Four things I'd want fixed as follow-ups, in order:

1. The merged diffusion test's VRAM assertions are vacuous (they measure the wrong process).
2. `_ensure_awake` swallows failures, so a wake failure surfaces as a wrong-test failure.
3. Nothing waits for VRAM release between the two class-scoped BAGEL engines anymore.
4. The `#4473` Repro A engine-level contract dropped from a merge gate to weekly-only.

Also: `buildkite/vllm-omni-amd-ci` is red. The AMD pipelines don't run `tests/entrypoints/` (checked `.buildkite/amd/test-amd-ready.yml` / `test-amd-merge.yml`), so it's very likely unrelated — but it's a listed gate and should be green or explicitly waived rather than assumed.

## Blocking-severity findings

### 1. `tests/entrypoints/test_omni_sleep_mode.py:340-373` — the merged VRAM block asserts nothing

`get_vram_info()` is per-**process** allocator state — its own docstring at line 46 says "Does not see other processes' usage." The diffusion stage runs out-of-process (`"runtime": {"process": True, "devices": "0,1"}`, line 181). The pytest process never loads BAGEL, so:

```python
vram_initial   = get_vram_info(1)["reserved"]   # ≈ 0.0
vram_sleeping  = get_vram_info(1)["reserved"]   # ≈ 0.0
vram_restored  = get_vram_info(1)["reserved"]   # ≈ 0.0
```

Which makes both assertions unconditionally true:

- Line 360: `reported_freed_gib > 14.0 or vram_sleeping < 5.0` → the right-hand side is `0.0 < 5.0`, so the ACK check is short-circuited away.
- Line 373: `abs(vram_restored - vram_initial) < 3.0` → `abs(0.0 - 0.0) < 3.0`.

This is inherited from the deleted `test_diffusion_vram_lifecycle_audit`, but the PR re-authors these lines and the docstring (315-317) presents them as preserved coverage, so it's worth fixing rather than carrying forward. The module already has the correct helper — `get_device_global_memory_used_gib` (line 68), whose docstring explicitly says to use it "when stages run in **separate worker processes**", and which sibling `test_cross_device_cleanup` uses for exactly this reason.

**Change:** either swap all three measurements to `get_device_global_memory_used_gib(0) + get_device_global_memory_used_gib(1)`, or delete the block and the ~4s of `asyncio.sleep` it carries and drop the `test_diffusion_vram_lifecycle_audit` bullet from the docstring. Real reclaim signal already exists in `test_cross_device_cleanup`, so deleting loses nothing.

Secondary: at lines 341/357/370, `torch.accelerator.empty_cache()` is called *outside* the `with torch.cuda.device(device_id)` block that `get_vram_info` opens and closes, so it empties the current device, not device 1. Moot while the values are unused, but fix it if you keep the block.

### 2. `test_omni_sleep_mode.py:111-116` — `_ensure_awake` swallows failures, misattributing the next test's failure

`_sleeping_tags` is engine-global, not per-stage (`vllm_omni/entrypoints/async_omni.py:1192-1194`), and `generate()` hard-rejects on it (`async_omni.py:514-517`). With function-scoped engines a failed wake died with the engine; with a shared class engine it leaks forward.

Concrete failure: if `test_cross_device_cleanup`'s `finally` wake fails, `_ensure_awake` logs a warning and returns. `test_diffusion_sleep_wake_generate` then fails on its **baseline** generate (line 333, before it has slept anything) with `RuntimeError: Generation rejected: Engine is partially or fully asleep` — pointing a debugger at the merged lifecycle test when the fault is in the previous one.

**Change:** make the failure explicit rather than silent. E.g. have `_ensure_awake` set a class attribute on failure and add a class-scoped autouse fixture that calls `pytest.fail("previous test left the shared engine asleep")` before the next test body runs. Anything that names the real culprit beats a warning line in a 900-second log.

### 3. `test_omni_sleep_mode.py:148-157, 169, 200` — no VRAM-release wait between the two shared engines

`clean_gpu_memory_between_tests` (removed from `pytestmark` at line 27) ran `run_pre_test_cleanup()` before every test, which is `wait_for_gpu_memory_to_clear(threshold_ratio=0.05, timeout_s=60)` (`tests/helpers/env.py:219-233`). That's the bulk of the reclaimed wall time, and dropping it to once per module is the right call — but the transition from `TestOmniLlmSleepMode` (BAGEL 2-stage on GPU0/1) to `TestOmniDiffusionSleepMode` (BAGEL TP=2 on GPU0,1) is now guarded only by `await asyncio.sleep(1.5)` at line 169. The deleted comment on that very line said "Subprocess / driver can lag releasing VRAM."

Spinning a TP=2 BAGEL load 1.5s after a 2-stage BAGEL shutdown is a plausible source of the `StageDiffusionProc died during handshake` failure already documented in the skip reason at line 393.

**Change:** replace the fixed sleep in both engine fixtures' teardown with `wait_for_gpu_memory_to_clear(devices=[0, 1], threshold_ratio=0.05, timeout_s=60)`. That's two bounded waits per module instead of eight, so the speedup survives essentially intact.

### 4. The `#4473` Repro A engine contract moved from merge gate to weekly-only

`test_level2_sleep_wake_raises` asserted `AsyncOmni.wake_up()` raises `NotImplementedError` after `sleep(level=2)` — the `_level2_sleeping` branch at `async_omni.py:1202-1208`. Its two replacements don't cover that:

- `test_invalid_server_control.py:109` runs only in `.buildkite/cuda/test-weekly.yml:48` ("Invalid parameters Test · H100", gated on `WEEKLY==1` or the `weekly-test` label).
- `test_omni_sleep_wakeup.py:178` mocks `wake_up` to raise the exception itself — as its own docstring concedes, it tests route propagation, not the engine contract. It cannot catch a regression in `async_omni.py`.

Net: a regression test that gated every merge now gates a weekly run. `_level2_sleeping` is pure Python bookkeeping with no GPU dependency.

**Change:** add a CPU-marked unit test that drives `AsyncOmni.sleep(level=2)` / `wake_up()` against a stubbed orchestrator and asserts the raise. Cheap, and it restores per-PR gating. A stronger version of the existing route test would build the app via upstream `build_openai_app` instead of a bare `FastAPI()`, which would also assert the 501 mapping on CPU rather than deferring it to weekly.

## Non-blocking

### 5. `test_omni_sleep_mode.py:500` vs `:27-29` — the new `core_model` mark collides with the module `advanced_model` mark

Verified by collection:

```
$ pytest tests/entrypoints/test_omni_sleep_mode.py --collect-only -q -m "core_model and cuda"
tests/entrypoints/test_omni_sleep_mode.py::test_pure_diffusion_sleep_wake
```

Before this PR the module contained zero `core_model` marks. So `test_pure_diffusion_sleep_wake` now runs in **both** the Ready per-PR "Entrypoints Test" (`test-ready.yml:104`, `-m 'core_model and cuda'`, l4_1, 30m) **and** the merge "Entrypoint Test with L4" (`test-merge.yml:68`, `-m "advanced_model and cuda and L4"`), because the module `pytestmark` keeps applying `advanced_model`.

The cost is modest — `tests/entrypoints/test_async_omni.py` already loads `riverclouds/qwen_image_random` on L4/core_model in Ready — but it's an unstated addition to per-PR time in a PR whose subject is reducing CI time, and running the same case in two pipelines is presumably not intended. Either drop `advanced_model` from the module `pytestmark` and mark the classes explicitly, or drop the `core_model` mark and keep it merge-only.

### 6. `test_omni_sleep_mode.py:318-320` — docstring overstates what was preserved

Two coverage drops are real, not relocations:

- `test_diffusion_model_sleep_tp` exercised the **default-config** `AsyncOmni(model=BAGEL, tensor_parallel_size=…)` path with auto-derived stages plus no-arg `sleep(level=1)` / `wake_up()`. `test_diffusion_sleep_wake_generate` uses an explicit `stages=[...]` engine and always passes `stage_ids=[0]`. The BAGEL auto-derived-stage path is now untested here. (`test_pure_diffusion_sleep_wake` still covers the no-arg API shape, but on a different model.)
- `test_pure_diffusion_scenario[2]` is gone. The PR says diffusion TP=2 "remains covered by `TestOmniDiffusionSleepMode`", but that engine is `model_class_name: "BagelPipeline"` (line 185) — a different pipeline from the standard diffusion path `qwen_image_random` exercises. TP=2 sleep/wake on the standard diffusion pipeline is dropped.

Both may be fine trade-offs for the wall-clock win. They should just be recorded as drops rather than as equivalences, so the next person reading line 318 doesn't believe the path is still gated.

### 7. `test_omni_sleep_mode.py:207` — `num_cards=1` on a test whose shared fixture needs two devices

`llm_engine` pins stage 0 to device `"0"` and stage 1 to device `"1"` (lines 133, 140). `cuda_marks` only attaches the `skipif(device_count < num_cards)` guard when `num_cards != 1` (`tests/helpers/mark.py:20-30`), so on a single-GPU box `test_llm_sleep_ack` doesn't skip — it errors during fixture setup while its two classmates skip cleanly. Pre-existing, but the class-scoped fixture makes the mismatch load-bearing. Make it `num_cards=2`.

### 8. `test_invalid_server_control.py` — three smaller points

- **Ordering (line 106):** the "keep this last" contract is enforced only by definition order. It survives `-k` and the single-param `_QWEN_IMAGE` grouping, but it silently breaks the moment someone appends a test below line 137. A `# --- do not add tests below this line: sleep(level=2) poisons the shared server ---` footer would make that visible at the point of edit, which the current header comment does not.
- **Test-plan / CI mismatch:** the PR documents `--run-level full_model`, but weekly actually runs `pytest -s -v tests/dfx/reliability/invalid_param_test/ -m "slow and H100"` with the default `--run-level core_model` (`test-weekly.yml:48`, and the default in `tests/helpers/fixtures/run_args.py:8`). Because the file is `@pytest.mark.diffusion`, `iter_omni_server` then substitutes a tiny model (`tests/helpers/runtime.py:3113-3115`) — so CI does not run `Qwen/Qwen-Image`. The test should still pass, since the 501 comes from the `_level2_sleeping` flag rather than from real discarded weights, but the "sleep(level=2) discards weights" rationale in the comment doesn't describe what CI executes, and the reported weekly result was from a different run-level than the pipeline uses.
- **`--enable-sleep-mode` blast radius (line 27):** it's now on for all 8 invalid-JSON cases, changing the allocator on a previously-passing server. The comment correctly notes those cases only hit request validation; worth keeping an eye on if they start flaking on startup.

### 9. `tests/entrypoints/openai_api/test_omni_sleep_wakeup.py:188` — the comment is factually wrong

> `# Re-raise in-process; default TestClient would wrap this as a 500 response.`

`raise_server_exceptions=True` **is** starlette's default. Passing it explicitly is good practice and I'd keep it, but the justification is inverted — someone trusting it could later "fix" the test in the wrong direction. Reword to something like "explicit for clarity: we want the exception to reach the test, not a JSONResponse."

The test itself is sound. I verified against `vllm_omni/entrypoints/openai/api_server.py:3497-3509` that the route awaits `wake_up` *before* clearing `sleeping_set`, so the `assert app.state.sleeping_stages == {0}` at line 195 is a genuine check, not a tautology. I also confirmed the 501 claim end-to-end: vLLM 0.26 registers `app.exception_handler(NotImplementedError)` (`vllm/entrypoints/openai/api_server.py:303`), `create_error_response` maps `NotImplementedError` → `HTTPStatus.NOT_IMPLEMENTED`, and `sanitize_message` does not strip parentheses, so the `"sleep(level=2)"` substring assertion at line 135 holds.
