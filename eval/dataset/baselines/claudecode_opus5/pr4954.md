## Verdict

**Request changes** (the production fix is right; the test-side relaxation is too broad and its own tests are dead in CI).

The one-line root cause is correctly diagnosed and correctly fixed: `tts_postprocess` writes `update_dict["codes"] = {"audio": frame}` (voxtral_tts.py:246) and every other Voxtral consumer (`stage_input_processors/voxtral_tts.py:19-31`) reads `codes.audio`, so `tts_preprocess` reading top-level `audio` was silently never getting feedback. I verified the producer/consumer round-trip locally — `tts_postprocess` → `tts_preprocess` now works end-to-end.

The problem is the second half of the PR. `_short_transcript_contains_expected` is applied unconditionally to *every* `/v1/audio/speech` test, and it accepts transcripts that are semantically wrong. This PR also deletes the sentence "Tests that do not opt in keep the strict behaviour" from the module docstring — that's an accurate description of what changed, and it's the part that needs rework. Both new assertion tests are also deselected by CI's marker filter, so nothing guards this.

Also note the two red gates (`buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci`) — the AMD ready job runs `pytest -sv tests/diffusion tests/model_executor -m 'core_model and cpu'`, which does pick up the new `test_tts_preprocess.py`, so those need to be green or explained rather than waved through.

## Findings

### 1. `tests/helpers/assertions.py:47-61` — the containment fallback accepts unrelated speech (blocking)

The rule is: expected text ≤ 15 chars, transcript has ≤ 2 extra words, and expected is a raw **character** substring of the transcript. I ran it against realistic transcripts; all of these currently **pass** the gate:

| transcript | expected | cosine | fallback |
|---|---|---|---|
| `how are you not really` | `how are you` | 0.45 | **passes** |
| `Bonjour how are you monsieur` | `how are you` | 0.33 | **passes** |
| `show are your dog` | `how are you` | 0.61 | **passes** |
| `hello world` | `hello` | 0.36 | **passes** |
| `how are you how are you` | `how are you` | 0.62 | fails |

Three separate defects:

- **Character-level containment**, not word-level: `"how are you"` is a substring of `"show are your dog"`. Split into words and check a contiguous word-subsequence instead.
- **`+2` extra words is a semantic escape hatch**, not a repeat-tolerance. `"how are you not really"` is a different utterance. If the target is "Whisper duplicated a leading word," check exactly that: transcript words, after collapsing adjacent duplicates, equal expected words. That would accept `"how how are you"` and reject every row above — and, notably, it would also accept `"how are you how are you"`, which the current rule rejects, so today's rule doesn't even cover the stated failure mode consistently.
- **`short_text` is dead logic**: since containment implies `len(expected_clean) <= len(transcript_clean)`, `min(...)` is always `len(expected_clean)`. Write `len(expected_clean) <= _SHORT_TEXT_THRESHOLD` and hoist the `15` to share the module-level constant with the duplicate at line 596 rather than hardcoding it twice.

The docstring says "very short speech clips," but nothing here looks at the clip — only at text length. Fix the wording or gate on audio duration.

### 2. `tests/helpers/assertions.py:658` — the fallback preempts the stronger opt-in check, and is not opt-in itself (blocking)

Two consequences of running this before escalation, unconditionally:

- `tests/e2e/online_serving/test_higgs_audio_v3.py:78` explicitly opted into `transcript_escalation_model: "large-v3"` for input `"Hello world."` (12 chars). That test now gets the loose containment check *first* and never reaches whisper-large — a `core_model` gate weakened by a PR that isn't about Higgs.
- Every other short-input speech test (`"Hello world."` across `test_higgs_audio_v2_expansion.py`, `"[SPEAKER0] hi"`, etc.) is silently relaxed.

Preferred fix: don't add a new global mechanism at all. `test_voxtral_tts_expansion.py:34-46` doesn't set `transcript_escalation_model`; adding it there reuses the existing, more precise, already-documented opt-in and solves the reported flake without touching any other model's gate. If you keep the containment path, make it opt-in via a `request_config` key and run it *after* escalation, not before.

### 3. `tests/helpers/assertions.py:659` — the rescue is unauditable

`print("short speech containment check passed")` omits both strings. The sibling check at line 609 prints `shorter_clean` and `longer_clean`. When this quietly rescues a run in CI, the log gives no way to tell whether the audio was actually correct. Include the transcript, expected text, and the failed similarity score.

### 4. `tests/helpers/test_assertions.py:1` — both new tests never run in CI

The file has no `pytestmark`. Every CPU job selects `-m 'core_model and cpu'` (`.buildkite/test-ready.yml:13,29`, `.buildkite/test-amd-ready.yaml:19,30`) and no conftest auto-adds platform markers. Confirmed:

```

```

Add `pytestmark = [pytest.mark.core_model, pytest.mark.cpu]`, matching `test_tts_preprocess.py:11`. (`tests/helpers/test_runtime_stage_cli.py` has the same gap — pre-existing, worth a follow-up.)

Coverage gap once they do run: there's no negative test for the over-permissive cases in finding 1. Add `"how are you not really"` and `"show are your dog"` as expected-failures — they're the cases that make the current rule unsafe.

### 5. `tests/model_executor/models/voxtral_tts/test_tts_preprocess.py:47-77` — the test doesn't lock the contract that broke

`FakeAudioGeneration.embed_multimodal` accepts anything and the test feeds a 2-D `torch.tensor([[1, 2, 3, 4]])`. The real payload is 3-D `(1, 1, num_codebooks)` — I confirmed by round-tripping the actual code:

```
postprocess update: {'codes': {'audio': torch.Size([1, 1, 37])}}
```

`embed_multimodal` asserts `audio_tokens.dim() == 3` (`voxtral_tts_audio_generation.py:1023`), so the test would pass against a payload the real model rejects. It only guards the key name.

Make it a producer/consumer round-trip instead — build the feedback dict by calling `tts_postprocess` with `{"codes": {"audio": [frame]}}` and pass the returned `update_dict` straight into `tts_preprocess` via `**update_dict`. That pins the exact coupling that regressed in #4527 and would have caught this bug. I verified this round-trip runs green with the current code.

Two smaller gaps: no case for `codes` present without `"audio"` (should fall through to the voice branch), and no case for both nested and legacy keys present (nested should win).

### 6. `voxtral_tts.py:214-217` — the legacy branch has no live producer, and the comment overstates what it does

No code path writes a top-level `audio` key for this stage: `tts_postprocess` writes `codes`, and the stage input processor only produces `codes.audio`. In-process request state doesn't survive a version upgrade, so "request state written before #4527" isn't a reachable scenario outside a version-skewed disaggregated deployment. Either drop the branch and its test, or replace the comment with the concrete deployment scenario that keeps it alive.

Separately, `info_dict.pop(...)` reads as "consume the frame," but `**info_dict` is a fresh dict per call and `_update_intermediate_buffer` (`gpu_model_runner.py:1968`) only merges — it never deletes. So nothing is consumed; correctness relies entirely on `tts_postprocess` overwriting `codes.audio` every step. Worth a comment, since a step that produces no `multimodal_outputs` will silently re-feed the previous frame.

### 7. `voxtral_tts.py:213` — two robustness nits

- `audio_tokens.to(input_ids.device)` assumes a tensor, but `embed_multimodal` itself handles a `list` of tensors (`voxtral_tts_audio_generation.py:1009`). A connector-delivered list payload would `AttributeError` before reaching that handling. Guard with `isinstance(audio_tokens, torch.Tensor)`.
- The feedback branch has no prefill guard, unlike the voice branch below it (which uses `_is_prefill_step`). If a request is ever preempted and recomputed, a stale `codes.audio` in the buffer would now hijack the prefill step and skip the voice-embedding overlay. That path was unreachable before this PR precisely because the key never matched. Gating the branch on `not self._is_prefill_step(info_dict, input_ids)` costs nothing and is strictly safer — feedback frames are only meaningful during decode anyway.
