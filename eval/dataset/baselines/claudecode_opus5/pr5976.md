# Review — PR #5976: Rebase to vLLM 0.27.0

## Verdict

**Request changes on the scheduler stale-drain fix** (already merged, so: follow-up fix needed urgently). The rebase itself is careful, well-annotated work — the `randomize_inputs`, `total_consumed`, `FusedMoEFactory`, `_copy_missing_attrs`, `is_interleaved`, `mm_hasher_algorithm`, and `MistralToolCall` moves are all correct mechanical adaptations, and the qwen3 forward-contract fix is genuinely well-reasoned and well-tested. But the headline fix — `c2b65233`, seeding the stale-output drain in scheduled-token units — **double-seeds the counter on one of its two discard sites**, and I reproduced it: it either swallows a valid new-segment frame (a hole in the codec stream) or trips its own `assert` and kills the engine core. That is the exact failure mode the commit set out to eliminate, and it is a live candidate for the WER regression the PR lists as still open.

Note on gates: `buildkite/vllm-omni-{amd,intel,npu,rebase}` are red. The XPU IR-priority default change (`vllm_omni/platforms/xpu/platform.py:139`) and the NPU `mamba_utils` import move (`vllm_omni/platforms/npu/worker/npu_generation_model_runner.py:14`) land in exactly those lanes and have no green signal behind them.

## Blocking

### 1. `num_stale_output_tokens` is seeded twice on the `replace_streaming_prompt` path

`vllm_omni/core/sched/omni_ar_scheduler.py:627-629` seeds the counter, then line 670 delegates to `_replace_streaming_session`, which seeds it **again** at `vllm_omni/core/sched/omni_scheduler_mixin.py:105`.

Reproduced against this checkout (one in-flight decode frame, `replace_streaming_prompt: True`):

```
seeded stale = 2 (expected 1)
late frame delivered?  False   stale left: 1
new-segment frame (2 scheduled tokens) -> AssertionError in update_from_output
```

With a 1-token new-segment frame it instead silently swallows a valid frame. This path is live: `vllm_omni/model_executor/stage_input_processors/minicpmo_4_5_omni.py:954` sets `replace_streaming_prompt = True` on every handoff, and `omni_ar_scheduler.py:663-671` is the consumer.

The new tests don't catch it because `tests/core/sched/test_omni_ar_scheduler_stale_drain.py:67` builds an update with **no** `model_intermediate_buffer` meta, so all four cases take the `super()._update_request_as_session` branch and only seed once.

Fix: make seeding happen exactly once per update. The cleanest shape given the two callers — `omni_ar_scheduler.py:611` and `omni_generation_scheduler.py:598`, the latter being a pure delegation to the mixin — is to drop the seed from `omni_ar_scheduler.py:627-629` and add it to `omni_generation_scheduler.py:604`'s caller, leaving `_replace_streaming_session` as the single site; **or** keep the AR seed and remove the mixin's, adding it explicitly to the generation scheduler. Either way, add a `replace_streaming_prompt: True` case to `test_omni_ar_scheduler_stale_drain.py` asserting `num_stale_output_tokens == num_in_flight_tokens` — that one assertion pins the invariant for both callers.

### 2. The drain's `assert` kills the engine core on any accounting divergence

`vllm_omni/core/sched/omni_ar_scheduler.py:339` and `vllm_omni/core/sched/omni_generation_scheduler.py:385`:

```python
request.num_stale_output_tokens -= num_tokens_scheduled
assert request.num_stale_output_tokens >= 0
```

The "commensurable by construction" argument in the comment is right in the happy path, but finding #1 is a live counterexample and this assert is what converts it from a dropped frame into a dead engine mid-serve. Given the counter is a best-effort discard signal, prefer:

```python
if request.num_stale_output_tokens < 0:
    logger.warning("stale-output drain underflow for %s (%d)", req_id, request.num_stale_output_tokens)
    request.num_stale_output_tokens = 0
```

Keep the strict form behind `if envs.VLLM_...` / a debug flag if you want the invariant pinned in CI.

## Should fix

### 3. The unconditional registry override extends the plain-vLLM path to Qwen2.5-Omni, which is not plain-vLLM safe

`vllm_omni/engine/arg_utils.py:107-116` drops the `if arch not in supported_archs` guard. On the installed vLLM the overlap is exactly two archs:

```
Qwen2_5OmniForConditionalGeneration
Qwen3OmniMoeForConditionalGeneration
```

Qwen3 was fixed (`qwen3_omni.py:144-148`, `qwen3_omni_moe_thinker.py:1512-1520`) and counterfactual-verified. Qwen2.5 got only half the treatment: `vllm_omni/model_executor/models/qwen2_5_omni/qwen2_5_omni.py:86` defaults `model_stage` so construction no longer raises `AttributeError`, but `forward` at line 326 still returns an `OmniOutput` unconditionally — and `OmniOutput` is a `NamedTuple` (`vllm_omni/model_executor/models/output_templates.py:9`), i.e. a tuple. Stock `GPUModelRunner` will index it with a tensor and produce the same `TypeError: only integer tensors of a single element can be converted to an index` this PR fixed for qwen3. So `vllm serve Qwen/Qwen2.5-Omni-7B` with vllm-omni installed goes from "upstream class, works" to "omni class, fails at profile_run".

Either run the same dummy-weight serve counterfactual for Qwen2.5-Omni and fix its non-staged return shape, or scope the unconditional override to the archs where omni actually needs to win (the comment cites `buffer_realtime_audio` on Qwen3-Omni specifically).

### 4. Generation stages still randomize dummy ids via the env-var path

`vllm_omni/worker/gpu_generation_model_runner.py:840-847` — the comment says "Never randomize generation-stage dummy ids", but the call is still `self.maybe_randomize_inputs(input_ids, inputs_embeds)`, and upstream's implementation randomizes whenever `VLLM_RANDOMIZE_DP_DUMMY_INPUTS and dp_size > 1`, independent of the kwarg. So the code2wav device-side assert (`code_embedding(codes + code_offset)`) still reproduces on any DP>1 deployment with that env var set. If the intent is "never", make it literal:

```python
contextlib.nullcontext(),  # generation stages never randomize; see below
```

### 5. `async_tokens_to_discard` writes are now dead — or worse

`omni_ar_scheduler.py:479` and `:634` still write it, and nothing in `vllm_omni` reads it (only `tests/core/sched/test_omni_ar_scheduler_streaming.py:124,221,243` assert the writes). Per the PR's own note, 0.27 removed it upstream, so on the target these are writes to a field with no consumer — a landmine for the next reader.

Worse on any vLLM that still drains it in `AsyncScheduler._update_request_with_output` (0.26, which is what's installed in this dev checkout and what these tests actually execute against): the new `continue` at `omni_ar_scheduler.py:348` returns *before* `_update_request_with_output` runs, so the old counter never drains, survives the stale window, and then eats the first valid new-segment token. Two overlapping discard mechanisms with one of them un-drained is exactly the "hole in the codec stream" shape.

Delete both writes and the three test assertions, or state in the comment which consumer keeps them alive.

### 6. Per-replica `VLLM_CACHE_ROOT` isolation mutates process-global state under the wrong lock

`vllm_omni/engine/stage_engine_startup.py:920-951` mutates `os.environ["VLLM_CACHE_ROOT"]` guarded by `_COMPILE_CACHE_ENV_LOCK`, but stage spawns run concurrently on a `ThreadPoolExecutor` (`vllm_omni/engine/stage_runtime.py:490`, sharing `_spawn_device_lock` at :144), and the replica-0 path never takes `_COMPILE_CACHE_ENV_LOCK`. A stage-2/replica-0 spawn that overlaps a stage-1/replica-3 spawn inherits the isolated root — the opposite of the intent, and nondeterministically. Pass the override into the child's env (`CoreEngineProcManager` env plumbing) rather than mutating the parent, or take the same lock on every spawn path. `tests/engine/test_stage_engine_startup_cache_env.py` is single-threaded and won't see this.

Secondary: each additional replica now keeps a full private compile cache forever (`~/.cache/vllm/omni_stage{N}_replica{M}/`); on a many-replica box that is N× disk with no eviction. Worth a note in the docstring at minimum.

## Minor

- **`omni_ar_scheduler.py:348` / `omni_generation_scheduler.py:396`** — the `continue` skips `_free_encoder_inputs(request)` and `chunk_transfer_adapter.save_async(...)` for the dropped frame, where the 0.26 mechanism only suppressed the token append. Encoder-cache entries for that step stay pinned until the request finishes. Probably acceptable, but it's a behavior change the comment doesn't mention.
- **`vllm_omni/patch.py:451-471`** — `sympy.cancel` on every negative `statically_known_multiple_of` query, uncached, inside inductor's hot path. `functools.lru_cache` on `(num, den)` (sympy exprs are hashable) would bound it. I confirmed the self-extinguishing probe works: on this checkout it logs `inductor factorable-divisibility patch: skipped (upstream already proves it)`.
- **`vllm_omni/entrypoints/openai/api_server.py:1001`** — `state.online_renderer.warmup()` is now unconditional where it was gated on `openai_serving_chat is not None` (i.e. `"generate" in supported_tasks`). Confirm it's a no-op for pure-diffusion / non-generate deployments; upstream parity is a reasonable defense but the gate genuinely changed.
- **`vllm_omni/benchmarks/patch/patch.py:1781-1784`** — if a real request raises, `asyncio.gather` propagates and `probe_task` is never cancelled (dangling task, probe keeps firing). Wrap the drain in `try/finally` with `probe_task.cancel()` + `suppress(CancelledError)`. `probe_outputs` is also collected and never used — intentional upstream parity, worth a one-line note.
- **`tests/e2e/accuracy/test_qwen_image.py:38` and `tests/diffusion/quantization/test_quantization_quality.py:518,537`** — both loosen a gate (SSIM 0.97→0.96 on the fallback path; both quality arms forced eager). Both are well-justified in comments, but forcing `enforce_eager=True` means the compiled path's quantization quality is no longer measured anywhere. Consider a separate compiled-vs-compiled arm so that coverage isn't silently dropped.

## What's good

The commit-level annotation discipline here is unusually high — nearly every hunk explains the upstream commit that forced it, the observed failure, and the reasoning. `qwen3_omni_moe_thinker.py:1512-1520` correctly handles the PP `IntermediateTensors` case before unpacking, and `tests/model_executor/models/qwen3_omni/test_qwen3_omni_forward_contract.py` pins all four corners of the return contract. The `_provably_factorable_multiple` patch is scoped soundly (can only add `True`, self-extinguishes when upstream regains the capability). The bagel `_validate_pixels` change (report all probes, paste-ready re-golden table) is the right instinct for a CI that doesn't upload artifacts. I ran the new CPU-only tests in this checkout: **105 passed** (4 stale-drain + 101 across the divisibility, cache-env, forward-contract, lingbot, and compile files).
