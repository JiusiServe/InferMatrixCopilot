## Verdict: **Request changes** — the four fixes are correctly diagnosed and three of them land cleanly, but fix #2 (the batch split-map race) only narrows the window it claims to close, and I reproduced the original hang against this exact HEAD.

The root-cause analysis in the description is excellent and I confirmed the two load-bearing claims independently:

- **Storage duplication is real.** `tensor._typed_storage()` returns a fresh wrapper per call, so pickle's memo does *not* dedupe views of one batch tensor within a single message — `tests/diffusion/test_diffusion_ipc.py::test_per_request_views_of_a_batch_tensor_do_not_ship_whole_storage` passes and demonstrates it. Fix #1 is right.
- **`result_mq` really is single-writer.** `MessageQueue.enqueue` mutates `self.current_idx` in `acquire_write` *and* writes the overflow marker to the ring before `local_socket.send_multipart` — two unsynchronized writers can both scramble the index and invert the marker/payload ordering. Fix #3 is right, and `_enqueue_result` now covers every worker-side call site (I checked: no bare `self.result_mq.enqueue` remains outside `_enqueue_result`).

Fix #4 is a clean, correct restructuring. Test coverage for the new code is genuinely good.

### Blocking

**1. `multiproc_executor.py:887-915` + `:648-651` — the batch split-map race is still open; requests still hang forever.**

The pump does check-then-act across an unlocked gap: it pops `_batch_split_map` under the lock (line 878-879), then unpacks SHM **outside** any lock (line 895), then re-acquires the lock to cache under `batch_id` (line 901-915). `execute_batch`'s new adoption check (line 648-651) only looks at `_completed_outputs`, which the pump hasn't populated yet. Interleaving:

1. Pump pops `_batch_split_map[batch_id]` → `None` (the early-arrival case).
2. Pump enters `unpack_diffusion_output_shm` — a multi-hundred-MB `/dev/shm` copy, so this window is *long*, arguably longer than the one the PR closed.
3. `execute_batch` pops `_completed_outputs[batch_id]` → `None` → registers `_batch_split_map[batch_id]`.
4. Pump finishes and caches the whole batch output under `batch_id`.
5. Nobody ever splits it. Every per-request waiter hangs until `_ASYNC_OUTPUT_TIMEOUT`.

Reproduced against HEAD by making `unpack_diffusion_output_shm` block until `execute_batch` has registered the map — your own new diagnostic prints the smoking gun:

```
STATE: async_output_id=batch-1/r0 waiting=0[] cached=1['batch-1'] unsplit_batches=1['batch-1'] pending_rpcs=0[]
HANG batch-1/r0
HANG batch-1/r1
HANG batch-1/r2
```

The existing regression test `TestBatchSplitDelivery::test_output_ready_before_split_map` can't catch this because the autouse `_mock_unpack` fixture makes unpacking instantaneous, so the pump always completes before `execute_batch` resumes.

Fix: make the pump's final decision atomic by **re-checking `_batch_split_map` under `_futures_lock` after unpacking**, rather than committing to the single-request branch at line 879:

```python
elif msg.kind == AsyncOutputKind.OUTPUT_READY:
    batch_id = msg.async_output_id
    # ... unpack first (unlocked), building output_result / exc ...
    with self._futures_lock:
        per_req_map = self._batch_split_map.pop(batch_id, None) if batch_id else None
        if per_req_map is None:
            # cache/resolve single-request under batch_id, as today
            ...
    if per_req_map is not None:
        self._deliver_batch_split(per_req_map, msg.output, msg.error)
```

`execute_batch`'s adoption path stays as-is and becomes the mirror case. Please add a test that makes the mocked unpack block on an event so the interleaving is actually exercised.

**2. `multiproc_executor.py:882-886` — batch-path SHM unpack failure is swallowed and ships raw handle dicts downstream.**

```python
try:
    unpack_diffusion_output_shm(msg.output)
except Exception:
    logger.exception("SHM unpack failed for batch %s", batch_id)
self._deliver_batch_split(per_req_map, msg.output, msg.error)
```

On failure, `msg.error` is `None`, so `_deliver_batch_split` happily resolves every per-request future with a `DiffusionOutput` whose `trajectory_latents` / `output` are still `{"__tensor_shm__": True, ...}` dicts. The failure then surfaces as an unrelated `TypeError` inside `postprocess_output`, far from the cause. The single-request branch you rewrote (lines 894-899) gets this right — the batch branch should match:

```python
    except Exception:
        logger.exception("SHM unpack failed for batch %s", batch_id)
        self._deliver_batch_split(per_req_map, None, msg.error or "SHM unpack failed")
        continue
```

**3. `ipc.py:131-138` — a zero-element view of a large storage now crashes packing.**

`max(view_bytes, storage_bytes)` is `storage_bytes` for an empty view, so it routes into `_tensor_to_shm` → `_array_to_shm` → `SharedMemory(create=True, size=0)`. Verified on this checkout:

```
view bytes 0 storage 4000000
RAISED: ValueError 'size' must be a positive number different from zero
```

Pre-PR this was unreachable (`view_bytes > threshold` implies non-empty). In `_async_output_loop` this aborts `pack_diffusion_output_shm` for the *whole* batch and turns it into an `OUTPUT_READY` error — i.e. this fix can itself fail the batch it was meant to save. One-line guard:

```python
if view_bytes > 0 and max(view_bytes, storage_bytes) > _SHM_TENSOR_THRESHOLD:
```

### Worth addressing

**4. `ipc.py:136` — packing is a heavier hammer than needed for the small-view case.** When `view_bytes <= threshold < storage_bytes`, the payload is genuinely small; the only problem is that it drags its storage through pickle. `val.detach().clone()` (or `.contiguous()` on a fresh storage) solves that without a `/dev/shm` segment per tensor per request. As written, a 32-request batch × k small trajectory tensors creates 32k shared-memory segments, and `_tensor_to_shm` calls `d2h_stream.synchronize()` once per tensor (`ipc.py:91`), so each one is a full stream barrier. A clone keeps the current inline behaviour for these and is strictly cheaper. If you prefer SHM for uniformity, that's defensible — but please say so in the docstring, because the current comment ("packing copies just the view") reads as if there's no cost difference.

**5. `diffusion_worker.py:983-1001` — `drain_async_outputs` stalls 10s per sleep if the background thread died.** `_async_output_loop`'s setup (line 943, `torch.accelerator.current_accelerator().type`) is outside any `try`, so if the thread dies at startup the pending counter monotonically increases and every sleep/wake cycle eats the full `_ASYNC_OUTPUT_DRAIN_TIMEOUT_S`. Add an early bail:

```python
thread = self._async_output_thread
if thread is None or not thread.is_alive():
    return True
```

Both call sites (`:1100-1101`, `:1163`) also discard the return value. That's the right pragmatic choice — proceeding beats hanging — but a comment saying so would stop the next reader from "fixing" it into a hard failure. Relatedly, the `finally` at line 977 is unreachable for the sentinel (the `break` at line 948 precedes the `try`), so the "Clamped: only items enqueued by `_return_result` are counted" comment describes a condition that can't arise; the `max(0, ...)` is fine as belt-and-braces but the comment is misleading.

**6. `multiproc_executor.py:915, :940, :999-1008` — `_completed_outputs` has no eviction and isn't cleared on shutdown.** When the engine's `asyncio.wait_for` times out at `diffusion_engine.py:343`, it cancels the wrapped concurrent future; the later `pending.done()` check is then `True`, so the pump falls into the `else` branch and parks a fully-unpacked output (a real CPU image/video tensor) in `_completed_outputs` that nothing will ever pop. `shutdown()` clears `_rpc_futures`, `_output_futures`, and `_batch_split_map` but not `_completed_outputs`. Given this PR is specifically about the timeout path, the recovery path leaking full outputs is worth closing — at minimum add `self._completed_outputs.clear()` at line 1008, and consider dropping the entry when the popped future is already cancelled.

**7. `diffusion_engine.py:818` — the sync `step()` path gets no diagnostics.** `fut.result(timeout=_ASYNC_OUTPUT_TIMEOUT)` raises a bare `TimeoutError` with none of the new `describe_pending_state` context. Since this is the same stall class, wrap it identically (factor the `except` block from lines 344-351 into a small helper).

### Nits

- `multiproc_executor.py:888-899`: the unpack now runs before the `if batch_id:` guard, so an `OUTPUT_READY` with no `async_output_id` unpacks (and thereby *unlinks*) its SHM segments and then discards the result. Shouldn't happen in practice, but hoisting the `if not batch_id: continue` check above the unpack is free.
- `multiproc_executor.py:657`: `except Exception` won't catch a cancelled future — `concurrent.futures.CancelledError` derives from `BaseException` on 3.8+. Not reachable today (cached futures are always pre-resolved), but `except BaseException` or an explicit `CancelledError` arm would be more robust.
- `diffusion_engine.py:344`: `asyncio.TimeoutError` *is* `TimeoutError` on 3.11+; the tuple is redundant (harmless).
- `docs/design/feature/async_diffusion_output.md`: "Draining typically completes within 10–50 ms under normal operation" is an unsourced number — either cite where it came from or drop the range. And the Batch Split paragraph asserts the early-arrival case is handled; please only keep that claim once finding #1 is actually fixed.
- `tools/pre_commit/check_pickle_imports.py:22-25`: the allowlist addition is well-justified and the rationale comment (pickle vs. `torch.save` storage dedup) is exactly the right thing to record. No objection.

Fixes #1, #3, #4 plus the drain hardening are solid work and I'd take them as-is modulo the empty-view guard. Fix #2 needs the atomic re-check before this can be relied on.
