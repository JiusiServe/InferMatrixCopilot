# Review: PR #5957 — [New Model] Support IndexTTS 2.5

## Verdict

**Approve with follow-ups (post-merge).** The IndexTTS 2.5 support itself is well-built: the two-stage split is faithful to the official path, the fail-fast payload contract is a genuine improvement over the previous "warn and synthesize a fallback" style, and the performance work (deferred D2H, varlen-packed DiT attention, ragged WaveNet reflect, per-request CFM noise) is careful and covered by real tests. 138 IndexTTS unit tests + 393 in the adjacent suites pass locally on vLLM 0.26.

My concerns are not with the new model. They are: (1) this PR silently changes runtime behavior of the **existing IndexTTS-2 (2.0)** model in at least six unconditional places, and the test plan only E2E-validated 2.5; (2) a few fail-fast conversions leave one silent-failure hole and one uninitialized-memory hole; (3) the PR carries a batch of unrelated vLLM-0.26↔0.27 / XPU-CI compat changes that make the red `buildkite/vllm-omni-amd-ci` gate hard to attribute.

## Blocking-severity comments

### 1. `mel_head.bias` can be silently uninitialized memory
`vllm_omni/model_executor/models/indextts2/indextts2_talker.py:233` and `:1240`

`ParallelLMHead._register_bias()` allocates the bias with `torch.empty(...)` — uninitialized. The load guard at `:1240` only checks that *some* parameter starting with `mel_head.` was loaded, which `mel_head.weight` alone satisfies. A checkpoint variant (or an FSDP key shape this PR's `_normalize_indextts_checkpoint_key` doesn't cover) that lacks `mel_head.bias` will load cleanly and then add garbage to every logit, with no error and no log line.

Note this switch to `bias=True` is unconditional, so it applies to IndexTTS-2 as well as 2.5.

**Change:** after the load loop, assert the specific key, not the prefix:
```python
if self.mel_head is not None and "mel_head.bias" not in loaded_params:
    raise RuntimeError("IndexTTS GPT checkpoint is missing mel_head.bias")
```
(or zero-fill `self.mel_head.bias.data` at construction so a missing key degrades to the pre-PR behavior rather than to noise).

### 2. A dropped Stage-0 payload still produces one sample of zero audio
`vllm_omni/model_executor/models/indextts2/indextts2_s2mel_decoder.py:364-371`

The `if not request_infos:` escape hatch is documented as the engine-init profiling path, but "no upstream payload" is exactly what a connector timeout or a dropped full-payload flush looks like at runtime. In that case a real request returns `{"audio": torch.zeros(1), "sr": 22050}` — the silent zero-audio outcome the PR description explicitly promises to eliminate everywhere else.

**Change:** gate on an explicit profiling signal (a dummy-run flag from the runner, or `input_ids` matching the synthetic profile batch) rather than on payload absence, and raise for a real request with no `model_intermediate_buffer`.

## Important comments

### 3. IndexTTS-2 (2.0) semantics change in six places, none E2E-validated
The test plan validated 2.5 only (H200, native 2.5 bundle). These changes all apply to 2.0:

| Change | Location | Old → new |
|---|---|---|
| `mel_head` bias | `indextts2_talker.py:233`, `:370` | bias dropped from logits → bias applied |
| Prefill span | `indextts2_talker.py:721` | pad/truncate → `ValueError` |
| Stage-1 tokenizer | `pipeline.py:46` | `tokenizer: "gpt2"` → none (relies on new `_TokenOnlyRenderer`) |
| Local asset lookup | `preprocess_utils.py:69` | Hub fallback for local dirs → `None` / `FileNotFoundError` |
| Missing w2v stat / emo+spk matrices / fbank / preload | `indextts2_talker.py:1113,1123,1010,1269`, `preprocess_utils.py:281` | `logger.warning` + degrade → raise |
| mel/latent length mismatch | `stage_input_processors/indextts2.py` | `min(...)` crop → `ValueError` |

The last one is the one I'd worry about most: the crop-to-common-length was presumably added because the two delta streams *can* differ by a row, and the test that asserted it (`test_talker2s2mel_full_payload_crops_mel_latent_to_common_length`) was rewritten into a rejection test. If that off-by-one is reachable in production, every affected 2.0 request now 500s instead of losing one frame.

**Ask:** run an IndexTTS-2 E2E smoke (same shape as the 2.5 one in the test plan) and post the result, or gate the newly-strict paths on `model_type == "indextts2_5"` where they change 2.0 behavior.

### 4. One-shot conditioning tensors are accumulated with CONCAT semantics
`vllm_omni/model_executor/stage_input_processors/indextts2.py` (module level — no `_FULL_PAYLOAD_REPLACE_KEYS`)

`accumulate_full_payload_output` concatenates any key whose value is a tensor with `dim() >= 2` unless the producer module declares it in `_FULL_PAYLOAD_REPLACE_KEYS`. `meta.S_ref` `[1,T,1024]`, `meta.ref_mel` `[1,80,T]`, and `meta.style` are all `dim>=2`, and they're emitted exactly once — on the step where `mel_code_count == 1`. That invariant holds on the happy path, but a preemption/recompute that re-runs prefill makes `mel_code_count == 1` a second time, and the two emissions get `torch.cat`-ed into a batch-2 conditioning tensor for a single request. That surfaces downstream as a confusing shape error (or worse, a silently wrong `ref_lengths`/batch pairing), not as a clear failure.

Every other producer module in the tree declares this constant explicitly (see `cosyvoice3.py:321`).

**Change:** add at module level
```python
_FULL_PAYLOAD_REPLACE_KEYS: frozenset[str] = frozenset({"meta.S_ref", "meta.ref_mel", "meta.style"})
```

### 5. `snapshot_mm_payload` does not copy CPU tensors, contradicting its own rationale
`vllm_omni/utils/mm_outputs.py:124-127`

The docstring says "CUDA graph outputs and runner input buffers may be reused on the next step, so retaining views is not sufficient" — but the CPU branch returns `tensor` (a detached view), not a copy. Runner-side CPU staging buffers are exactly as reusable as GPU ones. For IndexTTS 2.5 this is latent, because `info_update` builds its meta tensors with a fresh `.cpu().contiguous()`; the next model that opts into `omni_payload_at_request_end` while emitting a view into a persistent CPU buffer will silently read post-mutation values across decode steps.

**Change:** either clone on CPU too (the payloads that take this path are small metadata by construction), or narrow the docstring to state the contract explicitly: *producers must hand `snapshot_mm_payload` CPU tensors they already own.*

### 6. Prefix caching turns into a hard error, and nothing enforces it off
`vllm_omni/model_executor/models/indextts2/indextts2_talker.py:93-107`, `:721`

With `enable_prefix_caching: true`, a partial hit shortens the scheduled prefill span and `_require_exact_indextts_prefill_span` raises. Both deploy YAMLs set it false, and `_should_defer_full_payload_d2h` checks `omni_prefix_cache is None`, so the shipped configuration is safe — but the error message only names chunked prefill, so a user who flips prefix caching on gets an error that points at the wrong knob.

**Change:** mention prefix caching in the error text, and ideally reject `enable_prefix_caching` at model init for this architecture rather than at the first request.

### 7. `_TokenOnlyRenderer` changes renderer selection for every `skip_tokenizer_init` stage repo-wide
`vllm_omni/engine/stage_init_utils.py:1123-1147`

`build_stage0_input_processor` is used for **all** stages (`orchestrator.py:1492`), not just stage 0, so this now replaces the registry-selected renderer with a bare `BaseRenderer` subclass for every `skip_tokenizer_init` stage in the project. On the installed vLLM 0.26, `cached_tokenizer_from_config` already returns `None` for `skip_tokenizer_init` and `renderer_from_config` handles that, so the override appears to be there for a 0.27 accelerator-image difference.

**Change:** if this is a version-compat workaround, make it one — `try: renderer_from_config(...) except ...: _TokenOnlyRenderer(...)` — rather than an unconditional replacement of renderer selection for unrelated models.

## Minor

- **`indextts2_talker.py:566-569`** — the `duration_factor` range check runs for IndexTTS-2 too, but the message reads "IndexTTS 2.5 duration_factor must be between 0.5 and 2.0". Use `self.config.model_type` in the message.
- **`indextts2_s2mel_decoder.py:1007-1011`** — `_ref_mel_lengths` returns `[]` when any item is `None`, which then surfaces as a "reference-mel length/batch mismatch: lengths=0 batch=N" error. A missing `ref_mel` deserves its own message.
- **`codec/models.py:92-112`** — `EnhancedCodec.decode` is convolutional (`VocosBackbone` depthwise k=7, plus the `up` conv), so decoding a zero-padded batch couples a request's tail frames to the batch composition. The 2.0 RepCodec `vq2emb` path was pointwise and had no such coupling. The docs note waveform non-determinism across batches, but this is a conditioning difference rather than sampling noise — worth either masking padded frames or saying so explicitly.
- **`arg_utils.py:265`** — `tempfile.mkdtemp` for the patched config is never cleaned up (pre-existing, but this PR adds a new caller for a model whose *normal* path takes it, so it now leaks on every 2.5 launch).

## What's good

Worth saying plainly: the fail-fast contract (`_validate_payload_policy` / `_validate_payload_contract` / exact-span check) is the right direction and replaces several genuinely dangerous silent fallbacks. `_ref_mel_lengths` replacing the old `ref_mel.abs().sum()` heuristic removes a per-step D2H sync *and* a correctness hazard. The per-request seeded CFM noise (`_sample_cfm_noise`) is batch-invariant by construction, which is the hard way to do it and the correct one. The docs are honest about the limits (no beam search, Japanese TN gaps, batch-composition non-determinism) rather than overselling parity.
