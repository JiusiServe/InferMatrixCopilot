## Verdict: Request changes

The AAC priming fix is a genuine, verifiable improvement, and the profiler/`workdir` cleanups are good. But the two headline behavioral changes — clipping reference video **and** reference audio to the generated temporal window — land with no gate that can detect them going wrong, and the PR pays for its new coverage by deleting the only T2VA accuracy test. Both Buildkite gates are red on `86854432`; that has to be resolved first regardless of the comments below.

---

### 1. Reference conditioning is now silently truncated, and nothing added here validates it
`vllm_omni/diffusion/models/minimax_h3/reference_video.py:298`, `:394`, `vllm_omni/diffusion/models/minimax_h3/pipeline_minimax_h3.py:1726`

`MINIMAX_H3_MIN_OUTPUT_SECONDS = 4.0` (`pipeline_minimax_h3.py:117`) and `align_frame_count(96) == 107`, so the smallest output window is ~4.46 s. A user who supplies the maximum-allowed 15 s reference video plus a 15 s timbre-reference audio and asks for a 4 s clip now has ~70% of both references dropped — by `-frames:v` on the video and `waveform[..., :max_samples]` on the audio — with no log line and no error.

The added accuracy coverage cannot see this. `assert_video_similarity_metrics` (`tests/e2e/accuracy/helpers.py:303`) runs ffmpeg SSIM/PSNR on **video only**, and `_probe_audio` in the new test checks codec/sample-rate/channels, not content. So none of this PR's three audio changes (bounded standalone audio, bounded embedded audio, AAC priming) has an accuracy gate, and the one Ref2VA asset exercised is a *video-editing* case where reference ≈ output duration — precisely the case where `min()` barely binds.

What to change:
- Cite the model-card / reference-implementation line that specifies this bound in the commit message or a comment. It's obviously right for `[video editing]` Ref2VA; it is not obviously right for a voice-timbre reference (`<Audio 2>` in your own `REF2VA_PROMPT`).
- Add a waveform-level check to `_assert_official_video` (decode both to PCM, assert correlation/RMSE against the official reference). Without it the audio half of this PR is unguarded.
- Log at `info` when either bound actually clips, in `_transcode_reference_video` and `_encode_audio_conditions`.

### 2. Lossless RGB intermediate: unbounded temp disk, and a ~GB array held alive
`reference_video.py:296-314`, `:437-441`

Worst case is 362 frames × 1344×768 RGB ≈ 1.1 GB raw; `libx264rgb -crf 0 -preset veryfast` will write several hundred MB per request into the per-request tempdir. That file is then decoded in full **twice** — once at `reference_video.py:440` and again at `pipeline_minimax_h3.py:1274`.

Worse, `np.asarray(decoded_frames[source_index])` returns a *view*, so the full decoded array stays alive through `sampled_videos` for the rest of `encode_prompt`, per reference video. Fix:

```python
frames = [np.array(decoded_frames[i], copy=True) for i in indices]
del decoded_frames
```

And consider `-c:v ffv1 -level 3` in a `.mkv`/`.nut` instead — same losslessness, far cheaper than x264 lossless — or skip the intermediate re-encode for the Qwen path entirely.

### 3. `sample_reference_video_frames` mixes two frame-count sources
`reference_video.py:423` + `:440`

`indices` is built from `_probe_video(...)["frame_count"]` (ffprobe `-count_frames`, which is *itself* a full decode you're now paying for on top of the `load_video_frames` decode), but indexed into the decord/PyAV array. If the two disagree by one frame you get an `IndexError` or silently wrong samples. Since you decode the array anyway, derive the count from `len(decoded_frames)` and drop the `_probe_video` call — that also removes a whole decode pass. Note `test_ref2va_qwen_sampling_decodes_prepared_video_once` monkeypatches `_probe_video` to agree with the array, so it can't catch this.

### 4. Coverage regression: T2VA now has zero accuracy protection
`.buildkite/cuda/test-nightly.yml:430`, deletion of `tests/e2e/accuracy/minimax_h3/test_minimax_h3_t2va_similarity.py`

On main the T2VA case ran at SSIM ≥ 0.82 / PSNR ≥ 20.0. The commit sequence here is `c875d7fd tighten gate` → `f1cb3e8e remove case`: the bar was raised, T2VA failed the *new* bar, and the case was deleted. The stated reasoning ("this PR does not claim T2VA pixel-level alignment") justifies not raising the threshold; it doesn't justify removing the case. Keep T2VA in the new file at its original 0.82/20.0 thresholds (a third test, or parametrize the gate per case), or land a tracking issue and reference it in the file.

### 5. Nightly budget: two full-model runs in one 180-min step
`.buildkite/cuda/test-nightly.yml:428-434`

The step now does two 4-GPU × 50-step 1344×768 generations, two server cold starts (`--stage-init-timeout 1800`), **and** two separate HF snapshot downloads (`FL2VA/**` and `Ref2VA/**` are distinct multi-tens-of-GB partitions) under the same `timeout_in_minutes: 180` that previously covered one T2VA run. Please re-validate the budget or split into two steps.

### 6. Assets come from a vendor CDN on every run, behind a hard SHA assert
`tests/.../test_minimax_h3_i2va_ref2va_similarity.py:36-54`, `:147-163`

Two of the three assets live on `cdn.hailuoai.com`, not the model repo. A CDN rotation or re-transcode turns the nightly red with `Official ... reference changed` and no fallback; `timeout=120` is also tight for a multi-MB video, and nothing is cached between runs. Mirror the three assets into the model repo or an internal bucket.

Related: `MODEL_REVISION = "main"` (`:31`). The PR summary says "SHA-pinned model-card assets" — the *assets* are pinned, the *model* is not, so the quoted SSIM/PSNR numbers aren't reproducible across a repo update. Worth stating explicitly rather than letting "SHA-pinned" imply otherwise.

### 7. `snapshot_download` has no post-condition
`:111-116` — if the subfolder isn't literally `Ref2VA`, `allow_patterns` matches nothing, the function returns a snapshot root anyway, and the failure surfaces as an opaque server-start error much later. Add `assert (Path(snapshot_root) / component).is_dir()`.

### 8. The new `max_duration_seconds` guard is unreachable and mis-placed
`pipeline_minimax_h3.py:1210-1213`

The only caller passes `num_frames / 24` with `num_frames >= 107`, so `max_duration_seconds >= 4.45` always — `test_ref2va_audio_duration_validation_precedes_rank_branch` pins behavior that can't occur in production. Also, the guard sits *after* `if not audios: return None, []`, so if the intent is "validate before collectives", move it above that early return. `ValueError` is defensible for an internal invariant, but note everything user-facing in this path raises `OmniClientError`; a one-line comment saying which it is would help.

### 9. Dead fallback and now-stale metadata key
- `pipeline_minimax_h3.py:1324-1327`: `item.get("audio_duration_seconds", item.get("duration_seconds"))` — `prepare_reference_videos` always sets `audio_duration_seconds`, so the fallback is dead, and if it ever did fire it would silently restore exactly the unbounded behavior this PR removes. Use `item["audio_duration_seconds"]`.
- `reference_video.py:389`: `duration_seconds` now describes the *source segment*, while the prepared file is `-frames:v`-clipped to something shorter. Rename to `source_duration_seconds` or document the divergence inline — the next reader will assume it describes `prepared_path`.

### 10. `_encode_audio_conditions` skips the offload staging its siblings use
`pipeline_minimax_h3.py:1224`

`_encode_audio_condition` (`:1176`) and `_encode_video_audio_conditions` (`:1301`) both wrap in `self._component_on_device(self.audio_vae)`; the plural standalone path calls `self.audio_vae.encode_waveform` directly. Under `enable_layerwise_offload` / `enable_distributed_layerwise_offload` that runs against offloaded weights. Pre-existing, but you're editing this exact body and adding it to `_PROFILER_TARGETS` — good time to fix it.

### What's good

The AAC priming fix is correct and load-bearing — I verified it locally against the merge-base by exec'ing both versions of `media_utils.py` and muxing a 2048-sample ramp at 32 kHz:

- base: 3072 decoded samples, first 1024 all zeros
- this PR: 2048 decoded samples starting on the real signal, first packet `pts == -1024`

Two follow-ups:
- `vllm_omni/diffusion/utils/media_utils.py:194` is the shared server-side muxer (`vllm_omni/entrypoints/openai/video_api_utils.py:524`), so this shifts audio 32 ms earlier in **every** A/V MP4 the server emits, not just MiniMax H3. That belongs in the PR description — it's currently filed as a MiniMax H3 change.
- `tests/entrypoints/openai_api/test_video_server.py:270` asserts only `first_packet.pts < 0`. Assert the decoded sample count equals the input length (2048) instead or in addition — that's the property users actually experience, and it's what would catch a regression in the muxer.

Also good: dropping the per-frame ffmpeg invocation in `sample_reference_video_frames`, removing the unused `qwen_frames_*` workdir, and adding `_encode_audio_conditions` to `_PROFILER_TARGETS` (the profiler wrapper forwards `**kwargs`, so the new keyword-only argument is safe there).
