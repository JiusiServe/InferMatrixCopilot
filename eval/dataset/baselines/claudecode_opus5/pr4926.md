## Verdict: Request changes (follow-ups, since this is already merged)

The direction is sound and the wiring into `selector.py` / `DiffusionAttentionBackendEnum` is clean and consistent with the existing backends. But as written, the implementation doesn't actually deliver the bit-exactness guarantee that motivates it, it adds a large startup cost, and it bypasses the CUDA hardware guards that the surrounding selector is careful about. There's also ~150 lines of verbatim copy-paste. Findings below are ordered by severity; I verified the load path against the installed `kernels` 0.16.0 and the real Hub repos.

---

### 1. The hardcoded `version=1` defeats the PR's own purpose — `flash_attn_hub.py:96`, `:275`

`kernels` resolves `version=N` to the **head of branch `vN`**, not a pinned revision. I queried the repos:

```
kernels-community/flash-attn2 -> {1: v1@c269cc53, 2: v2@db6b5174, 3: v3@239bb21b}
kernels-community/flash-attn3 -> {1: v1@43f0bd26}
```

Loading FA2 with `version=1` makes the library itself print:

```
You are using version 1 of 'kernels-community/flash-attn2', but version 3 is available.
```

So a training stack that resolves v3 (the current default anyone would get) and a rollout that hardcodes v1 load **different compiled builds** — precisely the train↔rollout divergence this PR exists to remove. Two things needed: (a) make `repo_id` and `version`/`revision` configurable — `backend_kwargs` is already plumbed into `__init__` (`layer.py:87,102`) and is currently just discarded at `flash_attn_hub.py:88`; and (b) log the resolved commit SHA at startup so a run is auditable against the training side.

### 2. The three-step fallback cascade masks the real error and its last step is dead — `flash_attn_hub.py:96-103`, `:275-282`

`get_kernel(repo)` with neither `version` nor `revision` raises on current `kernels`:

```
ValueError: A kernel version or revision must be specified. Use `version=<major>` ...
```

(`kernels/_versions.py::select_revision_or_version`; confirmed on 0.16.0.) It isn't wrapped in a `try`, so when v1 and v2 genuinely fail — offline, or no build variant matching the local torch/CUDA — the user gets that ValueError instead of the actual cause (`FileNotFoundError: Cannot find a build variant for this system in ...`). The docs pin `kernels==0.14.1`, where the bare call still worked; the code shouldn't depend on that. Replace the cascade with a single `get_kernel(repo, version=<configured>)` and `raise RuntimeError(...) from e`, pointing at `DIFFUSION_ATTENTION_BACKEND=TORCH_SDPA` the way `flash_attn.py:171-176` does.

### 3. The kernel is fetched once per attention layer — `flash_attn_hub.py:92-103` + `layer.py:95-102`

`Attention.__init__` builds one Impl per module and nothing caches the load. Timed on this box with a **fully warm** HF cache:

```
call 0: 19.15 s   (cold)
call 1:  1.232 s
call 2:  1.188 s
```

`get_kernel` is uncached and re-resolves branch refs against the Hub API plus re-runs `snapshot_download` every call. A 40-block DiT with self+cross attention is ~80 modules → **~95 s of extra model-init time, 80 Hub round-trips, and 80 duplicate `Loading flash-attn2 kernel...` INFO lines** — and multiply the round-trips by TP/SP world size. The PR's own log already shows the unauthenticated rate-limit warning. Wrap the load in a module-level `@lru_cache` helper keyed by `(repo_id, version)` and use `logger.info_once`.

### 4. Hub backends skip every CUDA hardware guard — `vllm_omni/platforms/cuda/platform.py:122-146`

I simulated the selector across compute capabilities:

```
(7,5)  FLASH_ATTN -> SDPABackend          FLASH_ATTN_HUB -> FlashAttentionHubBackend
(10,0) FLASH_ATTN -> FlashAttentionBackend  FLASH_ATTN_3_HUB -> FlashAttention3HubBackend
(12,0) ...                                  FLASH_ATTN_3_HUB -> FlashAttention3HubBackend
```

- On sm_75 the local `FLASH_ATTN` correctly degrades to SDPA and `has_flash_attn_package` (`platform.py:42-46`) even excludes Turing/T4 by name — but `FLASH_ATTN_HUB` sails through to a repo that has no sm_75 variant, so you get a hard `FileNotFoundError` at model init instead of the "graceful fallback" the PR describes. Gate the HUB backends on the existing `compute_supported` and fall back to `TORCH_SDPA`.
- `platform.py:139` uses `compute_capability.major >= 9`, which admits Blackwell (major 10/12) while the warning text and the doc row both say "Hopper-class". Use `major == 9` or an explicit supported-SM set.
- `FLASH_ATTN_HUB` on Blackwell routes plain FA2 onto hardware that this very file says "plain FA2 will crash there" (`platform.py:63-67`). Decide explicitly — falling back to the platform default (CUDNN_ATTN) is the consistent choice.

Also, the `if backend_upper == "FLASH_ATTN_HUB" / elif ... == "FLASH_ATTN_3_HUB"` branches at `:126-136` are identical; collapse them.

### 5. Non-CUDA fallbacks force `FLASH_ATTN` even where it can't run — `npu/platform.py:110-116`, `xpu/platform.py:44-50`, `musa/platform.py:81-87`, `rocm/platform.py:91-97`

On NPU without `mindiesd` the auto-route picks SDPA, but the HUB→`FLASH_ATTN` rewrite hands back `FLASH_ATTN`, which then raises `ImportError` at forward time (`flash_attn.py:299-306`). ROCm happens to be covered by the `aiter` check just below; NPU/XPU/MUSA are not. Cleanest fix in all four files: after the warning, `return cls.get_diffusion_attn_backend_cls(None, head_size)` and let each platform's own availability logic decide.

### 6. Silently ignored under ring/sequence parallelism — `vllm_omni/diffusion/attention/parallel/ring.py:109-146`

Any non-SDPA `backend_pref` falls through to `ring_flash_attn_func`, i.e. the **local** FA2/FA3 install. With `ring_degree > 1`, selecting `FLASH_ATTN_HUB` silently computes with local kernels and the consistency guarantee is void, with no warning. At minimum log a `warning_once`; ideally thread the hub function through.

### 7. `_forward_varlen_masked` assumes varlen exists — `flash_attn_hub.py:147`, `:326`

The constructor only requires that *one* of `flash_attn_func`/`flash_attn_varlen_func` is non-None (`:108-109`, `:287-288`), but the masked path and the piecewise fallback `_run_varlen_dense` (`:21`) call `self.flash_attn_varlen_func` unconditionally. If only the dense func loaded, you get `TypeError: 'NoneType' object is not callable` mid-forward instead of a clear init-time error. Require varlen at init, or fall back to SDPA.

### 8. ~150 lines duplicated verbatim — `flash_attn_hub.py:74-226` vs `:253-406`

`FlashAttentionHubImpl` and `FlashAttention3HubImpl` differ only in the repo id and two log strings; the two Backend classes differ only in `get_name`/`get_impl_cls`. Collapse into a base with `_REPO_ID` / `_KERNEL_LABEL` class attributes. Every future fix currently has to be made twice — which is already visible in the two recent fixup commits.

### Test gaps — `tests/diffusion/attention/test_kernels_hub.py`

- **Only the trivial path is covered.** `test_kernels_hub_execution` exercises dense, unmasked, `causal=False`, `batch=1`. The masked varlen path (`_forward_varlen_masked`) and the piecewise path — including the `_run_varlen_dense` fallback that commit 332da8f2 was added specifically to fix — have **zero** coverage. Add a case with a 2D `attn_mask` containing padding and one with `full_attn_spans`, both compared against SDPA.
- **`k = q.clone(); v = q.clone()` (`:63-65`) is degenerate.** Use independent `randn` for q/k/v so a wrong `softmax_scale` or a layout mistake actually shows up in the diff.
- The fallback test never asserts the **positive** case (kernels importable at sm_80 → `FLASH_ATTN_HUB` path); that's one extra line and it's the case users will hit.
- `test_kernels_hub_execution` downloads from the Hub inside CI. On a network-restricted runner this fails with a confusing error. Add `pytest.importorskip("kernels")` and skip on `OSError`/`HfHubHTTPError`, or pre-fetch in the CI image.

### CI gates

`buildkite/vllm-omni-amd-ci` and `buildkite/vllm-omni-npu-ci` are both red and both are lanes this PR touches. One concrete thing to check first: `test_kernels_hub_platform_fallback` is marked `core_model` + `cpu`, so it is collected by the AMD lane's `pytest -sv tests/diffusion tests/model_executor -m 'core_model and cpu'` (`.buildkite/test-amd-ready.yaml:19`) and runs `CudaOmniPlatform` code on a ROCm box — and importing `vllm_omni.platforms.cuda.platform` pulls in `vllm.platforms.cuda`, which at module scope does `import vllm._C_stable_libtorch` and `torch.backends.cuda.enable_cudnn_sdp(False)`. If that's the failure, guard the test rather than leaving a CUDA-only test in the cpu lane. It passes locally here (CUDA box), so local green says nothing about those two lanes.

### Minor

- `flash_attn_hub.py:99,102` / `:278,281` — retry chatter at INFO should be `debug`, and the final failure should chain the original exception.
- Docs `attention_backends.md:229` — `pip install kernels==0.14.1` should be a floor (`>=`) that the code actually supports; a hard pin to a version whose behavior the code depends on (see #2) is fragile.
- `attention_backends.md:24` — "CUDA Hopper (sm_90+) only" needs reconciling with #4.
- Worth a doc note that these backends **download and execute compiled code from the Hub at model init**, plus guidance for air-gapped/multi-node deployments (pre-fetch the cache, `HF_HUB_OFFLINE`, `HF_TOKEN` for rate limits).
