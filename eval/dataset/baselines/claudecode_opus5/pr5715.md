## Comments

### 1. `docs/getting_started/installation/npu/npu.inc.md:62` — RC branch pin, and a ref convention this repo has never used

```bash
git clone -b releases/v0.26.0rc https://github.com/vllm-project/vllm-ascend.git
```

This is the one thing I'd want settled before merge. Two concerns:

- **It's a release candidate, while everything around it is stable.** Line 57 pins vLLM to the stable tag `v0.26.0`; lines 12–13 and 91–92 use stable images `quay.io/…/vllm-ascend:v0.26.0`; `docker/Dockerfile.npu:2` and `Dockerfile.npu.ci:2` both use `VLLM_ASCEND_TAG=v0.26.0`. Docs and Dockerfiles now disagree about which vLLM-Ascend a 0.26 NPU install gets.
- **The ref name mixes two conventions and matches neither.** The line this replaced used a *tag*: `v0.18.0rc1`. The commented-out Dockerfile lines (`docker/Dockerfile.npu:9`) use a *branch*: `releases/v0.18.0` — no `rc`. `releases/v0.26.0rc` is a hybrid of the two, which is exactly the shape a typo takes.

Please confirm the ref exists (`git ls-remote --heads https://github.com/vllm-project/vllm-ascend.git 'releases/*'`) and, if a stable `v0.26.0` tag is available, prefer it. A moving `releases/*` branch also makes these "pin the versions" instructions non-reproducible over time, which defeats the purpose of the pin.

### 2. `docs/getting_started/installation/README.md:3-4` — the new note contradicts a page it links to

The admonition sits directly above a list that includes **MThreads MUSA** (line 12), but `docs/getting_started/installation/gpu/musa.inc.md:31` still instructs `git checkout v0.18.0-dev` of vllm-musa. The index page now asserts "vLLM-Omni 0.26.x requires vLLM 0.26.x" one line above a link to a page that tells users to install a 0.18-line vLLM fork.

I understand MUSA was deliberately left out of this PR per review feedback — so the fix belongs in the note, not the MUSA page. Either add a carve-out, or state the rule without the concrete pin:

```markdown
!!! important
    vLLM-Omni is released against the matching upstream vLLM major/minor version —
    vLLM-Omni 0.26.x requires vLLM 0.26.x. (The MThreads MUSA path currently tracks
    vLLM-MUSA 0.18; see the MUSA instructions.)
```

Dropping the hardcoded `0.26.0` from this shared index also helps for a second reason: this page renders under `latest`, built from `main`, so it goes stale the moment main rebases onto 0.27/0.28. The major/minor *rule* is durable and code-enforced; the concrete pins are already on each per-platform page.

### 3. `docs/getting_started/installation/gpu/cuda.inc.md:8` — restates the index note, drops a useful pointer

The new sentence is near-verbatim the admonition from comment 2, and it discards what the old sentence was actually doing: telling the reader that the long block below is mostly vLLM's own install procedure, not vLLM-Omni's. That orientation is worth keeping. Suggest:

```markdown
The instructions below are mostly for installing vLLM itself, since vLLM-Omni 0.26.x
requires a matching vLLM 0.26.x.
```

### 4. `docs/getting_started/installation/npu/npu.inc.md:56-72` — the block no longer says where to run it

The `cd`/`cd ..` additions are a real fix: the old code cloned into `$PWD` and then `cd /vllm-workspace/vllm-omni`, which only worked by accident. But the block is now purely relative with no anchor, and the release block above is explicit that the container's default workdir is `/workspace` while the dev-mode checkouts live in `/vllm-workspace` (line 43). If a user runs this inside the vLLM-Ascend image at the default workdir, they get a second `pip install -e` copy of both vllm and vllm-ascend shadowing the dev-mode installs already present.

Add `cd /vllm-workspace` at the top of the block, or a sentence stating that this path assumes a clean environment rather than the pre-built image.

### 5. `docs/configuration/README.md:5` — version-pinned upstream URL is against local convention

Every other upstream docs link in the repo uses a floating channel: `/en/stable/` (`cuda.inc.md:15`, `docs/contributing/profiling.md:288`) or `/en/latest/` (`docs/community/governance.md:3`). This is the only version-pinned one, so it needs a manual bump every release — the previous `v0.16.0` value is evidence that it doesn't get one. `https://docs.vllm.ai/en/stable/configuration/` would track the release the reader is on.

Also worth a click-through: vLLM's docs are MkDocs-served with directory URLs, so `.../configuration/` is the canonical form and the `index.html` suffix is a legacy Sphinx shape. Low priority, but I couldn't check it from here.

### 6. `README.md:54`, `docs/README.md:55` — advertised feature has no page on the docs site

Grepping `docs/` for `duplex`/`realtime` turns up only these two new bullets plus two incidental CI-guide mentions. There's no page under `docs/serving/` or `docs/features/`, and the actual documentation (`vllm_omni/experimental/fullduplex/README.md` and `DESIGN.md`) isn't published. A reader who sees the bullet on the docs landing page has nowhere to go.

Cheapest fix now: link the bullet to the MiniCPM-o 4.5 recipe, matching how the news entry at `README.md:19` does it. A `docs/serving/realtime_api.md` would be the proper follow-up.

- The bullet is dated `[2026/06]` but opens with "Starting with 0.14.0", which shipped `[2026/02]`. Descending order is preserved, so this is cosmetic, but `[2026/02–2026/06]` would read more honestly for a span entry.

Line 19 is precise — the *full-duplex runtime* is what's new — but line 58's addition may read to a skimmer as "new model support in 0.26." Not worth blocking on; just confirming it's intentional.

Removing the `vllm-omni-skills` entry and folding away the arXiv link from the 0.14.0 bullet both look fine — the paper is still linked twice, in the header (`README.md:12`) and the Citation section (`README.md:79`), so no information was lost there.
