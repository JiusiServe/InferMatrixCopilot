# Review: PR #5723 — [Recipe] Document MiniMax H3 ROCm (gfx942 / gfx950) BF16 serving

## Verdict

**Request changes** (already merged, so treat these as follow-ups).

The ROCm serving content is welcome and the parts I could check against code hold up well: the gfx942/gfx950 scoping matches the actual gate in `vllm_omni/platforms/rocm/platform.py:95-99` (`is_aiter_found_and_supported() and 90 < capability < 100`), `FLASH_ATTN` really does resolve to AITER packed varlen (`vllm_omni/diffusion/attention/backends/utils/fa.py:38-45`), and the CFG / VAE-tile-mode caveats match `pipeline_minimax_h3.py:551` and `vae.py:156-166`.

But three things are wrong rather than merely imprecise:

1. `supported_models.md` does **not** actually mark AMD support — the footnote is orphaned, so the PR's headline change didn't land.
2. A rewritten "Known limitations" bullet asserts a reference-count restriction the code does not have, contradicting the same file's input matrix and its own curl examples.
3. Both ROCm `vllm serve` commands point `MODEL` at the `FL2VA` partition, which makes `task=ref2va` a hard error — directly under a paragraph claiming "All tasks work out of the box".

## Blocking

### 1. The AMD checkmark and the footnote marker are missing — `docs/models/supported_models.md:47`, `:101`

Line 47 is unchanged by this PR:

```
| `MiniMaxH3Pipeline` | MiniMax H3 T2VA, ... | `MiniMaxAI/MiniMax-H3` | ✅︎ | | | |
```

The AMD GPU cell is still empty, and `<sup>H3</sup>` appears nowhere in the table (`grep 'sup>'` returns only line 24's `<sup>1</sup>` and the new footnote itself). So the file now carries a dangling footnote that explains a support claim the table never makes. The PR description says "mark MiniMax H3 AMD GPU supported" — that edit is absent from the diff.

Fix (matching the existing marker convention on line 24):

```
| `MiniMaxH3Pipeline` | MiniMax H3 T2VA, first/last-keyframe FL2VA, and mixed-reference Ref2VA<sup>H3</sup> | `MiniMaxAI/MiniMax-H3` | ✅︎ | ✅︎ | | |
```

### 2. The reference-limit bullet is factually wrong — `recipes/MiniMaxAI/MiniMax-H3.md:727-731`

> "the current vLLM-Omni path takes exactly one image plus one audio reference, or one or more videos with no separate `audio_reference`"

`_validate_ref2va_reference_counts` (`pipeline_minimax_h3.py:309-326`, called at `:1587`) accepts up to 9 images, 3 videos, 3 standalone audios, 12 total, with the only structural rule being "at least one image or video". There is no one-image/one-audio restriction and no bar on video + standalone `audio_reference`.

This also contradicts two other places in the same file: the input matrix at line 663 (`images ≤9, videos ≤3, audios ≤3, total ≤12`) and the examples at lines 562-645 ("Image-only Ref2VA omits `audio_reference`…", "A video may use its embedded soundtrack, a separate `audio_reference`, or both").

The stale claim predates this PR, but the PR rewrote and expanded these exact lines into a more authoritative-sounding paragraph, so it should have been deleted instead. Drop the bullet; the input matrix already documents the real contract.

### 3. `MODEL` points at the FL2VA partition, so Ref2VA is rejected — `recipes/MiniMaxAI/MiniMax-H3.md:426`, `:446` (vs. `:416-418`)

`export MODEL="${MODEL_ROOT}/FL2VA"` resolves to `partition="fl2va"` (`pipeline_minimax_h3.py:125-141`, plus the parent-dir handling at `:150-152`), so `supported_tasks` is `{t2va, fl2va}` and any `task=ref2va` request fails at `:734-736` with *"checkpoint partition 'fl2va' supports ['fl2va', 't2va']"*. Meanwhile lines 416-418 tell the reader "All tasks work out of the box: the image bundles TorchCodec (for image+audio Ref2VA) and `ffmpeg` (for video-reference Ref2VA)", and the HTTP examples the reader goes to next include two Ref2VA requests. The evidence table also has no Ref2VA row, so nothing here supports the "all tasks" claim.

Two secondary problems in the same lines: `MODEL_ROOT` is never defined anywhere in this recipe (it appears once at line 205 as a script env var), and every other serve command in the file uses `export MODEL=MiniMaxAI/MiniMax-H3`.

I suspect the partition path was deliberate: under pure Ulysses each rank holds a full DiT copy, so combined serving is 2 × ~134 GiB per GPU, which does not fit MI300X's 192 GiB. If so, say that explicitly, e.g.:

> These commands serve the `FL2VA` partition only (T2VA and FL2VA). Combined serving replicates both DiTs on every Ulysses rank (~270 GiB), which does not fit gfx942/gfx950 HBM without offload; run a second server on `${MODEL_ROOT}/Ref2VA` for `ref2va`. Set `MODEL_ROOT` to a local MiniMax-H3 checkout containing the sibling `FL2VA/` and `Ref2VA/` directories.

and soften "All tasks work out of the box" to a statement about the image's decoder dependencies rather than about these servers.

## Should fix

### 4. "when the model shards across the GPUs" contradicts the bullet this PR added — `recipes/MiniMaxAI/MiniMax-H3.md:440-443`

The four-GPU command uses `--usp 4` with TP left at 1, so the DiT is replicated, not sharded — exactly what the new limitation at lines 740-742 says ("Pure Ulysses still replicates the full DiT on every rank"). Suggest: "…with no CPU offload; each rank holds a full copy of the FL2VA DiT, and only the text encoder is sharded (`--text-encoder-tp-size 4`)."

### 5. `aiter` is a hard requirement for the documented path, and its absence is nearly silent — `recipes/MiniMaxAI/MiniMax-H3.md:400-402`, `:410-414`

`aiter` is not in `requirements/rocm.txt` — it comes from the ROCm base image. Users who follow the wheel install (lines 410-414) may not have it, in which case `platform.py:110-118` logs a single `warning` and silently returns `TORCH_SDPA`, i.e. roughly half the throughput per this PR's own comparison. The CUDA sections model the right pattern ("Confirm the server log contains `Defaulting to diffusion attention backend TRTLLM_ATTN`"); the ROCm equivalents are `logger.debug`, so grepping for them won't work by default. Add something like:

> `FLASH_ATTN` requires the `aiter` library (present in the ROCm image; install it separately on the wheel path). It is already the ROCm default when aiter is usable (`platform.py:126-129`); passing the flag is explicit belt-and-braces. If the server log shows *"Flash Attention requires `aiter` library which is only supported on gfx942 and gfx950. Falling back to TORCH_SDPA backend."*, the measurements below do not apply.

### 6. "The VAE uses AITER GroupNorm on ROCm" is broader than what happens — `recipes/MiniMaxAI/MiniMax-H3.md:406`

`patch_groupnorm.py:41-52` only rewrites `model.vae`, which for H3 is `self.vae = self.video_vae` (`pipeline_minimax_h3.py:677`); the audio VAE is untouched. The swap is also skipped silently (`except Exception: logger.warning("Failed to apply AITER GroupNorm to VAE.")`) when aiter is missing. Say "video VAE", and point at the `AITER GroupNorm is enabled for VAE.` info log as the confirmation — or drop the sentence, since it doesn't change anything the reader types.

### 7. The gfx950 evidence row isn't reproducible from this recipe's own API — `recipes/MiniMaxAI/MiniMax-H3.md:481`

"T2VA, 832x480, ~4 s, 40 steps": T2VA requires an explicit named aspect ratio even when `width`/`height` are given (`pipeline_minimax_h3.py:346-348`, `:354-355`), and 832x480 is 26:15 — not one of the six supported names. So the row can only have been produced by passing some named ratio that disagrees with the canvas. Since this is the *sole* evidence behind the "gfx950 validated" claim in the supported-models footnote, either state the exact request used, or re-report at 1344x768/50 steps so it lines up with the gfx942 rows and the documented T2VA curl. As written, a reader copying the §1 curl gets a very different shape than the one behind "~0.73 s/denoise-step".
