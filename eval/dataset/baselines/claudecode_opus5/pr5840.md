# Review: [MiniMax-H3] TeaCache support and Cache-DiT validation (#5840)

## Overall verdict

**The integration itself is solid — the extractor is a faithful mirror of `MiniMaxH3DiTModel.forward`, the FL2VA/Ref2VA partition gating is correct, and the tests pass locally** (`8 passed` for `TestMiniMaxH3Extractor`, `38 passed` for `test_cache_backends.py`). I verified the two things most likely to be wrong in a packed-multimodal TeaCache port and both are right: the combined pipeline really does hold two DiTs (`pipeline_minimax_h3.py:634` / `:639`), so hooking only `pipeline.transformer` genuinely leaves Ref2VA uncached; and per-request state is reset via `TeaCacheBackend.refresh()` from `diffusion_model_runner.py:458`, so the packed sequence length changing between requests is not a hazard.

Two things should be followed up, one a wiring bug and one a claim-quality issue:

1. **The new model-specific default `rel_l1_thresh=0.17` never takes effect in the normal serving path** — the engine injects `0.2` before the config ever reaches the backend. Confirmed by executing the code.
2. **The calibrated polynomial is effectively a constant over its own calibration range and non-monotone in part of it** (R²=0.0949, as the PR itself reports). TeaCache's adaptivity is largely absent for this model; the docs describe the knob as if it were adaptive.

Also, `buildkite/vllm-omni-amd-ci` is red on this PR. That gate needs to go green or be explicitly waived — I'm not going to re-litigate what it reports.

## Blocking / high-value

### 1. `_MODEL_DEFAULT_REL_L1_THRESH` is dead code in the normal serving path

`vllm_omni/diffusion/cache/teacache/config.py:96-99`, `vllm_omni/engine/async_omni_engine.py:853-855`

`AsyncOmniEngine._get_default_cache_config("tea_cache")` returns `{"rel_l1_thresh": 0.2}` whenever the user sets `--cache-backend tea_cache` without `--cache-config`. `_normalize_cache_config` applies that before `DiffusionCacheConfig.from_dict`, so `config.rel_l1_thresh` is `0.2`, never `None`, and `TeaCacheConfig.__post_init__` never consults the model default. Verified:

```
_normalize_cache_config('tea_cache', None)      -> {'rel_l1_thresh': 0.2}
DiffusionCacheConfig.from_dict(...)             -> 0.2
TeaCacheConfig(MiniMaxH3DiTModel, 0.2)          -> 0.2      # what users actually get
TeaCacheConfig(MiniMaxH3DiTModel)               -> 0.17     # what the tests exercise
```

So the whole `float | None` sentinel change to a shared public config — which touches every TeaCache model — buys nothing today: 0.17 is reachable only if a user passes an explicit cache_config dict that *omits* the key (`--cache-config '{}'`). Note the PR's own online smoke ran at 0.2, and its log line (`rel_l1_thresh=0.2`) confirms this.

**Change:** drop `"rel_l1_thresh": 0.2` from `_get_default_cache_config` at `async_omni_engine.py:854-855` so the `None` sentinel flows through, and add a test that goes through `_normalize_cache_config` → `get_cache_backend` rather than constructing `DiffusionCacheConfig()` directly (`test_cache_backends.py:483` and `:492` both take the path the engine never takes, which is why this slipped through).

Until that is fixed, `recipes/MiniMaxAI/MiniMax-H3.md` ("The model-specific default and examples use `rel_l1_thresh=0.17`") is inaccurate for anyone who doesn't pass `--cache-config`.

### 2. The calibrated polynomial doesn't do the job the mechanism needs

`vllm_omni/diffusion/cache/teacache/config.py:86-93`

Evaluating the shipped coefficients over the PR's own stated calibration domain (input rel-L1 ∈ [0.010979, 0.159318]):

| input rel-L1 | 0.011 | 0.0245 (mean) | 0.037 | 0.10 | 0.159 |
|---|---|---|---|---|---|
| rescaled | 0.1812 | 0.1595 | **0.1545 (min)** | 0.1857 | 0.2568 |

Two consequences:

- **It's near-constant.** The rescaler emits ~0.155–0.257 no matter what the input distance is. Combined with the reported R²=0.0949, the 4th-order fit is barely distinguishable from predicting the mean — the "timestep-embedding-aware" part of TeaCache is mostly not functioning. What remains is a fixed skip cadence: the accumulator gains ≈0.16/step, so `rel_l1_thresh` degenerates into a stride selector (≈0.17 → skip every other step in the mid range; ≈0.32 → skip two of three).
- **It's non-monotone in the low range.** From x=0.011 to x=0.037 the rescaled value *decreases*. A *larger* change in the modulated input produces a *smaller* accumulated distance, i.e. more caching — inverted relative to TeaCache's premise.

This also makes the default fragile in a way the recipe doesn't convey: the global minimum of the polynomial over the calibration range is 0.1545, so **any threshold ≤ 0.154 yields zero cache hits** while still paying the extra per-step modulation and the residual bookkeeping. 0.17 sits ~10% above that floor.

**Change (pick one):**
- Refit with a monotone-constrained estimator (isotonic regression or a monotone cubic) and report R² against a constant-predictor baseline, or
- If the near-constant behavior is accepted, say so plainly in the recipe: describe `rel_l1_thresh` as a skip-cadence knob for this model, publish the measured cache-hit rate at 0.17 and 0.2, and state the ~0.154 floor below which caching never engages.

Worth investigating either way: `modulated_input` is computed over the **entire packed sequence** including text and padding rows (`extractors.py:1341-1348`), whose contribution is near-static across steps. Restricting the signal to the video/audio target rows (`img_pos` / `audio_pos`) before recalibrating is the obvious first thing to try.

## Should fix

### 3. Two full packed-sequence tensors are retained for the whole request

`vllm_omni/diffusion/cache/teacache/extractors.py:1389` (+ `hook.py:176`, `hook.py:154`)

`previous_modulated_input` and `previous_residual` are both `[S, H]` bf16, plus a transient `ori_hidden_states.clone()` on every computed step. At the validated 4 s / 256×448 config (S ≈ 13k, H = 5376) that's ~140 MB each; it scales linearly with duration × resolution, so a 720p / 6 s job is roughly 1.5 GB per tensor. The PR's own online run already reports a 75,310 MB peak on an 80 GB H100 — the headroom for a longer or larger job is thin. Please add this to the recipe's **Known limitations** with the scaling rule, so users don't discover it as an OOM at the exact settings where the speedup matters most.

### 4. Cached steps still compute RoPE over the full sequence

`vllm_omni/diffusion/cache/teacache/extractors.py:1321`

`rope_freqs = module.rope(img_position_ids).to(device)` is computed eagerly but is used **only** inside `run_transformer_blocks` (`:1351-1372`). On a cached step that's a wasted O(S) allocation and kernel launch. Move the call inside the closure.

### 5. E2E smoke can't detect that caching never engages

`tests/diffusion/models/minimax_h3/test_minimax_h3_e2e.py:141-186`

With `num_inference_steps=2` (line 170) the loop makes exactly two forwards, of which the first always computes — so at most one cache decision is exercised, and the test asserts nothing about it. If the extractor silently stopped ever hitting the cache, this test would still pass. Raise the step count (8–10) and assert at least one hit — e.g. read `hook.state_manager` counters, or count `blocks[0]` invocations the way `test_teacache_reuses_h3_block_residual` already does. The test also hardcodes `cache_config={"rel_l1_thresh": 0.17}` (line 156), so it doesn't cover the default-resolution path from finding 1 either.

### 6. Cache-hit test can't catch a stale-`t_emb` postprocess bug

`tests/diffusion/cache/test_teacache_extractors.py:670-697`

`test_teacache_reuses_h3_block_residual` calls `hook.new_forward` twice with **identical** `sample_inputs`, so `t_emb` is the same on both calls. If `postprocess` ever captured a stale timestep embedding, the assertions would still hold. Make the second call use a different `unique_timesteps` and assert the outputs differ from the first — that's what actually proves `final_layer` re-runs with fresh conditioning on the cached path, which is the whole correctness argument for reusing only the block-stack residual.

Minor, same file, line 591: `submodule.rope._forward_method = submodule.rope.forward_native` reaches into a vLLM `CustomOp` private. Worth a comment at minimum, since it will break silently if vLLM renames the dispatch attribute.

### 7. Drive-by change to an unrelated test's coverage

`tests/diffusion/models/minimax_h3/test_minimax_h3_e2e.py:22`, `:125-127`

Changing `_assert_joint_output` from 39 → 107 frames forced adding `duration`/`aspect_ratio` to the pre-existing **FP8** smoke so it would keep passing. That silently changes what the FP8 test covers (and its runtime and memory), purely so the new TeaCache test could reuse the helper. Prefer `_assert_joint_output(outputs, num_frames=39)` and leave the FP8 test's inputs alone.

## Minor

- `vllm_omni/diffusion/cache/teacache/hook.py:234-236`: `assert rel_l1_thresh is not None` is a type-narrowing assert on a hot path, and it vanishes under `python -O`. Cleaner: keep `float | None` as the *input* type and expose the post-init-resolved value as a non-optional attribute (or resolve the default in the backends before constructing `TeaCacheConfig`), so the annotation matches the runtime invariant without a runtime assert.
- `vllm_omni/diffusion/cache/teacache/backend.py:98-101`: the log line hardcodes `partition=FL2VA` even when `partition == "combined"`. It's accurate about *which DiT was hooked*, but reading it right after the `combined` warning is confusing. Suggest `partition={partition} (FL2VA DiT)`.
- `vllm_omni/diffusion/cache/teacache/backend.py:79-82`: a Ref2VA-only deployment with `--cache-backend tea_cache` now fails at startup, whereas the runner's own policy for unsupported models is warn-and-disable (`diffusion_model_runner.py:304-311`). The hard error is defensible and is documented in the recipe, but it's inconsistent with the surrounding convention — worth a deliberate call rather than an accident. (For the record, this is not a regression: before this PR the same config died with `KeyError: Cannot find coefficients for MiniMaxH3DiTModel`.)
- `docs/user_guide/diffusion_features.md:162`: the row now reads `✅ (FL2VA)` for TeaCache next to `✅` for SP in the same row, which reads as "TeaCache × Ulysses is supported". All validation in this PR was single-GPU. The decision is rank-consistent by construction (identical full-sequence inputs on every rank ⇒ identical skip decision, so no collective divergence), but it's untested — either add an 8-GPU TeaCache smoke alongside the existing `test_minimax_h3_t2va_ulysses8_smoke`, or footnote the table.

## What I verified and found correct

- `extract_minimax_h3_context` matches `MiniMaxH3DiTModel.forward` (`minimax_h3_transformer.py:1077-1189`) statement for statement: kwarg contract, shape validation, `_embed`, `combined_indices` with the `clamp(min=0)` padding convention, `sp_prepare`/`sp_gather` boundaries, row selection, and the `skip_mask_out_condition` / `update_audio_mask` guards. `test_extractor_matches_native_forward` pins this.
- Residual is captured across the block stack after `sp_gather`, so shapes are SP-independent; `postprocess` re-runs `final_layer` with the current step's `t_emb`, which is the correct split for this architecture.
- Cross-request state leakage is **not** an issue: `_refresh_cache_for_requests` → `TeaCacheBackend.refresh` → `reset_hook` runs per request batch, so the varying packed sequence length (text length alone varies per prompt) can't produce a shape mismatch in `previous_modulated_input`.
- Combined-partition claim holds: `transformers_ref` is a separate module (`pipeline_minimax_h3.py:639`, selected at `:737`) and is never hooked.
- `MiniMaxH3AdalnProj` uses `gather_output=True` (`minimax_h3_transformer.py:549`), so `modulated_input` is TP-rank-identical — no risk of divergent skip decisions deadlocking a collective under DiT tensor parallelism.
