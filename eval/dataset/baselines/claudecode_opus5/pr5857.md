# Review: [Docs] Add MiniMax-H3 recipe for RTX PRO 5000 (#5857)

## Verdict

**Approve with follow-up fixes.** Docs-only, no runtime risk, and I verified that every flag and value in the three serving commands is real and valid on `main`:

- All flags exist (`vllm_omni/entrypoints/cli/serve.py:394-737`, `:636-670`).
- `--num-gpus` ≥ `tp × usp × ring` holds for all three routes (`vllm_omni/diffusion/data.py:951`).
- Head divisibility holds: `num_attention_heads=56` (`minimax_h3_transformer.py:54`), so TP1/2/4 pass `:861` and local heads 56/28/14 are all divisible by Ulysses 2 (`:898-906`).
- `--text-encoder-tp-size` 2/4/8 all divide 64 and 8 (`pipeline_minimax_h3.py:552`).
- `--vae-patch-parallel-size` equals the DiT group size in each route, which is the only non-1 value H3 accepts (`minimax_h3/vae.py:167`).
- `--dlo-resident-layers 20` requires `--dlo-no-use-allgather` (`offloader/base.py:108-112`) — correctly paired; H3 declares `resident_dit_paths` (`pipeline_minimax_h3.py:469`) so the count takes effect.
- `duration:5.0` → 120 → snaps to **124** frames via the 17n+5 rule (`time_request.py:5-12`), and `num_inference_steps=50` yields 50 sigma points → 49 updates (`time_request.py:34-61`). The `denoise/49` claim and every per-step number in the table check out arithmetically.
- The 4-GPU `CUDA_VISIBLE_DEVICES=0,2,1,3` claim is genuinely correct: `RankGenerator(order="tp-sp-pp-cfg-dp")` (`distributed/parallel_state.py:838-846`) makes TP innermost, so SP groups are ranks {0,2},{1,3} → physical {0,1},{2,3}, the stated PXB pairs.

The problems below are all factual/consistency issues in the prose, but three of them will bite a user who follows the recipe literally.

## Should fix

### 1. `recipes/MiniMaxAI/MiniMax-H3-RTX-PRO-5000.md:16-17` — the host-RAM figures were carried over from a TP2 route, but this recipe's 2-GPU route is TP1

The capacity table's "200 GiB minimum / 384 GiB recommended" is lifted from `MiniMax-H3.md:73-75`, where it was derived for the **TP2** DLO route ("TP2 shards both the DiT and text encoder", `MiniMax-H3.md:154`). This recipe's 2-GPU route is `--tensor-parallel-size 1 --usp 2`, and with `--dlo-no-use-allgather` each worker pins *the standard loader's rank-local weights* (`offloader/base.py:100-120`; `dp_size` is forced to 1 at `:115`). At TP1 "rank-local" means the **full, unsharded DiT on both ranks** — roughly double the pinned host memory of the TP2 route.

The measured HBM corroborates this: 20 resident layers cost 27,726 MiB at TP2 (`MiniMax-H3.md:180`) vs 37,250 MiB here, i.e. ~0.9 GiB/layer instead of ~0.46 — exactly the 2× you'd expect from unsharded DiT weights.

Either re-state the actually-observed host RSS for this route, or raise the minimum and say why it differs from `MiniMax-H3.md`.

### 2. `:57` and `:92` — `numactl --membind=0` turns the RAM requirement into a *per-NUMA-node* requirement, and that isn't stated

The 2-GPU route combines `--membind=0` with DLO, whose host buffers are pinned by default (`OffloadConfig.pin_cpu_memory = True`, `offloader/base.py:27`). Pinned pages can't be swapped or migrated, so all ~2× DiT weights must fit in node 0's memory alone. On the "200 GiB minimum" host the doc advertises (dual-socket → ~100 GiB/node), this cannot succeed. Add a line making the constraint explicit — something like "with `--membind=0`, the minimum applies to NUMA node 0, not the whole host" — or use `--interleave=0,1` for the 2-GPU route as the 8-GPU route already does (`:122`).

### 3. `:56` — the 1800 s sync timeout is only valid for the 5-second workload that was measured

`VLLM_OMNI_VIDEO_SYNC_TIMEOUT` gates the `/v1/videos/sync` response (`entrypoints/openai/api_server.py:2969`). The 2-GPU route measured 515 s for a 5 s / 124-frame request. H3 accepts up to 15 s (`pipeline_minimax_h3.py:664`), which is ~3× the frames and would land near or past 1800 s at 10.3 s/update. The main recipe uses `14400` for exactly this reason on its DLO route (`MiniMax-H3.md:124`). Either raise it here or state that 1800 s is sized for the 5-second workload only.

### 4. `:143-144` — "restart the same command with `Ref2VA`" is unsafe for the 4-GPU route

The 4-GPU route is documented at 4.1 GiB headroom on a 71.7 GiB card, and validation was FL2VA-only (`:148-150`, and the PR's own matrix). `MiniMax-H3-5090.md:60-61` already warns that "Ref2VA reference video count and prompt length can increase activation memory". Reusing the 4-GPU command verbatim for Ref2VA is the most likely OOM a reader will hit. Carry that warning over, and point Ref2VA users at a lower-memory route.

### 5. `:177-179` — arithmetic error in the two-GPU headroom

> "The two-GPU route leaves about 34.7 GiB below the reported 73,415 MiB device capacity"

73,415 MiB = 71.69 GiB; minus the stated 36.38 GiB peak = **35.3 GiB**, not 34.7. The other two numbers in the same sentence are right under this method (71.69 − 67.58 = 4.11 ✓; 71.69 − 45.83 = 25.86 ✓), so just fix the outlier.

## Worth addressing

### 6. `:3-7` — the summary calls the DLO route a "resident configuration"

> "…the validated two-GPU DLO configuration **and the recommended resident configurations: TP1 x Ulysses2 with 20 resident layers on two GPUs**, TP2 x Ulysses2 on four GPUs…"

The two-GPU entry is listed under "resident configurations" and then two lines later the paragraph says "The four- and eight-GPU routes do not require offload." Drop the two-GPU entry from the resident list; "20 resident layers" is a DLO tuning knob, not residency.

### 7. `:36-38` — the eight-GPU device order contradicts the rule the section just stated

The section's stated principle is "map the Ulysses groups to the local PXB pairs", which `0,2,1,3` does for four GPUs. For eight GPUs with TP4×SP2, `0,4,1,5,2,6,3,7` gives SP groups of physical {0,2}, {4,6}, {1,3}, {5,7} — same NUMA node, but *not* the PXB pairs; what it actually does is pack each TP4 group with both PXB pairs across the two sockets. That's a defensible but **opposite** priority, and the doc offers no rationale ("with host memory interleaved across NUMA nodes 0 and 1" describes the `numactl` flag, not the device order). Since the doc tells readers to "reproduce the same PCIe and NUMA relationships" (`:37-38`), it needs to say which relationship each order is preserving. Citing the rank layout (TP innermost, `parallel_state.py:845`) would make both orders derivable instead of magic.

### 8. `:163-174` — the recommendation table drops the alternatives that justify the recommendation

The PR description contains two measured rows the doc omits: 4-GPU **TP4 × Ulysses1** at 50.25 GiB peak (the "safer-memory alternative") and 8-GPU **TP2 × Ulysses4** at 147.77 s (10% faster than the recommended route). Without them, `:111` ("The recommended eight-GPU route uses TP4 x Ulysses2") reads as arbitrary, and a reader stuck at 4.1 GiB headroom on four GPUs has no documented fallback — even though one was measured and passed. Add both rows, with a one-line note that TP4×Ulysses2 is recommended for headroom rather than peak speed.

### 9. `:63-75` — no rationale for TP1 × Ulysses2, or for keeping 20 resident layers on a 72 GiB card

Both numbers appear to be inherited from `MiniMax-H3-5090.md` (32 GiB cards), which used TP2 + 20 resident. Two things a reader will ask and the doc doesn't answer:

- Why TP1 here instead of TP2? TP2 halves both the pinned host memory (issue 1) and the per-resident-layer HBM cost, which would allow far more resident layers in the same budget.
- Why still 20 resident layers when the route leaves ~35 GiB of HBM idle? At ~0.9 GiB/layer, most of the remaining 30 blocks would fit.

The measured per-update time (10.3 s vs 5.7 s on 4 GPUs) suggests the stream is already well overlapped and the upside may be modest — but that's precisely the reasoning that belongs in the doc. At minimum, state the per-resident-layer HBM cost and tell readers to raise `--dlo-resident-layers` until the card is full, the way `MiniMax-H3.md:159-161` does.

### 10. `:148-150` — validation section omits the software version

Environment lists PyTorch/CUDA/driver but no vLLM or vLLM-Omni version. Both sibling recipes pin one (`MiniMax-H3.md:174-176`: "vLLM 0.26.0, vLLM-Omni 0.26.1.dev14+gae6577ea"). Add the commit — these numbers aren't reproducible without it.

## Nits

- `:139-141` says "Warm the server **once** before measuring", `:150` says the runs used "**two** warmups". Make them agree.
- `:13-14` "72 GiB per GPU" vs the "73,415 MiB" (71.69 GiB) capacity used for the headroom math at `:178`. The part is marketed as 72 **GB**; using GiB in the requirements table and MiB in the analysis invites a 2% error. Pick one unit.
- `:28-29` tells readers to run `nvidia-smi nvlink -s` immediately after `:24` states the card has no NVLink. Say what a reader should expect (empty/error output confirming PCIe-only), or drop the command.
- `recipes/README.md:48` — the new recipe isn't added to the "Available Recipes" index. Consistent with how `MiniMax-H3-5090.md` (#5764) and `MiniMax-H3-NPU.md` (#5706) landed, so this is a pre-existing gap rather than a regression, but all three could be indexed in one follow-up.
