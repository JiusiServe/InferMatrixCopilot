# Review: PR #5009 — Restore `vllm_c` IR op priority and `torch.nn.RMSNorm` for Qwen-Image

## Verdict

**Part 2 (`nn.RMSNorm` in the Qwen-Image transformer) is correct and well-motivated — approve.** I verified numerics and weight loading; it restores what #4074 shipped and #3588 accidentally reverted.

**Part 1 (unconditional `["vllm_c", "native"]` in `CudaOmniPlatform`) should not have been bundled here as-is.** The problem is not that it's wrong in principle — it's that, once Part 2 lands in the same PR, **Part 1 can no longer affect the Qwen-Image benchmark it is justified by**, while it silently flips the default for ~14 other diffusion models that have no measurements in this PR and whose prior perf work concluded the opposite. Since the PR is merged, these are follow-ups, not blockers.

Also note the three red hardware gates (`amd-ci`, `intel-ci`, `npu-ci`) — see finding 6 for a mechanism by which the new test file could contribute; that needs checking against the actual gate logs rather than assumed unrelated.

---

## Findings

### 1. Part 1 no longer affects the motivating benchmark after Part 2 — `vllm_omni/platforms/cuda/platform.py:250`

After Part 2, **no vLLM `RMSNorm` remains anywhere in the Qwen-Image path**, so the IR op priority is a no-op for it:

- `qwen_image_transformer.py:557,558,595,596,1009` are now all `nn.RMSNorm` (plain torch — not IR-dispatched).
- The only other norm in the file is `vllm_omni.diffusion.layers.adalayernorm.AdaLayerNorm` (`qwen_image_transformer.py:47`), which is an omni `CustomOp`, not an IR op.
- The text encoder is HF transformers, not vLLM layers: `pipeline_qwen_image.py:305` (`Qwen2_5_VLForConditionalGeneration.from_pretrained`), so it has no vLLM `RMSNorm` either.

The PR's Part-1 tables (`stage_0_gen_ms` 1288→1080 ms, `aten::mean` 2042→114) were all measured **without** Part 2 applied. The headline −26.9% number is the combined result, and the component that survives on the Qwen-Image path is Part 2. **Ask:** publish a Part-2-only measurement and a Part-1-on-top-of-Part-2 delta. If the latter is ~0 for Qwen-Image (which the code says it must be), Part 1 needs its own justification on a model it actually still touches.

### 2. Part 1's blast radius is ~14 other models, with no data and against prior in-repo conclusions — `vllm_omni/platforms/cuda/platform.py:253`

The default now applies to every diffusion model that uses vLLM's `RMSNorm`: `flux`, `flux2`, `flux2_klein`, `sd3`, `ovis_image`, `longcat_image`, `ernie_image`, `hunyuan_video_15`, `ltx2`, `omnigen2`, `wan2_2_s2v`, `t5_encoder`, `mistral_encoder`, `ming_flash_omni/t5_block_mapper`. None are benchmarked here.

This also directly contradicts the reasoning the repo already encodes for the same operation:

```python
# vllm_omni/diffusion/layers/norm.py:82-91
# ... Fall back to forward_native so inductor can fuse the pure-PyTorch ops itself.
if torch.compiler.is_compiling():
    return self.forward_native(x)
```

plus #3933 and #4074, both of which moved Qwen-Image *away* from fused kernels under compile for perf. Part 1 pushes the opposite way for everyone else. Part 1 and Part 2 are, in effect, contradictory fixes shipped together.

**Suggested change:** scope it to the models that demonstrably benefit, using the mechanism the repo already has — `registry.py:546-549` + `diffusion_worker.py:174-179`, with `pipeline_cosmos3.py:612-624` as the precedent (I confirmed the Cosmos3 hook still hard-overrides to `["native"]` at line 620, so Cosmos3 is genuinely protected). Failing that, keep the platform default but gate the nightly perf suite on at least one other affected model (e.g. FLUX.2 or Wan2.2) before the next release.

### 3. `RocmOmniPlatform` left on the old logic — `vllm_omni/platforms/rocm/platform.py:184-185`

```python
using_inductor = cc.backend == "inductor" and cc.mode != CompilationMode.NONE
default = ["native"] if using_inductor else ["vllm_c", "native"]
```

If the native-decomposition path is a real regression on CUDA, ROCm still has it. Either apply the same change or add one line saying why ROCm intentionally differs (e.g. aiter interaction). Relevant given `buildkite/vllm-omni-amd-ci` is red on this PR.

### 4. The rewritten docstring drops the "we deliberately diverge from upstream" signal — `vllm_omni/platforms/cuda/platform.py:252`

The removed docstring said "Copied from upstream CudaPlatformBase…". The replacement says only what the code does. That's precisely how #4709 caused this bug: someone re-syncs with `vllm/platforms/cuda.py:686-701` and the `using_inductor` branch comes back. Add something like:

```python
"""Prefer ``vllm_c`` CUDA kernels over ``native`` for diffusion IR ops.

Deliberately diverges from upstream CudaPlatformBase, which switches to
native-only when inductor is active. See #4964 / #4709 — re-syncing that
branch here regresses diffusion nightly perf. Guarded by
tests/platforms/test_cuda_ir_op_priority.py.
"""
```

### 5. No user escape hatch from the new default — `vllm_omni/diffusion/worker/diffusion_worker.py:290`

```python
vllm_config.kernel_config.ir_op_priority = _resolve_ir_op_priority(self.od_config, vllm_config)
```

This overwrites `kernel_config.ir_op_priority` wholesale, discarding any user-supplied value (upstream's `set_platform_defaults` merges rather than replaces — `vllm/config/kernel.py:282-291`). Pre-existing, but Part 1 makes it bite: a user hitting a slowdown on FLUX/SD3 can no longer opt back to `native` from the CLI, only by patching a per-model hook. Consider filling only fields the user left unset.

### 6. Test imports the CUDA platform at module scope, against repo precedent — `tests/platforms/test_cuda_ir_op_priority.py:7`

```python
from vllm_omni.platforms.cuda.platform import CudaOmniPlatform
```

Every other test defers this inside the test body (`tests/diffusion/attention/test_kernels_hub.py:24`, `tests/diffusion/attention/test_sage_attn3.py:92-93,120`), and `tests/platforms/npu/test_310p_patches.py` goes further, loading modules from source with fakes specifically to avoid platform imports. A module-scope import fails **collection**, not just the test, and collection is not filtered by `-m`: `.buildkite/scripts/hardware_ci/run-xpu-test.sh:54` runs `pytest -v -s -m "core_model and xpu and B60"` over the whole `tests/` tree. Move the import into the two test functions (or add `pytest.importorskip`), and check this against the red `intel-ci` / `npu-ci` / `amd-ci` gates rather than assuming they're unrelated.

### 7. Part 2 has no regression test — `vllm_omni/diffusion/models/qwen_image/qwen_image_transformer.py:557`

Part 1 got a guard; Part 2 didn't. #3588 (a W4A16 quant PR) silently reverted #4074 once and nothing caught it, so it can happen again. A CPU-cheap assertion in `tests/diffusion/models/qwen_image/` — construct `QwenImageCrossAttention` (or introspect the class source) and assert `isinstance(attn.norm_q, torch.nn.RMSNorm)` — would close the loop. Without it, the two halves of this PR have asymmetric protection.

### 8. Test nits — `tests/platforms/test_cuda_ir_op_priority.py:18-27`

- `CompilationMode.NONE` in the parametrize list is not a regression case: the old code returned `["vllm_c", "native"]` for it too (`mode != CompilationMode.NONE` was false). Harmless, but it makes the parametrize look like broader coverage than it is. The uncovered case that *would* be informative is `backend="eager"`.
- The oink test (line 30) asserts only `rms_norm` / `fused_add_rms_norm`; it doesn't pin that the `default` list stays `["vllm_c", "native"]` for other fields. `IrOpPriorityConfig` has only those two fields today, but the point of `with_default` is that upstream will add more — and when it does, omni's blanket default silently opts every new op into custom kernels under inductor. Worth an assertion and worth being aware of.

## What I verified

- **Test passes locally**: `pytest tests/platforms/test_cuda_ir_op_priority.py` → 4 passed (vLLM 0.26.0, L20X). The `monkeypatch.setattr(envs, "VLLM_USE_OINK_OPS", True)` trick does work against `vllm.envs`' lazy `__getattr__`.
- **Part 2 is numerically safe**: on a strided per-head view matching `qwen_image_transformer.py:632-643` (`[1,64,24,128]`, stride `(589824, 9216, 128, 1)`, non-contiguous), `nn.RMSNorm`, the IR `native` impl, and the `vllm_c` kernel all agree to the same bf16 rounding bound (max abs diff 0.0625 for all three, identical to the contiguous control). No stride-handling bug lurking in either direction.
- **Weight loading is unaffected**: `load_weights` uses `getattr(param, "weight_loader", default_weight_loader)` (`qwen_image_transformer.py:1257`), and both `nn.RMSNorm` and vLLM's `RMSNorm` expose a plain `weight` Parameter under the same name.
- **Scope of Part 1 is diffusion-only** (I initially suspected it leaked into the AR/LLM path): `CudaOmniPlatform.get_default_ir_op_priority` has exactly one non-test caller, `diffusion_worker.py:175`. `current_omni_platform` is a separate registry from vLLM's `current_platform` (`vllm_omni/platforms/__init__.py:174-187`), and the only override is a fallback for `UnspecifiedPlatform` (`entrypoints/cli/serve.py:59-63`). Text stages keep upstream's behavior.
- **fp8 fusion is not at risk**: `rms_quant_fusion.py` matches on `vllm.ir.ops.rms_norm` at IR level, before the lowering pass picks an impl, so the priority choice doesn't disable RMSNorm+quant fusion.
- **Lint**: `ARG` isn't in the ruff select list (`pyproject.toml:174-182`), so the now-unused `vllm_config` parameter is fine; `tests/**` ignores `E501`.
