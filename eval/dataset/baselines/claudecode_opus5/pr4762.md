## Overall verdict

**Approve the direction; request a follow-up fix.** The mechanism (declare `EndpointRestriction`s on a `PipelineConfig`, strip the route at app-build time, replace it with a 400 handler) is the right shape and the endpoint-policy module itself is small and well-tested. But this PR bundles a substantial `config_factory` refactor with the feature, and that refactor introduces a **config regression that silently disables `trust_remote_code` for every model whose deploy YAML sets it** — which is most of the TTS/omni fleet. Separately, the rejection is **incomplete**: the crash path this PR exists to close is still reachable via `POST /invocations`.

Two CI gates are red (`buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-npu-ci`) — those need to be green or explicitly triaged before this is considered settled; finding #1 below is a plausible cause worth checking against those logs first.

## Blocking-severity findings

### 1. `trust_remote_code=False` is now force-injected into CLI overrides and clobbers every deploy YAML
`vllm_omni/engine/async_omni_engine.py:220` and `:288`

```python
trust_remote_code: bool = False,     # 220
...
kwargs["trust_remote_code"] = trust_remote_code   # 288
```

`AsyncOmni` is constructed from `args.get_explicit_kwargs_dict()` (`api_server.py:691-694`), so before this PR `trust_remote_code` was absent from `kwargs` unless the user actually passed `--trust-remote-code`. Now it is *always* present. It flows `kwargs` → `_resolve_stage_configs` → `load_stage_configs_from_model` → `cli_overrides`, and `_create_from_registry` keeps any non-`None` value (`config_factory.py:341`), so it lands in `runtime_overrides`, which beat YAML engine args (`stage_config.py:897-900`).

Verified locally:

```
$ StageConfigFactory._create_from_registry("glm_tts", pipe, {})
no-cli   stage0 trust_remote_code=True   stage1 True     # deploy/glm_tts.yaml:15
$ ... _create_from_registry("glm_tts", pipe, {"trust_remote_code": False})
with-false stage0 False                  stage1 False    # clobbered
```

Affected deploy configs include `glm_tts.yaml`, `minicpmo_4_5_*.yaml`, `indextts2*.yaml`, `moss_tts_*.yaml`, `ming_flash_omni*.yaml`, `voxcpm2.yaml`, `qwen3_tts.yaml`, `aura_omni.yaml`, `covo_audio.yaml`, `soulxsinger_*.yaml`. Serving any of these without `--trust-remote-code` used to work and now hands the stage workers `trust_remote_code=False`.

**Fix:** make the parameter tri-state so "not specified" stays absent:

```python
trust_remote_code: bool | None = None,
...
if trust_remote_code is not None:
    kwargs["trust_remote_code"] = trust_remote_code
```

and pass `bool(trust_remote_code)` into `get_pipeline_endpoint_restrictions`. Add a regression test asserting that `_create_from_registry(..., cli_overrides={})` leaves a deploy YAML's `trust_remote_code: true` intact.

### 2. The restriction is bypassable via `POST /invocations`
`vllm_omni/config/endpoint_policy.py:65-91`

vLLM's `build_app` unconditionally attaches the SageMaker router (`vllm/entrypoints/openai/api_server.py:231-235`). `/invocations` does not route through `/v1/completions`; it pydantic-validates the body against `get_generate_invocation_types(...)` and **calls `create_completion` directly** (`vllm/entrypoints/serve/sagemaker/api_router.py:82-88`, `vllm/entrypoints/generate/factories.py:37-40`). It is guarded only by `get_handler(raw_request) is not None`, and omni sets `state.openai_serving_completion` whenever `"generate"` is in `supported_tasks` (`vllm_omni/entrypoints/openai/api_server.py:963-975`). A `ChatCompletionRequest` fails validation on a `{"model": ..., "prompt": ...}` body, so it falls through to `CompletionRequest` → the exact handler that crashes Qwen3-Omni.

**Fix:** don't rely on route removal alone. Map each `OmniServingCapability` to its `app.state` handler attribute and `None` it out in `shutdown_unsupported_routes`, e.g. `COMPLETIONS → "openai_serving_completion"`, `CHAT_COMPLETIONS_BATCH → "openai_serving_chat_batch"`. That closes `/invocations` and any future dispatcher that reaches handlers by state rather than by path, while keeping the nice 400 on the direct route. Worth an e2e assertion on `/invocations` too, since that's the interesting half of "can't be used to bring down a production instance".

## Should fix

### 3. Default `trust_remote_code` for pipeline detection flipped `True` → `False`
`vllm_omni/config/config_factory.py:274-286`, `vllm_omni/entrypoints/utils.py:348`

The removed `_auto_detect_model_type` was called with `cli_overrides.get("trust_remote_code", True)`. It's now `cli_overrides.get("trust_remote_code", False)`. For remote-code models, `get_config` then raises, `hf_config` is `None`, and the whole `if hf_config is not None:` arch-fallback block (`config_factory.py:246`) is skipped. Pipelines that can *only* be reached that way — `minicpmo_4_5` (HF reports `model_type="minicpmo"`, matched via `hf_architectures` + `hf_config_predicate`), `ming_tts` (`model_type="dense"`), `mimo_audio` (`qwen2`) — no longer resolve unless the user passes `--trust-remote-code` or an explicit `--deploy-config` carrying a `pipeline:` key. Either restore the `True` default for detection-only config loading, or state the flip deliberately in the PR/release notes as a security hardening and confirm each affected deploy YAML has `pipeline:` set.

Also at `utils.py:348`: `cli_overrides.get("trust_remote_code", False)` returns `None` when the key is present-but-`None`, which then reaches `get_config(model, trust_remote_code=None)` and creates a distinct `functools.cache` entry. Normalize with `bool(...)`.

### 4. Cache-clearing fixture is file-local but the caches are process-global
`tests/test_config_factory.py:43-50`, `config_factory.py:75/94/216`

`get_hf_config` / `try_infer_model_type` / `get_pipeline_config` are `@classmethod @functools.cache`, so results persist for the whole pytest process. The autouse `clear_config_factory_caches` fixture only exists in `tests/test_config_factory.py`. `tests/entrypoints/test_resolve_dreamzero_config.py:25-39` monkeypatches `_try_infer_model_type` and calls through `load_stage_configs_from_model`, seeding the global cache for `("GEAR-Dreams/DreamZero-DROID", False)` with a patched value that outlives the test. Move the fixture into a shared `conftest.py` (or make it session-scoped autouse) so any test touching the factory is isolated. Note also that `get_hf_config` hands the *same mutable* `PretrainedConfig` instance to every caller.

### 5. `hasattr` guard silently drops the global restrictions too
`vllm_omni/entrypoints/openai/api_server.py:513-517`

If `endpoint_restrictions` is missing, the code skips `shutdown_unsupported_routes` entirely — including `UNSUPPORTED_ROUTES`, so `/v1/chat/completions/batch` goes back to 500-ing, which is the thing that commit was written to prevent. Prefer:

```python
restrictions = getattr(engine_client, "endpoint_restrictions", ())
if not hasattr(engine_client, "endpoint_restrictions"):
    logger.warning("Engine client %s exposes no endpoint_restrictions; applying global restrictions only",
                   type(engine_client).__name__)
shutdown_unsupported_routes(app, restrictions)
```

The current message (`"engine client has no endpoint restrictions attribute"`) doesn't say which client or what the consequence is.

### 6. Restrictions can be read off a pipeline that isn't the one actually used
`config_factory.py:325-333` vs `:51-72`

`get_pipeline_endpoint_restrictions` resolves via `get_pipeline_config`, but `_create_from_registry` can still *swap* `pipeline_cfg` afterwards when the default `_DEPLOY_DIR/<model_type>.yaml` carries a mismatching `pipeline:` key. In that case the server enforces restrictions from the pre-swap pipeline. The new test (`test_deploy_override_uses_correct_endpoint_restrictions`) pins only the explicit-`deploy_config_path` case. Either resolve restrictions from the final `StageConfig`/pipeline that `create_from_model` actually returned, or add the implicit-default-deploy case to the test.

## Nits / polish

- `endpoint_policy.py:72` — a `vllm_omni/config/` module lazily importing `_remove_route_from_app` from `vllm_omni.entrypoints.openai.api_server` inverts the dependency and drags the entire server stack (torch, all vLLM serving) into a config-layer call. Move that ~10-line Starlette helper into `endpoint_policy.py` or a small `entrypoints/openai/route_utils.py` and have `api_server` import it. As a side effect `tests/config/test_endpoint_policy.py` becomes a genuine unit test — today it transitively imports `api_server`, which is why all four cases error out in my environment (`ModuleNotFoundError: vllm.entrypoints.serve.disagg`, a pre-existing vLLM-version mismatch here, not a PR defect — but it shows the coupling is load-bearing).
- `endpoint_policy.py:52-62` — `build_rejection_handler` has no return annotation; `raw_request` is unused (needed only for FastAPI signature — worth a one-line comment). Consider `include_in_schema=False` and a per-capability `name=` on `add_api_route` so OpenAPI operation ids don't all derive from `rejection_handler`.
- `config_factory.py:86-91` — `hf_config = None` then `return hf_config` is dead; the `try` already returns. Collapse to `return None`.
- `config_factory.py:67` — uses `StageConfigFactory.get_pipeline_config` instead of `cls.get_pipeline_config`; inconsistent with the rest of the class.
- `config_factory.py:268-278` — `cli_overrides` became keyword-only along with `trust_remote_code`. Any out-of-tree caller doing `create_from_model(model, overrides)` now breaks, and `**deprecated_kwargs` swallows it silently rather than warning. Consider logging unexpected `deprecated_kwargs` keys.
- `_get_deploy_override_pipe_config` (`config_factory.py:264-278`) dropped the old `try/except` + "falling back to auto-detection" warning around `load_deploy_config`. Failing loud is probably better, but it's an undocumented behavior change on malformed deploy YAML.
- Globally disabling `/v1/chat/completions/batch` for **all** models (commit `cdc825f0`) is a user-visible feature removal that isn't in the PR description and has no test asserting `UNSUPPORTED_ROUTES` is applied, nor one pinning the documented "UNSUPPORTED_ROUTES message wins on overlap" precedence (`endpoint_policy.py:74-76`). Add both, plus a release note.
- Test coverage gap: `QWEN3_OMNI_THINKER_ONLY_PIPELINE` correctly carries no restriction (thinker-only has no ChatML handoff), but nothing pins that — a cheap unit test on `resolve_qwen3_omni_pipeline(Qwen3OmniMoeConfig(enable_audio_output=False)).endpoint_restrictions == ()` would prevent someone "helpfully" moving the restriction onto the shared config later.
- `tests/e2e/online_serving/test_qwen3_omni.py:238-252` asserts the 400 but not the message. Asserting the reason string is what proves the *restriction* fired rather than some incidental validation error.
