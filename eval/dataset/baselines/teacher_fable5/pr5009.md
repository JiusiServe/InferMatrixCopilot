# Review: PR #5009 — Restore vllm_c IR op priority and torch.nn.RMSNorm for Qwen-Image

## Verdict

**Approve with follow-ups** (the PR is already merged, so these are follow-up items rather than blockers — except the red CI gates, which are unresolved on the merged head and need owning). The core change is sound: I verified in git history that #3588 did accidentally revert #4074's `torch.nn.RMSNorm` (the swap was incidental to the quant work — RMSNorm is never quantized, so nothing in the W4A16 path depends on vLLM's `RMSNorm` class), and Part 1 is a faithful restore of the pre-#4709 platform default, backed by a real regression test. Weight loading is unaffected: both classes expose an identical `weight` parameter key, and `load_weights` resolves norms via `named_parameters()` + `default_weight_loader` (`vllm_omni/diffusion/models/qwen_image/qwen_image_transformer.py:1252-1259`). No code anywhere isinstance-checks these norm modules. The accuracy recovery (SSIM/PSNR) is expected since diffusers itself uses torch's RMSNorm, so Part 2 restores bit-level parity with the reference.

## Blocking / must-own

**1. Three CI gates are red on the merged head.** `buildkite/vllm-omni-amd-ci`, `buildkite/vllm-omni-intel-ci`, `buildkite/vllm-omni-npu-ci` are failing — the gate speaks for itself and this was merged over it. One concrete suspect worth checking against those logs: the new test file sits at `tests/platforms/test_cuda_ir_op_priority.py` (directly in `tests/platforms/`, not in a `cuda/` subdirectory, unlike the existing `tests/platforms/npu/` convention) and unconditionally imports `CudaOmniPlatform`, which pulls in `vllm.platforms.cuda.CudaPlatformBase` at collection time (`tests/platforms/test_cuda_ir_op_priority.py:7`). If the AMD/Intel/NPU pipelines collect `tests/platforms/`, that import may fail on their stacks despite the `pytest.mark.cpu` marker (markers don't prevent collection-time imports). Either move it to `tests/platforms/cuda/` with a platform guard, or confirm those pipelines deselect it.

## Specific comments

**2. `vllm_omni/platforms/cuda/platform.py:251-252` — the change is platform-wide, not diffusion-scoped, and the docstring/PR description misstate this.** The new docstring says "for diffusion IR ops," and the PR description scopes this to "all diffusion models." But `get_default_ir_op_priority` is the hook vLLM core calls from `KernelConfig.set_platform_defaults` (`vllm/config/kernel.py:276` in the installed vLLM) for **every** engine — including AR/LLM stages of omni pipelines (thinker/talker models). Removing the `using_inductor` branch also opts those AR stages out of upstream v0.24's deliberate native-under-inductor default, forfeiting any inductor-fusion gains upstream intended for compiled LLM paths. This does match pre-#4709 Omni behavior, so it's not a regression against the old baseline — but a cleaner fix matching the stated scope would have been to keep the upstream-aligned platform default and inject the `["vllm_c", "native"]` preference in the diffusion-only `_resolve_ir_op_priority` hook (`vllm_omni/diffusion/worker/diffusion_worker.py:174-179`), which exists for exactly this purpose. At minimum, fix the docstring to say this applies to all CUDA workloads in Omni, and confirm AR-stage nightlies didn't move.

**3. `vllm_omni/platforms/rocm/platform.py:184-186` and `vllm_omni/platforms/xpu/platform.py:115-117` — the identical bug pattern survives on ROCm and XPU.** Both platforms still carry the exact `using_inductor → ["native"]` branch this PR removes from CUDA. If the regression mechanism in #4964 (compiled diffusion denoise loop forced onto native RMSNorm decomposition) applies to Qwen-Image on AMD/Intel — and both have CI pipelines, currently red on this PR — the same fix is needed there. Either port the change or file a tracked follow-up explaining why ROCm/XPU intentionally keep the inductor-aware default (e.g., aiter interplay). Right now the three platforms silently disagree for no documented reason.

**4. Part 1 has lost its nightly guard.** With Part 2 merged, the Qwen-Image transformer contains no vLLM `RMSNorm` at all, so the Qwen-Image nightly perf jobs that caught #4964 no longer exercise the `vllm_c` priority path this PR restores. The Part-1 ablation numbers in the description were measured on the pre-Part-2 tree. That's fine as evidence, but going forward the only guard on Part 1 is the new unit test, which asserts the config *value*, not actual kernel dispatch — a future refactor that changes how `rms_norm` priority is consumed would pass the test while regressing other vLLM-RMSNorm-based diffusion models (Wan, dreamzero, etc.). Worth noting which nightly workload now covers `vllm_c` dispatch, or adding one.

**5. `tests/platforms/test_cuda_ir_op_priority.py:12` — minor test gaps.** (a) The `backend` parameter of `_vllm_config` defaults to `"inductor"` and is never varied; a case with a non-inductor backend (e.g. `"eager"`) would document that the priority is backend-independent by design, which is the actual contract this PR establishes. (b) The tests only assert `rms_norm` and `fused_add_rms_norm`; asserting one other field equals `["vllm_c", "native"]` would also pin the `with_default` fallback. Both trivial. For what it's worth, all 4 tests pass on CPU in this checkout (vLLM 0.26 environment, 0.09s).

## What I checked and found clean

- The `VLLM_USE_OINK_OPS` behavior is preserved verbatim from the removed upstream-copied code, and the monkeypatch in the oink test targets the same `vllm.envs` module object `platform.py` imports, so it's effective.
- The Cosmos3 per-model override claim in the PR description checks out: `get_cosmos3_ir_op_priority_func` (`vllm_omni/diffusion/models/cosmos3/pipeline_cosmos3.py:612-624`) forcibly resets `rms_norm`/`fused_add_rms_norm` to `["native"]` regardless of the platform default, so models needing native-only are unaffected.
- All five swapped norms (`norm_q`, `norm_k`, `norm_added_q`, `norm_added_k`, `txt_norm`) are called with a single tensor argument at their call sites (`qwen_image_transformer.py:640-643`, `qwen_image_transformer.py:1140`) — no residual-tuple usage that vLLM's `RMSNorm.forward` supports but `nn.RMSNorm` doesn't.
- The now-unused `RMSNorm` import was removed; no other file in `vllm_omni/diffusion/models/qwen_image/` references it.
