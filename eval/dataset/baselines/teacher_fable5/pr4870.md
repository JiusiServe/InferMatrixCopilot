# Review: PR #4870 — Fix Qwen3-TTS no-async-chunk payload splitting

## Overall verdict

The core fix is correct and well-diagnosed. In the async-omni-output path, models that opt out of hidden payloads get an empty tail snapshot (`hidden_states[:0]`, `gpu_ar_model_runner.py:1611`), so the old `seq_len = hidden_states.shape[0]` was 0 and `to_payload_element` (`vllm_omni/utils/mm_outputs.py:131`) never matched `codes.audio`'s first dimension — every concurrent request received the full batched tensor via the clone fallback. Switching the split length to `scheduler_output.total_num_scheduled_tokens` matches the layout `codes.audio` is actually built in (per-request spans concatenated in `qwen3_tts_talker.py:593`) and also aligns with the convention the prefix-cache path already uses (`vllm_omni/core/prefix_cache.py:591-603`). The regression test reproduces the exact failure shape and I verified it passes locally. I would have approved this with the caveats below; since the PR is already merged, they are follow-up items — and note the **`buildkite/vllm-omni-amd-ci` check is failing** on this PR: that gate needs to be resolved (or explicitly waived) rather than left red on a merged bugfix.

## Comments

### 1. `vllm_omni/worker/gpu_ar_model_runner.py:1734` — new invariant may break hidden-aligned mm tensors under CUDA-graph padding (medium, follow-up)

The change assumes every per-token multimodal tensor has `dim0 == total_num_scheduled_tokens`. That holds for Qwen3-TTS `codes.audio`, but the runner is shared by all AR stages, and some models emit mm tensors cloned directly from the forward's hidden states — e.g. the Qwen3-Omni thinker's captured layers (`qwen3_omni_moe_thinker.py:552`: `hidden_states.clone().view(-1, H)`), shipped as `multimodal_outputs` via `qwen3_omni.py:497`. Under CUDA-graph padding, `hidden_states.shape[0]` is the *padded* token count (the builder itself acknowledges this — the `min(total, hidden.shape[0])` at line 1711 exists precisely to trim padding). Before this PR those padded tensors matched `seq_len` and were sliced per request; now they won't match, so each request silently gets the whole padded tensor via the clone fallback — the same corruption class this PR fixes, in the opposite direction. Suggested hardening: in `_build_omni_mm_payload`, slice when `dim0` equals *either* the scheduled total or the (padded) hidden length, or trim per-token mm tensors to `num_tokens_unpadded` at extraction time. At minimum, run a concurrent Qwen3-Omni audio E2E with cudagraph padding enabled to confirm this path isn't live.

### 2. `vllm_omni/platforms/npu/worker/npu_ar_model_runner.py:905` — NPU path still has the original bug (medium, follow-up)

The NPU runner is a parallel implementation of the same payload builder and still computes `seq_len = hidden_states.shape[0]`, feeding it to the same `to_payload_element` (line 1138). Qwen3-TTS `no_async_chunk` concurrent serving on NPU will still accumulate full-batch `codes.audio` per request. This PR intentionally scoped to the GPU path, but the divergence should be tracked with an issue or a follow-up PR so the fix doesn't get lost.

### 3. `vllm_omni/entrypoints/openai/serving_speech.py:3507` — config access is inconsistent with the rest of the file (low)

The new code reads `getattr(self.model_config, "async_chunk", True)` while essentially every other config read in this file goes through `self.engine_client.model_config` (~25 occurrences, e.g. lines 590, 631, 1852). They resolve to the same object in the current wiring (the unit test relies on that: it mutates `engine_client.model_config` and asserts the effect), but if the base-class `model_config` wiring ever changes, this check silently degrades to the `True` default and the branch never fires — with no test failure, because the mock keeps the two aliased. Prefer `self.engine_client.model_config` for consistency. Also note the `getattr` default (`True`) is the opposite of `OmniModelConfig.async_chunk`'s declared default (`False`, `vllm_omni/config/model.py:121`); it's the safe fail-open choice (preserves pre-PR DELTA behavior), but a one-line comment saying that's intentional would prevent someone "fixing" it later.

### 4. `vllm_omni/entrypoints/openai/serving_speech.py:3509` — FINAL_ONLY for streaming full-payload requests: correctness OK, latency claim unverified (low)

I traced the streaming consumers: `_generate_audio_chunks` (line 2749) handles both cumulative-list and per-step outputs, so a single FINAL_ONLY result is emitted as one chunk, and the SSE path (line 2883) and usage accounting sit on top of the same generator — nothing breaks. The remaining question is the premise "non-async-chunk TTS does not produce incremental audio chunks": if code2wav decodes the accumulated payload in chunks (`initial_codec_chunk_frames`), DELTA previously gave some incremental emission after the talker finished, and this change collapses it to one final blob — a silent time-to-first-byte regression for `stream=True` + `--no-async-chunk`. The E2E validation covered `stream=False` only. Worth one manual `stream=True` probe on the same H20 setup to confirm the premise.

### 5. `tests/worker/test_gpu_ar_model_runner.py:449` — regression test bypasses the production accumulation branch (nit)

The test forces `_should_accumulate_full_payload_output → False` and asserts on `inter_stage_outputs`, but the real `no_async_chunk` failure flowed through the accumulation branch (`accumulate_full_payload_output`, gpu_ar_model_runner.py:1805-1810 — the debug logs in the PR description show per-request *accumulation* of full-batch payloads). The slicing under test is upstream of both branches, so the test does pin the fix, but a variant asserting that `accumulate_full_payload_output` receives the per-request slice would mirror the actual failure more faithfully.

### 6. Signature change ripple (informational, verified)

Dropping the `seq_len` parameter from `_build_omni_model_runner_output_from_snapshot` is clean: the only call site (line 2027) and all six test call sites were updated, and the async path's `scheduler_output` snapshot is a dataclass `replace()` that preserves `total_num_scheduled_tokens` (line 1497-1512), so the new field read is safe in both sync and async output builders. Serving-speech unit tests can't run in this checkout (installed vLLM 0.26 vs. targeted 0.24 — `vllm.entrypoints.serve.disagg` missing), which is an environment mismatch, not a PR defect; the PR's H20 run covers them.
