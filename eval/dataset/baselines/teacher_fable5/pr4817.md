## Review: PR #4817 — Gate quack FP8 to datacenter Blackwell (sm_100.x) only

### Verdict

**Approve with one follow-up.** The core change is correct, minimal, and well-motivated: `tcgen05`-based CuteDSL kernels genuinely cannot run on cc 12.x (CuteDSL's `BlockScaledMmaOp` admits only `sm_100a`), so narrowing the auto-enable gate from `>= 10` to `== 10` in `vllm_omni/quantization/quack_fp8.py:32` fixes a real, severe perf regression on RTX 50-series / RTX PRO 6000 while leaving datacenter Blackwell and the `VLLM_OMNI_USE_QUACK_FP8` escape hatch untouched. I verified the rename `_is_blackwell` → `_is_quack_capable` is self-contained (the only external caller is `quack_enabled()`, reached via `install_quack_fp8_patch()` from `vllm_omni/patch.py:410-419`), and all 18 new tests pass locally with no GPU. The one thing that should not ship as-is: the new regression test never actually runs in CI.

### Comments

**1. [Should fix] The new regression tests are dead in CI — they get deselected by the marker filter.**
`tests/quantization/test_quack_fp8_gate.py` declares no pytest markers. The only CI steps that collect `tests/quantization/` are the catch-all steps in `.buildkite/test-ready.yml:29` and `.buildkite/test-merge.yml:29`, and both filter with `-m 'core_model and cpu'`. I ran the file under that exact filter and got **`18 deselected`** — so the regression guard this PR advertises in its test plan never executes on any pipeline. Add at module level (both markers are registered in `pyproject.toml:236,249`, so this is compatible with `--strict-markers`):

```python
pytestmark = [pytest.mark.core_model, pytest.mark.cpu]
```

This is worth a fast-follow PR since this one is already merged.

**2. [Minor] `warmup_quack_fp8` bypasses the gate you just fixed.**
`vllm_omni/quantization/quack_fp8.py:131-144` checks only `_load_quack()` (an import probe that succeeds on sm_120 when `quack-kernels` is installed), not `quack_enabled()`. The docs this PR edits still tell users to call `warmup_quack_fp8(...)` directly (`docs/user_guide/quantization/fp8.md:73-75`), and on sm_120 that call will attempt CuteDSL compilation and raise `OpError` uncaught — there's no try/except around `quack_scaled_fp8_mm` in the warmup loop. Pre-existing, but directly adjacent to this fix: add `if not quack_enabled(): return` at the top of `warmup_quack_fp8`, which also makes it respect `VLLM_OMNI_USE_QUACK_FP8=0`.

**3. [Nit] The docstring's arch list is slightly narrower than the PR's own citation.**
The docstring at `vllm_omni/quantization/quack_fp8.py:19-21` says `tcgen05` exists only on `sm_100a/101a/103a`, but the PR description (and PTX ISA) also lists `sm_110a` (cc 11.x). `== 10` excluding cc 11.x is still the right *default* — CuteDSL's `admissible_archs` hardcodes `sm_100a`, so quack would fail there anyway, and the env override covers it — but the docstring should say 11.x is excluded because CuteDSL doesn't admit it, not because the instruction doesn't exist. Prevents someone "correcting" the gate to `in (10, 11)` later based on the PTX docs.

**4. [Note, no action] Single-device probe.** `_is_quack_capable` checks `get_device_capability()` for device 0 only; a mixed sm_100 + sm_120 host would enable quack globally. This mirrors the pre-existing pattern and is an unusual config, so fine to leave — just flagging that the gate is process-global, not per-device.

**5. [Gate] Two required checks were red at merge:** `buildkite/vllm-omni-amd-ci` and `buildkite/vllm-omni-npu-ci`. Nothing in this diff plausibly touches AMD/NPU behavior (the gate is behind `torch.cuda.get_device_capability()`, and ROCm reports cc 9.x, so it stays False there), but the PR merged over failing required pipelines — those gates are the authority and should be re-run/triaged rather than argued past.

### Test quality

The test file itself is good: it covers the exact regression (`(12, 0)`/`(12, 1)` → False), keeps datacenter Blackwell enabled, and locks in both directions of the env override, hardware-free via monkeypatching. Two trivial gaps if anyone revisits it: no case for `get_device_capability()` raising (the `except` branch at `quack_fp8.py:33`), and the falsy-override test enshrines that an *empty* `VLLM_OMNI_USE_QUACK_FP8=""` means "explicitly off" rather than "unset" — that matches the implementation and is fine, but it's now contract.
