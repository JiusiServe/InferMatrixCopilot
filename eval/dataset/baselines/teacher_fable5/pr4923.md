# Review: PR #4923 — Align talker MTP CUDA graph capture with Qwen3-Omni & adapt to async output

## Verdict

The core change is sound and well-precedented: it copies the exact graph layout Qwen3-Omni already uses (`use_cuda_graphs=current_omni_platform.is_npu()` in `qwen3_omni_moe_code_predictor_mtp.py:21`, and the same three async-output flags in `qwen3_omni.py:162-164`), and the runner machinery it opts into (`_init_talker_mtp`, `_capture_talker_mtp_graphs`, the async-output gate) is generic and already exercised. I verified that capture-time and replay-time sampling params resolve to the same values (both come from `model_config.subtalker_sampling_params`), that `talker_mtp` has no data-dependent control flow that would be frozen into the graph, and that the hidden-state pooler-payload opt-out is safe (code2wav passes `text_hidden_states=None` everywhere in `qwen3_tts_code2wav.py`). The PR was merged; this review would have been "approve with requested changes" — the issues below are real but none invalidate the approach. The AMD and NPU CI gates were red at merge; the NPU fragility noted in comment 3 is a plausible contributor, and I'd point at those gates rather than merging over them.

## Comments

### 1. `vllm_omni/deploy/qwen3_tts.yaml:41-46` — the prefix-caching comment now says the opposite of the setting, and the real constraint is undocumented

The value flipped `true → false`, but the comment block directly above it still reads "Prefix caching on by default… any text repetition across requests… is a net throughput win. Disable explicitly if memory headroom is tight." The actual reason for the flip is load-bearing and appears nowhere: `_should_use_async_omni_output` returns `False` when `omni_prefix_cache is not None` (`gpu_ar_model_runner.py:1540`), so prefix caching and this PR's async-output fast-path are mutually exclusive. As written, this is a trap: the next person who follows the stale comment and re-enables prefix caching for throughput will silently disable the async path this PR ships, with no warning anywhere. Replace the comment with the real trade-off ("prefix caching disables the async omni output path; keep off while stage 0 uses `use_async_omni_output`"), and consider a `logger.info_once` in `_should_use_async_omni_output` when a model requests async output but is blocked by `omni_prefix_cache`.

### 2. `vllm_omni/deploy/qwen3_tts.yaml:6-8` — stale header comment

The file header still says "Stage 0 (talker) sets max_num_batched_tokens=512 for async-chunk latency tuning… small per-step batches keep first-chunk latency low," but the value is now 32768 (line 48). Either the latency rationale no longer holds (say why — presumably TTFA measurements with the new batching) or the header is wrong. Update it; same for `max_num_seqs: 10 → 64` if the "Tuned for Base voice clone" note on stage 1 (line 69) was tied to the old value.

### 3. `vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:327` + `qwen3_tts_code_predictor_vllm.py:39` — the NPU nested-graph invariant is enforced only by a deploy yaml

`talker_mtp_graph_safe = True` is declared unconditionally, but the code predictor keeps its inner device graphs on NPU (`use_cuda_graphs=current_omni_platform.is_npu()`). The NPU runner inherits the shared `_init_talker_mtp` (`gpu_model_runner.py:209`), so on NPU with any full-cudagraph mode the runner wraps `talker_mtp` in `ACLGraphWrapper` *around* the live inner NPU graphs — precisely the nested-capture bug this PR fixes on GPU. The only thing preventing it is the new `cudagraph_mode: PIECEWISE` pin in this one yaml (lines 98-102); any NPU deployment not using this file, or overriding the mode, hits nested capture and dies with the `RuntimeError` at `npu_ar_model_runner.py:184`. The invariant "inner graphs XOR outer wrap" belongs in code, not config: e.g. `talker_mtp_graph_safe = not current_omni_platform.is_npu()`, or gate the code predictor's `use_cuda_graphs` on `is_npu() and not cudagraph_mode.has_full_cudagraphs()`. (Qwen3-Omni has the same latent hazard via `has_separate_talker`, so fixing it here alone isn't enough — fine to fold into the existing `TODO(#4923)` follow-up, but the TODO should name it.) Note the NPU CI gate was failing on this PR; that gate is where this class of problem would surface.

### 4. `vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:343` + `gpu_model_runner.py:1851-1876` — seeded requests get the worst of both worlds under full cudagraphs, and the comment understates it

With `talker_mtp_accepts_per_row_generators=False` and the model graph-wrapped, a request carrying `tts_local_seed` in a multi-row decode batch still triggers the scalar fallback loop at `gpu_model_runner.py:1851` — N clone/copy round-trips plus N size-1 graph *replays*, and each replay ignores the `generator` kwarg entirely (capture at `gpu_ar_model_runner.py:562` passes no generator; `CUDAGraphWrapper` replay discards call kwargs). So seeded requests pay the full scalar-loop cost *and* get no reproducibility — the loop preserves nothing. Two fixes: (a) skip the scalar fallback when the model is graph-wrapped (batch the call, since the generators are dead weight either way) and (b) `logger.warning_once` that `tts_local_seed` is ignored under full cudagraphs. Also, the comment at line 343 says seeding "is silently dropped when the decode batch > 1" — it's dropped for batch == 1 too (the single `generator` at `gpu_model_runner.py:1885-1886` is equally ignored by the captured size-1 graph). Correct the comment.

### 5. `vllm_omni/model_executor/models/qwen3_tts/qwen3_tts_talker.py:346-349` — init-time `cudagraph_mode` read can diverge from the effective mode

The model snapshots `cudagraph_mode` at construction; the runner re-derives the same decision minutes later in `load_model` (`gpu_model_runner.py:189`), so they agree at init. But vLLM 0.26 can still *downgrade* the mode after model load (attention-backend resolution downgrades `FULL_AND_PIECEWISE → PIECEWISE` when the backend lacks full-graph support). In that case the wrapper never replays (forward-context mode won't be FULL), which is correct-but-slow — yet per-row generators stay disabled for nothing, so seeded eager-path requests lose reproducibility with zero offsetting benefit. This is a graceful degradation, not a bug, but it strengthens the case for the TODO already in the comment: move the gating into the runner where the final mode is known. Fine as a follow-up; flagging so the TODO captures the downgrade case explicitly.

### 6. `vllm_omni/model_executor/models/common/qwen3_code_predictor.py:477` — `code_predictor_prefix_graphs` becomes a dead knob on GPU for TTS

`_prefix_graphs_enabled` requires `wrapper_config.use_cuda_graphs and not is_npu`. With this PR that conjunction is unsatisfiable for Qwen3-TTS on every platform (GPU: `use_cuda_graphs=False`; NPU: `not is_npu` fails). A user requesting `code_predictor_prefix_graphs` via connector config gets only an `info_once` log. If prefix graphs are genuinely subsumed by the outer full-graph wrap (they cover the prefill-side call, which the outer wrapper — decode-only, `span_len == 1` at `gpu_model_runner.py:1754` — does not), that should be stated; otherwise this is a silent perf regression for configs that used it. At minimum document the interaction; ideally decouple prefix graphs from the decode-path `use_cuda_graphs` flag.

### 7. Test coverage — the new gating has none

The diff adds three behavior-changing flags and a mode-conditional, with no test changes. Existing tests only exercise mocks (`test_omni_gpu_model_runner.py:374` sets `talker_mtp_accepts_per_row_generators=True` on a stub). Cheap, worthwhile additions: a unit test that constructs the talker gating with `cudagraph_mode` ∈ {NONE, PIECEWISE, FULL_AND_PIECEWISE} and asserts `talker_mtp_accepts_per_row_generators` flips accordingly, and one asserting `_init_talker_mtp` wraps the TTS model (no `.talker` attr) when `talker_mtp_graph_safe=True`. That would have pinned down comments 4 and 5 mechanically.
