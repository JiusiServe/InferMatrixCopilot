# Review: PR #4950 — docs(recipe): fix MiniCPM-o 4.5 curl TTS example and clarify `chat_template_kwargs` usage

## Verdict: Approve

Docs-only change to `recipes/OpenBMB/MiniCPM-o-4_5.md`, and I verified every technical claim in it against the serving and model code rather than taking the PR description on faith. All of them check out. The old recipe text was genuinely wrong in two ways (the curl payload shape and the "text-only fallback" claim), and this PR corrects both accurately. No code paths are touched, so there is no regression risk.

## Claim-by-claim verification

**1. Top-level `chat_template_kwargs` vs nested `extra_body` — correct.**
`chat_template_kwargs` is a first-class pydantic field on `ChatCompletionRequest` (upstream vLLM `chat_completion/protocol.py:341`), and the template path reads only that field: vllm-omni validates `request.chat_template_kwargs` and folds it via `_effective_chat_template_kwargs` (`vllm_omni/entrypoints/openai/serving_chat.py:373-381`). A raw curl body's nested `extra_body` key is never merged into the template kwargs server-side — nested `extra_body` is consulted only for diffusion/image params and a few omni flags (`serving_chat.py:441`, `serving_chat.py:252-262`), never for the chat template. The OpenAI Python SDK does flatten `extra_body` into the JSON root client-side, so the "SDK may still use `extra_body`" caveat is also right — and it matters, because the bundled Gradio demo relies on exactly that (`examples/online_serving/minicpmo/gradio_demo.py:222-226`).

**2. "Silent audio, not text-only" — correct, and this is the subtlest and most valuable fix in the PR.**
The old text said omitting the flag gives a text-only (faster) response; that's wrong. The stage-1 input processor only attaches `tts_token_ids`/`tts_hidden_states` when a `<|tts_bos|>` (151703 for 4.5, matching the PR's root-cause table) is found in prompt+output tokens (`vllm_omni/model_executor/stage_input_processors/minicpmo_4_5_omni.py:97-119`). Without it, the talker takes its dummy path and returns a zero tensor instead of a waveform tuple (`minicpmo_4_5_omni_tts.py:406-409`), so the wrapper emits no `model_outputs` (`minicpmo_4_5_omni.py:324-331`). But the request doesn't fail: the AR runner still ships the zero hidden states as `payload["hidden"]` (`vllm_omni/worker/gpu_ar_model_runner.py:915`), and the output processor remaps `"hidden"` → `"audio"` for a final audio stage (`vllm_omni/engine/output_processor.py:178-181`), so the client receives a structurally valid, all-zeros WAV. Exactly what the new text says.

**3. Text and audio in separate `choices` entries — correct.**
The non-streaming generator appends per-modality choices from separate stage outputs (`serving_chat.py:2135-2185`), and the audio choice carries only `message.audio` with no `content` (`serving_chat.py:2569-2575`). The old "text in `choices[0].message.content` and WAV in `choices[0].message.audio.data`" wording was wrong.

**4. No hidden server-flag requirement.** I confirmed the corrected curl example works against the recipe's serve command as-is: `--trust-request-chat-template` only gates a request-supplied `chat_template` string, not ordinary kwargs like `use_tts_template` (upstream `renderers/online_renderer.py:273-279`).

## Comments (minor, non-blocking)

1. **`examples/online_serving/minicpmo/README.md:57-58`** — the sibling example doc still says the TTS trigger is "`extra_body.chat_template_kwargs.use_tts_template=True`". That's technically fine there (the demo goes through the OpenAI SDK, which flattens `extra_body`), but it's the exact phrasing that caused the recipe bug, and a reader copying it into curl hits the same silent-WAV trap. A follow-up PR should reword it the same way this one did, or cross-reference the recipe's curl note.

2. **`recipes/OpenBMB/MiniCPM-o-4_5.md:126-127`** — "you typically get two `choices` entries (one text, one audio)". Worth a parenthetical that both entries can carry `index: 0` (the text choice uses `output.index` and the audio choice independently uses `output.index`, both 0 for n=1 — `serving_chat.py:2453`, `serving_chat.py:2570`), so clients must distinguish them by inspecting `message.content` vs `message.audio`, not by index. "Typically" is doing some quiet work here; making the discrimination rule explicit would head off the next confused bug report.

3. **`recipes/OpenBMB/MiniCPM-o-4_5.md:224`** — "nested `extra_body.chat_template_kwargs` is ignored" is accurate for the chat-template path, but note the server *does* honor nested `extra_body` for some omni params (e.g. `return_stage_metrics`, diffusion knobs). The doc as written is scoped narrowly enough to be true; just flagging so nobody "simplifies" it later into a blanket "`extra_body` is always ignored for curl", which would be false.

4. **Failing gate**: `buildkite/vllm-omni-npu-ci` is red on this PR. The diff touches only a markdown recipe, so the failure cannot be caused by this change — but the gate is the gate; the merge went in over a red required check, and that's for the CI owners / branch-protection policy to reconcile, not something to re-litigate here.

## Summary

A small, high-quality docs fix that corrects real misinformation with a verified root cause. The most important part isn't the payload shape fix — it's replacing the wrong "text-only fallback" claim with the accurate "silent audio" behavior, which converts a very confusing failure mode (valid WAV, zero amplitude) into something a user can actually diagnose. Approve; the comments above are all follow-up material.
