# Review of PR #4859 — [BugFix][Ming-TTS] Improve Seed-TTS WER accuracy

## Verdict

The model-side alignment changes (stop-head gating, VAE latent sampling) look correct and are supported by the reported WER improvement. However, **the merged HEAD contains a real bug in the Seed-TTS WER eval path**: the branch-side change to parse captured PCM using the env sample rate collides with the capture-time 24 kHz normalization that arrived via the upstream merge, so the eval now double-converts audio whenever `VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE≠24000` — which is exactly what this PR's own test plan sets. The reported 1.83% WER was measured on the pre-merge branch state where this could not happen. Since the PR is already merged, this needs a follow-up fix. There are also stale docs for a removed API behavior and a shared-config mutation hazard. The `buildkite/vllm-omni-amd-ci` gate is failing — that gate should be resolved on its own terms; nothing below re-argues it.

## Findings

### 1. HIGH — Double sample-rate conversion in Seed-TTS WER eval at merged HEAD

`vllm_omni/benchmarks/data_modules/seed_tts_eval.py:188-200` — `_pcm_s16le_to_f32_16k` now interprets `tts_output_pcm_bytes` using `VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE`/`_CHANNELS`. But at this PR's head, every producer of that field normalizes it to **24 kHz mono first**:

- `vllm_omni/benchmarks/patch/patch.py:1215` (`_pcm_s16le_to_seed_tts_wer_bytes`, docstring: "Normalize streamed raw PCM to the 24 kHz mono PCM used by Seed-TTS WER"), using the same env values;
- the `openai-chat-omni` exporters at `patch.py:948` and `patch.py:957`;
- the field's own contract at `patch.py:427-429`: "Raw PCM s16le mono at 24 kHz for Seed-TTS WER".

So with the PR's documented setup (`VLLM_OMNI_BENCH_AUDIO_SAMPLE_RATE=44100`), the eval resamples an already-24 kHz buffer as if it were 44.1 kHz — audio effectively sped up ~1.84× before Whisper ASR, corrupting WER, SIM, and UTMOS. The only path where the env parse is correct is the exception fallback at `patch.py:1222` that stores raw bytes when normalization fails.

The history explains the contradiction: at `d40efb3e^` (the state the fix was developed and tested on, based on `0455bffc`), `async_request_openai_audio_speech` stored **raw** captured PCM (`output.tts_output_pcm_bytes = bytes(pcm_capture)`), so env-based parsing in the eval was correct there. The merge commit `6ff4ce59` then brought in upstream's capture-time normalization while keeping the branch's consumer-side env parsing — the two halves are individually consistent but mutually incompatible. The inconsistency is visible within a single function: `_save_seed_tts_eval_audio` (`seed_tts_eval.py:116`) still hard-codes `sample_rate=24000` for the same buffer that `_pcm_s16le_to_f32_16k` three lines later treats as 44.1 kHz.

**Fix:** revert `_pcm_s16le_to_f32_16k` to a fixed `pcm_sample_rate=24000`, mono (trust the normalized contract), and drop the new env-var sentence from the module docstring at `seed_tts_eval.py:42-43`. Env-based format handling belongs only at capture time in `patch.py`. Re-run the WER eval on the actual merged HEAD to confirm the headline number.

### 2. MEDIUM — Documented `language` → `方言` mapping removed without updating docs/examples

`vllm_omni/entrypoints/openai/serving_speech.py:2619` — dropping `include_language` removes the OpenAI `language` field → Ming `方言` (dialect) caption mapping. The motivation is sound (the Seed-TTS dataset sends `language: "English"` — `seed_tts_dataset.py:238` — which polluted the Ming caption and hurt WER), but this is a user-visible API removal and the docs still advertise it:

- `examples/online_serving/text_to_speech/ming_tts/README.md:101` — "`language` | Ming `方言` control";
- `examples/online_serving/text_to_speech/ming_tts/openai_speech_client.py:103-104,192` — `--dialect` maps to `payload["language"]`, now silently ignored.

Consider whether the right fix was benchmark-side (stop sending `language` from the Seed-TTS dataset, or ignore locale-like values such as "English"/"Chinese"/"Auto") rather than removing the serving feature. At minimum, follow up to update the README and example client (users can still pass `方言` via `instructions` JSON — say so).

### 3. MEDIUM — In-place mutation of a shared HF config object

`vllm_omni/model_executor/models/common/ming/audio_vae.py:140-142` — `config.num_hidden_layers = 4` mutates the same `Qwen2Config` instance already held by `self.encoder = Qwen2Model(config)` (line 131). Verified on transformers 5.14: the model keeps a reference (`model.config is config`), so after this line the main encoder's config claims 4 hidden layers while the module actually has N. A forward pass currently tolerates it (verified), but it is a latent hazard for anything that reads the config afterward (cache pre-allocation in future transformers versions, serialization, debugging), and it also means encoder and aggregator share one mutable config object. The previous code (`_qwen2_config({**encoder_args, "num_hidden_layers": 4})`) built an architecturally identical aggregator without the side effect — I see no functional reason for this change. Restore the fresh-config construction, or use `copy.deepcopy(config)` before mutating. Note this class is shared with `ming_flash_omni`.

### 4. INFO — VAE latent sampling: correct alignment, but wider blast radius than the PR title suggests

`audio_vae.py:349-351` — switching `encode_latent` from mean-only to reparameterized sampling (`mean + softplus(scale)·ε`) matches training-time conditioning and is empirically supported by the WER result. Two things worth noting:

- **Cross-model impact:** `encode_latent` is also used by `ming_flash_omni` voice presets (`vllm_omni/model_executor/models/ming_flash_omni/voice_presets.py:257`), so Ming-Flash preset embeddings now vary per server start. The test plan only covers Ming-TTS; a Ming-Flash accuracy spot-check would derisk this.
- **Determinism:** sampling is unseeded, so identical requests now produce different prompt latents (and different audio). Presumably intentional to match the HF path, but worth stating in the PR description or a code comment, since it affects reproducibility and any golden-output tests.

### 5. MINOR — Stop-gating `+1 → +2` is a correct alignment, with one behavior change

`vllm_omni/model_executor/models/ming_tts/patch_emission.py:130,151` — the new `min_stop_step + 2` makes the stop-head condition equivalent to the strict `step > min_new_token` used by the Ming-Flash talker (`ming_flash_omni/talker_module.py:733`), fixing an off-by-one where the stop head could fire one step early. Side effect: with the default `STOP_HEAD_MIN_STEPS = 3`, requests with `max_new_tokens=4` that previously validated now raise `ValueError` in `_validate_ming_decode_window`. That's a user-visible tightening; worth a release-note line.

### 6. NIT — `stream_pcm_format_from_env` clamp and placement

`vllm_omni/metrics/definitions.py:337` — `max(sample_rate, 1)` turns an explicit non-positive env value into 1 Hz; downstream, `_pcm_s16le_to_f32_16k` would then compute `target_len = len·16000/1` and attempt a 16000× upsample (memory blowout), where the old un-clamped code produced empty audio. Prefer falling back to the default with a warning, matching the `ValueError` branch. Also: benchmark-only env knobs (`VLLM_OMNI_BENCH_*`) now live in the Prometheus metric-definitions module — a layering smell; and the old `_audio_pcm_format` docstring's useful guidance (which models need overrides, e.g. MOSS 48 kHz stereo) was lost in the move.

### 7. NIT — No test coverage

None of the touched helpers (`stream_pcm_format_from_env`, `_pcm_s16le_to_f32_16k` multi-channel path, the `+2` stop-gating boundary) gained tests, and the existing suite has no assertions that would have caught finding #1. A small unit test pinning the "capture normalizes → eval assumes 24 kHz mono" contract would prevent regressions like this merge artifact.

## Summary

The core numerical fixes (#4, #5) are well-motivated and correctly aligned with the reference implementations. But finding #1 means the merged code likely does not reproduce the PR's headline 1.83% WER when run as documented — a follow-up PR should restore the fixed 24 kHz assumption in `seed_tts_eval.py`, re-validate WER at HEAD, and clean up findings #2 and #3 while there.
